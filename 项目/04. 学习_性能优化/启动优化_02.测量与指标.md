# 启动优化 02 — 测量与指标

> 学习日期：2026-04-20
> 对应 YAML card：036

---

## 一、三种启动类型

判定维度只有两个：**进程是否存活 × Activity 是否存活**

| 启动类型 | 进程状态 | Activity 状态 | 典型场景 | 耗时 |
|---------|---------|--------------|---------|------|
| 冷启动 | 不存在，需 Zygote fork | 不存在 | 首次安装后打开、被系统杀死后再开 | 最重 |
| 温启动 | 存在 | 被回收（内存紧张） | 按 Back 退出后再开 | 中等 |
| 热启动 | 存在 | 存活（在后台） | 按 Home 后切回来 | 最快 |

**冷启动生命周期**：
```
Zygote fork
    ↓
ActivityThread.main()
    ↓
Application.attachBaseContext()
    ↓
Application.onCreate()
    ↓
Activity.onCreate() → onStart() → onResume()
    ↓
首帧渲染上屏
```

**注意**：`onResume()` ≠ 启动完成。首帧上屏还受视图树层级影响，层级越深，渲染越慢。

## 二、TTID — Time To Initial Display

**含义**：从启动到首帧上屏的耗时。

**终点**：`WMS` 收到首帧提交 → 通知 `AMS` → logcat 自动打印：
```
Displayed com.xxx/.SplashActivity: +1s234ms
```

**特点**：
- 无需开发者埋点，系统自动记录
- 记录的是**启动 Activity**（通常是 SplashActivity）的首帧
- 这一帧可能只有布局骨架，数据未必加载完

**为什么系统能自动记录**：所有 Window 绘制都经过 WMS，首帧提交时 WMS 收到 `windowsDrawn` 回调，通知 AMS 打印 log，App 侧不需要做任何事。

---

## 三、TTFD — Time To Fully Drawn

**含义**：从启动到内容完全可用的耗时。

**终点**：开发者主动调用 `reportFullyDrawn()`

```kotlin
// 在 HomeActivity 首屏数据加载完、列表渲染稳定后调用
reportFullyDrawn()
```

调用后系统打印：
```
Fully drawn com.xxx/.MainActivity: +2s678ms
```

**不调用的后果**：系统不知道终点在哪 → Google Play Console 无 TTFD 数据 → 监控盲区 → 无法量化优化效果。

> 记忆口诀：TTID 是「有骨架」，TTFD 是「有肉」。

## 四、双端口径错位

系统口径和应用口径的**起点和终点都不一样**，不是同一把尺子。

```
系统口径（am start -W TotalTime）
├── 起点：AMS 收到 startActivity
│       ↑ 包含 Zygote fork、系统调度
├── [attachBaseContext] ← 应用口径起点（晚于系统起点）
│       ...应用执行...
├── 终点：首帧上屏（TTID）← 系统口径到此结束
│       ...数据加载 + 二次渲染...
└── [reportFullyDrawn] ← 应用口径终点（晚于系统终点）
```

**关系式**：
```
应用口径 = 系统口径 - 起点段（Zygote fork + 系统调度）+ 尾部段（TTID → reportFullyDrawn）
```

两者不是简单的大小关系，不能直接比较。

**⚠️ 常见误解**：「应用口径 = 系统口径 - Zygote fork 那段」——方向错了！
差值的主要来源在**末端**（reportFullyDrawn 延后），不在起点。

---

## 五、口径选型原则

| 场景 | 使用口径 | 原因 |
|------|---------|------|
| 竞品横向对比 | 系统口径（`am start -W`） | 基线统一，不受各家埋点姿势影响 |
| 自身瓶颈诊断 | 应用口径（自埋点） | 覆盖「用户真正能用」那段 |
| 线上监控 | 两套都要，保持一致 | 混用会产生误判 |

**⚠️ 核心原则：线下和线上必须使用同一套口径。**
混用后果：「线下显示劣化 100ms，线上其实快了 50ms」→ 错误决策。
