## 一、一页纸全景时序

```
用户点击 Launcher 图标
    │
    │ Binder 调用
    ↓
【system_server 进程】
ATMS.startActivity (Android 10+) / AMS.startActivity (10 之前)
    │
    │ 检测到目标 App 进程不存在
    │ AMS 通过 socket 通知 Zygote 进程
    ↓
【Zygote 进程】(socket 监听循环中)
fork()
    │
    ├─ 父进程(Zygote)拿到子进程的 pid(> 0)→ 回 socket 循环
    │
    └─ 子进程拿到返回值 0 → 走 App 分支
            ↓
【新诞生的 App 进程】
        Native 层:ProcessState::startThreadPool()  ← Binder 线程池已经就绪
            ↓
        RuntimeInit.applicationInit → 反射调用 ActivityThread.main()
            ↓
        【主线程从这里开始】
        Looper.prepareMainLooper()
        new ActivityThread()   ← 构造时 ApplicationThread 作为字段同时被 new
        thread.attach(false, startSeq)
            │
            │ 拿 AMS 的 Binder 代理,跨进程调用
            ↓
        ActivityManager.attachApplication(mAppThread, startSeq)
            │
            │ 跨进程:本体留在 App 进程,AMS 拿到 BinderProxy 代理
            ↓
        【回到 system_server】
        AMS 登记这个进程,同时反向调用 bindApplication
            │
            │ 跨进程:通过 ApplicationThread 的代理调回来
            ↓
        【回到 App 进程】
        Binder 线程池某线程被唤醒
            ↓
        ApplicationThread.bindApplication 方法体执行  ← ★ 不在主线程!
            │
            │ 方法体只做一件事:封装 AppBindData,sendMessage(H.BIND_APPLICATION)
            ↓
        主线程 MessageQueue 多了一条 BIND_APPLICATION 消息
        Looper.loop() 取出
            ↓
        H.handleMessage → case BIND_APPLICATION
            ↓
        ActivityThread.handleBindApplication(data)
            ├─ 1. 进程身份设置(改名、时区、Locale)
            ├─ 2. 加载 APK(LoadedApk,拿到 ClassLoader)
            ├─ 3. makeApplication
            │     ├─ 反射加载 Manifest 里声明的 Application 类
            │     ├─ 反射 new Application 实例
            │     └─ Application.attach(context)
            │           └─ attachBaseContext(context)  ← ★ 应用口径起点
            ├─ 4. installContentProviders   ← ★ Provider.onCreate 串行跑在主线程
            │     (Firebase / WorkManager / LeakCanary 等被"夹带"的 Provider)
            └─ 5. callApplicationOnCreate
                  └─ Application.onCreate()   ← 你写的代码终于跑了
            │
            │ handleBindApplication 返回
            │ 回到 Looper,取下一条消息
            ↓
        LAUNCH_ACTIVITY 消息(AMS 已经紧接着发过来了)
            ↓
        ActivityThread.handleLaunchActivity
            → performLaunchActivity
                ├─ newActivity(反射 new Activity 实例)
                ├─ Activity.attach(...)  ← 创建 PhoneWindow
                └─ callActivityOnCreate
                      └─ Activity.onCreate()
                            └─ setContentView(...)  ← XML → View 对象树,挂到 DecorView
            → handleStartActivity → Activity.onStart()
            → handleResumeActivity → Activity.onResume()
            │
            │ 同一条消息处理过程中,连续执行完 onCreate / onStart / onResume
            ↓
        onResume 返回后,ViewRootImpl 介入
            ↓
        等下一个 vsync 信号
            ↓
        ViewRootImpl.performTraversals
            ├─ performMeasure  ← 递归 measure 整棵 View 树
            ├─ performLayout   ← 递归 layout
            └─ performDraw     ← 构建 DisplayList,交给 RenderThread
            ↓
        【RenderThread】
        同步 DisplayList → 调 GPU 渲染 → 交给 SurfaceFlinger
            ↓
        SurfaceFlinger 合成所有图层,在下一个 vsync 时把帧推上屏
            ↓
        ★ 首帧上屏(TTID 终点)
        系统发 Displayed 日志
        Starting Window 被系统移除
```

## 二、分阶段深入

### 阶段 1:Launcher → ATMS/AMS(进程尚不存在)

用户点击 Launcher 图标,Launcher 进程通过 Binder 跨进程调用 `startActivity`,最终到达 **system_server 进程**。

**哪个系统服务处理**:

- Android 10 之前:**AMS** (ActivityManagerService) 统管一切
- Android 10 之后:**ATMS** (ActivityTaskManagerService) 专门管 Activity/Task 栈,AMS 仍然管进程创建和生命周期分发

看老源码/老文章只见 AMS 不必慌,知道 Android 10 分家了即可。

**ATMS 做的事**(此时目标进程不存在):

- 决策任务栈(放在哪个 task、用什么启动模式)
- 发现目标 App 进程不存在 → 通知 AMS 去创建
- AMS 通过 **socket**(不是 Binder)连接 Zygote

### 阶段 2:AMS → Zygote(为什么是 socket)

Zygote 是所有 App 进程的"模板父进程",系统启动时就预加载了:

- ART 虚拟机
- framework 常用类和资源
- 核心系统库

fork 出的子进程**直接继承这些**,不用重做。这是 Android 启动能做到秒级的关键。

**为什么 Zygote 用 socket 而不是 Binder**:

1. **Binder 驱动状态和进程绑定**:Binder 驱动在内核为每个进程维护独立状态(已打开的 Binder 节点、线程池登记等)。如果父进程的 Binder 状态被 fork "克隆"到子进程,两个进程会用同一份状态对内核说话,驱动立刻混乱。

2. **多线程 fork 不安全**:`fork()` 在多线程环境下危险 —— 它只复制"调用 fork 的线程"的状态,其他线程被斩断,但它们持有的锁会被克隆到子进程。Zygote 如果开了 Binder 线程池再 fork,100% 出问题。

**Zygote 的策略**:自己一辈子不开 Binder,只用 socket 监听请求;fork 出的子进程自己在初始化期再启动 Binder 线程池。

### 阶段 3:Zygote fork(父子分叉)

`fork()` 返回后,父子进程走**同一段代码**,用返回值区分身份:

| 谁              | fork() 返回值         | 接下来做什么                |
| --------------- | --------------------- | --------------------------- |
| Zygote(父)      | **子进程的 pid(> 0)** | 回 socket 循环,等下一个请求 |
| 新 App 进程(子) | **0**                 | 走 App 初始化分支           |

**为什么是 0 而不是子进程自己的 pid**:fork 返回值不是"当前进程的 pid",而是**"身份识别暗号"**。

- 0 不可能是任何真实 PID(PID 从 1 开始),用它作为"新生标记"不会冲突
- 父进程拿到"孩子的 pid"是因为它需要知道生了谁(便于后续管理孩子进程)

**子进程 fork 后做的事**(对开发者透明):

1. Native 层 `ProcessState::startThreadPool()` —— **启动 Binder 线程池**(所以 Binder 线程池在 main() 之前就绪)
2. `RuntimeInit.applicationInit()`
3. 反射找到 `android.app.ActivityThread` 类
4. 调用 `ActivityThread.main(args)` —— **主线程从这里开始跑 Java 代码**

### 阶段 4:ActivityThread.main(主线程起点)

主线程进入 `main()` 方法,做三件关键的事:

```java
public static void main(String[] args) {
    // 1. 给主线程准备 Looper + MessageQueue
    Looper.prepareMainLooper();
    
    // 2. 创建 ActivityThread 对象(此时 ApplicationThread 作为字段同时被 new 出来)
    ActivityThread thread = new ActivityThread();
    thread.attach(false, startSeq);
    
    // 3. 主线程进入死循环,开始处理消息
    Looper.loop();
    
    // 永远不会到这里(除非主线程退出 = 进程要死)
    throw new RuntimeException("Main thread loop unexpectedly exited");
}
```

**三个核心事实**:

1. **ActivityThread 不是线程**,是主线程上的管理对象。`new ActivityThread()` 不会创建新线程,它运行在当前主线程上。
2. **ApplicationThread 也不是线程**,是 ActivityThread 的内部类 + Binder 对象。它在 ActivityThread 构造时作为字段初始化(`final ApplicationThread mAppThread = new ApplicationThread()`),**不是 attach 时才创建**。
3. **Looper.loop() 是阻塞循环**,不是忙等。队列没消息时主线程通过 epoll 机制睡眠,不耗 CPU。

**Looper.loop 循环体简化**:

```java
for (;;) {
    Message msg = queue.next();         // 阻塞取消息,空队列时睡眠
    if (msg == null) return;
    msg.target.dispatchMessage(msg);    // msg.target 是 Handler
    msg.recycle();
}
```

### 阶段 5:thread.attach(...) 向 AMS 报到

**目的**:建立 App 进程 ↔ AMS 的双向 Binder 通信通道。

```java
private void attach(boolean system, long startSeq) {
    // ...
    final IActivityManager mgr = ActivityManager.getService();
    mgr.attachApplication(mAppThread, startSeq);   // ★ 关键跨进程调用
    // ...
}
```

**这次调用里传过去的 mAppThread 发生了什么**:

- 字面上:变量名叫 `mAppThread`,类型是 `ApplicationThread`(继承自 `IApplicationThread.Stub` → `Binder`)
- 实际跨进程传递:**本体留在 App 进程,AMS 那边拿到的是 BinderProxy 代理**
- 这是 Binder 驱动对 IBinder 类型参数的特殊处理 —— 不做序列化,而是"在对端生成代理"

**口诀:代理永远在调用方,本体永远在被调用方**

| 谁要调谁   | 调用方(持代理)                | 被调用方(本体)                    |
| ---------- | ----------------------------- | --------------------------------- |
| AMS 调 App | AMS 持 ApplicationThread 代理 | App 进程有 ApplicationThread 本体 |
| App 调 AMS | App 持 ActivityManager 代理   | system_server 有 AMS 本体         |

**attach 完成后的状态**:

- AMS 已登记这个进程(ProcessRecord)
- AMS 持有 ApplicationThread 的代理,能反向调 App 进程
- App 进程持有 ActivityManager 的代理,能主动调 AMS
- **双向 Binder 通道建立,App 进程成为 Android 系统的合法组件容器**

### 阶段 6:AMS 反向调 bindApplication

attach 之后,AMS 立刻反向调用:

```java
// AMS 里(system_server 进程)
applicationThreadProxy.bindApplication(
    processName, appInfo, providers, /* 一堆参数 */
);
```

**跨进程后的落地路径**:

```
【AMS,system_server 进程】调 BinderProxy.bindApplication
    ↓ Binder 驱动跨进程
【App 进程的 Binder 线程池】某个 Binder 线程被唤醒
    ↓ 执行 ApplicationThread 本体的 bindApplication 方法
ApplicationThread.bindApplication 方法体:
    封装参数为 AppBindData
    sendMessage(H.BIND_APPLICATION, data)   ← 投递消息到主线程
    return   ← Binder 线程立刻释放
    ↓
【主线程】Looper 取出 BIND_APPLICATION 消息
    ↓
H.handleMessage → ActivityThread.handleBindApplication(data)  ← ★ 真正的工作在主线程
```

**为什么要 Binder 线程→主线程"转一手"**:

1. **Binder 调用可能来自任何进程、任何线程,但 Activity/Application 生命周期必须串行在主线程**。转手让所有生命周期天然排队、天然在主线程执行。
2. **Binder 线程池要尽快释放**。总共就 16 个 Binder 线程,一次调用占着线程跑几百毫秒,其他系统调用会被堵。所以 ApplicationThread 的所有 `schedule*` 方法都只做"封装消息+投递",真正的活儿全交给主线程。

**印证**:任何 Activity 生命周期堆栈的栈底一定是 `Looper.loop → ActivityThread.main`,栈里看不到 Binder 线程的帧 —— 因为生命周期永远在主线程。

### 阶段 7:handleBindApplication(主线程上的 Application 初始化)

主线程进入这个方法,里面做的事分几段:

#### 7.1 进程身份设置

```java
Process.setArgV0(data.processName);   // 改进程名
DdmHandleAppName.setAppName(...);     // 改 DDMS 调试名
TimeZone.setDefault(...);             // 时区
// Locale、字体等全局配置
```

把这个刚 fork 出来的"白板进程"换上目标 App 的身份证。

#### 7.2 加载 APK

```java
data.info = getPackageInfoNoCheck(data.appInfo, ...);
```

创建 `LoadedApk` 对象,代表"一个已加载的 APK"。它持有:

- APK 路径
- **ClassLoader**(能加载这个 APK 里的所有类)
- **Resources**(能读这个 APK 里的所有资源)
- Application 类名(从 Manifest 读)
- ContentProvider 列表(从 Manifest 读)

**关键认知**:此步只是**准备好了 ClassLoader**,你的类**没有被真正加载到内存**。类加载是按需的 —— 首次引用某个类时,ClassLoader 才去加载。所以"类加载慢"的开销会在后续步骤里逐步累积。

#### 7.3 makeApplication(反射创建 Application)

```java
Application app = data.info.makeApplication(...);
```

展开:

```java
// 1. 拿 Application 类名(Manifest 里 <application android:name="..."/>)
String appClass = mApplicationInfo.className;
if (appClass == null) appClass = "android.app.Application";  // 默认空 Application

// 2. 用 APK 的 ClassLoader 反射加载这个类
// 3. 反射 new 实例
Application app = Instrumentation.newApplication(cl, appClass, appContext);

// 4. Application.attach(context)
//    内部触发 attachBaseContext(context)  ← ★ 应用口径起点
```

**为什么必须用反射**:

- ActivityThread 是 Android framework 代码,用系统 ClassLoader 加载
- MyApplication 是你 APK 里的业务代码,必须用 **APK 专属的 ClassLoader**(PathClassLoader)加载
- **系统 ClassLoader 看不见你 APK 里的类**,这是 Android 类加载隔离的设计
- 所以 ActivityThread 里无法直接 `new MyApplication()`(编译都过不了),**反射是跨 ClassLoader 创建实例的唯一途径**

**此刻状态**:

- ✅ Application 对象已创建
- ✅ attachBaseContext 已回调
- ❌ ContentProvider 还没初始化
- ❌ Application.onCreate 还没调

#### 7.4 installContentProviders(★ 启动优化最大金矿)

**反直觉事实**:ContentProvider.onCreate 比 Application.onCreate **先跑**,而且**全部串行在主线程**。

```java
// handleBindApplication 里,顺序:
Application app = data.info.makeApplication(...);      // attachBaseContext 已调
installContentProviders(app, data.providers);          // ★ 所有 Provider.onCreate
mInstrumentation.callApplicationOnCreate(app);         // 最后才是 Application.onCreate
```

`installContentProviders` 内部,对每一个 Provider:

1. 反射加载 Provider 类
2. 反射 new 实例
3. **同步调用 provider.onCreate()** ← 在主线程
4. 把 Provider 注册给 AMS(跨进程 Binder 调用)

**系统为什么这样设计**:

ContentProvider 是四大组件里唯一可以"在 App 没完全启动时,被其他 App 通过 Binder 查询"的组件。系统要保证 Provider 在 Application.onCreate 之前就绪,防止外部查询时 Provider 还没初始化。

**但这个设计在你 App 冷启动场景下非常尴尬** —— 此时根本没有外部查询,但 Provider 还是被强制串行初始化了。你付了代价,没收到回报。

**"夹带"问题**:第三方 SDK 热衷用 ContentProvider 做自己的初始化,因为系统保证它在 Application.onCreate 之前自动跑,SDK 作者不需要 App 开发者写任何代码 —— "零接入成本"是 SDK 的卖点,代价是从你启动时间里偷走。

典型夹带:

- Firebase 的 `FirebaseInitProvider`
- WorkManager 的 `WorkManagerInitializer`
- LeakCanary 的 `LeakCanaryInstaller`
- AndroidX App Startup 的 `InitializationProvider`

**审查自己 App 有多少 Provider**:

```bash
adb shell dumpsys package com.xx.app | grep -i provider
```

或看 Android Studio 里的 "Merged Manifest"。

**"集成 App Startup 一定更快"是幻觉**:它本身也是一个 ContentProvider。它的价值不是"让启动更快",而是"**把多个 Provider 合并成一个 + 提供编排框架**"。工具本身不优化启动,合理使用工具 + 砍掉不必要的初始化才优化启动。

**Provider 优化三层决策树**:

1. **能删的直接删**:审查每个 SDK 是不是真在用,砍掉僵尸 SDK(零风险最高 ROI)
2. **能合并的合并**:剩下的用 AndroidX Startup 合并成一个 Provider(减少注册开销)
3. **能延迟的延迟**:Provider.onCreate 里的耗时活儿挪到子线程,或延迟到首次使用时

**坑**:Provider.onCreate 里不能直接 post 到主线程"延迟",因为本身就在主线程,post 只是排队到后面。必须 post 到子线程,或用 IdleHandler。

#### 7.5 Application.onCreate

```java
mInstrumentation.callApplicationOnCreate(app);
// → app.onCreate()  ← 你写的代码在这里跑
```

**Application.onCreate 不是"独立启动阶段",它是主线程正在处理 BIND_APPLICATION 消息的一行代码**。你写的每一行代码直接加在启动时间上。

onCreate 结束那一刻的系统状态:

| 维度             | 状态                          |
| ---------------- | ----------------------------- |
| 进程             | 存在,主线程活跃               |
| Application      | 已创建,onCreate 调完          |
| ContentProvider  | 全部已初始化完                |
| ClassLoader      | 就绪                          |
| Activity         | **还没创建**                  |
| Window / View 树 | **不存在**                    |
| 用户屏幕         | **Starting Window(系统占位)** |
| 消息队列         | 下一条是 LAUNCH_ACTIVITY      |

### 阶段 8:Starting Window(用户到底看到了什么)

**事实**:从 AMS 决定启动 Activity 那一刻,系统就立刻显示了一个占位窗口,叫 **Starting Window**。用户点击图标后不会看到黑屏/白屏,看到的是这个窗口。

Starting Window 的内容(按 Android 版本):

| 版本              | 默认内容                                               |
| ----------------- | ------------------------------------------------------ |
| Android 11 及之前 | Activity 主题的 `windowBackground`(通常是纯色)         |
| Android 12+       | 系统 SplashScreen API 的启动画面(默认带 launcher icon) |

**它会一直显示,直到你 Activity 的第一帧真正上屏,系统才移除它**。

**对启动优化的三层影响**:

1. **"主题背景图伪造 TTID"的原理**:
   - Android 11 及之前,改 Activity 主题的 `windowBackground` 为一张假首页图
   - Starting Window 直接显示这张图,系统认为窗口"已绘制"
   - TTID 数据瞬间降到几十毫秒,但用户真实等待时间没变
   - 这就是"TTID 容易作弊"的底层机制

2. **Android 12+ 改了规则**:系统会在你的背景上叠一层 SplashScreen,老技巧失效。必须主动适配 SplashScreen API。

3. **"主题预设 windowBackground" 为什么是零成本优化**:改 XML 一个属性就能让 Starting Window 显示你想要的内容,不需要写代码,这是第 5 轮决策树"感知性能"分支最便宜的一条。

### 阶段 9:LAUNCH_ACTIVITY 消息处理

Application.onCreate 返回后,主线程 Looper 取下一条消息 —— 是 **LAUNCH_ACTIVITY**(AMS 早就连发过来了)。

消息队列前几条的典型结构:

```
[Head]
  1. BIND_APPLICATION      ← 已处理完
  2. LAUNCH_ACTIVITY       ← 现在开始处理
  3. 可能还有 Application.onCreate 里 post 的任务
[Tail]
```

**路径和 BIND_APPLICATION 同构**:

```
AMS → ApplicationThread.scheduleLaunchActivity (Binder 线程)
    → 封消息 sendMessage(H.LAUNCH_ACTIVITY)
    → 主线程 Looper 取出
    → H.handleMessage → case LAUNCH_ACTIVITY
    → ActivityThread.handleLaunchActivity
```

掌握了 bindApplication 的流程,scheduleLaunchActivity 前半段完全一样。

### 阶段 10:performLaunchActivity(Activity 的诞生)

`handleLaunchActivity` 核心调用 `performLaunchActivity`:

```java
// 步骤 1:创建 Activity 的 Context
ContextImpl appContext = createBaseContextForActivity(r);

// 步骤 2:反射创建 Activity 实例
Activity activity = mInstrumentation.newActivity(cl, className, intent);
// 内部:cl.loadClass(className).newInstance()
// 要求:Activity 必须有无参构造(和 Application 同理)

// 步骤 3:Activity.attach(...)   ← 第三个 attach 了
activity.attach(appContext, this, ..., window, ...);

// 步骤 4:设主题
activity.setTheme(theme);

// 步骤 5:调用 onCreate
mInstrumentation.callActivityOnCreate(activity, r.state, r.persistentState);
```

**Activity.attach 做的事**:

```java
final void attach(Context context, ..., Window window, ...) {
    attachBaseContext(context);
    
    mWindow = new PhoneWindow(this, window, ...);  // ★ Window 在这里诞生
    mWindow.setCallback(this);
    
    mMainThread = aThread;
    mInstrumentation = instr;
    mToken = token;
    // ...
}
```

**关键事件**:PhoneWindow 是 Activity.attach 里 new 的。此时:

- ✅ Window 对象存在
- ❌ DecorView 还没创建(setContentView 时才建)
- ❌ View 树不存在

### 阶段 11:Activity.onCreate + setContentView

主线程调到你写的 `MainActivity.onCreate`,第一行通常是 `super.onCreate` + `setContentView`。

**setContentView 分三阶段**:

**阶段 1:确保 DecorView 存在**

第一次调用 setContentView 时:

```java
// PhoneWindow.setContentView
if (mContentParent == null) {
    installDecor();   // 创建 DecorView
}
```

`installDecor` 做的事:

1. `new DecorView(...)` —— 创建 DecorView 对象
2. 根据 Activity 主题选一个**系统布局模板**(带 ActionBar 的、不带的、全屏的)inflate 进 DecorView
3. 从模板里找到 `@android:id/content` 这个 FrameLayout —— 就是 `mContentParent`

此时层级:

```
DecorView
├─ (可选)ActionBar 等系统元素
└─ FrameLayout (@android:id/content)   ← mContentParent,此时为空
```

**所以你的根布局不是整个 Activity 的顶层**。Layout Inspector 里看到你最外层之上还有几层,就是这来的。

**阶段 2:LayoutInflater 解析 XML**

```java
mLayoutInflater.inflate(layoutResID, mContentParent);
```

LayoutInflater 做的事:

1. 解析 APK 里的二进制 XML
2. 遇到每个 `<TextView>`/`<Button>`/... 标签 → **反射创建对应 View 类实例**
3. 解析 `android:xxx` 属性,调对应 setter
4. 根据嵌套,调 `parent.addView(child)` 构建层级
5. 挂到 `mContentParent` 下

**主线程重计算耗时点**:

- XML 解析(越大越慢)
- 反射 new 每个 View(层级深 + 节点多 → 慢)
- 属性 setter(设置 background 要加载 drawable,设置 src 要解码图片)

这就是第 4 轮"布局 Inflate 过深"瓶颈 pattern 的源头。

**阶段 3:setContentView 返回**

此时:

- ✅ View 树已挂到 DecorView 下
- ❌ **没有任何 View 调过 measure**
- 所以 `view.width / view.height` 全是 **0**

### 阶段 12:onStart → onResume(连续执行)

`performLaunchActivity` 调完 onCreate 后,**在同一条 LAUNCH_ACTIVITY 消息处理过程中**,紧接着推进到 onStart 和 onResume:

```
handleLaunchActivity
  → performLaunchActivity → Activity.onCreate
  → handleStartActivity → Activity.onStart
  → handleResumeActivity → Activity.onResume
```

**关键事实**:这三个生命周期回调发生在**同一个主线程调用栈里、同一条消息处理中**。中间 Looper **不会**回去取新消息。

**工程含义**:

- 不能指望在 onCreate 里 post 一个任务让它"在 onStart 之前执行" —— post 出去的消息进了队列,要等整个 LAUNCH_ACTIVITY 处理完才会取
- 三个回调中的任何耗时都直接加到启动时间

**onStart / onResume 系统侧做的事**:

- onStart:标记状态为 STARTED,触发 ActivityLifecycleCallbacks
- onResume:标记为 RESUMED,**触发 ViewRootImpl 开始工作**(下一阶段)

系统侧其实不重,重的是你代码里写了什么。

**常见坑**:把首屏数据同步加载放在 onResume 里 → onResume 返回被拖慢 → ViewRootImpl 介入延后 → TTID 变慢。而且温启动、热启动每次都跑,持续拖累。

### 阶段 13:ViewRootImpl 介入

onResume 返回后,主线程的调用栈退回 `handleLaunchActivity → H.handleMessage → Looper.loop`,Looper 准备取下一条消息。

**但在 onResume 执行过程中,有一个关键动作**:`WindowManager.addView(decorView, params)` 被调用,这一步会:

1. 创建一个 `ViewRootImpl` 实例
2. `ViewRootImpl.setView(decorView)` 把 DecorView 交给它
3. ViewRootImpl 向 WindowManagerService 注册,申请 Surface(用于绘制的画布)
4. 调用 `requestLayout()` —— 标记"需要一次 traversal",注册一个 Choreographer 回调

**ViewRootImpl 的角色**:是"**Activity 的 View 树**"和"**系统窗口系统 + 渲染系统**"之间的桥梁。一个 Window 对应一个 ViewRootImpl,它负责:

- 监听 vsync 信号
- 驱动 measure / layout / draw 的执行
- 和 RenderThread、SurfaceFlinger 通信

**为什么 measure/layout 不在 onCreate 里立刻跑**:Android 把布局/绘制和生命周期解耦,让生命周期快速返回,把渲染工作攒到 vsync 时机统一处理,避免每次布局变化都立刻重绘,提高性能。

### 阶段 14:Choreographer 触发 vsync 回调

ViewRootImpl 注册的 Choreographer 回调会在**下一个 vsync 信号**到达时被触发。

**vsync(Vertical Sync)是什么**:屏幕硬件每 1/60 秒(60Hz 屏幕)发一次垂直同步信号,告诉系统"现在可以准备下一帧了"。SurfaceFlinger 在每个 vsync 周期合成所有图层推到屏幕。Android 4.1(Project Butter)开始,应用端也监听 vsync,这样"应用产帧 + 系统合帧 + 屏幕显示"同步节奏,避免撕裂。

**Choreographer 做的事**:

- 维护多个回调队列(input、animation、traversal、commit)
- 收到 vsync 时,按顺序触发各队列的回调
- **traversal 队列的回调就是 ViewRootImpl.doTraversal**

所以:

```
onResume 返回
    ↓ 主线程 Looper 继续循环
等下一个 vsync 信号
    ↓ (最多 16.6ms)
Choreographer 收到 vsync
    ↓ 触发 traversal 回调
ViewRootImpl.doTraversal
    ↓
ViewRootImpl.performTraversals   ← 真正的渲染工作开始
```

### 阶段 15:performTraversals(measure / layout / draw)

`performTraversals` 是**整个 View 树渲染的总指挥**,它依次调用:

#### 15.1 performMeasure

递归调用每个 View 的 `measure(widthMeasureSpec, heightMeasureSpec)` → `onMeasure()`。

- 父 View 把约束(MeasureSpec)传给子 View
- 子 View 根据约束 + 自身 LayoutParams 计算 `mMeasuredWidth / mMeasuredHeight`
- ViewGroup 还要把所有子 View measure 完后,才能算出自己的尺寸

**复杂度**:如果 View 树层级深 + 每个 ViewGroup 有多个子 View,measure 可能被重复调用多次(RelativeLayout、LinearLayout 带 weight 尤其容易触发两次 measure)。这是布局优化的重点战场:减少层级、用 ConstraintLayout 替代嵌套、避免 weight 的二次 measure。

#### 15.2 performLayout

递归调用每个 View 的 `layout(l, t, r, b)` → `onLayout()`。

- 父 View 根据 measure 结果,确定每个子 View 的位置(四个坐标)
- 调用 `child.layout(l, t, r, b)` 设置子 View 的位置

layout 相对 measure 轻得多,一次走完。layout 结束后,所有 View 才有**真实的 width/height/位置**,这时候 `view.width` 才不是 0。

#### 15.3 performDraw

递归构建 DisplayList(绘制指令列表),**不直接画到屏幕**。

- 每个 View 的 `onDraw(canvas)` 被调用,但这里的 canvas 是记录型 canvas
- 所有绘制操作被记录成 DisplayList(类似一个"待执行的绘制脚本")
- DisplayList 被同步给 RenderThread
- **主线程的 traversal 到这里就结束了**

**关键认知**:硬件加速开启时(默认),主线程**不实际绘制像素**,只构建 DisplayList。真正的 GPU 绘制在 RenderThread。这是 Android 4.0 后的架构。

### 阶段 16:RenderThread + SurfaceFlinger + 首帧上屏

#### 16.1 RenderThread 接手

主线程把 DisplayList 交给 RenderThread 后就解放了(可以回去处理下一条消息)。

RenderThread 做的事:

1. 解析 DisplayList,翻译成 OpenGL/Vulkan 命令
2. 通过 GPU 渲染到 Surface(一块由 SurfaceFlinger 分配的 GraphicBuffer)
3. 渲染完成后,通过 BufferQueue 把 buffer 交给 SurfaceFlinger

**为什么要单独一个 RenderThread**:把 GPU 命令提交从主线程剥离,主线程可以继续处理触摸、输入、业务逻辑,不被渲染阻塞。动画、滚动流畅度主要靠 RenderThread。

#### 16.2 SurfaceFlinger 合成

SurfaceFlinger 是一个**系统进程**,负责把所有 App 的 Surface、系统 UI(状态栏、导航栏)、Starting Window 等合成一张最终的图像。

它在每个 vsync 周期:

1. 从所有 App 的 BufferQueue 拿最新 buffer
2. 用硬件合成器(HWC)或 GPU 合成所有图层
3. 把最终帧交给显示硬件

#### 16.3 首帧上屏

你的 Activity 第一帧被 SurfaceFlinger 合成到最终画面 → 显示硬件推到屏幕。

此刻:

- ★ **用户真正看到你的 Activity 内容**
- WindowManagerService 收到"首帧绘制完成"回调
- 系统打 **`ActivityTaskManager: Displayed com.xx.app/.MainActivity: +XXXms`** 日志
- Starting Window 被系统移除(从占位窗口切换到你的真实 Activity)
- **TTID 在这一刻结束**

TTFD 通常比这个点晚,要等你 `reportFullyDrawn()` 被调用。

## 三、关键对象职责卡片

### ActivityThread

- **是什么**:主线程上的核心调度对象(不是线程!)
- **职责**:接收系统 Binder 指令,分发到各生命周期处理方法
- **线程归属**:所有方法都在主线程执行(除了 Binder 线程里的 ApplicationThread 方法体)
- **常见误解**:名字带 Thread 就以为是线程;以为创建它会启线程
- **你在哪见它**:crash 堆栈里的 `at android.app.ActivityThread.xxx` 永远表示"主线程上发生的事"

### ApplicationThread

- **是什么**:ActivityThread 的内部类 + Binder 对象
- **职责**:作为 AMS 的"遥控器",接收系统跨进程调用,把任务投递到主线程
- **线程归属**:方法体执行在 Binder 线程池!不是主线程
- **生命周期**:ActivityThread 构造时作为字段同时创建,和 ActivityThread 同生共死
- **设计要点**:方法只做"封装消息 + 投递",把活儿全转给主线程,让 Binder 线程快速释放

### H(主线程 Handler)

- **是什么**:ActivityThread 的内部类,继承 Handler
- **职责**:主线程上的"分诊台",根据 `msg.what` 分发到 ActivityThread 的对应方法
- **典型消息**:BIND_APPLICATION、LAUNCH_ACTIVITY、PAUSE_ACTIVITY、RESUME_ACTIVITY、CREATE_SERVICE、RECEIVER 等几十种
- **关键事实**:所有组件生命周期、所有系统发来的指令,都是通过 H 进入主线程的

### AMS / ATMS

- **AMS (ActivityManagerService)**:Android 10 之前统管一切(Activity、进程、Task);10 之后负责进程创建和生命周期分发
- **ATMS (ActivityTaskManagerService)**:Android 10+ 新拆出,专门管 Activity 和 Task 栈
- **位置**:运行在 system_server 进程
- **开发者接触方式**:通过 `ActivityManager`(AMS 的 Binder 代理)间接调用

### Zygote

- **是什么**:所有 App 进程的父进程(模板进程)
- **位置**:独立进程,系统启动早期创建
- **职责**:预加载 ART 虚拟机 + framework 类/资源,接受 AMS 的 fork 请求,fork 出新 App 进程
- **通信方式**:socket(不是 Binder)
- **为什么不用 Binder**:Binder 驱动状态不能被 fork 安全克隆,多线程 fork 不安全

### PhoneWindow

- **是什么**:Activity 持有的 Window 对象(Window 的具体实现)
- **创建时机**:Activity.attach 里 `new PhoneWindow(...)`
- **职责**:持有 DecorView(View 树的根),管理窗口属性、主题装饰
- **和 ViewRootImpl 的关系**:ViewRootImpl 是它的"绘制引擎"

### DecorView

- **是什么**:整个 Window 的根 View(最顶层)
- **创建时机**:第一次 `setContentView` 时,`installDecor()` 里创建
- **层级**:DecorView > 系统主题模板(可能有 ActionBar)> @android:id/content FrameLayout > **你的布局**
- **常见困惑**:Layout Inspector 里看你的布局外面多几层,就是这

### ViewRootImpl

- **是什么**:View 树和系统窗口系统之间的桥梁
- **创建时机**:WindowManager.addView 被调用时(通常在 onResume 中)
- **职责**:监听 vsync,驱动 performTraversals,管理 Surface,和 RenderThread 通信
- **一 Window 一实例**:每个 Window(Activity / Dialog / Toast)都有自己的 ViewRootImpl

### LoadedApk

- **是什么**:代表"一个已加载 APK"的对象
- **持有什么**:APK 路径、ClassLoader、Resources、Application 类名、Provider 列表
- **创建时机**:handleBindApplication 的 `getPackageInfoNoCheck`
- **为什么关键**:它持有的 ClassLoader 是后续加载所有业务类的唯一途径

## 四、关键线程地图

启动期 App 进程里活跃的线程:

### 主线程(main)

- 从 `ActivityThread.main()` 开始
- 跑 Looper.loop 死循环
- 处理:所有生命周期、所有 UI 操作、所有同步初始化、measure/layout、发起 draw
- **启动优化的主战场**

### Binder 线程池(Binder:xxx_N)

- Zygote fork 后,进入 Java 层前,Native 层就已经启动了
- 默认 1 个,按需扩展到最多 16 个
- 处理:所有系统发来的跨进程调用(AMS → ApplicationThread 的 schedule* 方法全在这)
- **不做重活,立刻转手给主线程**

### RenderThread

- 系统创建,每个有硬件加速 Window 的进程一个
- 专门执行 GPU 命令提交
- 不跑业务代码,只跑 DisplayList → OpenGL/Vulkan
- **滚动/动画流畅度的关键**,主线程卡也能动画流畅就靠它

### HeapTaskDaemon(GC 相关)

- ART 虚拟机自带
- 后台 GC 任务
- **启动期如果内存压力大可能触发 GC stop-the-world,主线程被冻结**

### 一般不需要关心的

- FinalizerDaemon、FinalizerWatchdogDaemon:GC finalize 队列
- ReferenceQueueDaemon:弱引用处理
- Signal Catcher:信号处理

## 五、易错记忆校准 ★ 独家

> 这一节保留"自己踩过的坑和易错的记忆点",是这份笔记最值钱的部分。

### 校准 1:fork 返回值方向(踩过两次!)

**正确**:

- Zygote(父)拿到 **子进程的 pid(> 0)**
- 子进程拿到 **0**

**口诀**:"**0 是新生儿,非 0 是当爹的**"

**为什么 0 代表子进程**:fork 返回值不是"当前进程的 pid",而是"身份识别暗号"。0 不可能是任何真实 PID(PID 从 1 开始),用它当新生标记不会冲突。父进程拿"孩子的 pid"是因为它要知道生了谁。

**反向错误记忆的典型**:以为"子进程有自己的 pid,所以返回值是它自己的 pid"。这是把"fork 返回值"和"getpid() 返回值"混淆了。子进程真要知道自己 pid,得调 `getpid()`。

### 校准 2:代理和本体的位置

**正确**:**代理永远在调用方,本体永远在被调用方**

| 谁要调谁   | 调用方(持代理)                | 被调用方(本体)                    |
| ---------- | ----------------------------- | --------------------------------- |
| AMS 调 App | AMS 持 ApplicationThread 代理 | App 进程有 ApplicationThread 本体 |
| App 调 AMS | App 持 ActivityManager 代理   | system_server 有 AMS 本体         |

**常犯错误**:`mgr.attachApplication(mAppThread)` 这一行,容易误说成"传递 ApplicationThread 代理"。错,传的是**本体的 Binder 引用**,AMS 那边生成代理。代理永远在"想调"的那一方。

### 校准 3:ApplicationThread 的创建时机

**正确**:`new ActivityThread()` 的**构造**时,ApplicationThread 作为字段同时被 new 出来。**不是 attach 时**。

```java
public final class ActivityThread {
    final ApplicationThread mAppThread = new ApplicationThread();  // 字段初始化
    
    private void attach(...) {
        mgr.attachApplication(mAppThread, startSeq);  // 这里只是使用,不是创建
    }
}
```

**为什么重要**:关系到"ApplicationThread 生命周期" —— 它和 ActivityThread 同生共死,一个 App 进程一辈子只有一个 ApplicationThread 实例,不是"attach 临时创建用完就丢"。

### 校准 4:bindApplication 是指令名,Application.onCreate 是生命周期名

**容易混的两个词**:

| 词                                       | 是什么                    | 谁调                       | 谁实现                             |
| ---------------------------------------- | ------------------------- | -------------------------- | ---------------------------------- |
| `ApplicationThread.bindApplication(...)` | AMS 下发给 App 的**指令** | AMS 调                     | App 进程实现(ApplicationThread 里) |
| `Application.onCreate()`                 | 应用**生命周期回调**      | handleBindApplication 里调 | 你写的 MyApplication 实现          |

**关系**:`bindApplication` 是"把 Application 初始化起来"这个指令的**代号**,`Application.onCreate` 是执行这个指令过程中的**最后一步**(前面还有 attachBaseContext 和 ContentProvider 初始化)。

**错误表述**:"AMS 通过 ApplicationThread 调用 application.onCreate" —— 错。AMS 调的是 bindApplication,onCreate 是 handleBindApplication 里的一个子步骤。

### 校准 5:ActivityThread / ApplicationThread 都不是线程

**命名坑**:

- `ActivityThread` 不继承 Thread,是主线程上的管理对象
- `ApplicationThread` 不继承 Thread,是 Binder 对象

**验证方法**:`adb shell ps -T <pid>` 看不到任何叫 ActivityThread 或 ApplicationThread 的线程。

**命名来源猜测**:Android 早期"ActivityThread is also known as the UI thread",指"代表主线程那个类"。但 Thread 后缀误导无数人。

### 校准 6:onResume ≠ 启动完成

**正确路径**:

```
onResume 返回
    ↓
(等下一个 vsync)
    ↓
ViewRootImpl.performTraversals
    ↓
measure → layout → draw
    ↓
RenderThread 渲染
    ↓
SurfaceFlinger 合成
    ↓
首帧上屏 ← 这才是启动完成
```

onResume 只是"告诉系统该绘制了",不是"绘制完了"。`view.width` 在 onCreate/onStart/onResume 全都是 **0**,要等 layout 完成。

### 校准 7:setContentView 不跑 measure

**事实**:setContentView 只做"XML → View 对象 + 挂到 DecorView 下",**不调用任何 View 的 measure**。

所以在 onCreate 里 `findViewById(...).width` 永远是 0(如果 setContentView 之前调,直接 NPE;如果之后调,width = 0)。

**正确拿 width 的时机**:`view.doOnPreDraw { }` 或 `view.post { }`(post 会排到下次 Looper 循环,此时 traversal 可能已完成)。

### 校准 8:onCreate → onStart → onResume 同一条消息、同一个调用栈

**事实**:这三个回调在 LAUNCH_ACTIVITY 消息的**同一次处理**中**连续调用**,中间 Looper 不会取新消息。

**推论**:

- 不能在 onCreate 里 post 一个任务让它"在 onStart 之前执行"
- 三个回调里任何耗时都直接计入启动时间
- 三个回调串起来看,就是启动期主线程一次长调用

### 校准 9:反射创建要求无参构造

**Android 四大组件 + Application,全都是系统反射创建**,铁律:**必须有无参构造函数**。

```kotlin
// ❌ 错误示范
class MainActivity(val userId: String) : AppCompatActivity() { ... }
// 启动时崩:InstantiationException: has no zero argument constructor
```

Kotlin 主构造一旦带参,默认无参就没了。反射 `newInstance()` 直接崩。

**正确传参**:用 Intent.putExtra + onCreate 里 intent.getStringExtra。

### 校准 10:ContentProvider.onCreate 先于 Application.onCreate

**执行顺序(handleBindApplication 内部)**:

```
attachBaseContext
   ↓
Provider1.onCreate   ┐
Provider2.onCreate   │  全都在主线程同步串行
...                  │
ProviderN.onCreate   ┘
   ↓
Application.onCreate   ← 你以为的"应用第一次执行代码",实际是中间点
```

**推论**:

- "减少 Application.onCreate 耗时"不是启动优化第一步,**审查 ContentProvider 才是**
- 第三方 SDK 夹带的 Provider 可能占几百 ms,你代码里一行都看不到

### 校准 11:Starting Window 是系统给的占位

**用户点击图标后立刻看到的不是你的 Activity,是 Starting Window**:

- Android 11 及之前:Activity 主题的 windowBackground
- Android 12+:系统 SplashScreen API 画面

**推论**:

- 改 windowBackground 为"假首页图"→ TTID 看起来变快,实际没变(伪造 TTID 的原理)
- Android 12+ 这招被系统破解(SplashScreen 会盖在上面)
- 这是"感知性能优化"最便宜的一条路径

## 六、从笔记到启动优化(钩子)

这一节不是"优化方法",而是"**本笔记流程里的哪些点是启动优化的手术位**",作为后续轮次的锚点。

| 流程节点                                 | 对应的优化切入                                         | 在哪一轮            |
| ---------------------------------------- | ------------------------------------------------------ | ------------------- |
| Zygote fork(~50-150ms)                   | 不可优化,系统固定开销                                  | —                   |
| Binder 线程池初始化                      | 不可优化                                               | —                   |
| attach / bindApplication 往返            | 不可优化                                               | —                   |
| **ContentProvider.onCreate(串行主线程)** | **★ 启动优化第一金矿**:删/合并/延迟                    | 第 5 轮决策树       |
| Application.onCreate 里的代码            | 异步化 / 懒加载 / App Startup 编排                     | 第 5 轮             |
| 反射创建类的成本(类加载)                 | 减少启动期触及的类;避免巨大基类链                      | 第 4 轮 pattern     |
| setContentView(inflate)                  | 减少层级、ViewStub、AsyncLayoutInflater                | 第 4 轮 pattern     |
| measure / layout(递归)                   | 降层级、ConstraintLayout、避免 weight 二次 measure     | 第 4 轮 pattern     |
| SharedPreferences / DB 同步读            | 异步 + 占位 / 数据预热                                 | 第 4 轮 pattern     |
| Starting Window                          | 主题预设 windowBackground / SplashScreen API(感知性能) | 第 5 轮决策树根节点 |
| reportFullyDrawn 时机选择                | 精确定位 TTFD,避免伪装                                 | 第 1 轮已讲         |

### 和 ANR 链路的对照

两条链路本质都是"读懂主线程在干嘛",终点不同:

- **ANR 链路**:终点是**诊断**(主线程卡死了,倒查是谁占着)
- **启动链路**:终点是**优化**(主线程没卡死,主动找冗余砍)

启动优化比 ANR 多一层"**取舍**":不是所有耗时都要砍,要按 ROI 排序、按业务优先级保护关键路径(比如首屏可见 vs 全功能可用)。
