## 02.核心概念

### 2.1 是什么？

状态本质是被特殊监听的变量，用于在自身被修改后触发UI的重绘

```
// ❌ 普通变量：改变后UI不会更新
let count = 0
count = 1  // UI不会刷新

// ✅ 状态变量：改变后UI会自动更新
@State count: number = 0
this.count = 1  // UI会自动刷新！
```


### 2.2 解决什么问题？

解决了手动刷新UI的问题，形成了状态驱动型UI，此时用户通过触发组件的事件方法，改变状态数据，即可自动改变UI，实现UI和操作的解耦。

## 03.原理机制

### 3.1 底层实现原理简介

Android的基于回调的UI  VS  鸿蒙的状态驱动型UI

- Android是基于回调的，这是常用的flow和liveData

  - ```
    // Kotlin Flow: 本质是回调链
    viewModel.userState.collect { user ->
        // 这是一个回调函数
        updateUI(user)
    }
    
    // LiveData: 也是回调
    viewModel.liveData.observe(this) { data ->
        // 这也是回调
        updateUI(data)
    }
    ```

  - 原理：这里的Observe 和 collect本质是注册了回调函数，当数据变化时，会自动调用内部的回调函数，更新UI

- 鸿蒙是基于代理拦截式

  - ```
    // 鸿蒙底层实现原理（伪代码）
    class StateProxy {
      constructor(target) {
        // 使用Proxy拦截对象的get和set操作
        return new Proxy(target, {
          // 读取属性时：收集依赖
          get(target, key) {
            collectDependency(key)  // ← 记录"谁在使用这个属性"
            return target[key]
          },
          
          // 修改属性时：触发更新
          set(target, key, value) {
            target[key] = value
            triggerUpdate(key)  // ← 通知所有使用该属性的UI组件更新
            return true
          }
        })
      }
    }
    ```

  - 原理：读取时：自动收集依赖（记录哪些UI组件在使用这个属性）；修改时：自动触发更新（通知相关UI组件重新渲染）

- 提问：鸿蒙是基于代理拦截，Android是基于回调，这真的对吗？Android难道不也是代理拦截？属性变更后触发map中的UI回调？ 鸿蒙难道不也是基于回调？代理拦截set方法后触发UI更新？只是这个更新是系统回调build方法
- 目前我可以确认的一点是：Android的回调相对于鸿蒙宽松很多，鸿蒙只能执行UI操作，Android可以执行的很多，可以进行用户自定义操作，但是我还不理解他们本质的区别。AI说是代理拦截的层级不同，鸿蒙是语言层级，Android是库层级，这有道理，但是即使是这样，我们也可以把鸿蒙的状态和Android的联系起来，因为他们本质都是一样的

鸿蒙的底层依赖收集过程

- 这是代码

  - ```
    // @file: VideoPatrolPage.ets
    @Provide('videoPatrolState') globalState: VideoPatrolState = new VideoPatrolState()
    
    build() {
      Column() {
        // 依赖收集点1：DeviceSwitchBar 读取 deviceState
        DeviceSwitchBar({ 
          deviceState: this.globalState.deviceState,
          isDropdownVisible: $isDropdownVisible 
        })
        
        // 依赖收集点2：VideoPlayComponent 读取 deviceState 和 videoPlaybackState
        VideoPlayComponent({
          deviceState: this.globalState.deviceState,
          videoPlaybackState: this.globalState.videoPlaybackState
        })
      }
    }
    ```

- **底层执行流程：**

  - ```
    阶段1：初始渲染
      ↓
    执行 build() 方法
      ↓
    访问 this.globalState.deviceState
      ↓
    Proxy 拦截 get 操作
      ↓
    依赖收集：
      - DeviceSwitchBar 依赖 deviceState
      - VideoPlayComponent 依赖 deviceState
      - VideoPlayComponent 依赖 videoPlaybackState
    
    阶段2：数据更新
      ↓
    修改 this.globalState.deviceState.shopName = "新门店"
      ↓
    Proxy 拦截 set 操作
      ↓
    查找依赖列表：[DeviceSwitchBar, VideoPlayComponent]
      ↓
    仅重新渲染这两个组件（其他组件不受影响）
    ```

通过@Track进行精细化的控制

- 这是没有track和有track的对比

  - ```
    // ❌ 没有 @Track：修改任何属性都会触发UI更新
    class MyState {
      name: string = "张三"
      age: number = 18
      address: string = "北京"  // UI不使用，但修改也会触发更新
    }
    this.state.address = "上海"  // 触发不必要的UI更新
    
    // ✅ 使用 @Track：只有标记的属性才会触发UI更新
    class MyState {
      @Track name: string = "张三"
      @Track age: number = 18
      address: string = "北京"  // 不加 @Track
    }
    this.state.address = "上海"  // 不会触发UI更新，性能优化！
    ```

### 3.2 常见状态装饰器

鸿蒙的状态装饰器分为@Observed，@Track，@Prop，@State，@Link，@Provide，@Consume等。

我们要先理清楚他们的关系

- 关系：
  - 
    @Observed - 用于类定义，使类的实例可被观察
  - @Track \- 用于 Observed 类的属性，实现属性级精确更新
  - @State/@Prop/@Link/@Provide/@Consume \- 用于组件的状态同步

- 关键点：Observed 装饰的是类本身，State/@Provide 等装饰的是组件中的变量，只有当变量的类型是 Observed 类时，才可以实现深度响应。

- 我们可以用一段代码理解这个关系：先用@Observed定义这个类是可以被观察的。然后才能在组件中修饰这个类的实例变量，让其在各组件中传递

  - ```
    // 1. 定义可观察的类
    @Observed
    class User {
      @Track name: string = ''
      @Track age: number = 0
    }
    
    // 2. 在组件中使用
    @Component
    struct Parent {
      @Provide('user') user: User = new User()  // ✅ 提供
    }
    
    @Component  
    struct Child {
      @Consume('user') user: User  // ✅ 消费
    }
    ```

好，由此我们引出装饰器的两个层次

- 第一层：**类级别**（定义数据结构）

  - ```
    @Observed  // ← 让类的实例可被观察
    class User {
      @Track name: string    // ← 精确追踪这个属性
      @Track age: number
      address: string        // ← 不加 @Track，变化不会触发更新
    }
    ```

- 第二层：**实例变量级别**（组件中的类的实例变量使用数据）

  - ```
    @Component
    struct MyComponent {
      @State user: User           // 组件内状态
      @Provide('user') user: User // 提供给子组件
      @Consume('user') user: User // 从父组件消费
      @Prop user: User            // 单向接收
      @Link user: User            // 双向绑定
    }
    ```

好，我们来分别简易的看看各个装饰器

- Observed：让类可被观察。他会把类包装成 Proxy，让其属性变化会被拦截并触发更新。

- Track：用于 Observed 类的属性，实现属性级精确更新

- Provide/@Consume 实现状态传递

  - ```
    // 定义数据结构
    @Observed
    class AppState {
      @Track theme: string = 'light'
      @Track user: User = new User()
    }
    
    @Observed
    class User {
      @Track name: string = ''
    }
    
    // 顶层提供
    @Entry
    @Component
    struct App {
      @Provide('appState') appState: AppState = new AppState()
      // ✅ appState 是 @Observed 类的实例
      
      build() {
        Column() {
          Header()
          Content()
        }
      }
    }
    
    // 子组件消费
    @Component
    struct Header {
      @Consume('appState') appState: AppState
      // ✅ 直接消费，自动响应式
      
      build() {
        Text(this.appState.user.name)
          .onClick(() => {
            this.appState.user.name = 'New Name'
            // ✅ 会触发所有使用 appState.user.name 的组件更新
          })
      }
    }
    ```

- Prop和Link：实现父子组件间状态共享。只不过一个是双向绑定，一个是单向绑定

  - ```
    @Component
    struct Parent {
      @State count: number = 0
      
      build() {
        Child({ count: $count })  // 注意 $ 符号
      }
    }
    
    @Component
    struct Child {
      @Link count: number  // 双向绑定
      
      build() {
        Button('Add').onClick(() => {
          this.count++  // ✅ 会同步到父组件
        })
      }
    }
    
    @Component
    struct Child {
      @Link count: number  // 双向绑定
      
      build() {
        Button('Add').onClick(() => {
          this.count++  // ✅ 会同步到父组件
        })
      }
    }
    ```

- 我们来看看小结

  - | 装饰器           | 作用域   | 数据流 | 传递方式 | 典型场景                 |
    | :--------------- | :------- | :----- | :------- | :----------------------- |
    | State            | 组件内部 | -      | -        | 组件自己的状态           |
    | Prop             | 父→子    | 单向   | 深拷贝   | 展示型组件，不需要修改   |
    | Link             | 父↔子    | 双向   | 引用     | 表单输入，需要双向同步   |
    | Provide/@Consume | 跨层级   | 双向   | 引用     | 跨多层传递，避免逐层传递 |

问题一：provide 是否要先通过 Observed 标注？

- 答案：取决于数据类型。简单类型 → 不需要 Observed；复杂对象 → 需要Observed

  - ```
    @Provide('count') count: number = 0  // ✅ 直接提供
    @Provide('name') name: string = ''   // ✅ 直接提供
    
    // ❌ 错误：对象属性变化不会触发更新
    class User { name: string = '' }
    @Provide('user') user: User = new User()
    
    // ✅ 正确：用 @Observed 包装
    @Observed
    class User { 
      @Track name: string = '' 
    }
    @Provide('user') user: User = new User()
    ```

问题二：Prop vs Link 的选择？

- ```
  // 用 @Prop：子组件只读
  struct DisplayCounter {
    @Prop count: number  // 只展示，不修改
  }
  
  // 用 @Link：子组件需要修改
  struct EditCounter {
    @Link count: number  // 可以修改，同步回父组件
  }
  
  子组件需要修改这个值吗？
  ├─ 是 → 用 @Link
  └─ 否 → 用 @Prop
  ```

### 3.3 @Provide/@Consume  ， @ObjectLink ，@Prop， 底层原理

@ObjectLink 的本质：引用参数传递 + Proxy 订阅

- 这是代码

  - ```
    // 父组件
    @Component
    struct Parent {
      @Provide('videoPatrolState') globalState: VideoPatrolState  // Proxy对象
      
      build() {
        Column() {
          // 传递 Proxy 对象的引用给子组件
          Child({ videoPlaybackState: this.globalState.videoPlaybackState })
        }
      }
    }
    
    // 子组件
    @Component
    struct Child {
      // ✅ 接收引用，并订阅这个 Proxy 对象
      @ObjectLink videoPlaybackState: VideoPlaybackState
      
      build() {
        Text(`播放状态: ${this.videoPlaybackState.livePlayState.isPlaying()}`)
      }
    }
    ```

- 这是对应流程

  - ```
    // 内存中的 Proxy 对象
    const proxyObj = new Proxy(videoPlaybackState, { /* ... */ })  // 0x12345678
    
    // 父组件
    Parent.globalState.videoPlaybackState = proxyObj  // 引用地址：0x12345678
    
    // 子组件（通过参数传递）
    Child.videoPlaybackState = proxyObj  // 引用地址：0x12345678（同一个对象）
    
    // 订阅关系
    proxyObj.__subscribers__ = [Parent, Child]  // 两个组件都订阅了
    
    // 当状态变化时
    proxyObj.setter() → 通知所有订阅者
      ├─ Parent.triggerUpdate()  // 父组件刷新
      └─ Child.triggerUpdate()   // 子组件刷新
    ```

@Provide/@Consume 底层原理：这里不是参数传递，而是通过作用域链查找

- 这是类似的代码

  - ```
    // ============ @Provide 注册机制 ============
    @Component
    struct Parent {
      @Provide('videoPlaybackVm') vm: VideoPlaybackViewModel
      
      // ArkUI 内部伪代码
      constructor() {
        // 在当前组件的"提供者映射表"中注册
        this.__providerMap__ = new Map()
        this.__providerMap__.set('videoPlaybackVm', this.vm)
      }
    }
    
    // ============ @Consume 查找机制 ============
    @Component
    struct Child {
      @Consume('videoPlaybackVm') vm: VideoPlaybackViewModel
      
      // ArkUI 内部伪代码
      constructor() {
        // 沿着组件树向上查找（类似作用域链）
        let ancestor = this.parent
        while (ancestor) {
          if (ancestor.__providerMap__?.has('videoPlaybackVm')) {
            // 找到了！获取引用
            this.vm = ancestor.__providerMap__.get('videoPlaybackVm')
            return
          }
          ancestor = ancestor.parent  // 继续向上查找
        }
        throw new Error(`Provider 'videoPlaybackVm' not found`)
      }
    }
    ```

- 这是查找过程

  - ```
    组件树结构：
    VideoPatrolPage (有 __providerMap__: { 'videoPlaybackVm': vmInstance })
        ↓ parent
    VideoPlayComponent (没有提供 'videoPlaybackVm')
        ↓ parent
    BottomControlBar (@Consume 'videoPlaybackVm')
        ↓ 查找过程
        1. 检查 BottomControlBar.__providerMap__ → 没有 'videoPlaybackVm'
        2. 检查 parent (VideoPlayComponent).__providerMap__ → 没有
        3. 检查 parent.parent (VideoPatrolPage).__providerMap__ → ✅ 找到了！
        4. 返回 vmInstance（引用传递）
        
    结果：BottomControlBar.vm = VideoPatrolPage.vm（同一个对象）
    ```

小结：@ObjectLink 和 @Provide/@Consume 响应式原理完全相同，只是传递方式不同。一个是参数传递，一个是作用域链查找。获取到引用后都是会和状态建立响应关系

@Prop底层原理：

- 这个是值拷贝，不是引用传递，这也是为什么子组件更新不会影响到父组件，因为不是一个引用。那为什么父组件更新影响到子组件呢？因为会给一个新的值拷贝

- 代码

  - ```
    @Observed
    class User {
      name: string = 'Alice'
      age: number = 18
    }
    
    @Component
    struct Parent {
      @State user: User = new User()
      
      build() {
        Child({ user: this.user })  // ← 这里发生深拷贝
      }
    }
    
    @Component
    struct Child {
      @Prop user: User  // ← 收到的是拷贝
      
      build() {
        Button('Change').onClick(() => {
          this.user.name = 'Bob'
          // ❌ 只改了自身的拷贝，Parent.user.name 还是 'Alice'
        })
      }
    }
    ```
