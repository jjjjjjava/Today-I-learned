## Phase 1: 需求背景与技术选型

### 1.1 业务需求分析

#### 核心功能需求

```
视频巡店场景下的实时语音对讲功能
├── 用户在App端通过摄像头进行语音对讲
├── 支持按住说话（Push-to-Talk）模式
├── 需要实时音量反馈（显示波形/音量条）
└── 需要连接状态提示（连接中、已连接、断开）
```

#### 多设备支持需求

项目需要对接**4种不同厂商**的设备：

| 设备类型 | 厂商 | 协议特点 | 复杂度 |
|---------|------|---------|--------|
| **WDZ_NVR** | 自研 | HTTP模拟POST，简单直连 | ⭐ |
| **KEDA** | 科达 | 自定义TCP协议头 | ⭐⭐ |
| **YUSHI** | 宇视 | 复杂握手协议（4步） | ⭐⭐⭐⭐ |
| **EZVIZ** | 萤石云 | SDK方式（暂未实现） | ⭐⭐⭐ |

**关键问题**：每种设备的连接方式、数据格式、握手流程完全不同，如何用统一的API对接？

#### 非功能性需求

**1. 性能要求**
- 音频采集延迟 < 100ms
- 端到端延迟 < 500ms
- 内存占用稳定，无泄漏
- 低端机型流畅运行

**2. 稳定性要求**
- 网络异常自动重连
- 设备离线优雅降级
- 超时保护机制
- 资源自动释放

**3. 可维护性要求**
- 代码职责清晰
- 新增设备类型简单
- 易于调试和监控

### 1.2 技术挑战识别

#### 挑战1：设备协议差异巨大

**宇视设备（最复杂）**

```kotlin
// 握手流程（4步）
1. Server → Client: ReleaseRandomKey { random: "abc123..." }
2. Client → Server: RequireSession { key: encrypt(random, streamKey) }
3. Server → Client: SessionAck { session: "xxx" }
4. Server → Client: BridgeReady { ... }

// ⚠️ 只有收到BridgeReady后才能发送音频数据！
```

**科达设备（中等复杂）**
```kotlin
// 连接成功后立即发送协议头
POST /postAudio?streamKey=xxx RS/1.1\r\n
Host: \r\n
Content-Length:\r\n
Session-Id:\r\n
Authentication:\r\n\r\n

// 然后直接发送音频数据
```

**自研NVR（最简单）**
```kotlin
// 模拟HTTP POST
POST /control/audio HTTP/1.1\r\n
Host: 192.168.1.100:8000\r\n
Content-Length: 99999999\r\n
Content-Type: application/octet-stream\r\n\r\n

// 然后持续发送音频数据
```

**❌ 如果用if-else会怎样？**
```kotlin
// 反模式：难以维护
fun startAudioCall() {
    if (deviceType == "YUSHI") {
        // 100行握手代码
    } else if (deviceType == "KEDA") {
        // 50行协议头代码
    } else if (deviceType == "WDZ_NVR") {
        // 30行HTTP模拟代码
    }
    // 新增设备时要改这里，违反开闭原则
}
```

#### 挑战2：音频处理的线程协调

**❌ 传统单线程做法的问题**

```
采集 → 编码 → 发送  (串行执行)

问题分析：
├── AudioRecord.read() 阻塞 20-40ms
├── G.711编码耗时 1-2ms
├── Socket.send() 可能阻塞（网络慢）
└── 总延迟累加，容易掉帧
```

**✅ 解决思路：流水线并行处理**

```
┌─────────┐        ┌─────────┐        ┌─────────┐
│ 线程1:  │ Queue1 │ 线程2:  │ Queue2 │ 线程3:  │
│ 采集    ├───────→│ 编码    ├───────→│ 发送    │
└─────────┘        └─────────┘        └─────────┘
  阻塞20ms           CPU 1-2ms         网络不定

优势：
- 每个阶段独立运行
- 队列缓冲，削峰填谷
- 某阶段慢不会拖累其他阶段
```

#### 挑战3：内存和GC压力

**问题分析**：
```kotlin
// 采样率8000Hz，16bit，单声道
// 每次读取640字节（40ms数据）
// 每秒产生: 1000ms / 40ms = 25个buffer对象

// ❌ 传统做法
fun capture() {
    while (true) {
        val buffer = ByteArray(640)  // 每次new，每秒25个对象
        audioRecord.read(buffer, 0, 640)
        encode(buffer)  // 又产生编码后的对象
    }
}
// 每秒至少50个对象，频繁触发GC！
```

**✅ 解决思路：对象池复用**
```kotlin
val pool = ByteBufferPool(bufferSize = 640, maxPoolSize = 10)

fun capture() {
    while (true) {
        val buffer = pool.acquire()  // 从池中获取
        // ... 使用buffer
        pool.release(buffer)  // 归还到池中
    }
}

// 效果：只创建10个对象，复用率95%以上，GC大幅降低
```

### 1.3 技术选型决策

#### 🎯 核心约束条件

| 约束 | 原因 | 影响 |
|------|------|------|
| ✅ **必须用G.711编码** | 服务端只支持G.711 | 不能用MediaCodec的AAC/Opus优化 |
| ✅ **必须用TCP Socket** | 服务端不支持WebSocket | 不能用现成的WebSocket库 |
| ✅ **必须支持多种设备** | 业务需求 | 必须有良好的扩展机制 |

#### 选型决策表

| 技术点 | 方案对比 | 最终选择 | 理由 |
|--------|---------|---------|------|
| **编码方案** | MediaCodec (AAC/Opus) vs 纯Java G.711 | ✅ G.711 | 服务端约束 |
| **传输协议** | WebSocket vs TCP Socket | ✅ TCP Socket | 服务端约束 |
| **设备适配** | if-else vs 策略模式 | ✅ 策略模式 | 可扩展性 |
| **线程模型** | 单线程 vs 多线程流水线 | ✅ 三线程流水线 | 性能和解耦 |
| **内存优化** | 每次new vs 对象池 | ✅ ByteBufferPool | 降低GC |
| **组件协调** | 单一类 vs Manager协调 | ✅ Manager模式 | 职责清晰 |

#### 为什么不用MediaCodec？（深入分析）

```kotlin
// ❌ 如果用MediaCodec
MediaCodec.createEncoderByType("audio/mp4a-latm")  // AAC编码

优势：
├── 硬件加速，性能更好
├── 压缩率更高（10:1 vs G.711的2:1）
└── 音质更好（支持高码率）

劣势（致命）：
└── 服务端不支持！无法解码！

// ✅ 实际使用G.711
G711Code.G711aEncoder(pcmSamples, encodedData, size)

优势：
├── 服务端直接支持（硬件摄像头标准）
├── 编码简单，延迟低
└── 无需额外依赖

劣势（可接受）：
├── 压缩率低（2:1），带宽占用较大（64Kbps）
└── 音质一般（电话音质级别）
```

**🤔 为什么服务端只支持G.711？**

- 硬件摄像头普遍使用G.711（行业标准）
- 解码实现简单，无需复杂的DSP
- 实时性好，适合对讲场景
- 成本低，固件占用空间小

#### 为什么不用WebSocket？（深入分析）

```kotlin
// ❌ 如果用WebSocket
val client = OkHttpClient()
val request = Request.Builder()
    .url("ws://192.168.1.100:8000/audio")
    .build()
client.newWebSocket(request, listener)

优势：
├── 现成的库（OkHttp、Scarlet）
├── 自动心跳、重连机制
├── 支持文本和二进制
└── 协议标准化

劣势（致命）：
├── 服务端不支持WebSocket协议！
├── 多一层协议开销
└── 宇视/科达的私有协议无法兼容
```

**🤔 为什么服务端不支持WebSocket？**
- 设备固件老旧，只支持原始TCP
- 厂商私有协议，不遵循标准
- 升级设备固件成本高（大量存量设备）
- WebSocket握手过程增加延迟

#### 架构模式选型

**策略模式 (Strategy Pattern)**
```kotlin
// 封装设备差异
interface IDeviceStrategy {
    fun configureChannel(...)  // 每种设备实现不同的握手逻辑
    fun createEncoder(): IEncoder
    fun canSendAudio(): Boolean  // 宇视需要等握手完成
}

// ✅ 扩展新设备只需新增一个策略类
class NewDeviceStrategy : IDeviceStrategy {
    override fun configureChannel(...) { /* 新设备的握手逻辑 */ }
    override fun createEncoder() = G711Encoder(Type.PCMA)
    override fun canSendAudio() = true
}

// ✅ 无需修改Manager代码
val strategy = DeviceStrategyFactory.create(deviceType)  // 工厂创建
```

**流水线模式 (Pipeline Pattern)**
```kotlin
// 三阶段解耦
captureThread:  audioSource.read() → pcmQueue
encoderThread:  pcmQueue.poll() → encoder.encode() → encodedQueue  
senderThread:   encodedQueue.poll() → channel.send()

优势：
├── 每个阶段独立运行，互不阻塞
├── 队列缓冲，削峰填谷
├── 某个阶段慢不会拖累其他阶段
└── 易于监控和调优（可以看每个队列的长度）
```

**协调者模式 (Mediator Pattern)**
```kotlin
// Manager负责组装和协调
class VoiceIntercomManager {
    fun start(config: VoiceIntercomConfig) {
        // 1. 创建策略
        val strategy = DeviceStrategyFactory.create(config.deviceType)
        
        // 2. 创建组件
        val source = AudioCapturerImpl()
        val encoder = strategy.createEncoder()
        val channel = TcpAudioChannel()
        val processor = AudioProcessorImpl()
        
        // 3. 组装依赖
        processor.init(source, encoder, channel, strategy)
        
        // 4. 启动流程
        channel.connect() → source.init() → processor.start()
    }
}

优势：
├── 各组件职责单一，易于测试
├── Manager负责编排，逻辑清晰
└── 组件间低耦合，易于替换
```

### 1.4 核心设计原则

#### SOLID原则的体现

**S - 单一职责原则 (Single Responsibility)**

```kotlin
✅ IAudioSource        → 只负责音频采集（AudioRecord封装）
✅ IEncoder           → 只负责编码（PCM → G.711）
✅ IAudioChannel      → 只负责网络传输（TCP Socket封装）
✅ IDeviceStrategy    → 只负责设备适配（握手协议）
✅ IAudioProcessor    → 只负责流水线协调（三线程管理）
✅ VoiceIntercomManager → 只负责组件组装（不实现具体功能）

// 每个类都有明确的职责，不越界
```

**O - 开闭原则 (Open-Closed)**

```kotlin
// ✅ 对扩展开放
class NewDeviceStrategy : IDeviceStrategy { 
    // 新增设备类型，无需修改现有代码
}

// ✅ 对修改关闭
// VoiceIntercomManager、AudioProcessorImpl 等核心类无需改动
// 只需在DeviceStrategyFactory中增加一个case

object DeviceStrategyFactory {
    fun createStrategy(deviceType: DeviceType): IDeviceStrategy {
        return when (deviceType) {
            DeviceType.WDZ_NVR -> WdzNvrStrategy()
            DeviceType.YUSHI -> YuShiStrategy()
            DeviceType.KEDA -> KedaStrategy()
            DeviceType.NEW_DEVICE -> NewDeviceStrategy()  // 只改这里
        }
    }
}
```

**L - 里氏替换原则 (Liskov Substitution)**

```kotlin
// 任何IDeviceStrategy的实现都可以替换使用
fun test(strategy: IDeviceStrategy) {
    strategy.configureChannel(channel, config, listener)
    val encoder = strategy.createEncoder()
    val rate = strategy.getSampleRate()
}

// 可以传入任何实现
test(YuShiStrategy())   // ✅ 工作正常
test(KedaStrategy())    // ✅ 工作正常
test(WdzNvrStrategy())  // ✅ 工作正常

// Manager的代码无需改变
```

**I - 接口隔离原则 (Interface Segregation)**
```kotlin
// ❌ 不好的设计：大而全的接口
interface IChannel {
    fun connect()
    fun disconnect()
    fun send()
    fun receive()
    fun setListener()
}
// 问题：使用者可能只需要send功能，却要实现全部方法

// ✅ 好的设计：职责分离
interface IConnectable {
    fun connect(host: String, port: Int, listener: OnConnectionListener?)
    fun disconnect()
    fun isConnected(): Boolean
}

interface ISendable {
    fun send(data: ByteArray)
    fun sendString(message: String)
}

interface IReceivable {
    fun setOnDataReceivedListener(listener: OnDataReceivedListener?)
}

// 组合接口
interface IAudioChannel : IConnectable, ISendable, IReceivable

// 组件只依赖需要的接口
class AudioSender(private val sendable: ISendable) {
    // 只需要发送功能，不关心连接和接收
}
```

**D - 依赖倒置原则 (Dependency Inversion)**
```kotlin
// ✅ 高层模块依赖抽象接口，不依赖具体实现
class VoiceIntercomManager {
    // 依赖抽象接口
    private var audioSource: IAudioSource?        // 接口
    private var encoder: IEncoder?                // 接口
    private var channel: IAudioChannel?           // 接口
    private var deviceStrategy: IDeviceStrategy?  // 接口
    
    fun start(config: VoiceIntercomConfig) {
        // 具体实现在运行时注入
        audioSource = AudioCapturerImpl()      // 具体类
        encoder = G711Encoder(Type.PCMA)       // 具体类
        channel = TcpAudioChannel()            // 具体类
        
        // 易于测试：可以注入Mock对象
        audioSource = MockAudioSource()  // 单元测试时
    }
}
```

#### 其他设计原则

**迪米特法则 (Law of Demeter)**
```kotlin
// ✅ 组件间不直接通信，通过Manager协调
class AudioProcessorImpl {
    private var audioSource: IAudioSource?
    private var encoder: IEncoder?
    private var channel: IAudioChannel?
    
    // ❌ 不会这样做
    // audioSource.getChannel().send(data)  // 跨层调用
    
    // ✅ 只和直接朋友通信
    val data = audioSource.read()
    val encoded = encoder.encode(data)
    channel.send(encoded)
}
```

**合成复用原则**
```kotlin
// ✅ 优先使用组合，而不是继承
class VoiceIntercomManager {
    // 组合各个组件
    private var audioSource: IAudioSource?
    private var encoder: IEncoder?
    private var channel: IAudioChannel?
    
    // 而不是
    // class VoiceIntercomManager : AudioSource, Encoder, Channel
}
```

### 2.3 数据流转路径

#### 完整数据流（采集 → 编码 → 发送）

```
┌─────────────────────────────────────────────────────────────┐
│  阶段1: 音频采集 (CaptureThread)                              │
└─────────────────────────────────────────────────────────────┘
    AudioRecord (Android系统)
         ↓ 每40ms产生640字节PCM数据
    AudioCapturerImpl.read(buffer: ByteBuffer)
         ↓ 阻塞读取，直到有数据
    ByteBuffer (从ByteBufferPool获取)
         ↓ 计算音量 (300ms更新一次)
    pcmQueue.offer(buffer)  ← 非阻塞，队列满则丢弃
         ↓
┌─────────────────────────────────────────────────────────────┐
│  Queue1: pcmQueue (容量20)                                   │
│  存储原始PCM数据，解耦采集和编码                              │
└─────────────────────────────────────────────────────────────┘
         ↓
┌─────────────────────────────────────────────────────────────┐
│  阶段2: 音频编码 (EncoderThread)                              │
└─────────────────────────────────────────────────────────────┘
    pcmQueue.poll(100ms)  ← 阻塞等待，超时返回null
         ↓ 有数据则继续
    ByteBuffer → ByteArray (转换)
         ↓ 640字节
    G711Encoder.encode(pcmData: ByteArray)
         ↓ 2:1压缩
    ByteArray (320字节，G.711数据)
         ↓ 回收ByteBuffer到池
    encodedQueue.offer(encodedData)  ← 非阻塞
         ↓
┌─────────────────────────────────────────────────────────────┐
│  Queue2: encodedQueue (容量20)                               │
│  存储编码后的数据，解耦编码和发送                             │
└─────────────────────────────────────────────────────────────┘
         ↓
┌─────────────────────────────────────────────────────────────┐
│  阶段3: 网络发送 (SenderThread)                               │
└─────────────────────────────────────────────────────────────┘
    encodedQueue.poll(100ms)  ← 阻塞等待
         ↓ 有数据则继续
    deviceStrategy.canSendAudio()  ← 检查是否可以发送
         ↓ true则发送，false则丢弃
    TcpAudioChannel.send(encodedData: ByteArray)
         ↓ 320字节
    SocketClient.send()
         ↓ 通过TCP发送到服务端
    [服务端摄像头] 播放音频
```

#### 关键设计点解析

**1. 为什么采集线程用非阻塞offer？**
```kotlin
// CaptureThread
val offered = pcmQueue.offer(buffer)  // 非阻塞
if (!offered) {
    Log.w(TAG, "PCM queue full, dropping frame")
    pool.release(buffer)  // 立即回收
}

理由：
✅ 采集不能被阻塞，否则AudioRecord内部缓冲区会溢出
✅ 队列满说明下游处理不过来，丢帧是合理的
✅ 音频对讲场景，丢几帧影响不大（人耳不敏感）
```

**2. 为什么编码/发送线程用阻塞poll？**
```kotlin
// EncoderThread / SenderThread
val data = queue.poll(100ms, TimeUnit.MILLISECONDS)  // 阻塞等待

理由：
✅ 编码和发送不是时间关键任务，等待是合理的
✅ 避免CPU空转（while循环检查队列）
✅ 100ms超时保证响应停止信号
```

**3. 队列容量为什么是20？**
```kotlin
val pcmQueue = LinkedBlockingQueue<ByteBuffer>(20)
val encodedQueue = LinkedBlockingQueue<ByteArray>(20)

计算：
- 每帧40ms
- 20帧 = 800ms的缓冲
- 足以应对短暂的处理抖动
- 不会占用过多内存（20 * 640B = 12.8KB）
```

#### start() 方法详细流程（10个步骤）

```kotlin
fun start(config: VoiceIntercomConfig) {
    // ====== 步骤1: 状态检查 ======
    if (isRunning) {
        Log.w(TAG, "Already running!")
        return
    }
    
    // ====== 步骤2: 启动性能监控 ======
    performanceMonitor.recordStart(NODE_TOTAL_START)
    
    // ====== 步骤3: 启动总体超时保护 ======
    timeoutManager.startTimeout(TOTAL_START_TIMEOUT_MS, "VoiceIntercomStart") {
        callback?.onError(Exception("Start timeout"))
        stop()
    }
    
    // ====== 步骤4: 创建设备策略 ======
    deviceStrategy = DeviceStrategyFactory.createStrategy(config.deviceType)
    // 根据deviceType创建对应的策略：YuShi/Keda/WdzNvr/Ezviz
    
    // ====== 步骤5: 创建核心组件 ======
    audioSource = AudioCapturerImpl()
    encoder = deviceStrategy?.createEncoder()  // 策略决定编码器类型
    channel = TcpAudioChannel()
    audioProcessor = AudioProcessorImpl()
    
    // ====== 步骤6: 配置AudioSource ======
    deviceStrategy?.configureAudioSource(audioSource)
    // 例如：宇视设置640字节，其他设备514字节
    
    // ====== 步骤7: 配置Channel ======
    val deviceConfig = DeviceConfig.fromVoiceIntercomConfig(config)
    channel?.configure(deviceConfig)
    
    // ====== 步骤8: 初始化AudioProcessor ======
    audioProcessor?.init(audioSource, encoder, channel, deviceStrategy)
    // 注入所有依赖
    
    // ====== 步骤9: 配置Channel连接（异步） ======
    deviceStrategy?.configureChannel(channel, deviceConfig, object : OnConnectionListener {
        override fun onConnected() {
            // 连接成功，进入步骤10
            onChannelConnected(config)
        }
        override fun onDisconnected() { ... }
        override fun onError(e: Exception) { ... }
    })
    // 策略内部会调用 channel.connect() 并设置握手逻辑
    
    // ====== 步骤10: 连接成功回调 ======
    // 见 onChannelConnected() 方法
}

private fun onChannelConnected(config: VoiceIntercomConfig) {
    // 防止重复调用
    if (isRunning) return
    
    // 取消总体超时
    timeoutManager.cancelTimeout()
    
    isRunning = true
    callback?.onConnected()  // 通知业务层
    
    // 初始化AudioRecord
    val sampleRate = deviceStrategy?.getSampleRate() ?: config.sampleRate
    val success = audioSource?.init(sampleRate)
    if (!success) {
        callback?.onError(Exception("AudioRecord init failed"))
        stop()
        return
    }
    
    // 启动流水线
    audioProcessor?.start()
    
    // 输出性能统计
    performanceMonitor.recordEnd(NODE_TOTAL_START)
    performanceMonitor.logStatistics()
}
```

#### stop() 方法流程

```kotlin
fun stop() {
    if (!isRunning) return
    
    isRunning = false
    
    // 步骤1: 停止音频处理器（会停止3个线程）
    audioProcessor?.stop()
    
    // 步骤2: 停止音频源
    audioSource?.stop()  // 释放AudioRecord
    
    // 步骤3: 断开通道
    channel?.disconnect()  // 关闭Socket
    
    // 步骤4: 清理资源
    cleanup()  // 将所有组件置为null
}
```

## Phase 3: 协调层 - VoiceIntercomManager

### 3.1 Manager的核心职责

#### VoiceIntercomManager 的定位

```kotlin
/**
 * VoiceIntercomManager - 纯协调者
 * 
 * 它就像一个"项目经理"：
 * - ✅ 知道需要哪些人（组件）
 * - ✅ 知道如何组建团队（依赖注入）
 * - ✅ 知道工作流程（启动步骤）
 * - ✅ 协调各方合作（回调转发）
 * 
 * 但它不做具体工作：
 * - ✗ 不采集音频
 * - ✗ 不编码数据
 * - ✗ 不发送网络包
 */
class VoiceIntercomManager private constructor(
    private val callback: VoiceIntercomCallback?
) {
    // 组件引用（全部是接口）
    private var audioSource: IAudioSource? = null
    private var encoder: IEncoder? = null
    private var channel: IAudioChannel? = null
    private var deviceStrategy: IDeviceStrategy? = null
    private var audioProcessor: IAudioProcessor? = null
    
    // 辅助工具
    private val mainHandler = Handler(Looper.getMainLooper())
    private val timeoutManager = TimeoutManager()
    private val performanceMonitor = PerformanceMonitor()
    
    // 状态标志
    @Volatile private var isRunning = false
}
```

#### 职责清单（5大职责）

| 职责 | 具体内容 | 代码体现 |
|------|---------|---------|
| **1. 组件创建** | 根据deviceType创建对应的策略和组件 | `DeviceStrategyFactory.createStrategy()`<br>`AudioCapturerImpl()`<br>`G711Encoder()`<br>`TcpAudioChannel()` |
| **2. 依赖注入** | 将组件注入到Processor | `processor.init(source, encoder, channel, strategy)` |
| **3. 流程编排** | 按正确顺序启动各组件 | 10步骤start()流程 |
| **4. 线程切换** | 回调切换到主线程，避免UI错误 | `mainHandler.post { callback?.onXxx() }` |
| **5. 资源管理** | 生命周期管理、超时保护、性能监控 | `timeoutManager`<br>`performanceMonitor`<br>`release()` |

### 3.2 start() 方法深度解析（10个步骤）

#### 完整代码注解版

```kotlin
fun start(config: VoiceIntercomConfig) {
    // ==================== 步骤1: 状态检查 ====================
    if (isRunning) {
        Log.w(TAG, "VoiceIntercom already running!")
        return
    }
    
    Log.d(TAG, "Starting voice intercom: deviceType=${config.deviceType}, host=${config.host}:${config.port}")
    
    // ==================== 步骤2: 启动性能监控 ====================
    performanceMonitor.recordStart(PerformanceMonitor.NODE_TOTAL_START)
    // 作用：记录总启动时间，用于性能分析
    
    // ==================== 步骤3: 启动总体超时保护 ====================
    timeoutManager.startTimeout(AudioConfig.TOTAL_START_TIMEOUT_MS, "VoiceIntercomStart") {
        // 20秒后仍未启动成功，强制失败
        Log.e(TAG, "Voice intercom start timeout after ${AudioConfig.TOTAL_START_TIMEOUT_MS}ms")
        mainHandler.post {
            callback?.onError(Exception("Start timeout"))
        }
        stop()
    }
    // 为什么需要？防止某个环节卡住导致永久等待
    
    try {
        // ==================== 步骤4: 创建设备策略 ====================
        deviceStrategy = DeviceStrategyFactory.createStrategy(config.deviceType)
        Log.d(TAG, "Device strategy created: ${deviceStrategy?.javaClass?.simpleName}")
        
        // 工厂根据deviceType返回对应的策略：
        // - DeviceType.YUSHI → YuShiStrategy()
        // - DeviceType.KEDA → KedaStrategy()
        // - DeviceType.WDZ_NVR → WdzNvrStrategy()
        // - DeviceType.EZVIZ → EzvizStrategy()
        
        // ==================== 步骤5: 创建核心组件 ====================
        audioSource = AudioCapturerImpl()
        encoder = deviceStrategy?.createEncoder()  // 策略决定编码器
        channel = TcpAudioChannel()
        audioProcessor = AudioProcessorImpl()
        
        Log.d(TAG, "Core components created: source=${audioSource}, encoder=${encoder}, channel=${channel}")
        
        // ==================== 步骤6: 配置AudioSource ====================
        deviceStrategy?.configureAudioSource(audioSource)
        // 策略会设置buffer大小：
        // - 宇视：640字节（固定）
        // - 其他：514字节（标准）
        
        // ==================== 步骤7: 配置Channel ====================
        val deviceConfig = DeviceConfig.fromVoiceIntercomConfig(config)
        channel?.configure(deviceConfig)
        // 设置host、port、timeout等参数
        
        // ==================== 步骤8: 初始化AudioProcessor ====================
        val source = requireNotNull(audioSource) { "AudioSource not created" }
        val enc = requireNotNull(encoder) { "Encoder not created" }
        val chan = requireNotNull(channel) { "Channel not created" }
        val strategy = requireNotNull(deviceStrategy) { "DeviceStrategy not created" }
        val processor = requireNotNull(audioProcessor) { "AudioProcessor not created" }
        
        processor.init(source, enc, chan, strategy)
        // 注入所有依赖，但不启动
        
        // 设置Processor监听器
        processor.setProcessorListener(object : IAudioProcessor.OnProcessorListener {
            override fun onError(e: Exception) {
                Log.e(TAG, "Processor error", e)
                mainHandler.post {
                    callback?.onError(e)
                }
            }
            
            override fun onVolumeChanged(volume: Int) {
                mainHandler.post {
                    callback?.onAudioVolume(volume)
                }
            }
        })
        
        // ==================== 步骤9: 配置Channel连接（关键！） ====================
        // 这是异步操作，需要等待连接成功
        
        // 针对宇视设备：需要将握手消息回传给VideoActivity
        (strategy as? YuShiStrategy)?.setMessageListener { message ->
            mainHandler.post {
                callback?.onResponse(message)
            }
        }
        
        // 开始连接监控
        performanceMonitor.recordStart(PerformanceMonitor.NODE_CONNECTION)
        
        // 策略会调用 channel.connect() 并设置握手逻辑
        strategy.configureChannel(chan, deviceConfig, object : IConnectable.OnConnectionListener {
            override fun onConnected() {
                // 连接成功！进入步骤10
                performanceMonitor.recordEnd(PerformanceMonitor.NODE_CONNECTION)
                
                // 策略连接成功，启动音频采集和处理
                onChannelConnected(config)
            }
            
            override fun onDisconnected() {
                isRunning = false
                mainHandler.post {
                    callback?.onDisconnected()
                }
            }
            
            override fun onError(e: Exception) {
                Log.e(TAG, "Channel error", e)
                mainHandler.post {
                    callback?.onError(e)
                }
                cleanup()
            }
        })
        
        // ==================== 步骤10: 等待异步连接 ====================
        // 此时start()方法返回，等待onChannelConnected()回调
        
    } catch (e: Exception) {
        Log.e(TAG, "Failed to start voice intercom", e)
        mainHandler.post {
            callback?.onError(e)
        }
        cleanup()
    }
}
```

#### 步骤10：onChannelConnected() 详解

```kotlin
/**
 * 连接成功回调 - 启动音频流水线
 * 
 * 为什么单独拆出这个方法？
 * 1. start()是同步方法，连接是异步的
 * 2. 宇视设备需要握手，连接成功≠可以发送音频
 * 3. 逻辑清晰，易于测试
 */
private fun onChannelConnected(config: VoiceIntercomConfig) {
    // 防止重复调用（宇视设备可能触发两次）
    if (isRunning) {
        Log.w(TAG, "Already running, ignore duplicate connection callback")
        return
    }
    
    Log.d(TAG, "Channel connected successfully")
    
    // 取消总体超时（连接成功）
    timeoutManager.cancelTimeout()
    
    isRunning = true
    
    // 通知业务层：连接成功
    mainHandler.post {
        callback?.onConnected()
    }
    
    // ==================== 初始化AudioRecord ====================
    // 为什么在这里初始化？
    // 1. AudioRecord初始化耗时（可能200-500ms）
    // 2. 等连接成功后再初始化，避免浪费资源
    // 3. 如果连接失败，不会占用麦克风
    
    val sampleRate = deviceStrategy?.getSampleRate() ?: config.sampleRate
    Log.d(TAG, "Initializing audio source: sampleRate=$sampleRate Hz")
    
    // 监控AudioRecord初始化耗时
    performanceMonitor.recordStart(PerformanceMonitor.NODE_AUDIO_INIT)
    val success = audioSource?.init(sampleRate)
    performanceMonitor.recordEnd(PerformanceMonitor.NODE_AUDIO_INIT)
    
    if (!success) {
        Log.e(TAG, "Failed to initialize audio source")
        mainHandler.post {
            callback?.onError(Exception("Failed to initialize audio source"))
        }
        stop()
        return
    }
    
    // ==================== 启动Processor流水线 ====================
    Log.d(TAG, "Starting audio processor...")
    performanceMonitor.recordStart(PerformanceMonitor.NODE_PROCESSOR_START)
    audioProcessor?.start()
    performanceMonitor.recordEnd(PerformanceMonitor.NODE_PROCESSOR_START)
    
    // ==================== 完成总体启动 ====================
    performanceMonitor.recordEnd(PerformanceMonitor.NODE_TOTAL_START)
    
    // 输出性能统计
    performanceMonitor.logStatistics()
    
    Log.d(TAG, "Voice intercom fully started!")
}
```

#### 关键设计点解析

**1. 为什么start()不直接初始化AudioRecord？**

```kotlin
// ❌ 不好的做法
fun start(config) {
    audioSource.init(8000)  // 先初始化
    channel.connect()       // 再连接
}

问题：
├── AudioRecord初始化需要200-500ms
├── 如果连接失败，白白占用麦克风
└── 资源浪费

// ✅ 好的做法
fun start(config) {
    channel.connect()  // 先连接
}
private fun onChannelConnected() {
    audioSource.init(8000)  // 连接成功后再初始化
}

优势：
├── 连接失败不占用麦克风
├── 并行操作，总耗时更短
└── 资源利用更合理
```

**2. 为什么需要防重复调用？**

```kotlin
private fun onChannelConnected(config: VoiceIntercomConfig) {
    if (isRunning) {
        Log.w(TAG, "Already running, ignore duplicate connection callback")
        return
    }
    // ...
}

原因：
宇视设备握手流程可能触发两次连接回调：
1. TCP连接成功
2. BridgeReady消息到达

防重复可以避免：
├── AudioRecord重复初始化（报错）
├── Processor重复启动（资源泄漏）
└── 回调多次触发（UI错乱）
```

**3. 为什么用主线程Handler？**
```kotlin
mainHandler.post {
    callback?.onConnected()
}

原因：
├── callback可能会更新UI（显示"已连接"）
├── Android规定只能在主线程更新UI
├── 连接回调可能在Socket的IO线程
└── 必须切换到主线程

如果不切换：
└── CalledFromWrongThreadException: Only the original thread that created a view hierarchy can touch its views.
```

```kotlin
class VoiceIntercomManager {
    // 主线程Handler
    private val mainHandler = Handler(Looper.getMainLooper())
    
    // 所有回调都切换到主线程
    private fun onChannelConnected(config: VoiceIntercomConfig) {
        // 当前可能在Socket线程
        
        mainHandler.post {
            // 切换到主线程
            callback?.onConnected()
        }
    }
    
    // Processor错误回调
    processor.setProcessorListener(object : IAudioProcessor.OnProcessorListener {
        override fun onError(e: Exception) {
            // 当前可能在编码线程或发送线程
            
            mainHandler.post {
                // 切换到主线程
                callback?.onError(e)
            }
        }
        
        override fun onVolumeChanged(volume: Int) {
            // 当前在采集线程
            
            mainHandler.post {
                // 切换到主线程
                callback?.onAudioVolume(volume)
            }
        }
    })
}
```

### 3.5 重启机制 restart()

#### restart()的实现

```kotlin
/**
 * 重启语音对讲
 * 
 * 使用场景：
 * 1. 切换设备类型（宇视 → 科达）
 * 2. 切换设备地址（192.168.1.100 → 192.168.1.101）
 * 3. 网络异常重连
 * 
 * @param config 新的对讲配置
 */
fun restart(config: VoiceIntercomConfig) {
    Log.d(TAG, "Restarting voice intercom...")
    
    // 如果正在运行，先停止
    if (isRunning) {
        stop()
    }
    
    // 启动新的连接
    start(config)
}
```

#### 为什么不复用组件？

```kotlin
// ❌ 方案1: 复用组件（看似高效）
fun restart(config: VoiceIntercomConfig) {
    // 只重置连接，复用其他组件
    channel?.disconnect()
    channel?.connect(config.host, config.port)
}

问题：
├── 策略可能变化（宇视 → 科达）
├── AudioSource配置可能不同（640 → 514）
├── Encoder类型可能不同（PCMA → PCMU）
├── 状态难以保证干净
└── 容易出现诡异的bug

// ✅ 方案2: 完全重建（简单可靠）
fun restart(config: VoiceIntercomConfig) {
    stop()   // 完全清理
    start(config)  // 重新创建
}

优势：
├── 逻辑简单，易于理解
├── 状态干净，无残留
├── 代码复用（调用现有方法）
├── 不易出bug
└── 性能损失可忽略（几百毫秒，用户无感知）

性能分析：
├── stop()耗时：50-100ms（停止线程、释放资源）
├── start()耗时：200-500ms（创建组件、连接、初始化）
└── 总耗时：250-600ms（可接受，用户感知为"重连中"）
```

### 面试要点总结

#### Manager的核心价值

| 方面 | 价值 |
|------|------|
| **解耦** | 业务层不知道AudioSource、Encoder等细节 |
| **封装** | 复杂的启动流程封装成一个start()调用 |
| **灵活** | 通过策略模式支持多种设备，易扩展 |
| **安全** | 线程切换、超时保护、资源管理都由Manager负责 |
| **可测** | 依赖注入，易于Mock测试 |

#### 面试可能的问题

**Q1: 为什么不把所有逻辑都写在Manager里？**
```
A: 违反单一职责原则。
   Manager是协调者，不应该实现具体功能。
   类似于"项目经理不应该亲自写代码"。
```

**Q2: 为什么用接口而不是具体类？**
```
A: 依赖倒置原则。
   高层模块（Manager）不应依赖低层模块（具体实现）。
   易于测试（可以Mock）、易于替换（实现新的AudioSource）。
```

**Q3: start()方法为什么分10个步骤？**
```
A: 职责分离、依赖顺序、异步处理。
   1. 策略必须先创建（决定其他组件配置）
   2. 组件必须先创建再配置
   3. 连接是异步的，需要回调
   4. AudioRecord初始化慢，放在连接成功后
```

**Q4: 为什么回调要切换到主线程？**
```
A: Android UI线程模型。
   业务层可能更新UI，必须在主线程。
   不切换会抛CalledFromWrongThreadException。
```

**Q5: restart()为什么不复用组件？**
```
A: 简单可靠 > 性能优化。
   1. 设备类型可能变化，组件配置不同
   2. 完全重建保证状态干净
   3. 性能损失可忽略（几百毫秒）
   4. 代码复用，不易出bug
```

## Phase 4: 策略层 - 设备适配策略

### 4.1 策略接口设计 IDeviceStrategy

#### 接口定义与职责

```kotlin
/**
 * 设备策略接口 - 设备特定的适配逻辑
 * 
 * 职责：
 * 1. 配置AudioSource（如宇视需要640字节buffer）
 * 2. 创建Encoder（返回对应的编码器实例）
 * 3. 配置Channel握手（设备特有的连接协议）
 * 4. 提供采样率（不同设备可能不同）
 * 5. 控制发送时机（如宇视需要等握手完成）
 */
interface IDeviceStrategy {
    
    /**
     * 配置音频源
     * 
     * @param audioSource 音频源实例
     * 
     * 作用：设置设备特定的配置
     * - 宇视：640字节（固定，协议要求）
     * - 其他：514字节（标准大小）
     */
    fun configureAudioSource(audioSource: IAudioSource?)
    
    /**
     * 创建编码器
     * 
     * @return 编码器实例
     * 
     * 作用：根据设备支持的编码格式创建对应编码器
     * - 大部分设备：PCMA (A-law)
     * - 少数设备：PCMU (μ-law)
     */
    fun createEncoder(): IEncoder?
    
    /**
     * 配置通道（最核心的方法）
     * 
     * @param channel 音频通道实例
     * @param config 设备配置
     * @param connectionListener 连接监听器
     * 
     * 作用：设置设备特有的连接流程
     * - 宇视：复杂的4步握手协议
     * - 科达：发送协议头
     * - 自研NVR：发送HTTP header
     * 
     * 注意：策略负责调用 channel.connect() 并设置握手逻辑
     */
    fun configureChannel(
        channel: IAudioChannel?, 
        config: DeviceConfig?,
        connectionListener: IConnectable.OnConnectionListener?
    )
    
    /**
     * 获取采样率
     * 
     * @return 采样率（Hz）
     * 
     * 作用：提供设备支持的采样率
     * - 大部分设备：8000Hz（电话音质）
     * - 高清设备：16000Hz（预留，暂未使用）
     */
    fun getSampleRate(): Int
    
    /**
     * 是否可以发送音频
     * 
     * @return true 可以发送，false 需要等待
     * 
     * 作用：控制发送时机
     * - 大部分设备：连接成功即可发送，返回 true
     * - 宇视设备：需要等握手完成（BridgeReady），初始返回 false
     * 
     * 默认实现：返回 true（大部分设备适用）
     */
    fun canSendAudio(): Boolean = true
}
```

#### 接口方法设计的权衡

| 方法 | 为什么这样设计？ | 如果不这样设计会怎样？ |
|------|----------------|---------------------|
| **configureAudioSource** | 允许策略定制buffer大小 | ❌ 宇视设备640字节的需求无法满足 |
| **createEncoder** | 策略决定编码器类型 | ❌ 如果设备需要不同编码格式，无法扩展 |
| **configureChannel** | 策略完全控制握手流程 | ❌ 宇视的复杂握手无法实现 |
| **getSampleRate** | 策略提供采样率 | ❌ 如果设备需要不同采样率，写死会出问题 |
| **canSendAudio** | 策略控制发送时机 | ❌ 宇视设备会在握手前就发送数据，导致失败 |

## Phase 5: 核心组件层

### 5.1 三线程流水线的设计思路

#### 问题：为什么必须是三线程？

**如果用单线程：**

```
[采集 → 编码 → 发送] 串行执行
问题：每个环节都阻塞，总延迟 = 40ms(采集) + 5ms(编码) + 20ms(网络) = 65ms
结果：AudioRecord内部buffer会溢出，丢帧严重
```

**如果用双线程（采集+编码合并）：**
```
[Thread1: 采集→编码] → [Thread2: 发送]
问题：编码5ms会延迟下一次采集，40ms节奏被打乱
结果：仍然会丢帧
```

**三线程流水线：**
```
[Thread1: 采集40ms] → Queue1 → [Thread2: 编码5ms] → Queue2 → [Thread3: 发送20ms]
优势：每个线程独立运行，队列解耦，可以并行处理
```

**本质：将阻塞操作解耦，用队列缓冲，实现流水线并行**

---

### 5.2 队列选型的精髓（核心！）

#### 5.2.1 为什么用 LinkedBlockingQueue 而不是 ArrayBlockingQueue？

**关键差异对比：**

| 特性 | ArrayBlockingQueue | LinkedBlockingQueue |
|------|-------------------|---------------------|
| **底层结构** | 数组 | 链表 |
| **锁机制** | **单把锁**（putLock == takeLock） | **两把锁**（putLock ≠ takeLock） |
| **并发性** | put和take**互斥** | put和take**可以并发** |
| **内存** | 预分配数组 | 按需分配节点 |

**为什么两把锁至关重要？**

在我们的三线程流水线中：
```
CaptureThread → [pcmQueue.put()] ← [pcmQueue.take()] ← EncoderThread
                                          ↓
                                   [encodedQueue.put()]
                                          ↓
SenderThread ← [encodedQueue.take()]
```

**如果用 ArrayBlockingQueue（单把锁）：**
- `pcmQueue`的put（采集）和take（编码）**互斥**，吞吐量减半
- `encodedQueue`同理

**LinkedBlockingQueue（两把锁）：**
- CaptureThread的put和EncoderThread的take**可以并发**
- **吞吐量提升50%+**

**这就是为什么必须用 LinkedBlockingQueue 的核心原因！**

---

#### 5.2.2 为什么容量都是 20？

**计算过程：**
```
采样率：8000Hz
位深：16bit = 2字节
声道：单声道
帧大小：640字节
帧时长：640 / (8000 * 2) = 0.04秒 = 40ms

队列容量 20 = 20帧 = 800ms缓冲
```

**为什么是 800ms？**

| 容量 | 缓冲时长 | 优点 | 缺点 |
|------|---------|------|------|
| 5帧 | 200ms | 延迟低 | ❌ 网络抖动易丢帧 |
| 20帧 | 800ms | ✅ 足够缓冲网络抖动 | 可接受的延迟 |
| 50帧 | 2000ms | 极高容错 | ❌ 延迟太大，不适合实时对讲 |

**设计权衡：**

- **实时性要求**：对讲延迟最好 < 1秒
- **网络容错**：需要缓冲短暂的网络抖动（200-500ms）
- **最终选择**：800ms = 实时性和容错性的平衡点

---

#### 5.2.3 为什么采集用 offer，编码/发送用 poll？（核心！）

**CaptureThread：必须用 offer（非阻塞）**

```kotlin
val offered = pcmQueue.offer(buffer)  // 非阻塞
if (!offered) {
    // 队列满，主动丢弃最新帧
    bufferPool.release(buffer)
}
```

**为什么不能用 put（阻塞）？**

```
AudioRecord的工作机制：
- 硬件驱动每40ms填充一次内部buffer
- 如果应用不及时read()，内部buffer会溢出
- 溢出后，数据永久丢失

如果用put阻塞：
1. 队列满，CaptureThread阻塞在put()
2. 阻塞期间，AudioRecord内部buffer继续填充
3. 40ms, 80ms, 120ms... 内部buffer溢出
4. 一旦溢出，丢失的不是1帧，而是N帧！

如果用offer非阻塞：
1. 队列满，立即返回false
2. 主动丢弃当前帧（1帧）
3. CaptureThread继续下一次read()
4. AudioRecord内部buffer不溢出
5. 只丢1帧，损失最小
```

**设计哲学：主动可控的丢帧 > 被动不可控的溢出**

---

**EncoderThread/SenderThread：用 poll（阻塞）**

```kotlin
val buffer = pcmQueue.poll(100, TimeUnit.MILLISECONDS)  // 阻塞等待
```

**为什么不用 take（无限阻塞）？**

```
take()问题：
- 无限阻塞，无法响应stop信号
- 停止时需要interrupt线程（不优雅）

poll(timeout)优势：
1. 阻塞100ms，如果有数据立即返回
2. 如果超时，检查shouldStop标志
3. 可以优雅退出
4. 100ms足够短，不影响响应性
```

---

### 5.3 ByteBufferPool 对象池的精髓（核心！）

#### 5.3.1 为什么懒加载而不是预分配？

**错误的理解（预分配）：**
```kotlin
// ❌ 不是这样的：
init {
    repeat(10) { pool.offer(ByteBuffer.allocate(640)) }
}
```

**实际的实现（懒加载）：**

```kotlin
fun acquire(): ByteBuffer {
    val buffer = pool.poll()  // 尝试从池中取
    return if (buffer != null) {
        buffer.clear()  // 复用
        buffer
    } else {
        createCount++  // 池为空才创建
        ByteBuffer.allocate(bufferSize)
    }
}
```

**为什么懒加载更聪明？**

| 对比 | 预分配10个 | 懒加载 |
|------|-----------|--------|
| **启动速度** | 慢（立即分配6.4KB） | 快（按需分配） |
| **内存效率** | 浪费（实际只需3个） | 高效（只创建需要的） |
| **扩展性** | 差（固定10个） | 好（自动扩展到maxPoolSize） |
| **适应性** | 差（无法感知实际并发） | 强（根据实际负载调整） |

**真实场景分析：**
```
启动阶段（前200ms）：
- CaptureThread还没开始采集
- 池为空，无需预分配
- 节省内存，启动更快

稳定运行阶段（200ms后）：
- 3个线程并发：
  * CaptureThread持有1个buffer（正在read）
  * EncoderThread持有1个buffer（正在encode）
  * 队列中2-3个buffer
- 总共需要4-5个buffer

高峰阶段（网络卡顿）：
- 队列堆积，可能需要8-10个buffer
- 懒加载会自动创建到这个数量

恢复阶段：
- 网络恢复，队列清空
- 多余的buffer回到池中
- 复用率提高，不再创建新对象
```

**设计哲学：按需分配 > 提前猜测**

---

#### 5.3.2 为什么用 ConcurrentLinkedQueue 而不是 LinkedBlockingQueue？

**关键差异：**

| 队列类型 | acquire操作 | release操作 |
|---------|-----------|------------|
| **LinkedBlockingQueue** | poll可能阻塞 | put可能阻塞 |
| **ConcurrentLinkedQueue** | poll立即返回 | offer立即返回 |

**为什么对象池必须非阻塞？**

```kotlin
// CaptureThread中：
val buffer = bufferPool.acquire()  // 必须立即返回！
val bytesRead = audioSource.read(buffer)
```

**如果 acquire 阻塞会怎样？**
```
1. bufferPool为空（所有buffer都在队列中）
2. acquire阻塞等待
3. CaptureThread卡住，无法read AudioRecord
4. AudioRecord内部buffer溢出
5. 灾难！
```

**非阻塞的正确行为：**
```
1. bufferPool为空
2. acquire立即创建新buffer返回
3. CaptureThread继续read
4. 稳定运行
```

**这就是为什么必须用 ConcurrentLinkedQueue 的原因！**

---

#### 5.3.3 为什么 useDirect = false？

**DirectBuffer 的特性：**
- 堆外内存（Native Memory）
- 不受 JVM GC 管理
- 分配/释放比堆内慢
- 适合 JNI 调用（避免拷贝）

**我们的场景分析：**

```kotlin
// AudioRecord.read()的两个版本：
audioRecord.read(byteArray, ...)      // 需要从native拷贝到Java堆
audioRecord.read(byteBuffer, ...)     // 如果是DirectBuffer，零拷贝
```

**理论上 DirectBuffer 更好？**
- 是的，零拷贝更快

**但为什么默认 useDirect = false？**

**原因 1：对象池已经解决了 GC 问题**
```
没有对象池：
- 每40ms new byte[640]
- 每秒25个对象
- GC压力大 → DirectBuffer有意义

有对象池：
- Buffer长期存活，不会被GC
- GC压力已经很小
- DirectBuffer的优势不明显
```

**原因 2：DirectBuffer 的隐藏成本**
```
DirectBuffer的分配：
- 调用native方法malloc
- 需要系统调用
- 比堆内慢10-20倍

我们的场景：
- 懒加载，按需创建
- 启动阶段会创建4-5个buffer
- DirectBuffer会拖慢启动速度
```

**原因 3：简单性**
```
堆内Buffer：
- Java对象，GC自动回收
- 不会内存泄漏

DirectBuffer：
- 需要手动释放（虽然有Cleaner）
- 可能泄漏Native Memory
- 更复杂
```

**设计决策：**
```
useDirect = false（默认）：
- 简单、快速、安全
- 对象池已经优化了GC
- 适合大部分场景

useDirect = true（可选）：
- 如果性能测试发现read()是瓶颈
- 可以开启DirectBuffer优化
- 提供灵活性
```

---

#### 5.3.4 命中率统计的意义（性能调优关键！）

```kotlin
fun getStats(): Stats {
    return Stats(
        hitRate = ((acquireCount - createCount) * 100.0 / acquireCount)
    )
}
```

**命中率的含义：**
```
hitRate = 95%：
- 100次acquire，95次从池中获取，5次新创建
- 说明池大小合适
- 优化效果好

hitRate = 60%：
- 100次acquire，60次从池中获取，40次新创建
- 说明池太小，频繁创建新对象
- 应该增加maxPoolSize
```

**真实调优案例：**
```
初始配置：maxPoolSize = 5
运行1分钟后：hitRate = 65%
分析：池太小，网络抖动时不够用

调整配置：maxPoolSize = 10
```

### 5.4 AudioProcessorImpl 完整实现解析

#### 5.4.1 三线程的启动顺序

```kotlin
override fun start() {
    // 1. 清空队列（确保干净状态）
    pcmQueue.clear()
    encodedQueue.clear()
    
    // 2. 重置状态标志
    shouldStop = false
    isProcessing = true
    
    // 3. 按顺序启动线程
    startCaptureThread()   // 生产者
    startEncoderThread()   // 消费者+生产者
    startSenderThread()    // 消费者
}
```

**为什么这个顺序？**
- 先启动CaptureThread：开始采集数据
- 再启动EncoderThread：准备好消费
- 最后启动SenderThread：准备好发送
- 即使顺序反了也不会出错（队列是空的），但这个顺序更合理

---

#### 5.4.2 三线程的停止策略

```kotlin
override fun stop() {
    // 1. 设置停止标志（告诉线程该停了）
    shouldStop = true
    
    // 2. 中断线程（唤醒阻塞的poll）
    captureThread?.interrupt()
    encoderThread?.interrupt()
    senderThread?.interrupt()
    
    // 3. 等待线程结束（最多1秒）
    captureThread?.join(1000)
    encoderThread?.join(1000)
    senderThread?.join(1000)
    
    // 4. 清理资源
    pcmQueue.clear()
    encodedQueue.clear()
    bufferPool.clear()
}
```

**为什么需要 interrupt + join？**

```
只用shouldStop：
- 如果线程阻塞在poll(100ms)
- 需要等100ms才能检查shouldStop
- 停止不及时

interrupt + shouldStop：
- interrupt立即唤醒poll
- 线程检查shouldStop或InterruptedException
- 立即退出循环
- 停止及时
```

### 6.2 超时管理 TimeoutManager

#### 6.2.1 为什么需要超时管理？

**异步操作的困境：**
```
宇视设备握手流程：
1. 发送RequireSession
2. 等待SessionAck
3. 等待BridgeReady

问题：如果服务器不回复SessionAck怎么办？
- 没有超时：永远等待，用户卡死
- 有超时：15秒后自动失败，用户体验好
```

#### 6.2.2 设计思路：基于 Handler 的延迟任务

**核心实现：**
```kotlin
class TimeoutManager(private val handler: Handler) {
    
    fun scheduleTimeout(timeoutMs: Long, onTimeout: () -> Unit): TimeoutTask {
        val task = TimeoutTask(onTimeout)
        handler.postDelayed(task, timeoutMs)
        return task
    }
    
    class TimeoutTask(private val callback: () -> Unit) : Runnable {
        @Volatile
        private var isCancelled = false
        
        override fun run() {
            if (!isCancelled) {
                callback()
            }
        }
        
        fun cancel() {
            isCancelled = true
        }
    }
}
```

**使用示例：**
```kotlin
// YuShiStrategy握手超时
val timeoutTask = timeoutManager.scheduleTimeout(15000) {
    Log.e(TAG, "Handshake timeout!")
    listener.onError("握手超时")
}

// 收到BridgeReady后取消超时
onReceiveBridgeReady {
    timeoutTask.cancel()
}
```

#### 6.2.3 为什么用 Handler 而不是 Timer？

| 对比 | Timer | Handler |
|------|-------|---------|
| **线程** | 独立线程 | 复用Looper线程 |
| **回调线程** | Timer线程（后台） | 主线程（需要） |
| **取消机制** | timer.cancel() | removeCallbacks() |
| **内存泄漏风险** | 高（静态引用） | 低（生命周期管理） |

**我们的场景：**
- 超时回调需要在主线程（更新UI）
- Handler天然在主线程
- 不需要额外的线程切换

### 6.3 加密工具 EncryptionHelper

#### 6.3.1 宇视握手的加密需求

**协议要求：**
```json
// 服务器发送
{ "pt": "ReleaseRandomKey", "random": "abc123xyz" }

// 客户端需要：
1. 用streamKey加密random
2. 加密算法：XOR + 字符过滤
3. 发送加密结果
{ "pt": "RequireSession", "key": "encrypted_result" }
```

#### 6.3.2 XOR加密算法实现

```kotlin
object EncryptionHelper {
    
    /**
     * XOR加密
     * @param data 要加密的数据（random）
     * @param key 密钥（streamKey）
     * @return 加密结果（过滤后的字符串）
     */
    fun xorEncrypt(data: String, key: String): String {
        if (data.isEmpty() || key.isEmpty()) return ""
        
        val result = StringBuilder()
        var keyIndex = 0
        
        for (i in data.indices) {
            val dataChar = data[i].code
            val keyChar = key[keyIndex % key.length].code
            val encrypted = dataChar xor keyChar
            
            // 只保留有效字符（32-126: 可打印ASCII）
            if (encrypted in 32..126) {
                result.append(encrypted.toChar())
            }
            
            keyIndex++
        }
        
        return result.toString()
    }
}
```

**为什么要过滤字符？**
```
XOR结果可能是任意字节：
- 0x00（null）：JSON会截断
- 0x0A（换行）：协议解析出错
- 0x7F以上：非ASCII，传输可能乱码

只保留可打印ASCII（32-126）：
- 安全传输
- 协议兼容
- 不影响加密效果（随机性仍然够用）
```

```
  因为前者是双锁，put和take可以并发，吞吐量提升50%
- 采集用offer（非阻塞），防止队列满时阻塞导致AudioRecord溢出
- 编码/发送用poll（阻塞），提升响应性"
```

**亮点3：对象池优化GC（30秒）**
```
"音频采集每40ms产生一个640字节的buffer，
每秒25个对象，GC压力大。

我实现了ByteBufferPool：
- 懒加载，按需创建（不预分配）
- 用ConcurrentLinkedQueue保证非阻塞
- 统计命中率，数据驱动优化

最终GC从25次/秒降到2次/秒，降低90%。"
```

### 7.2 深挖问题：面试官常问的10个问题

#### Q1: 为什么用LinkedBlockingQueue而不是ArrayBlockingQueue？

**标准答案：**
```
核心差异是锁机制：
- ArrayBlockingQueue：单把锁，put和take互斥
- LinkedBlockingQueue：双锁，put和take可以并发

我们的场景：
- CaptureThread在put
- EncoderThread在take
- 如果用ArrayBlockingQueue，这两个操作互斥，吞吐量减半
- LinkedBlockingQueue允许并发，吞吐量提升50%+

这是我选择LinkedBlockingQueue的核心原因。
```

---

#### Q2: 为什么采集线程用offer而不是put？

**标准答案：**
```
这是为了防止AudioRecord溢出：

AudioRecord的工作机制：
- 硬件每40ms填充一次内部buffer
- 如果应用不及时read()，内部buffer会溢出
- 溢出后数据永久丢失

如果用put（阻塞）：
- 队列满时，CaptureThread阻塞
- 阻塞期间，AudioRecord继续填充
- 最终溢出，丢失N帧

如果用offer（非阻塞）：
- 队列满时，主动丢弃当前帧（1帧）
- CaptureThread继续read下一帧
- 损失可控

这是"主动可控的丢帧"优于"被动不可控的溢出"的设计哲学。
```

---

#### Q3: 对象池为什么懒加载而不是预分配？

**标准答案：**
```
懒加载的优势：
1. 启动快：不需要立即分配6.4KB内存
2. 自适应：根据实际负载动态创建
3. 节省内存：实际只需要4-5个buffer

预分配的问题：
1. 启动慢：立即分配10个buffer
2. 浪费：可能实际只需要3个
3. 不灵活：无法应对高峰场景

我用命中率统计来验证池大小是否合适：
- hitRate > 90%：说明池大小合适
- hitRate < 80%：说明池太小，需要增大

这是数据驱动的优化思路。
```

---

#### Q4: 为什么用ConcurrentLinkedQueue而不是LinkedBlockingQueue作为对象池？

**标准答案：**
```
关键是对象池必须非阻塞：

CaptureThread中：
  val buffer = bufferPool.acquire()
  audioSource.read(buffer)

如果bufferPool用LinkedBlockingQueue：
- 池为空时，acquire会阻塞
- CaptureThread卡住，无法read AudioRecord
- AudioRecord溢出

如果用ConcurrentLinkedQueue（非阻塞）：
- 池为空时，acquire立即创建新buffer返回
- CaptureThread继续运行
- 系统稳定

这是实时系统的核心要求：永远不能阻塞关键路径。
```

#### Q5: 策略模式的扩展性体现在哪里？

**标准答案：**
```
新增设备只需3步：

1. 添加枚举：DeviceType.NEW_DEVICE
2. 实现接口：class NewDeviceStrategy : IDeviceStrategy
3. 注册工厂：DeviceStrategyFactory.createStrategy()

核心组件（Manager、Processor、Channel）无需修改，
这就是开闭原则（对扩展开放，对修改关闭）。

实际案例：

- 每次都不影响现有代码
```

#### Q6: 三线程如何优雅退出？

**标准答案：**
```
采用双重机制：

1. shouldStop标志：
   - 线程循环中检查：while (!shouldStop)
   - stop()时设置为true

2. interrupt唤醒：
   - 线程可能阻塞在poll(100ms)
   - interrupt立即唤醒
   - 检查shouldStop或InterruptedException

3. join等待：
   - 最多等1秒
   - 防止主线程继续执行时线程还没停

这样能保证：
- 快速响应（不用等100ms超时）
- 优雅退出（资源正确释放）
- 无僵尸线程
```

#### Q7: 宇视握手超时怎么处理？

**标准答案：**
```
用TimeoutManager实现：

1. 发送RequireSession后启动15秒超时：
   val task = timeoutManager.schedule(15000) {
       listener.onError("握手超时")
   }

2. 收到BridgeReady后取消：
   task.cancel()

3. 为什么用Handler而非Timer？
   - Handler回调在主线程，可以直接更新UI
   - Timer回调在后台线程，需要切换线程
   - Handler生命周期管理更方便

这确保了永远不会无限等待，用户体验好。
```

#### Q8: 如何保证线程安全？

**标准答案：**
```
多个维度保证：

1. 队列（天然线程安全）：
   - LinkedBlockingQueue内部用锁保护
   - ByteBufferPool用ConcurrentLinkedQueue

2. 状态标志（Volatile）：
   - shouldStop: @Volatile
   - isProcessing: @Volatile
   - 保证可见性

3. 回调线程切换：
   - 所有业务回调都post到主线程
   - 避免CalledFromWrongThreadException

4. 对象池命中率统计（AtomicLong）：
   - acquireCount、createCount用原子类
   - 无锁，性能好

我的原则是：能用并发容器就不自己加锁。
```
