  - 已有VoiceWaveAnimation、VoiceIntercomManager等组件
  - 需集成到VideoPatrolPage和状态管理体系

非功能性要求

- 性能要求：
  
  - 设备切换的速度
  
    - ```
      目标：< 500ms 完成切换
      关键路径：
      - Step1: 停止旧播放器 + 重置状态 (150ms)
      - Step2: 加载新RVC配置 (100ms)  
      - Step3: 获取新流地址 (100ms)
      - Step4: 启动播放器 + 首帧渲染 (150ms)
      
      优化措施：
      - 使用reset()而非release()，复用播放器实例
      - 预加载设备RVC配置（DeviceManager缓存）
      - 并行执行独立操作（流地址获取 + UI重置）
      ```
  
  - 视频播放的速度
  
    - ```
      首帧时间：< 300ms (RTSP) / < 500ms (HLS)
      缓冲策略：
      - RedPlayer配置：max-buffer-size=512KB
      - 0延迟模式：开启（直播场景）
      - 硬件解码：优先启用
      ```
  
  - 状态管理
  
    - ```
      原则：精准更新，避免全量刷新
      ```
- 可维护性要求
  
  - 我们的Android版本存在典型的"上帝类"问题：
    -  VideoActivity达到7000+行代码
    - 集成了10+功能模块（直播、回放、对讲、云台、抓拍、录制...）
    - 3-5人并行开发时，Git冲突率超过60%
    - 修改一个功能，经常影响其他模块，回归测试成本很高
  - 所以在鸿蒙版重构时，我的核心目标是：
    - 支持Feature独立开发，降低Git冲突
    - 新增功能不影响已有代码
    -  状态管理清晰，避免混乱

蔡老板，您好，
目前已完成 **鸿蒙端的直播和语音对讲支持**，并同步完成了核心架构重构。整体采用 **MVVM** 架构设计，主要优化点如下：

1. 架构重构成果

- **View 层仅负责观测 State、渲染 UI**
- **ViewModel 持有并修改 State，负责业务逻辑分发**
- **Manager 负责调用底层能力，底层用 Interface + Impl 的策略模式实现**
- 这样整个响应链路清晰：UI → ViewModel → Manager → 底层 → 回调更新 State。

2. 模块化拆分（原先上帝类 7000 行 → 现在 260 行）

- 原来 `VideoActivity`（7000 行）与 `VideoPlayFragment`（5000 行）高度耦合
- 现在已彻底拆分为 **40+ 个清晰职责的代码文件**
- 主页面 Page 减少到 **260 行**，可读性和可维护性大幅提升

3. 大幅提升后续开发的并行性

- 通过 **feature 目录结构拆分**，不同功能能够独立开发
- 例如 PTZ 将独立放在：`/ets/feature_ptz_control/`
- State 聚合统一放在 `common/` 下，避免状态分散
- 同一模块多人开发时不再频繁产生 Git 冲突

4. 可测性与可定位性显著增强

- 通过查看对应 ViewModel 中 state 的变化，就能快速定位问题
- UI、逻辑、底层的边界更清晰，排查路径大幅缩短

5. 开发效率工具支持

- 已提供 `ps1` 脚本：输入功能名称即可自动生成对应的 feature 目录结构
- 方便后续团队保持统一的编码风格和结构
