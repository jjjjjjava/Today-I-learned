## 03.原理机制

### 3.1 引子

假如我们要渲染视频，考虑一种CPU路径：

- ```
  MediaCodec解码 → YUV byte[] → CPU做YUV→RGB → Bitmap → 上传GPU(glTexImage2D) → 渲染
  ```

那么1080p 30fps 的数据量：

- 每帧：1920 × 1080 × 1.5字节（YUV420）≈ 3MB
- 每秒：3MB × 30 = 90MB/s 的 CPU 计算 + 内存拷贝
- CPU 做 YUV→RGB：每像素 6 次浮点运算 × 6000万像素/秒 = CPU 直接炸

瓶颈有三个：

- CPU 计算 YUV→RGB 太慢
- Bitmap 创建频繁 GC
- glTexImage2D 每帧从 CPU 内存拷贝到 GPU 显存，这是最大的瓶颈

### 3.2 Android零拷贝图形管线

Android 的解法核心是：不让数据经过 CPU，让解码器直接把数据写到 GPU 能访问的显存里。

核心结构

- **BufferQueue** 是基础：内部维护约 3 个 **GraphicBuffer**（ION 共享内存，CPU/GPU 均可访问，不是普通 byte[]）。

  - ```
    producer（写入端）  →  BufferQueue  →  consumer（读取端）
    ```

组件职责

- | 组件             | 职责                                                         |
  | ---------------- | ------------------------------------------------------------ |
  | `SurfaceTexture` | 持有 consumer                                                |
  | `Surface`        | 包装 producer → 对外暴露为 `ANativeWindow`（C 接口）         |
  | `MediaCodec`     | 通过 `configure(format, surface)` 拿到 `ANativeWindow`，即 producer |

数据流

- ```
  MediaCodec.configure(format, surface)
      ↓ 拿到 ANativeWindow（producer）
  dequeueBuffer → 取得空闲 GraphicBuffer
      ↓
  硬件解码器直接写入 GraphicBuffer（YUV，CPU 不参与）
      ↓
  queueBuffer → 通知 consumer 有帧可用
      ↓
  调用 updateTexImage()（必须主动调用）
      ↓
  consumer 从队列取最新帧（跳过积压旧帧）
      ↓
  eglCreateImageKHR(GraphicBuffer) → EGLImage（显存句柄，无拷贝）
      ↓
  glEGLImageTargetTexture2DOES → 绑定到 GL_TEXTURE_EXTERNAL_OES 纹理
      ↓
  着色器采样：硬件 sampler 自动完成 YUV→RGB（非 shader 手写）
  ```

#### 1.BufferQueue 是什么

BufferQueue 是一个独立的对象，它内部有一个 GraphicBuffer 池（通常3块）。

它对外暴露两个角色：

- Producer：写入端，负责 dequeue/queue
- Consumer：读取端，负责 acquire/release

```
IGraphicBufferProducer    BufferQueue    IGraphicBufferConsumer
（写入端）          →    [buf1,buf2,buf3]   →    （读取端）
```

GraphicBuffer 本质是一块 GPU/DMA 可直接访问的共享显存，不是普通的堆内存。所以 Producer 写入数据，Consumer 拿到的是同一块显存的引用，没有拷贝。

#### 2.MediaCodec 作为 Producer

当你这样配置：

- ```
  MediaCodec.configure(format, surface, null, 0);
  ```

你给的是 Surface，不是 ByteBuffer。

这意味着：解码器硬件把 YUV 数据直接写入 GraphicBuffer，然后推入 BufferQueue。CPU 全程没有碰数据。

#### 3.如何理解Surface，SurfaceTexture，BufferQueue

BufferQueue 创建时，它自己就同时创建了写入端和读取端两个对象：

- ```
  BufferQueue::createBufferQueue(
      &producer,   // 写入端，IGraphicBufferProducer
      &consumer    // 读取端，IGraphicBufferConsumer
  );
  ```

这两个对象是 BufferQueue 吐出来的，然后这两个端分别交给不同的人持有：

- ```
  producer → 包装成 Surface → 交给 MediaCodec
  consumer → SurfaceTexture 自己持有
  ```

那么BufferQueue是谁创建的呢？我们看整体流程

- SurfaceTexture 构造时：
  - BufferQueue.createBufferQueue(&producer, &consumer)

  - 自己持有 consumer

  - 把 producer 包装成 Surface 暴露出去
-  你把 Surface 传给 MediaCodec.configure()：
  - MediaCodec 内部拿到 producer
  - 把它包装成 ANativeWindow（C接口）
- 解码一帧时：
  - MediaCodec 调 ANativeWindow_dequeueBuffer(window)
    - 实际调的是 producer.dequeueBuffer()
    - BufferQueue 从池子里找一块 FREE 状态的 GraphicBuffer
    -  返回给 MediaCodec
  - 硬件把 YUV 写入这块 GraphicBuffer
  -  MediaCodec 调 ANativeWindow_queueBuffer(window, buffer)
    - 实际调的是 producer.queueBuffer()
    - BufferQueue 把这块状态改为 QUEUED
    - 通知 consumer：有新帧了
  - SurfaceTexture 收到通知：
    - 触发 onFrameAvailable 回调
    - 你调 updateTexImage()
      - consumer.acquireBuffer() 取出 QUEUED 的那块
      - 通过 EGLImage 绑定成 GPU 纹理
      - consumer.releaseBuffer() 归还，状态改回 FREE

#### 4.EGLImage 机制

先说普通纹理是怎么上传的

- 正常你用 glTexImage2D 上传一张图片：

  - ```
    CPU内存（Bitmap数据）
        ↓ glTexImage2D
    GPU显存（纹理对象）
    ```

- 这里发生了一次内存拷贝：从 CPU 内存 → GPU 显存。

GraphicBuffer 的数据已经在显存里了

- MediaCodec 解码完，数据在 GraphicBuffer 里，GraphicBuffer 本身就是 GPU 可访问的显存。

- 如果还走 glTexImage2D，就是：

  - ```
    GraphicBuffer（显存）→ 拷贝到 CPU → 再拷贝回 GPU
    ```

- 完全没必要，绕了一大圈。

EGLImage 的作用：直接把显存变成纹理句柄

- EGLImage 是 EGL 层的一个机制，本质是：

- 给一块已有的显存（GraphicBuffer）创建一个 GPU 纹理句柄，不拷贝数据。

  - ```
    // 把 GraphicBuffer 包装成 EGLImage
    EGLImageKHR image = eglCreateImageKHR(
        display, 
        EGL_NO_CONTEXT,
        EGL_NATIVE_BUFFER_ANDROID,
        graphicBuffer->getNativeBuffer(),  // 就是那块显存
        attrs
    );
    
    // 把 EGLImage 绑定到纹理
    glEGLImageTargetTexture2DOES(GL_TEXTURE_EXTERNAL_OES, image);
    
    ```

- GPU 拿到的是同一块显存的引用，没有任何拷贝。

为什么是 GL_TEXTURE_EXTERNAL_OES 而不是普通纹理

- 普通纹理 GL_TEXTURE_2D 要求数据格式是标准的 RGBA。

- 但 GraphicBuffer 里存的是 YUV，格式不标准，而且可能是硬件私有格式（不同厂商的 GPU 格式不一样）。

- GL_TEXTURE_EXTERNAL_OES 是专门为这种场景设计的：

  - 不要求标准格式
  - GPU driver 自己知道怎么读这块显存
  - 采样时 driver 自动完成 YUV → RGB 转换，这一步是硬件做的，不是 shader 手写的

- 所以 shader 里要这样写：

  - ```
    #extension GL_OES_EGL_image_external : require
    uniform samplerExternalOES sTexture;
    
    void main() {
        gl_FragColor = texture2D(sTexture, vTexCoord);
        // driver 在这里自动做了 YUV→RGB，你感知不到
    }
    ```

- 小结

  - ```
    GraphicBuffer（显存）
        ↓ eglCreateImageKHR（不拷贝，只创建句柄）
    EGLImage
        ↓ glEGLImageTargetTexture2DOES
    GL_TEXTURE_EXTERNAL_OES（纹理）
        ↓ shader 采样
    GPU 自动 YUV→RGB
    ```

  - 整个过程零拷贝，YUV→RGB 也是硬件完成的
