# 06 · 单点归因：归并处理

## 目标

线程状态只是路标。最终把主线程现场归并为三个实际排查方向，决定下一步追什么证据。

## A：主线程自己执行太久

常见证据：

- 业务计算；
- 图片压缩或编解码；
- 文件、数据库 IO；
- 同步 Binder 调用。

```text
主线程正在执行什么
→ 为什么进入响应关键路径
→ 数据量或外部等待为什么失去时间上界
→ 哪个调用边界应该缩短或迁移
```

Camera 图片保存属于 A 类。

## B：主线程等待其他执行单元

常见证据：

- `BLOCKED` 等 monitor；
- `WAITING` 等条件、任务或线程；
- native `futex`、`pthread_mutex`、`pthread_join`；
- Binder 请求等待远端返回。

```text
主线程等待什么
→ 谁负责释放锁、完成条件或返回结果
→ 对方为什么没有完成
→ 依赖链最终落到哪里
```

极验死锁和 IJK `pthread_join` 属于 B 类。

## C：当前主线程样本无法解释超时

常见证据：

- 主线程只有 `nativePollOnce`；
- 栈缺失或采样过晚；
- 只有“低端机”“系统负载”等相关性，没有时序证据；
- 单个快照无法证明持续时间。

处理：

```text
不强行归因
→ 换同聚类样本
→ 补连续采样或系统 trace
→ 仍无证据则明确记录证据不足
```

## 输出模板

```text
入口：
共性/爆发边界：
代表 issue：
主线程现场有效性：
主线程状态或栈形态：
A / B / C：
直接原因：
继续追踪后的责任方：
当前证据边界：
```

## 复习检查

1. A 类和 B 类的下一步动作为什么不同？
2. 哪些情况下必须停在 C 类？
3. 直接原因与最终责任方怎样区分？
