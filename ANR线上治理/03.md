### 正确答案

**第 1 题：类型为什么必须在前？**

> ANR 类型说明系统在等待哪项职责完成；职责决定责任线程。Input 和 Service 通常重点看主线程，同步 Receiver 看实际执行 `onReceive()` 的线程，`goAsync()` 看工作线程，ContentProvider 慢查询可能看 Binder 线程。因此不能机械固定观察主线程。

**第 2 题：如何描述 nativePollOnce？**

> 采样这一刻主线程处于消息队列空闲等待，当前栈没有直接业务归因价值。可能是抓取偏晚、观察线程选错或系统调度问题；没有更多证据时不能在这些原因中强行选择一个。

**第 3 题：goAsync() 后看谁？**

> 看真正执行异步任务的线程或线程池，沿提交关系确认它是否承担该 Receiver 的工作，再检查阻塞点、队列和 `finish()` 调用路径。

## 正文内容

完成前面三步后，我们已经知道：

```text
这是什么类型的 ANR
→ 应该观察哪条线程
→ 当前堆栈是否值得继续分析
```

接下来进入单点归因的第四步：**结合线程状态与调用栈，判断责任线程是在执行太久，还是等待太久。**

### 一、状态、栈和职责必须一起看

一条线程信息通常包含三层含义：

1. **线程职责**：系统为什么在等它，例如主线程要响应输入、Receiver 工作线程要完成异步广播。
2. **线程状态**：RUNNABLE、BLOCKED、WAITING、TIMED_WAITING 等。
3. **调用栈**：它具体执行到了哪段代码、正在等待哪个同步原语或跨进程调用。

这三层不能拆开使用。

例如：

```text
main  RUNNABLE
```

只能说明 JVM 视角下线程处于可运行状态，不能说明它一定正在持续占用 CPU。

再加上调用栈：

```text
main  RUNNABLE
→ FileOutputStream.write
→ saveImageToGallery
→ CameraClickActivity
```

才得到一个具体方向：主线程采样时正在执行保存相册的文件 IO。

因此判断公式是：

> **线程职责 + 线程状态 + 调用栈 = 当前可提出的根因假设。**

它仍然是“假设”，证据强度还要结合持续时间、重复样本、源码路径和修复结果。

### 二、RUNNABLE：可能在执行，也可能卡在 native 调用

`RUNNABLE` 容易被误读为“线程正在占满 CPU”。实际上，它可能处于以下情况：

- 正在执行 Java/Kotlin 计算；
- 可以运行但暂时没有被 CPU 调度；
- 进入 native 方法执行文件 IO、数据库或图片处理；
- 进行同步 Binder 调用；
- 在某些内核调用中等待返回，但 JVM 仍把它显示为 RUNNABLE。

所以看到 RUNNABLE 后，继续读栈顶和业务调用链。

#### 栈顶是计算

```text
main  RUNNABLE
→ sortLargeList
→ buildPageData
→ Activity.onCreate
```

方向是主线程计算过重。接下来检查数据规模、算法复杂度、循环以及它是否位于启动或输入响应的关键路径。

#### 栈顶是 IO

```text
main  RUNNABLE
→ FileOutputStream.write
→ saveImageToGallery
→ CameraClickActivity
```

方向是主线程阻塞 IO。这与 `CameraClickActivity` 案例一致：页面聚集负责选出排查范围，有效单点栈把问题指向保存相册路径，源码再确认该调用运行在主线程。

#### 栈顶是 Binder

```text
main  RUNNABLE
→ BinderProxy.transactNative
→ BinderProxy.transact
→ 某系统服务或远程服务接口
```

方向是同步 Binder 调用返回过慢。此时不能只说“主线程 Binder 导致 ANR”，还要继续判断远端进程、Binder 线程池或 system_server 为什么没有及时返回。

因此 RUNNABLE 的工作结论应写成：

> **责任线程采样时正在某条调用路径中；根据栈顶判断计算、IO 或 Binder 方向，再用更多证据确认它是否持续得足够久。**

### 三、BLOCKED：正在竞争 Java monitor

`BLOCKED` 通常表示线程正在尝试进入一个 `synchronized` monitor，但锁被其他线程持有。

典型 trace 会给出类似信息：

```text
main  BLOCKED
waiting to lock <0x0fd09ed5>
held by thread 58
```

这时能确定的直接原因是：

> 主线程需要锁 A，但锁 A 当前由线程 58 持有，所以主线程无法继续执行。

但线程 58 才是下一步真正要看的对象：

- 它是否在锁内执行耗时 IO 或计算？
- 它是否在等待另一把锁？
- 它是否又通过某条依赖链等待主线程？
- 它持锁的代码是否属于自有代码或三方 SDK？

所以 `BLOCKED` 不等于“找到根因”。它只是给出了第一条明确的依赖边：

```text
main → 等锁 A → A 由线程 58 持有
```

下一篇会从这里继续，完整追踪极验案例中的 A、B 两把锁和 58、54 两条线程。

### 四、WAITING：在等一个条件，不一定是等 synchronized 锁

`WAITING` 表示线程在没有明确超时时间地等待其他动作发生。常见栈包括：

- `Object.wait()`；
- `LockSupport.park()`；
- `Thread.join()`；
- `CountDownLatch.await()`；
- `Future.get()`；
- 条件变量或并发队列等待。

例如：

```text
main  WAITING
→ CountDownLatch.await
→ loadConfigSynchronously
→ Activity.onCreate
```

这不是 Java monitor 的 `BLOCKED`，也不一定有一个可以直接搜索的锁地址。下一步要问：

- 谁负责执行 `countDown()`？
- 那个任务有没有提交成功？
- 它是不是排在线程池中一直得不到执行？
- 它是否反过来等待主线程？

因此 WAITING 的核心是找**完成条件的责任方**，而不是机械寻找“持锁线程”。

### 五、TIMED_WAITING：等待有超时，但超时仍可能超过 ANR 预算

`TIMED_WAITING` 常见于：

- `Thread.sleep()`；
- `Object.wait(timeout)`；
- `Thread.join(timeout)`；
- `LockSupport.parkNanos()`；
- 带超时的 Future、Latch 或条件等待。

有超时并不等于安全。如果主线程调用 `sleep(10_000)`，即使它最终会自动醒来，也可能已经超过 Input dispatch 的响应预算。

分析时要看：

1. 等待上限是多少；
2. 它位于哪条系统职责的关键路径；
3. 等待结束后是否还要执行其他耗时任务；
4. 这个等待是否本来就不应该出现在责任线程。

### 六、平台显示 Native 时仍然要看具体 native 栈

有些线上平台会把线程显示为 Native，这不是一个足够具体的根因分类。

- `MessageQueue.nativePollOnce` 通常表示 Looper 空闲等待；
- `BinderProxy.transactNative` 可能表示同步跨进程调用；
- native 文件读写可能表示磁盘或设备 IO；
- futex、pthread mutex 等可能表示 native 锁竞争。

所以“Native 态”本身不能统一等于无效样本。仍然需要结合 ANR 类型、责任线程和完整 native/Java 栈判断。

### 七、把状态归并成三个实际排查方向

在线上排查时，不必停留在背线程枚举，可以把它们归并成三个工作方向：

#### A. 责任线程自己在执行

常见信号：RUNNABLE，栈中出现业务计算、IO、图片处理、数据库或 Binder。

```text
责任线程
→ 当前执行什么
→ 为什么这段工作会这么久
→ 能否移出关键线程或缩短关键路径
```

#### B. 责任线程在等待其他执行单元

常见信号：BLOCKED、WAITING、TIMED_WAITING，栈中出现 monitor、park、Latch、Future、join 等。

```text
责任线程
→ 在等待什么条件或资源
→ 谁负责释放锁或完成条件
→ 那个线程为什么没有完成
```

#### C. 当前样本不能解释超时

常见信号：责任线程 `nativePollOnce`、缺失栈、采样过晚，或者只有系统因素假设但没有系统证据。

```text
不强行归因
→ 换同聚类样本
→ 检查其他责任线程
→ 有条件时补系统 trace
→ 平台没有相关信息时明确记录“证据不足”
```

### 八、单点归因 SOP 更新到第四步

现在完整路径已经推进到：

```text
确定 ANR 类型
→ 确定责任线程
→ 判断堆栈是否有效
→ 同时看线程状态与调用栈
   ├─ RUNNABLE：追计算、IO、Binder 等执行路径
   ├─ BLOCKED：找锁地址与持锁线程
   ├─ WAITING：找完成等待条件的责任方
   ├─ TIMED_WAITING：看等待时长是否超过响应预算
   └─ 当前栈无法解释：换样本或补证据
```

下一步不是立即修改主线程代码，而是沿已经暴露出的依赖关系继续向下追：持锁线程在做什么、等待条件由谁完成、Binder 远端为什么没返回。只有追到不能再向下解释的责任代码，根因链才闭合。
