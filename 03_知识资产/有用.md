## 2 启动优化

###  2.1 引子

这是我们今年一季度的考核目标。当时线上启动耗时的 P50 是 1.8s，P90 是 4.5s。季度目标是将 P50 优化 10%，将 P90 优化 20%，也就是分别降低到 1.62s 和 3.6s。

### 2.2 线上定位方向

这个任务由 Leader 交给我们处理。接到任务后，我们没有立即尝试在线下复现，而是先查看线上各个启动阶段的耗时，初步判断可能的优化方向。

从线上启动链路的 Span 数据来看，`Stage_home_build` 在 P50 和 P90 中的耗时占比都比较高，其中 P90 耗时达到了 1.9s，是启动链路中最主要的耗时阶段之一。

`Stage_home_build` 覆盖了首页从 `onCreate` 开始，到页面首次渲染完成的整个构建过程。因此，我们初步将首页构建和渲染链路确定为重点排查方向，并提出了几个猜想：

1. 首页的 View 层级或者布局嵌套过深，导致 View 树过重，增加了 `measure` 和 `layout` 的耗时；
2. 布局实现不够合理，例如频繁嵌套 RelativeLayout，可能触发多次测量，可以考虑使用 ConstraintLayout 扁平化布局层级；
3. 首页本身是一个重页面，ViewPager 中包含了多个 Fragment，可能存在页面预加载过多、没有真正实现懒加载的问题。

带着这些猜想，我们进入了线下复现和验证流程。
### 2.3 Tinker 热修复原理

在应用启动的 `bindApplication` 流程中，系统创建 `TinkerApplication` 并调用其 `attachBaseContext()`，Tinker 会在这里尝试加载补丁。

低版本将补丁 `dexElements` 插入原 AppClassLoader 搜索数组头部；高版本创建新的 Tinker ClassLoader 作为后续类加载入口，并保留原 ClassLoader 兜底。这样业务类首次加载时会按照“系统类 → 补丁 Dex → 原 APK Dex”的顺序查找，同名类优先由补丁 Dex 定义，后续调用的自然是修复后的方法实现。它并非替换已经加载的旧类，因此通常需要重启进程生效。

比如：
假设原 APK 中有：

```
class LoginManager {
    boolean isVip() {
        return false; // Bug
    }
}
```

补丁 Dex 中有同名类：

```
class LoginManager {
    boolean isVip() {
        return true; // 修复后
    }
}
```

### 2.4 DAG 任务编排（后续优化思路）

针对 `Application.onCreate()` 中大量 SDK 串行初始化的问题，我们还考虑过使用 DAG 做进一步治理。不过这个方案目前没有正式落地，主要停留在初步设计阶段。

我们项目启动时涉及 Network、个推、WebRTC 和地图等 SDK。初步思路是将每段初始化逻辑抽象成一个任务，并为任务声明前置依赖、执行线程和业务优先级。例如，Network 内部的 API 配置、HTTP Manager、OkGo 和 Token Header 存在一定的先后关系，可以组成一条启动关键链；如果个推初始化依赖 Network 或 Token，就在对应的前置任务完成后执行。地图和 WebRTC 如果与 Network 没有依赖，而且首页不会立即使用，就可以作为独立节点，不再串行阻塞 `Application.onCreate()`，而是在对应的业务入口前完成初始化。

拓扑排序发生在 `Application.onCreate()` 收集完任务并构建依赖图之后。调度器先统计每个任务的入度，优先执行入度为零的任务；任务完成后，再减少其后继任务的入度。当后继任务的入度变为零时，就将其加入可执行队列。这样既能保证存在依赖的任务按照正确顺序执行，也能让互不依赖的任务并行或者延迟执行。

### 2.5 Baseline Profile 优化

启动过程中还可以通过 Baseline Profile 进行优化。

Java代码有一个特性：一次编译到处执行，原理就是：编译的产物是字节码文件，执行则是依靠解释器翻译成对应机器平台的机器码的形式。还有JIT优化的形式，将高频使用的字节码直接编译为对应平台的机器码。

Android 应用的 Java、Kotlin 代码最终会被编译成 DEX 字节码。其方法是ART 在运行时会先通过解释器执行；当方法达到一定热度后，再通过 JIT 将其编译成当前设备平台的机器码。

Baseline Profile 会记录启动关键路径中涉及的类和方法，并将这些规则随安装包一起发布。应用安装时，ART 可以根据 Profile 对这些关键方法进行 AOT 编译。这样在首次启动时，关键方法就能直接执行已经编译好的机器码，从而减少解释执行和运行时 JIT 编译的成本。

### 2.6 总结

总结来看，这次启动优化不是几个零散优化点的堆叠，而是一套完整的工程闭环：从线上监控预定位问题，到线下稳定复现、定义启动口径、选择分析工具，再通过 Perfetto 进行结构化分析和源码归因，之后完成方案分级、同口径验证、回归问题修复，最终将优化结果回填为新的基线和性能预算。

整个过程中，我们以 Android 系统启动链路为主线，分析不同阶段的治理手段，包括 Baseline Profile、ContentProvider 初始化治理、DAG 任务编排、XML 加载优化以及首屏渲染链路裁剪。最终沉淀的不只是一次启动耗时优化，而是一套可定位、可验证、可回归、可持续守护的启动性能治理方法。

## 3.ARouter
### 3.1 流程概述

> 灰度劣化 → Stage/Task 下钻 → 首次启动复现 → Dex 扫描 → 恢复编译期插桩 → Java 21/ASM 修复 → 验证并回馈上游

这个项目经历了两轮处理。第一轮是在 Gradle、AGP 升级后，灰度 LOW 档 P90 从约 4.5 秒上升到 12.8 秒。我们暂停放量，通过 Stage/Task 下钻到 `arouter.init`，再在线下首次启动场景中用 Profiler 定位到 `openDexFileNative`。

结合源码确认，旧插件依赖的 Transform 接入方式在 AGP 8 下失效，ARouter 没有完成编译期注册，运行时回退成全量 Dex 扫描。我们改用兼容新 AGP 的插桩方式，并修复 Variant 匹配，最终让 ARouter 初始化从约 7.84 秒降低到 100 毫秒以内，线上 P90 也恢复到原基线。

第二轮是在升级 Java 21 后，旧 ASM 无法解析新版 Class。我们统一升级 ASM、修复插件运行时依赖和 Variant 链路，发布自维护版本，并将修复提交上游，相关 PR 最终被合并。

## 4.ANR
### 4.0 线上 ANR 的归因分层

面对一批线上 ANR，不能随机打开一条 Trace 就开始改代码。应该先在批量问题层收敛范围和优先级，再进入代表 issue，用单点证据证明技术根因。

```text
共性归因：从空间和公共特征上回答“问题集中在哪里”，也就是最可能的影响因子。
爆发归因：从时间和增量上回答“为什么现在突然上涨”，也就是当前的增长切片占比。
单点归因：结合代码根因定位，回答：代码中这一阶段主线程是什么状态，在做什么？“这一条为什么会超时”
```
面对一段时间积累的存量 issue。第一步不是随机挑一条修，而是寻找影响面最大的共同边界。

```text
日常看板 → 共性归因 → 代表 issue → 单点归因
```

面对短时间异常上涨。第一步先确认是否真实爆发、影响是否仍在扩大。

```text
机器人告警 → 爆发确认/止损 → 共性切片 → 代表 issue → 单点归因
```
### 4.1 Camera 图片保存：主线程同步 IO

> 页面聚类到 `CameraClickActivity` → 主线程 `Bitmap.compress / FileOutputStream.write` → 整条保存链切到 IO 线程

拍照确认流程通过 `observeOn` 切回主线程后，又同步执行图片压缩和文件写入。修复时把压缩、写文件和媒体库刷新整体放到 IO 线程，完成后再回主线程更新页面。

### 4.2 “茉莉奶白”：线上爆发归因

> 机器人告警 → 事件量和用户数上涨 → 多维切片集中到企业 → 对齐业务开关 → 关闭后指标回落

企业聚类只是定位线索；开启开关后上涨、关闭后回落，才构成更完整的反向验证。

### 4.3  如果没有 ANR

如果没有 ANR，App 卡住后，用户无法判断是短暂卡顿还是永久死锁，只能反复点击或强杀进程；系统也没有统一标准判断应用只是慢，还是已经无法响应；开发者事后还拿不到当时的线程现场。

所以 ANR 要回答的是：系统交给 App 的有时限关键任务，是否在规定时间内完成。如果没完成，那么给用户弹框和反馈，给开发者dump对应的线程现场

### 4.4 ANR 的设计思路：从 Linux Watchdog 到埋雷、拆雷、爆雷

> Linux Watchdog：派发任务并开始计时 → 按时完成就“喂狗”取消超时 → 没有喂狗则判定失去响应

```text
映射到组件类 ANR：
埋雷 → system_server 派发任务，记录时间并安排超时检查
拆雷 → App 完成任务，通过 Binder 通知 system_server 销账
爆雷 → 超时检查触发，复查任务仍未完成，进入 ANR
```

> 计时和判定放在 `system_server`：App 卡死后无法可靠监控自己，裁判必须在被检测进程之外。

### 4.5 Service ANR 源码例子

```text
埋雷：
startService → AMS / ActiveServices
→ bumpServiceExecutingLocked
→ 记录 executingStart，加入 mExecutingServices
→ 集合空→非空时 scheduleServiceTimeoutLocked

拆雷：
scheduleCreateService → App Binder 线程
→ ActivityThread.mH → 主线程执行 Service 生命周期
→ serviceDoneExecuting
→ executeNesting--，归零后移出 mExecutingServices
→ 集合为空时移除超时消息

爆雷：
serviceTimeout
→ 找 executingStart 最早的 Service
→ 确认超过前台 20s / 后台 200s
→ appNotResponding
```

> 三个提示：
>
> 1. 一个进程只有一颗 Service 雷。
> 2. `executeNesting` 判断单个 Service；`mExecutingServices` 是否为空决定能否拆雷。
> 3. 超时消息只是检查触发器，`executingStart` 是否真正超时才是判据。

### 4.6 Input ANR 源码例子

> Input 不发延时雷，而由 `InputDispatcher` 持续检查：事件发出是埋雷，App 返回 ACK 是拆雷，等待超时就是爆雷。

```text
内核 /dev/input
→ InputReader
→ mInboundQueue
→ InputDispatcher / outboundQueue
→ Socket 发给 App，并进入 waitQueue
→ InputEventReceiver → ViewRootImpl → View
→ finishInputEvent 返回 ACK
→ 从 waitQueue 移除

超时：
dispatchOnce 检查 waitQueue 头部
→ now - eventTime ≥ 5s
→ onANRLocked → appNotResponding
```

> 三个提示：
>
> 1. `mInboundQueue` 待分发，`outboundQueue` 待发送，`waitQueue` 已发送待 ACK。
> 2. 输入高频、低延迟，所以使用独立 Reader/Dispatcher 线程和 Socket，避免占满 Binder 线程池。
> 3. 从 `eventTime` 起算，系统排队、传输、App 处理和 ACK 全部计入 5 秒。

### 4.9 堆栈分析

核心公式：

> ANR 语境 + 主线程状态或栈形态 + 完整调用栈 = 当前可以提出的根因假设

#### 第一步：先判断现场是否有效

Bugly 发现异常、采集堆栈和平台展示之间存在时机差，看到的可能是阻塞结束后的快照。因此先确认样本属于目标聚类和时间窗口，再检查主线程栈是否完整、是否存在能够解释长时间无响应的执行或等待路径。

如果主线程只停在：

```text
MessageQueue.nativePollOnce
→ MessageQueue.next
→ Looper.loop
```

它只能说明采样这一刻主线程正在等待新消息，不能证明此前没有阻塞，也不能直接归因成系统问题。此时应换同聚类的有效样本，或者补连续采样、系统 Trace；没有更多证据就明确记录“证据不足”。

#### 第二步：结合状态读取完整调用栈

- `RUNNABLE`：不等于 CPU 满载。继续看栈中是否有业务计算、图片处理、文件或数据库 IO、同步 Binder。Camera 案例就是主线程执行 `Bitmap.compress` 和文件写入。
- `BLOCKED`：表示主线程在等待进入 Java monitor。先找到锁的持有者，再看持锁线程是在执行耗时任务、等待另一把锁，还是已经形成 AB-BA 死锁。
- `WAITING`：表示等待条件成立。看到 `Object.wait` 找谁负责 `notify`；看到 `CountDownLatch.await` 找谁负责 `countDown`；看到 `Future.get` 找任务为何未完成；看到 `Thread.join` 找被等待线程为何不退出。
- `NATIVE`：它是平台展示或栈形态，不是独立的 Java 线程状态。必须继续读 native 栈顶：`transactNative` 看 Binder，`read/write/fsync` 看 IO，`futex/pthread_mutex` 看锁，`pthread_join` 看被等待线程。

单次快照通常只能提出方向。还需要结合更多同类样本、源码调用路径、线程边界和修复后的指标变化，才能把假设加强为根因。



### 4.7 极验登录：AB-BA 死锁

> main 等锁 A → 线程 58 持有 A、等待 B → 线程 54 持有 B、等待 A → 闭源三方库死锁

极验把联通一键登录的带锁任务提交到主线程，联通内部两个线程加锁顺序相反，形成 AB-BA 死锁，主线程也因此永久等待。由于根因在闭源三方库，只能反馈厂商或更换方案。

### 4.8 IJK 播放器：主线程等待音频线程退出

> 公共播放器组件 → main `pthread_join` → 音频线程阻塞在 `AudioTrack.write` → 后台释放播放器

多个视频页面的公共栈最终都落到播放器释放。代表 issue 中，主线程的完整调用链是：

```text
main
→ VideoPlayChildView.onDetachedFromWindow
→ VideoPlayChildView.stopPlay
→ IjkPlayView.stopPlayback
→ IjkMediaPlayer.release
→ ijkmp_shutdown_l
→ ffp_wait_stop_l
→ SDL_AoutCloseAudio
→ SDL_WaitThread
→ pthread_join
```

被等待的音频线程同时停在：

```text
IJK audio thread
→ AudioTrack.write
→ AudioTrack::obtainBuffer
→ ClientProxy::obtainBuffer
```

`pthread_join` 说明主线程正在等待音频线程退出；音频线程必须先从阻塞式 `AudioTrack.write()` 返回，才能检查退出标记。修复没有删除正常释放流程，而是让 UI 先放弃旧播放器，再把 `stop()` 和 `release()` 整体移到后台线程。


### 4.10 归因后的归并处理

线程状态只是路标，最终要把主线程现场归并成 A、B、C 三个实际方向。

#### A：主线程自己执行太久

常见证据是业务计算、图片压缩、编解码、文件或数据库 IO。继续追问：主线程正在做什么、为什么进入响应关键路径、耗时为什么失去上界、哪个调用边界可以缩短或迁移。

处理方向是减少工作量、拆分任务，或者把无 UI 依赖的工作移出主线程。Camera 图片保存属于 A 类。

#### B：主线程等待其他执行单元

常见证据是 `BLOCKED`、`WAITING`、`futex`、`pthread_mutex`、`pthread_join` 或同步 Binder。不能停在“主线程正在等”，还要继续追：它在等谁、谁负责释放锁或完成条件、对方为什么没有完成。

处理方向是沿依赖链找到最终责任方，再统一加锁顺序、缩短持锁范围、移除主线程同步等待，或者调整线程边界。极验死锁和 IJK 播放器释放属于 B 类。

#### C：当前样本无法解释超时

常见情况是主线程只有 `nativePollOnce`、堆栈缺失、采样过晚，或者只有“低端机、系统负载”等相关性，没有时序证据。此时不强行归因，换同聚类样本或补系统 Trace；仍然无法证明就明确记录证据不足。

最后可以用下面这条线收口：

```text
代表 issue
→ 现场是否有效
→ 主线程状态与完整调用栈
→ 归并 A / B / C
→ 直接原因
→ 沿执行或依赖链找到最终责任方
→ 修复与反向验证
```

## 5.鸿蒙FFmpeg
### 5.1 项目背景

> 版本下架整改 → 补齐录像下载和图片水印 → 建设统一媒体处理底座

鸿蒙巡店模块最初沿用 H5，但 Web 无法完成录像下载和视频加水印，版本最终被下架。我独立负责这部分的调研、开发、FFmpeg 源码改造、性能优化和插件发布。

### 5.2 FFmpeg 选型

> RTSP 录像：读取 → 重封装 MP4
>
> 图片水印：解码 → overlay 合成 → 重新编码 → MP4 封装

录像下载可以直接重封装，但水印改变了画面像素，必须重新编解码。相比自己组合网络、OpenGL、编解码和封装模块，FFmpeg 能统一覆盖整条媒体链路，更适合当时紧急整改和后续复用。

### 5.3 四个技术难点

#### 难点一：OpenHarmony 交叉编译与 fftools 嵌入

**难点：** FFmpeg 原本是桌面命令行程序，鸿蒙 App 不能直接启动并复用它的进程模型，需要把 fftools 和 `libav*` 编译成 App 能调用的 Native 产物。

**处理：** 使用 Lycium、HPKBUILD 和 OpenHarmony SDK/NDK 工具链完成交叉编译，打开 RTSP、封装、滤镜和编解码配置，把 `libav*` 与 fftools 聚合成单一 `.so`，再把 `main(argc, argv)` 改造成 `exe_ffmpeg_cmd(argc, argv)`。

#### 难点二：fftools 会结束宿主进程

**难点：** 命令行程序执行完成后调用 `exit(ret)` 很正常，但 fftools 嵌入 `.so` 后，`exit()` 会直接结束整个 App。并且一次命令结束后，fftools 的全局状态还可能污染下一次执行。

**处理：** 在函数入口通过 `setjmp` 保存返回点，深层 `exit_program` 改为 `longjmp` 回到入口；先保存返回码，再执行 `reset_ffmpeg_state`，最后把结果返回 C++ 桥接层。由于全局状态仍非线程安全，上层保持串行执行。

#### 难点三：ArkTS 与 Native 双向通信

**难点：** 视频处理不能阻塞 ArkTS 线程，Native 侧还要持续回传进度和最终结果；同时要解决跨线程调用 JS，以及多个任务之间回调不能串线的问题。

核心原理其实是两件事：**跨语言类型转换，以及把任务交给对应的线程执行。** 去程把 ArkTS 数据转换成 C++、C 能识别的数据，并交给 Native 工作线程；回程把 C 回调转换成 JS 函数调用，再交给 JS 线程执行。

**去程注册：** 先用 `JSBIND_ADDON(ffmpegutils)` 把 `.so` 注册成 Native Addon，再通过下面的绑定把 C++ 方法导出到 `exports`：

```cpp
JSBIND_GLOBAL() {
    JSBIND_PFUNCTION(executeFFmpegCommandAPP);
}
```

`JSBIND_PFUNCTION` 会生成 Promise 包装、参数和返回值转换，并把耗时函数提交到非 JS 线程。ArkTS 调用后可以立即拿到 Promise，不会让 FFmpeg 长时间占用 JS 线程。

**去程转换：**

```text
ArkTS string / number / string[]
→ AKI
→ std::string / int / vector<string>
→ char **argv
→ exe_ffmpeg_cmd
→ Native 工作线程执行 fftools
```

第一层转换解决 ArkTS 与 C++ 的类型差异，第二层把 C++ 容器恢复成 fftools 熟悉的 `argc/argv`。这里要保证字符串内存的生命周期覆盖整次命令执行。

**回调注册：** ArkTS 在执行前通过 `JSBind.bindFunction`，使用 UUID 分别注册进度、成功和失败回调。UUID 用于区分不同任务，避免后一次任务覆盖前一次任务的函数。

```text
uuid_onFFmpegProgress
uuid_onFFmpegSuccess
uuid_onFFmpegFail
```

Native 再使用同一个 UUID，通过 `aki::JSBind::GetJSFunction(...)` 取回对应的 `aki::JSFunction` 句柄。

```cpp
auto progress = aki::JSBind::GetJSFunction(
    uuid + "_onFFmpegProgress"
);
```

**回程转换：** fftools 是 C 代码，不认识 `aki::JSFunction`，所以中间定义一组纯 C 函数指针。fftools 只负责调用函数指针，C++ 桥接函数再从 `thread_local` 中取得当前任务的 JS 函数句柄，并调用 `Invoke`。

```text
fftools
→ C 函数指针
→ C++ 桥接函数
→ thread_local 当前任务回调
→ JSFunction.Invoke
→ AKI 调度 JS 线程
→ ArkTS 回调
```

Native 工作线程不能直接操作 JS 虚拟机。`Invoke` 的作用就是把 JS 函数调度到 JS 线程执行；Native 调用线程可能等待回调完成，因此进度回调必须轻量。

进度是在命令执行期间由 fftools 通过 C 函数指针主动上报；成功和失败则在 `exe_ffmpeg_cmd` 结束后，根据返回码选择对应的 JS 函数执行。

最后要注意，`JSBIND_PFUNCTION` 只保证长任务不直接占用 JS 线程，不代表每次都会新建线程，也不代表 fftools 已经具备并发安全。由于 fftools 仍有全局状态，多个命令继续由上层单线程排队执行。

#### 难点四：硬件编码适配与参数链

**难点：** 两分钟视频加水印耗时约 150 秒，说明可能仍在软件编码；接入硬件编码后，开源用户又反馈 `-b:v` 码率参数不生效。

**处理：** 第一轮指定 `h264_ohosavcodec` 后，根据“codec 不存在”的 Native 日志确认当前 `.so` 没有编入鸿蒙硬件适配。补齐适配源码和构建配置、重新交叉编译后，处理时间从约 150 秒降低到 27 秒。

第二轮沿 ArkTS 命令、fftools 解析、Native 参数一路下钻，最终发现 `ohosvideoencoder.cpp` 没有把 `format_->bit_rate` 写入 `OH_AVFormat`。补写 `OH_MD_KEY_BITRATE` 后重新编译，并通过 `ffprobe` 验证视频轨码率。

### 5.4 项目结果

> 业务重新上架 → `ffmpeg_tools` 发布 GitHub 和 OHPM → 性能优化 → 社区问题反哺上游

这个项目形成了从业务落地、基础能力开源，到社区反馈、底层定位和上游回馈的完整闭环。


## 6.蓝牙配网
我做过一个智控平台项目，负责 ESP32 智能网关蓝牙配网功能。业务目标是：用户重置网关后，App 通过蓝牙找到设备，把 Wi-Fi 信息发送给网关，网关联网后再完成后台注册，最终进入设备首页。

技术上没有自己实现整套蓝牙协议，使用 Espressif 官方 `esp-idf-provisioning-android` SDK。我的工作主要是 SDK 接入、业务封装、状态管理和异常处理。官方 SDK 已经封装 BLE 扫描、GATT 连接、安全会话、Wi-Fi 扫描和配网能力。[Espressif SDK](https://github.com/espressif/esp-idf-provisioning-android)

我把 SDK 封装成 `ESP32DeviceManager` 和 `ESP32ConfigHelper`。上层只关心几个状态：扫描设备、连接设备、配置 Wi-Fi、检查注册结果。完整流程是：先申请蓝牙权限并扫描带指定名称前缀的设备；拿到设备广播中的 Primary Service UUID；连接 GATT 并发现服务；建立安全会话；把用户选择的 SSID 和密码交给 SDK；最后根据配网回调和设备 MAC 查询后台注册状态。成功进入设备页；密码错误允许原地重试；扫描失败、连接失败或超时则释放连接，返回设备重置或扫描页面。[项目流程记录](https://github.com/jjjjjjava/Today-I-learned/blob/master/%E9%A1%B9%E7%9B%AE/00.%20%E9%A1%B9%E7%9B%AE%E5%BD%92%E6%A1%A3/02.%20%E6%99%BA%E6%8E%A7%E5%B9%B3%E5%8F%B0_0729/04.%20feat_%E6%99%BA%E6%8E%A7%E5%B9%B3%E5%8F%B0_DeviceHome%E6%96%B0%E5%A2%9E%E7%BD%91%E5%85%B3%E8%AE%BE%E5%A4%87.md)

联调时遇到过一次典型问题：设备能扫描到，但连接时提示 `Service not found`，部分情况下出现 GATT 133。开始怀疑日志里不断变化的 UUID，后来确认那个是 Android 注册 GATT Client 时生成的标识，不是设备服务 UUID。继续按“扫描、连接、服务发现、会话建立、配网”分阶段看日志，最终定位到设备模型转换时丢失了广播中的 Primary Service UUID。修正 UUID 传递后，服务发现恢复正常。

还有一个容易误判的问题：Wi-Fi 信息发送成功后，ESP32 会断开 BLE 并重启连接路由器。这个断开不一定代表失败。因此最终成功标准不能只看蓝牙连接，而要看设备配网状态和后台注册结果。通过这次项目，我掌握了 IoT 配网业务闭环，也形成了按通信阶段定位 BLE 问题的方法。



## 7.串口
智控平台项目主要使用 BLE 配网，我没有直接负责串口模块。不过以前做 Linux 侧协议对接时接触过串口，理解串口通信原理和 Android 接入方式。

串口通常指 UART 异步串行通信。双方先约定波特率、数据位、停止位和校验方式，例如 `115200 8N1`，表示波特率 115200、8 个数据位、无校验、1 个停止位。发送一个字节时，会依次发送起始位、数据位、可选校验位和停止位。

UART 只解决字节传输。实际项目还要定义上层协议，例如帧头、数据长度、命令字、数据区和 CRC，用于拆包、校验及区分业务指令。

Linux 中，串口一般表现为 `/dev/ttyS*`、`/dev/ttyUSB*` 或 `/dev/ttyACM*`。程序通过 `open` 打开设备节点，用 `termios` 设置串口参数，再通过 `read/write` 收发数据。

Android 分两种情况。定制设备上的板载 UART，一般通过厂商 SDK，或者 JNI 调用 Linux 的设备节点接口；同时需要处理设备节点权限和 SELinux。普通手机连接 USB 转串口设备，则使用 Android USB Host API：枚举设备、通过 VID/PID 匹配、申请 USB 权限、打开设备并获取读写 Endpoint，然后在工作线程异步收发数据。

所以这部分我有原理和 Linux 侧使用经验，也清楚 Android 接入方案，但没有把它包装成自己在该项目中的实际产出。
