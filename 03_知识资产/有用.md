## 2 启动优化

###  2.1 引子

这是我们今年一季度的考核目标。当时线上启动耗时的 P50 是 1.8s，P90 是 4.5s。季度目标是将 P50 优化 10%，将 P90 优化 20%，也就是分别降低到 1.62s 和 3.6s。

### 2.2 线上定位方向

这个任务由 Leader 交给我们处理。接到任务后，我们没有立即尝试在线下复现，而是先查看线上各个启动阶段的耗时，初步判断可能的优化方向。

从线上启动链路的 Span 数据来看，`Stage_home_build` 在 P50 和 P90 中的耗时占比都比较高，其中 P90 耗时达到了 1.9s，是启动链路中最主要的耗时阶段之一。

`Stage_home_build` 覆盖了首页从 `onCreate` 开始，到页面首次渲染完成的整个构建过程。因此，我们初步将首页构建和渲染链路确定为重点排查方向，并提出了几个猜想：

1. 首页的 View 层级或者布局嵌套过深，导致 View 树过重，增加了 `measure` 和 `layout` 的耗时；
2. 布局实现不够合理，例如频繁嵌套 RelativeLayout，可能触发多次测量，可以考虑使用 ConstraintLayout 扁平化布局层级；
3. 首页本身是一个重页面，ViewPager 中包含了多个 Fragment，可能存在页面预加载过多、没有真正实现懒加载的问题。

带着这些猜想，我们进入了线下复现和验证流程。
### 2.3 Tinker 热修复原理

在应用启动的 `bindApplication` 流程中，系统创建 `TinkerApplication` 并调用其 `attachBaseContext()`，Tinker 会在这里尝试加载补丁。

低版本将补丁 `dexElements` 插入原 AppClassLoader 搜索数组头部；高版本创建新的 Tinker ClassLoader 作为后续类加载入口，并保留原 ClassLoader 兜底。这样业务类首次加载时会按照“系统类 → 补丁 Dex → 原 APK Dex”的顺序查找，同名类优先由补丁 Dex 定义，后续调用的自然是修复后的方法实现。它并非替换已经加载的旧类，因此通常需要重启进程生效。

比如：
假设原 APK 中有：

```
class LoginManager {
    boolean isVip() {
        return false; // Bug
    }
}
```

补丁 Dex 中有同名类：

```
class LoginManager {
    boolean isVip() {
        return true; // 修复后
    }
}
```

### 2.4 DAG 任务编排（后续优化思路）

针对 `Application.onCreate()` 中大量 SDK 串行初始化的问题，我们还考虑过使用 DAG 做进一步治理。不过这个方案目前没有正式落地，主要停留在初步设计阶段。

我们项目启动时涉及 Network、个推、WebRTC 和地图等 SDK。初步思路是将每段初始化逻辑抽象成一个任务，并为任务声明前置依赖、执行线程和业务优先级。例如，Network 内部的 API 配置、HTTP Manager、OkGo 和 Token Header 存在一定的先后关系，可以组成一条启动关键链；如果个推初始化依赖 Network 或 Token，就在对应的前置任务完成后执行。地图和 WebRTC 如果与 Network 没有依赖，而且首页不会立即使用，就可以作为独立节点，不再串行阻塞 `Application.onCreate()`，而是在对应的业务入口前完成初始化。

拓扑排序发生在 `Application.onCreate()` 收集完任务并构建依赖图之后。调度器先统计每个任务的入度，优先执行入度为零的任务；任务完成后，再减少其后继任务的入度。当后继任务的入度变为零时，就将其加入可执行队列。这样既能保证存在依赖的任务按照正确顺序执行，也能让互不依赖的任务并行或者延迟执行。

### 2.5 Baseline Profile 优化

启动过程中还可以通过 Baseline Profile 进行优化。

Java代码有一个特性：一次编译到处执行，原理就是：编译的产物是字节码文件，执行则是依靠解释器翻译成对应机器平台的机器码的形式。还有JIT优化的形式，将高频使用的字节码直接编译为对应平台的机器码。

Android 应用的 Java、Kotlin 代码最终会被编译成 DEX 字节码。其方法是ART 在运行时会先通过解释器执行；当方法达到一定热度后，再通过 JIT 将其编译成当前设备平台的机器码。

Baseline Profile 会记录启动关键路径中涉及的类和方法，并将这些规则随安装包一起发布。应用安装时，ART 可以根据 Profile 对这些关键方法进行 AOT 编译。这样在首次启动时，关键方法就能直接执行已经编译好的机器码，从而减少解释执行和运行时 JIT 编译的成本。

### 2.6 总结

总结来看，这次启动优化不是几个零散优化点的堆叠，而是一套完整的工程闭环：从线上监控预定位问题，到线下稳定复现、定义启动口径、选择分析工具，再通过 Perfetto 进行结构化分析和源码归因，之后完成方案分级、同口径验证、回归问题修复，最终将优化结果回填为新的基线和性能预算。

整个过程中，我们以 Android 系统启动链路为主线，分析不同阶段的治理手段，包括 Baseline Profile、ContentProvider 初始化治理、DAG 任务编排、XML 加载优化以及首屏渲染链路裁剪。最终沉淀的不只是一次启动耗时优化，而是一套可定位、可验证、可回归、可持续守护的启动性能治理方法。

## 4.ANR
### 4.1 thread.join 案例：主线程等待 IJK 音频线程退出

**共性归因**

线上 5.32.01 版本存在一批视频场景 ANR。按页面和机型切片后，没有发现单一影响因素：`VideoActivity`、`VideoSplitAllActivity` 等多个 Activity 都有同类问题，机型分布也较分散。

继续比较调用栈，发现不同页面最终都经过同一条公共组件路径：

```text
VideoPlayChildView.onDetachedFromWindow
VideoPlayChildView.stopPlay
IjkPlayView.stopPlayback
IjkMediaPlayer.release
```

所以 Activity 只是触发场景，真正应该进入单点归因的是公共组件 `VideoPlayChildView` 和 `IjkPlayView` 的播放器释放逻辑。

**单点归因**

代表 issue 中，主线程在 RecyclerView 重新布局、回收子 View 时触发 `onDetachedFromWindow()`，随后同步释放 IJK 播放器：

```text
main
→ IjkMediaPlayer.release
→ ijkmp_shutdown_l
→ ffp_wait_stop_l
→ SDL_AoutCloseAudio
→ SDL_WaitThread
→ pthread_join
```

完整线程 dump 同时显示，IJK 音频写入线程停在：

```text
Thread-444
→ AudioTrack.write
→ AudioTrack::obtainBuffer
→ ClientProxy::obtainBuffer
```

`pthread_join` 表示主线程正在等待音频线程退出。IJK 虽然设置了退出标记，但音频线程必须先从阻塞式 `AudioTrack.write()` 返回，才能重新检查标记并结束。

这里平台把主线程显示为 Native，而不是 Java 的 `WAITING`。但从依赖关系看，它仍属于“等待另一线程结束”：直接原因是主线程阻塞在 `pthread_join`，触发因素是音频线程卡在 `AudioTrack.write()`，应用侧根因是在主线程执行了没有时间上界的播放器释放。

**修复**

提交 `1c07c850` 没有删除 `pthread_join`，而是调整播放器释放的线程边界：

```java
IMediaPlayer player = mMediaPlayer;
mMediaPlayer = null;

new Thread(() -> {
    player.stop();
    player.release();
}).start();
```

主线程先保存旧播放器引用并清空成员字段，立即更新页面和播放状态；后台任务继续持有局部变量 `player`，负责执行可能阻塞的 `stop()` 和 `release()`。

严格来说，Java 没有语言级所有权转移。这里表示业务责任转移：UI 组件不再提供旧播放器的操作入口，后台任务接管它的最终释放。即使 `pthread_join` 仍然等待较久，阻塞的也是释放线程，不再是主线程。

### 4.2 小结：把状态归并成三个实际排查方向

在线上排查时，不必停留在背线程枚举，可以把它们归并成三个工作方向：

#### A. 责任线程自己在执行

常见信号：RUNNABLE，栈中出现业务计算、IO、图片处理、数据库或 Binder。

```text
责任线程
→ 当前执行什么
→ 为什么这段工作会这么久
→ 能否移出关键线程或缩短关键路径
```

#### B. 责任线程在等待其他执行单元

常见信号：BLOCKED、WAITING，栈中出现 monitor、Latch、Future、join 等。

```text
责任线程
→ 在等待什么条件或资源
→ 谁负责释放锁或完成条件
→ 那个线程为什么没有完成
```
#### C. 当前样本不能解释超时

常见信号：责任线程 `nativePollOnce`、缺失栈、采样过晚，或者只有系统因素假设但没有系统证据。

```text
不强行归因
→ 换同聚类样本
→ 检查其他责任线程
→ 有条件时补系统 trace
→ 平台没有相关信息时明确记录“证据不足”
```

## 5.鸿蒙FFmpeg
### 5.1 介绍
#### 项目全景

鸿蒙版本上线时，巡店模块沿用 H5 方案。受 Web 能力边界限制，语音对讲、录像下载、视频加水印等核心功能未能实现。华为在联合沟通群中多次发出整改警告，团队未在要求期限内完成补齐，最终版本被下架。下架事件使功能补齐从普通迭代升级为影响版本上架的紧急任务。

本项目聚焦录像下载与视频加水印。目标不只是补两个页面功能，而是在鸿蒙端建设统一媒体处理底座，让业务层通过 ArkTS API 调用录像下载、水印、转码等能力。

我独立负责技术调研、方案设计、功能开发、FFmpeg 源码修改、性能优化、测试验证及插件发布。平台沟通不由我负责；语音对讲虽由我参与，但不纳入本项目说明。

#### 为什么选择 FFmpeg

录像下载不是普通 HTTP 文件下载。应用先通过取流接口获取设备 RTSP 地址，按业务策略使用主码流、不使用辅码流，再把 RTSP 媒体流保存为本地 MP4。

视频加水印需要把图片叠加到视频画面。画面像素发生变化，处理链路必须包含视频解码、图片合成、重新编码和文件封装。

团队调研过“网络模块拉流 + OpenGL 图像处理 + 系统编解码与封装”的组合方案。OpenGL 是图形渲染 API，不负责 RTSP 协议、媒体解复用、编解码和 MP4 封装。

组合方案理论可行，但需要拼接多套组件，自行维护时间戳、数据流、状态和异常。面对紧急整改周期，这条路线开发及维护成本过高。

FFmpeg 统一覆盖网络协议、解复用、编解码、滤镜和文件封装。录像下载与图片水印都能通过 fftools 命令完成，还能承载后续媒体处理需求，因此被选为鸿蒙端统一基础能力。

#### FFmpeg 的核心能力

FFmpeg 不是单个“视频处理内核”，而是一组媒体库：

| 模块 | 核心职责 | 本项目用途 |
| --- | --- | --- |
| `libavformat` | 协议、I/O、解复用、封装 | 读取 RTSP，输出 MP4 |
| `libavcodec` | 音视频编解码 | 解码输入视频，编码水印结果 |
| `libavfilter` | 音视频滤镜 | 使用 `overlay` 合成图片水印 |
| `libavutil` | 时间戳、日志、内存与公共结构 | 支撑各模块运行 |
| `libswscale` | 缩放与像素格式转换 | 适配滤镜和编码输入 |
| `libswresample` | 音频重采样 | 仅在音频转换场景使用 |

直接调用 `libav*` 需要自行管理输入输出、编解码器、数据帧和错误状态。FFmpeg 源码中的 `fftools` 已把这些能力封装成命令行工具，负责解析参数并编排完整处理流程。

#### 从 Mac 命令到鸿蒙 Native 调用

Mac 终端执行命令时，Shell 把命令拆成 `argc / argv`，启动独立 `ffmpeg` 进程。fftools 接收参数、驱动 `libav*`，完成后通过退出码结束进程。

```text
Mac Shell
  -> ffmpeg main(argc, argv)
  -> fftools
  -> libav*
  -> exit(ret)
```

鸿蒙应用不能直接复用桌面进程模型。项目把 fftools 编入 Native 动态库，将 `main(argc, argv)` 改造成可调用的 `exe_ffmpeg_cmd(argc, argv)`，再通过 AKI/NAPI 暴露给 ArkTS。

```text
ArkTS 命令数组
  -> AKI/NAPI
```
