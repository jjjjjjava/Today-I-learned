### 2.2 线上定位方向

这个任务由 Leader 交给我们处理。接到任务后，我们没有立即尝试在线下复现，而是先查看线上各个启动阶段的耗时，初步判断可能的优化方向。

从线上启动链路的 Span 数据来看，`Stage_home_build` 在 P50 和 P90 中的耗时占比都比较高，其中 P90 耗时达到了 1.9s，是启动链路中最主要的耗时阶段之一。

`Stage_home_build` 覆盖了首页从 `onCreate` 开始，到页面首次渲染完成的整个构建过程。因此，我们初步将首页构建和渲染链路确定为重点排查方向，并提出了几个猜想：

1. 首页的 View 层级或者布局嵌套过深，导致 View 树过重，增加了 `measure` 和 `layout` 的耗时；
2. 布局实现不够合理，例如频繁嵌套 RelativeLayout，可能触发多次测量，可以考虑使用 ConstraintLayout 扁平化布局层级；
3. 首页本身是一个重页面，ViewPager 中包含了多个 Fragment，可能存在页面预加载过多、没有真正实现懒加载的问题。

带着这些猜想，我们进入了线下复现和验证流程。
### 2.3 Tinker 热修复原理

在应用启动的 `bindApplication` 流程中，系统创建 `TinkerApplication` 并调用其 `attachBaseContext()`，Tinker 会在这里尝试加载补丁。

低版本将补丁 `dexElements` 插入原 AppClassLoader 搜索数组头部；高版本创建新的 Tinker ClassLoader 作为后续类加载入口，并保留原 ClassLoader 兜底。这样业务类首次加载时会按照“系统类 → 补丁 Dex → 原 APK Dex”的顺序查找，同名类优先由补丁 Dex 定义，后续调用的自然是修复后的方法实现。它并非替换已经加载的旧类，因此通常需要重启进程生效。

比如：
假设原 APK 中有：

```
class LoginManager {
    boolean isVip() {
        return false; // Bug
    }
}
```

补丁 Dex 中有同名类：

```
class LoginManager {
    boolean isVip() {
        return true; // 修复后
    }
}
```

### 2.4 DAG 任务编排（后续优化思路）

针对 `Application.onCreate()` 中大量 SDK 串行初始化的问题，我们还考虑过使用 DAG 做进一步治理。不过这个方案目前没有正式落地，主要停留在初步设计阶段。

我们项目启动时涉及 Network、个推、WebRTC 和地图等 SDK。初步思路是将每段初始化逻辑抽象成一个任务，并为任务声明前置依赖、执行线程和业务优先级。例如，Network 内部的 API 配置、HTTP Manager、OkGo 和 Token Header 存在一定的先后关系，可以组成一条启动关键链；如果个推初始化依赖 Network 或 Token，就在对应的前置任务完成后执行。地图和 WebRTC 如果与 Network 没有依赖，而且首页不会立即使用，就可以作为独立节点，不再串行阻塞 `Application.onCreate()`，而是在对应的业务入口前完成初始化。

拓扑排序发生在 `Application.onCreate()` 收集完任务并构建依赖图之后。调度器先统计每个任务的入度，优先执行入度为零的任务；任务完成后，再减少其后继任务的入度。当后继任务的入度变为零时，就将其加入可执行队列。这样既能保证存在依赖的任务按照正确顺序执行，也能让互不依赖的任务并行或者延迟执行。

### 2.5 Baseline Profile 优化

启动过程中还可以通过 Baseline Profile 进行优化。

Java代码有一个特性：一次编译到处执行，原理就是：编译的产物是字节码文件，执行则是依靠解释器翻译成对应机器平台的机器码的形式。还有JIT优化的形式，将高频使用的字节码直接编译为对应平台的机器码。

Android 应用的 Java、Kotlin 代码最终会被编译成 DEX 字节码。其方法是ART 在运行时会先通过解释器执行；当方法达到一定热度后，再通过 JIT 将其编译成当前设备平台的机器码。

Baseline Profile 会记录启动关键路径中涉及的类和方法，并将这些规则随安装包一起发布。应用安装时，ART 可以根据 Profile 对这些关键方法进行 AOT 编译。这样在首次启动时，关键方法就能直接执行已经编译好的机器码，从而减少解释执行和运行时 JIT 编译的成本。

### 3.2 一轮处理
![[5369b011fc74d28f4005930954c56c58_compress.jpg]]
#### 1. 路由表生成

运行时查的 RouteMeta 并不是启动时动态分析业务类得到的，而是在编译期生成。

**1.RouteProcessor 扫描 `@Route`**

业务页面声明：

```kotlin
@Route(path = "/user/login")
class UserLoginActivity : Activity()
```

Java 注解处理阶段会调用 ARouter 的 `RouteProcessor`。Kotlin 项目通常通过 kapt 接入这个 Java 注解处理器。

编译器会把当前轮次的信息封装在 **RoundEnvironment** 中。处理器通过：

```java
roundEnv.getElementsAnnotatedWith(Route.class)
```

取得所有被 `@Route` 标注的 **Element**。

Element 不是运行时的 `UserLoginActivity.class`，而是编译期对该类型的结构化描述。处理器可以从中取得：

```text
类型名和包名
父类与实现接口
注解
成员信息
```
**2.生成RouteMeta**
`RouteProcessor` 会结合注解与类型工具提取封装成 RouteMeta，并按 group 整理：

```text
user group
├── /user/login → RouteMeta(UserLoginActivity.class)
└── /user/profile → RouteMeta(UserProfileActivity.class)
```

**3.JavaPoet 生成路由表 Java 类**

APT 负责扫描和分析，**JavaPoet** 负责生成 Java 源文件。核心生成类包括：

```text
ARouter$$Group$$user
    loadInto(routes)：写入 path → RouteMeta

ARouter$$Root$$app
    loadInto(groupsIndex)：写入 group → Group Class

```

完整生成链是：

```text
@Route
→ RouteProcessor 扫描
→ RoundEnvironment 提供当前轮次元素
→ 解析 Element 与注解
→ 封装 RouteMeta
→ 按 group 整理
→ JavaPoet 生成 Group / Root / Provider 等 Java 类
→ Java/Kotlin 编译产出 Class
→ 后续进入 Dex
```

到这里，路由表已经“存在于安装包中”，但 ARouter 初始化仍然要解决一个问题：**怎样找到这些生成类并调用 `loadInto()`？**
#### 2. 路由表加载
这里有两层字符串判断：

```text
第一层：className.startsWith("com.alibaba.android.arouter.routes")

第二层：
ARouter$$Root$$...         → Root
ARouter$$Providers$$...    → Provider
ARouter$$Interceptors$$... → Interceptor
```

因此，默认模式确实主要依靠**类的全限定名**做包名和生成类名前缀匹配

但真正昂贵的不是 `startsWith()`：为了执行这几个很轻的字符串判断，前面必须先找到所有 Dex、打开它们，并枚举其中的全部类名。项目 Dex 越多、类越多，发现少量路由表类付出的全量扫描成本越高。

本项目 APK 体量超过 400MB，同时 Dex 和类规模较大。这个项目事实用于说明扫描成本为何被放大；它不等于“Dex 文件本身有 400MB”。

#### 3. 方案设计
| 方案     | 能否消除 Dex 扫描 | 主要问题                                     | 结论    |
| ------ | ----------- | ---------------------------------------- | ----- |
| 异步初始化  | 不能          | 成本仍在；首个路由请求可能早于初始化完成，需要等待或兜底             | 不治本   |
| 更换路由框架 | 可以绕开        | 页面、Provider、Interceptor、多模块调用迁移范围大，回归风险高 | 成本过高  |
| 恢复插件注册 | 可以          | 需要解决新 AGP 的构建兼容                          | 最贴近根因 |

最终选择 register 插件方案。

它的本质是把“启动期打开 dex、遍历类名找 routes 类”替换成“运行时执行 `loadRouterMap()` 里的简单 `register(...)` 方法调用”。也就是把重扫描从运行时挪到编译期，启动时不再逐个打开 dex，所以耗时会明显缩短。

#### 4. 方案验证
验证要从运行路径、功能、对照实验和线上指标四层闭合，不能只说“启动变快了”。

运行路径验证

`loadRouterMap()` 本身无论是否插桩都能正常执行，所以“方法调用成功”不是插件生效的证据。需要确认其中的 `register()` 真正被执行。

```text
loadRouterMap() 执行 register()
→ registerByPlugin 被置为 true
→ 不进入 ClassUtils.getFileNameByPackageName()
→ 不再打开和遍历 Dex
```

#### 4.LogisticsCenter **插桩**

1.为什么必须先扫描全部 Class
插件还要从全部输入中定位：

```text
com/alibaba/android/arouter/core/LogisticsCenter.class
```

找到后不会立即插桩，而是先缓存原始字节码。原因是 Class 遍历顺序不确定：

```text
可能先遇到 LogisticsCenter.class
→ 当时只收集到一部分 Root / Provider / Interceptor
→ 如果立即插入 register()
→ 后面才遇到的路由表类会永久遗漏
```

正确过程必须分成两阶段：

```text
阶段一：扫描全部 Class
├── 收集完整 Root / Provider / Interceptor 类名
├── 缓存 LogisticsCenter 原始字节码
└── 复制其他 Class

阶段二：统一修改 LogisticsCenter.class
├── 使用完整类名集合插入 register()
└── 输出修改后的 LogisticsCenter.class
```

这里缓存的目的不是性能优化，而是解决**遍历顺序与全量信息依赖**：插桩结果依赖全部扫描结果，所以必须等信息完整后再生成。

2.Visitor 链各自负责什么

修改目标时使用：

```text
ClassReader
→ ClassVisitor
→ MethodVisitor
→ ClassWriter
```

职责分别是：

| 组件 | 职责 |
|---|---|
| `ClassReader` | 解析 `LogisticsCenter.class` 的结构和方法字节码 |
| `ClassVisitor` | 遍历类，并在 `visitMethod()` 中找到 `loadRouterMap()` |
| `MethodVisitor` | 遍历目标方法的 JVM 指令，在返回点插入新指令 |
| `ClassWriter` | 输出修改后的 Class 字节数组 |

3.两条关键 JVM 指令

Java 等价代码是：

```java
LogisticsCenter.register(
    "com.alibaba.android.arouter.routes.ARouter$$Root$$app"
);
```

ASM 插入的不是 Java 源码，而是 JVM 指令。

第一步，用 `LDC` 把类名字符串压入当前方法的操作数栈：

```kotlin
methodVisitor.visitLdcInsn(className)
```

第二步，调用静态方法：

```kotlin
methodVisitor.visitMethodInsn(
    Opcodes.INVOKESTATIC,
    "com/alibaba/android/arouter/core/LogisticsCenter",
    "register",
    "(Ljava/lang/String;)V",
    false
)
```

五个参数分别表示：

```text
INVOKESTATIC：静态方法调用
owner：LogisticsCenter 的 JVM 内部类名
name：register
descriptor：(Ljava/lang/String;)V
isInterface：false
```

最后 `ClassWriter` 输出修改后的 `LogisticsCenter.class`，替换原始版本，再交给 D8。
#### 5. 为何有问题
`.class` 文件头包含 major version，用来表示该 Class 格式对应的 Java 版本。关键对应关系是：

```text
Java 17 → major version 61
Java 21 → major version 65
```

ASM 的 `ClassReader` 构造时要先读取并校验这个版本，确认当前 ASM 是否支持解析该格式。原插件使用的 ASM 较旧，不认识 major version 65，于是抛出：

```text
Unsupported class file major version 65
```

异常发生顺序是：

```text
读取 Class 文件头
→ 检查 major version
→ 发现超出旧 ASM 支持范围
→ 直接抛异常
```

此时还没有进入：

```text
ScanClassVisitor.visit()
ClassVisitor.visitMethod()
MethodVisitor.visitInsn()
ClassWriter
```

准确根因是：

> 插件运行时使用的旧 ASM `ClassReader` 无法解析 Java 21 生成的 Class 文件。

#### 6. 解决方案
1.升级完整 ASM 依赖族

```kotlin
implementation("org.ow2.asm:asm:9.7")
implementation("org.ow2.asm:asm-commons:9.7")
implementation("org.ow2.asm:asm-tree:9.7")
```

三个模块保持同一版本，避免核心解析、工具类和 Tree API 之间出现版本错配。

2.Visitor API 调整为 ASM9

```text
Opcodes.ASM7 → Opcodes.ASM9
```

这里的 API 常量表示 Visitor 按哪个 ASM API 级别工作。它和 `ClassReader` 能否解析 major version 是相关但不同的两层：只改常量、仍运行旧 ASM Jar，无法让旧 `ClassReader` 突然认识 Java 21。
3.修改一个api

### 4.3  如果没有 ANR

如果没有 ANR，App 卡住后，用户无法判断是短暂卡顿还是永久死锁，只能反复点击或强杀进程；系统也没有统一标准判断应用只是慢，还是已经无法响应；开发者事后还拿不到当时的线程现场。

所以 ANR 要回答的是：系统交给 App 的有时限关键任务，是否在规定时间内完成。如果没完成，那么给用户弹框和反馈，给开发者dump对应的线程现场

### 4.4 ANR 的设计思路：从 Linux Watchdog 到埋雷、拆雷、爆雷

> Linux Watchdog：派发任务并开始计时 → 按时完成就“喂狗”取消超时 → 没有喂狗则判定失去响应

```text
映射到组件类 ANR：
埋雷 → system_server 派发任务，记录时间并安排超时检查
拆雷 → App 完成任务，通过 Binder 通知 system_server 销账
爆雷 → 超时检查触发，复查任务仍未完成，进入 ANR
```

> 计时和判定放在 `system_server`：App 卡死后无法可靠监控自己，裁判必须在被检测进程之外。

### 4.5 Service ANR 源码例子

```text
埋雷：
startService → AMS / ActiveServices
→ bumpServiceExecutingLocked
→ 记录 executingStart，加入 mExecutingServices
→ 集合空→非空时 postDelay一个延迟消息充当炸弹到AMS的消息队列中。

拆雷：
scheduleCreateService → App Binder 线程
→ ActivityThread.mH → 主线程反射创建service执行 Service 生命周期
→ serviceDoneExecuting
→ executeNesting--，归零后移出 mExecutingServices
→ 集合为空时移除超时消息

爆雷：
serviceTimeout
→ 找 executingStart 最早的 Service
→ 确认超过前台 20s / 后台 200s
→ appNotResponding
```

> 三个提示：
>
> 1. 一个进程只有一颗 Service 雷。
> 2. `executeNesting` 判断单个 Service；`mExecutingServices` 是否为空决定能否拆雷。
> 3. 超时消息只是检查触发器，`executingStart` 是否真正超时才是判据。

### 4.6 Input ANR 源码例子

> Input 不走消息队列的形式，而是for-loop事件流，因为执行频率太高了。而由 `InputDispatcher` 持续检查：事件发出是埋雷，App 返回 ACK 是拆雷，等待超时就是爆雷。

```text
内核 /dev/input
→ InputReader
→ mInboundQueue
→ InputDispatcher / outboundQueue
→ Socket 发给 App，并进入 waitQueue
→ InputEventReceiver → ViewRootImpl → View
→ finishInputEvent 返回 ACK
→ 从 waitQueue 移除

超时：
dispatchOnce 检查 waitQueue 头部
→ now - eventTime ≥ 5s
→ onANRLocked → appNotResponding
```

> 三个提示：
>
> 1. `mInboundQueue` 待分发，`outboundQueue` 待发送，`waitQueue` 已发送待 ACK。
> 2. 输入高频、低延迟，所以使用独立 Reader/Dispatcher 线程和 Socket，避免占满 Binder 线程池。
> 3. 从 `eventTime` 起算，系统排队、传输、App 处理和 ACK 全部计入 5 秒。

### 4.9  主线程状态 + 堆栈状态分析
- `RUNNABLE`：不等于 CPU 满载。继续看栈中是否有业务计算、图片处理、文件或数据库 IO、同步 Binder。Camera 案例就是主线程执行 `Bitmap.compress` 和文件写入。

- `BLOCKED`：表示主线程在等待进入 Java monitor。先找到锁的持有者，再看持锁线程是在执行耗时任务、等待另一把锁，还是已经形成 AB-BA 死锁。

- `WAITING`：表示等待条件成立。看到 `Object.wait` 找谁负责 `notify`；看到 `CountDownLatch.await` 找谁负责 `countDown`；看到 `Future.get` 找任务为何未完成；看到 `Thread.join` 找被等待线程为何不退出。

- `NATIVE`：它是平台展示或栈形态，不是独立的 Java 线程状态。必须继续读 native 栈顶：`transactNative` 看 Binder，`read/write/fsync` 看 IO，`futex/pthread_mutex` 看锁，`pthread_join` 看被等待线程。

#### RUNABLE
`RUNNABLE` 容易被误读为“线程正在占满 CPU”。实际上，它可能处于以下情况：

- 正在执行 Java/Kotlin 计算；
- 执行文件 IO、数据库或图片处理；
- 进行同步 Binder 调用；
- 可以运行但暂时没有被 CPU 调度；

所以看到 RUNNABLE 后，继续读栈顶和业务调用链。

 栈顶是计算

```text
main  RUNNABLE
→ sortLargeList
→ buildPageData
→ Activity.onCreate
```

方向是主线程计算过重。接下来检查数据规模、算法复杂度、循环以及它是否位于启动或输入响应的关键路径。

栈顶是 IO

```text
main  RUNNABLE
→ FileOutputStream.write
→ saveImageToGallery
→ CameraClickActivity
```

方向是主线程阻塞 IO。这与 `CameraClickActivity` 案例一致：页面聚集负责选出排查范围，有效单点栈把问题指向保存相册路径，结合源码再确认该调用运行在主线程。

栈顶是 Binder

```text
main  RUNNABLE
→ BinderProxy.transactNative
→ BinderProxy.transact
→ 某系统服务或远程服务接口
```

方向是同步 Binder 调用返回过慢。此时不能只说“主线程 Binder 导致 ANR”，还要继续判断远端进程、Binder 线程池或 system_server 为什么没有及时返回。

因此 RUNNABLE 的工作结论应写成：

> **责任线程采样时正在某条调用路径中；根据栈顶判断计算、IO 或 Binder 方向，再用更多证据确认它是否持续得足够久。**

#### BLOCKED：正在竞争 Java monitor

`BLOCKED` 通常表示线程正在尝试进入一个 `synchronized` monitor，但锁被其他线程持有。

典型 trace 会给出类似信息：

```text
main  BLOCKED
waiting to lock <0x0fd09ed5>
held by thread 58
```

这时能确定的直接原因是：

> 主线程需要锁 A，但锁 A 当前由线程 58 持有，所以主线程无法继续执行。

此时核心看的部分不是主线程，线程 58 才是下一步真正要看的对象：

- 它是否在锁内执行耗时 IO 或计算？
- 它是否在等待另一把锁？
- 它是否又通过某条依赖链等待主线程？
- 它持锁的代码是否属于自有代码或三方 SDK？

所以 `BLOCKED` 不等于“找到根因”。它只是给出了第一条明确的依赖边：

```text
main → 等锁 A → A 由线程 58 持有
```

极验登录：AB-BA 死锁

> main 等锁 A → 线程 58 持有 A、等待 B → 线程 54 持有 B、等待 A → 闭源三方库死锁

极验把联通一键登录的带锁任务提交到主线程，联通内部两个线程加锁顺序相反，形成 AB-BA 死锁，主线程也因此永久等待。由于根因在闭源三方库，只能反馈厂商或更换方案。

#### WAITING：在等一个条件，不一定是等 synchronized 锁

`WAITING` 表示线程正在等待某个条件成立。它与 `BLOCKED` 的排查方向不同：

- `BLOCKED` 是为了进入 `synchronized` 临界区而等待获得锁，重点查“谁持有这把锁”；
- `WAITING` 是等待某个状态改变、任务完成或线程结束，重点查“谁负责让条件成立”。

常见的等待条件可以归纳为以下四类：

| 等待的条件  | 常见栈/API                                    | 谁负责让它继续                              |
| ------ | ------------------------------------------ | ------------------------------------ |
| 共享状态改变 | `Object.wait()`                            | 修改共享状态后调用 `notify()` / `notifyAll()` |
| 一组任务完成 | `CountDownLatch.await()`                   | 一个或多个任务调用 `countDown()`              |
| 异步结果完成 | `Future.get()` / `CompletableFuture.get()` | 执行任务的线程完成、失败或取消                      |
| 另一线程结束 | `Thread.join()`                            | 被 `join` 的线程退出                       |

 IJK 播放器：主线程等待音频线程退出
 我们查到：VideoSplitAllActivity，VideoPlayActivity。多个，然后共性分析发现走的同一个巩固组件库

> 公共播放器组件 → main `pthread_join` → 音频线程阻塞在 `AudioTrack.write` → 后台释放播放器

多个视频页面的公共栈最终都落到播放器释放。代表 issue 中，主线程的完整调用链是：

```text
main
→ VideoPlayChildView.onDetachedFromWindow
→ VideoPlayChildView.stopPlay
→ IjkPlayView.stopPlayback
→ IjkMediaPlayer.release
→ ijkmp_shutdown_l
→ ffp_wait_stop_l
→ SDL_AoutCloseAudio
→ SDL_WaitThread
→ pthread_join
```

被等待的音频线程同时停在：

```text
IJK audio thread
→ AudioTrack.write
→ AudioTrack::obtainBuffer
→ ClientProxy::obtainBuffer
```

`pthread_join` 说明主线程正在等待音频线程退出；音频线程必须先从阻塞式 `AudioTrack.write()` 返回，才能检查退出标记。
修复没有删除正常释放流程，而是让 UI 先放弃旧播放器，再把 `stop()` 和 `release()` 整体移到后台线程。

#### Native

采样时，线程已经从 Java/Kotlin 调用栈进入了 native 层。一般来说是进入系统调用或者走到so的代码

 MessageQueue.nativePollOnce
 BinderProxy.transactNative


```text
main
→ BinderProxy.transactNative
→ BinderProxy.transact
→ PackageManager.getPackageInfo
→ 业务代码
```

这里是业务代码同步调用PackageManager系统服务，然后进入 Binder 的 native 实现，等待远端返回。这类 Native 栈可能非常有价值。需要继续检查调用了什么服务，以及对端为什么没有及时返回。
native 文件读写

```text
main
→ read / write / fsync
→ FileInputStream / FileOutputStream
→ 业务代码
```

可能是 Java 文件 API 最终进入 native 系统调用，也可能是 App 或 SDK 的 `.so` 在读写文件。

futex、pthread_mutex
这表示线程可能在 native 层等待锁。此时要找哪个线程持有 native 锁，以及持锁线程正在做什么。

因此，排查 Native 栈时要同时看两部分：

```text
native 栈顶：当前具体在 poll、transact、read、futex，还是计算？
Java 调用链：是谁把线程带进这个 native 方法的？
```
### 4.10 归因后的归并处理

我们要将上面归并为三个实际的可能方向

#### A：主线程自己执行太久

常见信号：RUNNABLE，栈中出现业务计算、IO、图片处理、数据库或 Binder。

```text
责任线程
→ 当前执行什么
→ 为什么这段工作会这么久
→ 能否移出关键线程或缩短关键路径
```

#### B：主线程等待其他执行单元

常见证据是 `BLOCKED`、`WAITING`、`futex`、`pthread_mutex`、`pthread_join` 或同步 Binder。不能停在“主线程正在等”，还要继续追：它在等谁、谁负责释放锁或完成条件、对方为什么没有完成。

处理方向是沿依赖链找到最终责任方，然后看责任方为什么被卡住？再统一加锁顺序、缩短持锁范围、移除主线程同步等待，或者调整线程边界。极验死锁和 IJK 播放器释放属于 B 类。

#### C：当前样本无法解释超时

常见情况是主线程只有 `nativePollOnce`、堆栈缺失、采样过晚，或者只有“低端机、系统负载”等相关性，没有时序证据。此时不强行归因，换同聚类样本或补系统 Trace；仍然无法证明就明确记录证据不足。

最后可以用下面这条线收口：

```text
代表 issue
→ 现场是否有效
→ 主线程状态与完整调用栈
→ 归并 A / B / C
→ 直接原因
→ 沿执行或依赖链找到最终责任方
→ 修复与反向验证
```

### 4.11 小结
总结来看，线上 ANR 治理不能从单条 Trace 直接猜测根因，而要建立从批量问题到单点证据的分层归因流程。通过共性分析和爆发分析初步判断问题的核心影响因子；随后选择代表 issue，沿主线程状态、完整调用栈和线程依赖链定位最终责任方。

整个过程中，我们串联了Bugly原理， Service、Input ANR 的埋雷、拆雷与爆雷机制，介绍了 `RUNNABLE`、`BLOCKED`、`WAITING` 和 Native 栈的判断方法，并将问题归并为主线程执行过久、等待其他执行单元或当前证据不足三类。最终沉淀的不只是同步 IO、死锁或线程等待的单点修复，而是一套从告警确认、共性与爆发归因、有效现场筛选、单点依赖追踪到修复后反向验证的线上 ANR 的成体系的治理方法。

### 5.2 问题分析
![[ba1b2ac765856dc58475af071289d071_compress.jpg]]
### 5.3  技术选型

> RTSP 录像：读取 → 重封装 MP4
>
> 图片水印：解码 → overlay 合成 → 重新编码 → MP4 封装

录像下载可以直接重封装，但水印改变了画面像素，必须重新编解码。相比自己组合网络、OpenGL、编解码和封装模块，FFmpeg 能统一覆盖整条媒体链路，更适合当时紧急整改和后续复用。

### 5.3 技术原理
FFmpeg 不是单个“视频处理内核”，而是一组媒体库：`libavformat``libavcodec``libavfilter``libavutil``libswresample`

直接调用 `libav*` 需要自行管理输入输出、编解码器、数据帧和错误状态。FFmpeg 源码中的 `fftools` 已把这些能力封装成命令行具，负责解析参数并编排完整处理流程。

Mac 终端执行命令时，Shell 把命令拆成 `argc / argv`，启动独立 `ffmpeg` 进程。fftools 接收参数、驱动 `libav*`，完成后通过退出码结束进程。

```text
Mac Shell
  -> ffmpeg main(argc, argv)
  -> fftools
  -> libav*
  -> exit(ret)
```

鸿蒙应用不能直接复用桌面进程模型。我们可以启动native线程执行上面的任务项目，在arkts层去通过napi技术调用到native层的线程执行命令。    把 fftools 编入 Native 动态库，将 `main(argc, argv)` 改造成可调用的 `exe_ffmpeg_cmd(argc, argv)`，再通过 AKI/NAPI 暴露给 ArkTS。

```text
ArkTS 命令数组
  -> AKI/NAPI
  -> exe_ffmpeg_cmd(argc, argv)
  -> fftools
  -> libav*
  -> 返回码与回调
```


### 5.3 四个技术难点

#### 难点一：OpenHarmony 交叉编译与 fftools 嵌入

**难点：** FFmpeg 原本是桌面命令行程序，鸿蒙 App 不能直接启动并复用它的进程模型，需要把 fftools 和 `libav*` 编译成 鸿蒙系统 能调用的 Native 产物。

**处理：** Lycium 是 OpenHarmony C/C++ 三方库适配与构建框架，里面有HPKBUILD，负责组织源码、配置、交叉编译和产物管理，本身不是编译器。OpenHarmony SDK/NDK 中的 LLVM、Clang 和链接器是真正执行交叉编译的工具链。

项目通过华为工单获取 OpenHarmony 适配版 FFmpeg 源码，基于 Lycium 修改 `HPKBUILD`，开启 RTSP、封装、滤镜及编解码等所需配置，最终把 FFmpeg 核心能力与 fftools 聚合为单一 `.so`。

#### 难点二：fftools 会结束宿主进程

**难点：** 命令行程序执行完成后调用 `exit(ret)` 很正常，但 fftools 嵌入 `.so` 后，`exit()` 会直接结束整个 App。

**处理：** 在函数入口通过 `setjmp` 保存返回点，深层 `exit_program` 改为 `longjmp` 回到入口；先保存返回码，再执行 `reset_ffmpeg_state`，最后把结果返回 C++ 桥接层。由于全局状态仍非线程安全，上层保持串行执行。

#### 难点三：ArkTS 与 Native 双向通信

#### 卡片一：核心原理

> 双向通信本质上做两件事：跨语言类型转换，以及把任务交给正确的线程执行。

```text
去程：ArkTS 数据 → C++ 类型 → C 参数 → Native 线程执行
回程：C 回调 → C++ JSFunction → JS 线程执行
```

普通 `.so` 即使有 C++ 函数，ArkTS 也不知道怎样加载、导出和转换参数。因此需要 Native Addon 建立模块入口，再由 AKI 完成两端适配。

#### 卡片二：ArkTS 如何调用 Native

```cpp
JSBIND_ADDON(ffmpegutils)

JSBIND_GLOBAL() {
    JSBIND_PFUNCTION(executeFFmpegCommandAPP);
}
```

- `JSBIND_ADDON`：把 `.so` 注册成 ArkTS 可以导入的 Native 模块。
- `JSBIND_PFUNCTION`：把 C++ 方法挂到 `exports`，生成 Promise、参数转换和异步执行逻辑。
- `.d.ts`：只提供编译期类型，运行时函数由 Addon 和 `exports` 提供。

完整去程：

```text
ArkTS import .so
→ Addon 初始化 exports
→ 调用 executeFFmpegCommandAPP
→ AKI 转换参数
→ JSBIND_PFUNCTION 提交非 JS 线程
→ vector<string> 转 argc / argv
→ exe_ffmpeg_cmd → fftools
```

这里有两次转换：

```text
ArkTS string / number / string[]
→ std::string / int / vector<string>
→ char **argv
```

`P` 表示 Promise 异步函数，保证耗时任务不直接占用 JS 线程，但不代表每次调用都会创建一条新线程。

#### 卡片三：Native 如何回调 ArkTS

ArkTS 回调是 JS 虚拟机管理的对象，不能把它当成稳定的 C 函数地址。执行前先按 UUID 注册：

```text
JSBind.bindFunction(uuid + "_onFFmpegProgress", callback)
JSBind.bindFunction(uuid + "_onFFmpegSuccess", callback)
JSBind.bindFunction(uuid + "_onFFmpegFail", callback)
```

Native 使用相同 UUID 取回句柄：

```cpp
aki::JSBind::GetJSFunction(
    uuid + "_onFFmpegProgress"
);
```

fftools 是 C 代码，不认识 `aki::JSFunction`，因此通过纯 C 函数指针和 C++ 桥接：

```text
fftools
→ C 函数指针
→ C++ 桥接函数
→ thread_local 当前任务上下文
→ JSFunction.Invoke
→ AKI 调度 JS 线程
→ ArkTS 回调
```

进度由 fftools 在执行期间主动回调；成功和失败在 `exe_ffmpeg_cmd` 返回后，根据返回码选择对应的 JS 函数。

#### 难点四：硬件编码适配与参数链

**难点：** 两分钟视频加水印耗时约 150 秒，说明可能仍在软件编码；接入硬件编码后，开源用户又反馈 `-b:v` 码率参数不生效。

**处理：** 第一轮指定 `h264_ohosavcodec` ，从工单获取的硬编码指令，根据“codec 不存在”的 Native 日志确认当前 `.so` 没有编入鸿蒙硬件适配。补齐适配源码和构建配置、重新交叉编译后，处理时间从约 150 秒降低到 27 秒。

第二轮沿 ArkTS 命令、fftools 解析、Native 参数一路下钻，最终发现 `ohosvideoencoder.cpp` 没有把 `format_->bit_rate` 写入 `OH_AVFormat`。补写 `OH_MD_KEY_BITRATE` 后重新编译，并通过 `ffprobe` 验证视频轨码率。
现有测试记录：

| 样本 | 码率 | 文件大小 |
| --- | ---: | ---: |
| 原视频，6 分 48 秒 | 约 1012 kbps | 49.2 MB |
| 设置 `-b:v 500k` | 约 648 kbps | 31.5 MB |
| 设置 `-b:v 300k` | 约 440 kbps | 21.4 MB |

目标 `500k` 和 `300k` 控制的是视频轨码率。播放器或文件信息页显示的总码率，还包含音频轨码率与 MP4 封装开销。

因此不能仅用文件总码率判断 `-b:v` 是否精确。应分别检查视频轨与容器总码率：

```text
ffprobe -select_streams v:0 \
  -show_entries stream=bit_rate \
  -of default=noprint_wrappers=1 \
  output.mp4
```

若音频约为 `128k`，视频 `300k` 加音频与封装开销后，总码率接近 `440k` 是合理现象。这比简单归因于 VBR 更完整。

## 6.蓝牙配网
我做过一个智控平台项目，负责 ESP32 智能网关蓝牙配网功能。业务目标是：用户重置网关后，App 通过蓝牙找到设备，把 Wi-Fi 信息发送给网关，网关联网后再完成后台注册，最终进入设备首页。

技术上没有自己实现整套蓝牙协议，使用 Espressif 官方 `esp-idf-provisioning-android` SDK。我的工作主要是 SDK 接入、业务封装、状态管理和异常处理。官方 SDK 已经封装 BLE 扫描、GATT 连接、安全会话、Wi-Fi 扫描和配网能力。[Espressif SDK](https://github.com/espressif/esp-idf-provisioning-android)

我把 SDK 封装成 `ESP32DeviceManager` 和 `ESP32ConfigHelper`。上层只关心几个状态：扫描设备、连接设备、配置 Wi-Fi、检查注册结果。完整流程是：先申请蓝牙权限并扫描带指定名称前缀的设备；拿到设备广播中的 Primary Service UUID；连接 GATT 并发现服务；建立安全会话；把用户选择的 SSID 和密码交给 SDK；最后根据配网回调和设备 MAC 查询后台注册状态。成功进入设备页；密码错误允许原地重试；扫描失败、连接失败或超时则释放连接，返回设备重置或扫描页面。[项目流程记录](https://github.com/jjjjjjava/Today-I-learned/blob/master/%E9%A1%B9%E7%9B%AE/00.%20%E9%A1%B9%E7%9B%AE%E5%BD%92%E6%A1%A3/02.%20%E6%99%BA%E6%8E%A7%E5%B9%B3%E5%8F%B0_0729/04.%20feat_%E6%99%BA%E6%8E%A7%E5%B9%B3%E5%8F%B0_DeviceHome%E6%96%B0%E5%A2%9E%E7%BD%91%E5%85%B3%E8%AE%BE%E5%A4%87.md)

联调时遇到过一次典型问题：设备能扫描到，但连接时提示 `Service not found`，部分情况下出现 GATT 133。开始怀疑日志里不断变化的 UUID，后来确认那个是 Android 注册 GATT Client 时生成的标识，不是设备服务 UUID。继续按“扫描、连接、服务发现、会话建立、配网”分阶段看日志，最终定位到设备模型转换时丢失了广播中的 Primary Service UUID。修正 UUID 传递后，服务发现恢复正常。

还有一个容易误判的问题：Wi-Fi 信息发送成功后，ESP32 会断开 BLE 并重启连接路由器。这个断开不一定代表失败。因此最终成功标准不能只看蓝牙连接，而要看设备配网状态和后台注册结果。通过这次项目，我掌握了 IoT 配网业务闭环，也形成了按通信阶段定位 BLE 问题的方法。



## 7.串口
智控平台项目主要使用 BLE 配网，我没有直接负责串口模块。不过以前做 Linux 侧协议对接时接触过串口，理解串口通信原理和 Android 接入方式。

串口通常指 UART 异步串行通信。双方先约定波特率、数据位、停止位和校验方式，例如 `115200 8N1`，表示波特率 115200、8 个数据位、无校验、1 个停止位。发送一个字节时，会依次发送起始位、数据位、可选校验位和停止位。

UART 只解决字节传输。实际项目还要定义上层协议，例如帧头、数据长度、命令字、数据区和 CRC，用于拆包、校验及区分业务指令。

Linux 中，串口一般表现为 `/dev/ttyS*`、`/dev/ttyUSB*` 或 `/dev/ttyACM*`。程序通过 `open` 打开设备节点，用 `termios` 设置串口参数，再通过 `read/write` 收发数据。

Android 分两种情况。定制设备上的板载 UART，一般通过厂商 SDK，或者 JNI 调用 Linux 的设备节点接口；同时需要处理设备节点权限和 SELinux。普通手机连接 USB 转串口设备，则使用 Android USB Host API：枚举设备、通过 VID/PID 匹配、申请 USB 权限、打开设备并获取读写 Endpoint，然后在工作线程异步收发数据。

所以这部分我有原理和 Linux 侧使用经验，也清楚 Android 接入方案，但没有把它包装成自己在该项目中的实际产出。
