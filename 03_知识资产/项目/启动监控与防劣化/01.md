# 线上埋点与指标体系：把「实验室口径」搬到千万台真机上

> 前置知识：首页启动优化课程 01（TTID/TTFD 口径、bindApplication 起点）、02（Perfetto + marker 分工）
> 难度：进阶
> 预计阅读时间：15 分钟

## 正文内容

### 0. 先接上你的项目：你已经有口径了，缺的是「线上化」

在首页启动优化里，你做过一件最重要的事：**定口径**——`bindApplication` → `TTFD_HomeWorkDesk`，权限模块 View 添加并经下一次 draw 后打点。但那套度量是**线下的**：Perfetto 抓 trace、SQL 算耗时，一次只能测一台机器。

线上监控要回答的是另一个问题：**这个口径在一千万台真机上，P50/P90/P99 分别是多少，今天比昨天变了没有？**

Perfetto 不能上线上（全量插桩开销大、trace 文件几十 MB 没法回传），所以线上方案的本质是一次降级换取规模：

> **线下：全量细节 × 一台机器（Perfetto）；线上：关键点采样 × 千万台机器（埋点上报）。**
> 两者不是替代关系，是接力关系——线上发现「哪个阶段劣化了」，线下用 Perfetto 复现「具体是哪行代码」。

面试里这句对比是高分句，它说明你理解两套工具各自的适用边界。

### 1. 阶段切分：粒度决定归因能力

只报一个「启动总时长」，等于体检报告只写「身体不太好」。当 P50 从 1.2s 涨到 1.6s，一个总数无法告诉你该去查 SDK 初始化还是首屏布局。所以线上埋点第一原则：**分阶段**。

```
T0 进程创建
 → T1 Application.attachBaseContext
 → T2 Application.onCreate 完成
 → T3 Activity.onCreate
 → T4 首帧绘制（TTID）
 → T5 内容可交互（TTFD）
```

相邻两点的差值就是一个阶段的耗时，每个阶段对应明确的「嫌疑人」：

| 阶段 | 变长了该查谁 |
|------|-------------|
| T0→T1 | 系统侧（fork、dex 加载、MultiDex）——基本不可控，但要监控它以排除系统性波动 |
| T1→T2 | **ContentProvider 自动初始化 + Application.onCreate 里的 SDK**——劣化重灾区 |
| T2→T3 | 主线程消息队列被插队（Application 阶段 post 的任务） |
| T3→T4 | 布局 inflate、首帧 measure/layout/draw——你在首页启动优化 03 篇拆过的那些 |
| T4→T5 | 首屏数据加载、网络请求——「空壳陷阱」发生地 |

对应到你的项目：你线下归因出 inflate 106 次、RelativeLayout 双重测量都落在 T3→T4，门店页缓存优化的收益落在 T4→T5。**线上阶段埋点就是把你线下的归因框架固化成常驻雷达。**

实现上用一个轻量单例记录时间戳即可（关键点：用 `LongArray` 预分配而非 `HashMap`——启动路径上避免自动装箱、哈希计算和扩容分配；每个 mark 只是一次数组写入）。打点位置：`attachBaseContext`、`onCreate` 首尾、Activity `onCreate`、`OnPreDrawListener` 首帧回调、首屏内容 ready。

### 2. TTID vs TTFD：两个都要，缺一个就有盲区

- **TTID（Time To Initial Display）**：进程创建 → 第一帧绘制完成。系统自动测量，logcat 的 `Displayed` 行就是它。衡量「用户看到东西了」。
- **TTFD（Time To Full Display）**：进程创建 → 内容完整可交互。系统不知道你的「内容 ready」是什么时候，需要你自己调 `reportFullyDrawn()` 告诉它。衡量「用户能用了」。

**空壳陷阱**：只盯 TTID 的团队，会把数据加载全部异步化——TTID 漂亮了，但 SplashScreen 退出后用户对着一个转圈的空列表再等 2 秒。技术指标好，用户感知差。这正是你项目里选 TTFD 作主口径的原因：首帧可见 ≠ 首页工作台可见。

线上要**双指标同时采集**，而且第三篇会讲：`TTFD − TTID` 这个差值本身就是一条告警线——差值扩大意味着「壳出来了但内容变慢了」，通常是首屏接口或数据层劣化，纯看 TTID 完全发现不了。

`reportFullyDrawn()` 除了打日志，还会喂给系统的性能统计（Play Vitals、`ApplicationStartInfo`），并影响 Baseline Profile 对「启动路径」的界定——所以即使你有自建监控，也建议照调。

### 3. 🔧 机制一：T0（进程创建时刻）从哪来

埋点的起点是最微妙的：你的代码最早也要到 `attachBaseContext` 才能执行，但那时进程已经跑了几百毫秒（fork、绑定 Application、加载 dex）。**T0 必须问内核要，而不是自己记。**

**API 24+（Android 7.0）**：`Process.getStartElapsedRealtime()`，直接返回进程创建时刻（elapsedRealtime 时基）。⚠️ 原文写「API 33」是错的，这个 API 从 N 就有；现代 App minSdk 基本 ≥ 24，实践中直接用它即可。

**更低版本 / 理解原理**：读 `/proc/self/stat`。这个文件是内核暴露的进程统计，格式是 `pid (comm) state ppid ...` 共 50+ 个字段，其中第 22 个字段 `starttime` 是**进程创建时刻距系统启动的 clock ticks 数**。解析时先 `substringAfter(") ")` 跳过进程名（进程名本身可能含空格和括号，必须以右括号为锚点），再按空格切分后取 index 19（= 整体第 22 字段 − 前面被跳过的 2 个字段 − 0 起始下标）。换算：

```
startMs = starttime(ticks) × 1000 / sysconf(_SC_CLK_TCK)    // _SC_CLK_TCK 通常是 100，即 1 tick = 10ms
```

**为什么全链路统一 elapsedRealtime 时基？** 三个理由，面试追问必出：
1. `currentTimeMillis` 是墙钟，用户改时间、NTP 校时都会跳变，跨时间戳做差会算出负数或离谱值；
2. `uptimeMillis` 不含深度休眠时间，而 `/proc/self/stat` 的 starttime 是从内核 boot time 起算的（含休眠），只有 elapsedRealtime 和它同源可比；
3. 上报后要做的是**同设备内做差**（阶段耗时），不需要跨设备对齐绝对时间，单调时钟就是最优选择。

### 4. 🔧 机制二：Looper Printer——线上版的「谁在主线程捣乱」

阶段埋点告诉你「T1→T2 变长了」，但不知道是哪个 SDK 干的。线下你会开 Perfetto，线上的轻量替代是 **Looper 消息监控**。

原理：`Looper.loop()` 每分发一条消息，前后会调用你通过 `setMessageLogging(Printer)` 注入的 Printer：

```
分发前: ">>>>> Dispatching to Handler {...} callback {...} what=..."
分发后: "<<<<< Finished to ..."
```

在 Printer 里对这两条日志做时间戳差值，超过阈值（如 16ms）就抓主线程堆栈上报。开销几乎为零——每条消息只多两次字符串前缀判断和一次时间戳读取，**没有插桩、没有字节码修改**，可以全量常开在启动阶段。

配合阶段埋点就形成两级定位：**阶段埋点圈出「哪一段」，慢消息堆栈指认「哪个调用」**。第五篇实战案例（analytics SDK 的 `loadFromDisk()` 280ms）就是这么揪出来的。

但要主动讲出它的**两个局限**（面试官最爱追问「这方案有什么问题」）：

1. **堆栈时机滞后**：你是在消息**结束后**（收到 `<<<<< Finished`）才去抓堆栈的，此时慢代码已经执行完了，抓到的堆栈可能是消息末尾的无辜代码。严谨做法是像 Matrix 那样：子线程按周期对主线程采样，消息超时后回溯期间采到的堆栈。启动场景消息大多是「一个 init 占满整条消息」，简化方案够用，但要知道边界。
2. **唯一槽位冲突**：`setMessageLogging` 是覆盖式的单一 slot，不是监听器列表。如果接入的某个 APM SDK 也调了它，后设置的会把先设置的顶掉。兼容做法：设置前先取出已有 Printer，包一层代理把日志转发给它。

### 5. 收束成面试表达

被问「你们优化完之后怎么保证不回退」，第一段就可以这么讲：

> 「我们先把线下的口径线上化了。线下我用 Perfetto + marker 定义了 bindApplication 到首页工作台可见的 TTFD 口径，线上把这条链路切成进程创建、attach、Application、Activity、首帧、内容 ready 六个点位分阶段上报——进程创建时刻高版本用 `Process.getStartElapsedRealtime()`，低版本读 `/proc/self/stat` 的 starttime 换算，全链路统一 elapsedRealtime 时基。TTID 和 TTFD 双指标都采，防止『首帧快但内容慢』的空壳劣化。再配一个 Looper Printer 慢消息监控兜底，阶段埋点圈范围、慢消息堆栈指认代码，线上劣化可以直接定位到调用链。」

后面几篇会把 CI 卡口、灰度、组织机制接到这段话后面，拼成完整的防劣化叙事。

### 6. 补丁（对话修正，2026-07-06）

1. **点位跟责任边界走，不是死的 5/6 个**。本项目是 Splash → HomeOld 双 Activity 链，实际点位：attach → appOnCreate 首/尾 → Splash.onCreate → Splash 首帧 → startActivity(Home) 发起 → Home.onCreate → setContentView 完成 → Home 首帧（**业务 TTID**）→ TTFD_HomeWorkDesk。系统 `Displayed`/TTID 只算到**Splash 首帧**，必须与业务 TTID 分开命名；Splash→Home 跳转间隙要单独成段。
2. **TTID 具体埋法**：`decorView` 挂 `OnPreDrawListener`（即将首帧 draw，偏早）mark 一次，回调内再 `post` 到主线程队尾 mark 一次——当前 doFrame 消息执行完、绘制指令提交 RenderThread 后才轮到它，近似「首帧提交完成」。
3. **Printer 字段（handler/callback/what）认不出业务代码**：启动期消息大头是 `ActivityThread.H`（what=110 BIND_APPLICATION 等），十个 SDK init 挤在同一条系统消息里。字段只负责计时和粗分类，指认靠超阈值后的堆栈——Printer 是秒表，堆栈才是照片。
4. **堆栈滞后的严谨解法**：子线程周期采样主线程堆栈存环形缓冲（Matrix 思路），或 Dispatching 时子线程 postDelayed 看门狗到点抓栈、按时结束则取消——抓「执行中」而非「冲线后」的现场。
