## 正文内容

### 0. 为什么有了线上监控还要 CI 卡口：成本阶梯

线上监控再灵，发现劣化时**用户已经在承受了**，而且此时代码可能已经合入两周、上面又叠了十个 commit，回滚代价陡增。拦截劣化的成本是一条阶梯：

> **MR 合入前拦住（CI）≪ 灰度期发现（1%-5% 用户受影响）≪ 全量后回滚（全体用户 + 热修复成本）**

CI 卡口的目标就是把拦截点推到最左边：一个会导致启动劣化的 PR，**在合入 main 之前就被自动挡回去**，作者自己改，不用任何人追查。

### 1. 把 Macrobenchmark 变成「能自动判 pass/fail 的测试」

你在首页启动优化里用 Macrobenchmark 做过基准测量，CI 化的核心是加上**环境固定**和**判定规则**两件事。

**环境固定**——benchmark 数据的大敌是波动，CI 上必须消灭一切变量：

- 固定同一个 AVD 镜像（如 Pixel_6_API_33），`-no-snapshot-load` 冷启动模拟器；
- 关闭动画：`window_animation_scale`、`transition_animation_scale` 置 0（动画时长会直接混进 TTID）；
- 固定 `CompilationMode`（编译状态不同，同一份代码能差出 30%）；
- 真机农场则要 lock CPU 频率（`lockClocks`），防止温控降频污染数据。

**判定规则**——两个关键设计，面试必问：

- **取 P50 而非平均值判定**（iterations ≥ 5）：均值会被单次离群值（一次 GC、一次后台抖动）拉偏，P50 天然抗噪。
- **双轨阈值：绝对阈值 + 相对基线容忍度**。配置形如：

```json
{
  "cold_start_ttid_p50_ms": 1500,        // 绝对底线
  "regression_tolerance_pct": 10,        // 相对 main 基线不得慢超 10%
  "action": "block_merge"
}
```

为什么要两轨？只有绝对阈值，1499ms 的项目每个 PR 劣化 1ms 都能过，直到撞线那天没人知道该怪谁；只有相对容忍度，会被**温水煮青蛙**——连续十个 PR 各涨 9%，个个合规，累计翻倍。所以：相对容忍度拦「单次大劣化」，绝对阈值兜「累计越线」，缺一不可。基线本身用 main 分支最近 N 次运行的滚动中位数，避免拿单次波动当基准。

流水线上只在 MR 和 main 分支触发，benchmark 产物（JSON 结果）留档，由一个解析脚本和 thresholds 配置比对，超限直接 block merge。

### 2. Baseline Profile：容易被忽略的「隐形劣化源」

**机制一句话**：Baseline Profile 是一份「启动路径热点方法清单」，打包进 APK（`baseline-prof.txt`），安装时 ART 据此**直接 AOT 编译这些方法**——首次冷启动就跑机器码，跳过解释执行和 JIT 预热。没有它，新装用户的前几次启动要慢 20%-30%。

它和防劣化的关系在于一个隐蔽的事实：**Profile 会过期**。启动路径随代码演进不断漂移——重构改了类名、新首页组件上线、初始化顺序调整——半年前生成的 Profile 覆盖不到新热点，这些方法悄悄回到解释执行。结果是：**没有任何人写过一行慢代码，启动却在缓慢劣化**。这是一种纯粹的「不作为劣化」，线上曲线只会缓慢爬升，永远不会触发「突增」告警。

对策是把再生成自动化：CI 里加一个 **weekly job**，用 `BaselineProfileRule` 跑一遍「启动 + 首屏关键操作」的采集脚本，自动提 PR 更新 `baseline-prof.txt`。benchmark 侧用 `CompilationMode.Partial` 跑一组对照，顺便验证 Profile 还有收益。

### 3. CI 卡口的盲区：为什么绿灯了线上还会炸

这是本篇最重要的认知，也是你叙事里连接下一篇（灰度与线上监控）的桥：

- **模拟器 I/O 严重失真**：CI 模拟器的宿主机磁盘（NVMe SSD）比低端真机的 eMMC 快一个数量级。第五篇的真实案例：analytics SDK 的 `loadFromDisk()` 在 CI 上 30ms（绿灯通过），低端真机上 280ms（线上告警）；
- **没有厂商 ROM**：各家的启动管控、进程调度、后台冻结策略完全不同；
- **没有真实环境竞争**：真机上有几十个后台进程抢 CPU/IO，有存储碎片化、文件系统老化，模拟器一尘不染；
- **设备谱系单一**：CI 跑一两种配置，线上是几千种机型。

所以正确的定位是：**CI 卡口是粗滤网，拦「明确的大劣化」；线上监控是细筛，接住 CI 物理上测不到的部分。** 面试里被问「有了 CI 为什么还要线上监控」（或反过来），这一段就是完整答案。

### 4. 收束成面试表达

接在 01 篇那段「口径线上化」之后：

> 「光有监控只是事后发现，我们把拦截点前移到了 MR 合入前：CI 流水线跑 Macrobenchmark 冷启动基准，固定模拟器镜像、关动画、固定编译模式消除波动，5 次迭代取 P50，用双轨阈值判定——相对 main 基线劣化超 10% 直接 block merge，绝对阈值兜住累计越线，防温水煮青蛙。另外用 weekly job 自动重新采集 Baseline Profile 提 PR，防止启动路径漂移导致 Profile 过期这种『没人写慢代码但启动变慢』的隐形劣化。当然 CI 是粗滤网——模拟器的 I/O 比真机快一个数量级，所以真正兜底的还是灰度和线上监控。」

## 思考题

> 🔥 grill 模式：主问 + 追问一起答。

**第 1 题（数据可信度）**
主问：「CI 在模拟器上跑 benchmark，这数据能信吗？你们怎么控制波动？」
追问：「判定为什么用 P50 不用平均值？相对容忍度 10% 会不会被连续十个各涨 9% 的 PR 温水煮青蛙——你的体系里谁拦这个？」

**第 2 题（Baseline Profile）**
主问：「Baseline Profile 的原理是什么？没有它，新装用户的启动会经历什么？」
追问：「Profile 过期算不算一种劣化？它的劣化曲线长什么样，为什么『突增告警』永远抓不到它？你们怎么防？」

**第 3 题（体系推演）**
主问：「举一个 CI 绿灯但线上炸掉的真实场景，说清楚它为什么能骗过 CI。」
追问：「在你的完整体系里，这个劣化最终会在哪一环被逮住？从它合入到被修复，整条链路走一遍。」
