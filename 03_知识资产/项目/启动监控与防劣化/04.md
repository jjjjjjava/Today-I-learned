### 正确答案

**第 1 题主问（告警规则换位推演）：**
> 低端机用绝对阈值，因为它承载的是**体验底线**——底线天然是绝对概念（超过 4 秒用户就流失，不管相对昨天涨没涨）；而且低端机样本波动大，相对规则天天误报。大盘用相对突增，因为大盘 P50 的绝对值由**设备结构**决定（低端机占比高的渠道天然慢），定绝对阈值要么永远不响、要么天天响，而「1 小时涨 20%」这种形态只有真实事件（版本放量、配置错误、后端故障）才制造得出来。换过来的后果：大盘绝对阈值随设备结构漂移而失效；低端机相对告警被日常波动淹没，狼来了效应让告警失去信任。

**第 1 题追问（寒潮）：**
> 会误报——大面积低温降频会推高低端机 P90 触发 P2。救你的正是上报协议里的**环境字段**：拉出告警时间窗内样本的 `batteryLevel` / 温控字段分布，如果「低温/低电样本占比」同步突增而过滤掉这些样本后指标正常，就是环境性波动，不立劣化案。这就是「决策二：环境字段用来排除不可归因样本」的实战形态。

**第 2 题主问（只有低端机涨）：**
> 第一假设：新版本在 Activity.onCreate 路径上加了**资源敏感型工作**（同步磁盘 IO、重 inflate、CPU 密集计算）——高端机快到无感、低端机被放大。这正是 ANR 课设备轴的结论迁移：「环境没导致问题，环境把本就临界的代码戳破了」。验证路径三步：① 拉低端机 tier 该时间窗的慢消息堆栈聚合；② git 对比新版本 Activity.onCreate 及其调用链的变更；③ 线下拿低端真机 + Perfetto 复现确认。

**第 2 题追问（Top1 只占 12%、高度分散）：**
> 87% 集中 = **单一凶手**，某个具体调用变慢了，代码修复能解决。12% 分散 = **没有单点热点，是系统性变慢**——所有代码都均匀慢了一点。嫌疑方向完全不同：Baseline Profile 过期（解释执行普遍变慢）、依赖库/编译配置变更、设备结构漂移（低端机占比上升）、或进程外资源挤压。这对应你 ANR 课的判据「多样本落点随机且都是正常代码 → 推断环境/系统性原因」。**堆栈聚合的集中度本身就是归因信号。**

**第 3 题主问（两套三条件）：**
> 是同一套统计学工具（最小样本量防小数定律、观察窗口防周期波动、幅度阈值防把噪声当信号），但**防的误判方向相反**：ANR 收敛三条件防「其实没修好，却误判为修好了」（假疗效）；灰度劣化三条件防「其实是噪声，却误判为劣化」（假警报）。一个防止你过早庆祝，一个防止你冤枉正常版本。面试里能说出「同一套显著性检验思想，应用方向相反」，就把两门课焊在一起了。

**第 3 题追问（14.9% 扩不扩）：**
> 开放题，考的是「阈值是什么」的理解。要点：**阈值是触发人工判断的门，不是代替判断的开关**——14.9% 和 15.1% 在统计上没有本质区别，机械二分是自欺。决策依据看两个变量：① **归因进度**：如果已初步定位（比如确认是某个可开关的 SDK），风险可控可以小步扩；如果完全没头绪，涨幅贴着线更应该停——未知原因的劣化在更大样本上只会更清晰也更伤人；② **不可逆性不对称**：暂停扩量的代价是延期（可恢复），扩量后的用户伤害不可回收。所以贴线情况下的合理动作是：暂停 24 小时换取归因时间，或者带保护地扩（比如扩量名单排除低端机 tier）。答「按规定不满足就不扩」不算错，但说不出背后权衡的，面试评级上不去。

## 正文内容

### 0. 为什么最后一环是组织，不是代码

前三篇的工具链（埋点、CI、看板）都到位之后，劣化还是会回来，因为工具只能发现问题，**决定「谁在乎、谁负责、谁有权说不」的是组织机制**。文章开头那个故事的三个劣化来源——新同事加同步 SDK、实习生塞阻塞调用、紧急热修改回同步——没有一个是工具能预防的，全是流程和权责的缺口。启动优化最常见的死法是：优化 → 指标变好 → 领导满意 → 没人管了 → 慢慢劣化 → 再来一轮。打破循环靠四件组织手段，每件拦一类劣化来源。

### 1. 四件组织手段，各拦一个缺口

| 手段 | 拦住的缺口 | 核心动作 |
|------|-----------|---------|
| Owner 机制 | 「大家都负责 = 没人负责」 | 明确一个人/小组：看板值班、劣化 Review、启动路径 PR 审查权、定期周报维持关注度 |
| CODEOWNERS | 「新人不知道这里动不得」 | 启动路径文件（App.kt、SplashActivity、MainActivity、startup/、Manifest、阈值配置）强制 perf-team Review 才能合入 |
| 启动预算制度 | 「启动变慢了」吵不出结果 | 把目标总时长切成各阶段预算；新增初始化先申报占用，预算用完就走延迟/异步 |
| SDK 接入 Checklist | 照抄 SDK 文档的 `onCreate` 里 `init()` | PR 模板必填六问，逼出「测过耗时、考虑过延迟」的证据 |

**启动预算**是四件里最值得展开讲的，它把一个模糊的抱怨变成精确的账本。以高端机冷启动 TTID ≤ 1500ms 为例：

```
进程创建 → attach：      200ms（系统侧，监控不改造）
Application.onCreate：   400ms（SDK 初始化大头）
Activity.onCreate → setContentView：300ms（inflate）
首帧 M/L/D：             200ms
首屏数据 → TTFD：        400ms
```

新业务要在 Application 里加 SDK？先问：**你要占多少预算？** 这一阶段预算用完了，要么延迟初始化、要么从别的阶段挤。讨论从「你把启动搞慢了」（互相扯皮）变成「你超预算了 80ms」（账目清晰）。这和 02 篇 CI 阈值是同一个思想在两个层面的落地：**CI 阈值管总量，预算管分配**。

**SDK Checklist 六问**（进 PR 模板，涉及新 SDK 时必填）：

1. 必须启动时同步初始化吗？（大多数不需要）
2. `init()` 实测耗时多少？（要数据，不要估计——记住 CI 30ms ≠ 真机 280ms）
3. 能否延迟到首帧后？能否异步？
4. 是否用 ContentProvider 自动初始化？（考虑 App Startup 统一收编）
5. 启动路径上有无磁盘 IO / 网络请求？
6. 接入后 CI benchmark 结果？

### 2. 实战案例：从告警到回填的完整六步

这个案例的碎片你在前几篇都见过了，现在按时间线串成一条能在面试里讲的完整链路：

> **第一步 · 告警**：v3.8.0 灰度期，P1 告警——冷启动 P50 从 1.2s 涨到 1.6s，涨 35%（灰度门 15% 早已击穿，扩量自动暂停）。
> **第二步 · 阶段定位（一级）**：看板阶段拆解面板，`appOnCreateDuration` 380ms → 720ms，其他段没动。范围锁定 Application.onCreate。
> **第三步 · 堆栈指认（二级）**：慢消息聚合，Top1 堆栈占 87%——`AnalyticsSDK.init() → Config.loadFromDisk()`，低端机上 280ms 的同步磁盘读。
> **第四步 · git 追溯**：定位到引入的 MR。关键发现：**这个 MR 的 CI benchmark 是绿的**——模拟器 SSD 上 loadFromDisk 只要 30ms。CI 盲区被真机戳穿，这就是「必须两层都有」的活证据。
> **第五步 · 修复**：init 移入 DAG 异步调度器子线程执行（有降级开关的话先开关止血更快）；同时给 SDK 方提 issue——好的 SDK 不应该阻塞宿主启动路径。修复版灰度，同层对比回到 1.2s，收敛三条件满足后恢复扩量。
> **第六步 · 回填（防复发三件事）**：① App.kt 加入 CODEOWNERS 划给 perf-team；② CI 加 lint 规则——检测 Application.onCreate 里的直接 SDK 调用，必须走启动框架注册；③ Checklist 升级为 PR 模板必填项。
>
> 注意六步的性质：前五步是救火，**只有第六步在改变系统**——下一个同类问题会死在 lint（第①层防线），而不是烧到灰度。这就是你那张飞轮图的「回填箭头」转了一圈。

### 3. 全课收束：完整面试叙事（最终版）

把四篇的表达段拼起来，这是「你们怎么防止启动优化成果回退」的完整答案（约 2 分钟，可按追问深度伸缩）：

> 「防回退我们做了一套四层防线加救火闭环。**合入前**，lint 扫 onCreate 里的直接 SDK 调用，CODEOWNERS 把启动路径划给性能 owner 强制 review，新 SDK 要过接入 checklist 申报启动预算。**CI 层**，MR 流水线跑 Macrobenchmark 冷启动基准，固定环境取 P50，双轨阈值判定——相对基线劣化超 10% block merge，绝对阈值防温水煮青蛙；weekly job 自动重采集 Baseline Profile，防 Profile 过期这种没人写慢代码的隐形劣化。**但 CI 是粗滤网**——模拟器 I/O 比真机快一个量级，所以**灰度层**做同设备层横向对比，涨 15% 暂停扩量，判定要过样本量、观察窗口、涨幅阈值三条件。**线上**把线下口径线上化：进程创建时刻从内核取、统一 elapsedRealtime 时基、六个点位分阶段全量上报、TTID/TTFD 双指标，配 Looper 慢消息监控做两级定位——阶段圈范围、堆栈指认代码；告警三条：P50 突增抓阶跃、低端机 P90 绝对阈值守底线、TTFD 减 TTID 差值抓主线程工具看不到的异步劣化。出了问题走救火闭环：聚合归因、开关优先止血、修复灰度验证收敛，最后把教训回填成更靠前的防线——比如那次 analytics SDK 同步读盘骗过了 CI、被灰度逮住，修完之后对应的 lint 规则和 checklist 条目都加上了。体系的目标是：同类问题第二次出现时，死在更便宜的防线上。」

这段叙事和 ANR 复习课 07 篇是同一副骨架的两个实例——面试官问「还治理过什么」，你换掉工具名就能再讲一遍，**体系复用本身就是最强的加分项**。
