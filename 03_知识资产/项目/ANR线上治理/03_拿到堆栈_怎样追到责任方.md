# 03｜拿到堆栈，怎样追到责任方？

> 掌握状态：`0/5`。先学习 RUNNABLE、BLOCKED、WAITING、NATIVE，最后再归并结果。

## 本篇只解决一个问题

已经拿到主要聚类中的代表 issue。怎样从线程 dump 追到真正责任方？

```text
样本一：main RUNNABLE → FileOutputStream.write
样本二：main BLOCKED → waiting to lock A, held by thread 58
样本三：main WAITING → CountDownLatch.await
样本四：main NATIVE → pthread_join
```

四种现场都可能让关键职责无法完成，但追踪方向完全不同。

## RUNNABLE：当前路径正在做什么？

`RUNNABLE` 不等于持续占满 CPU。线程还可能位于 native IO、同步 Binder，或者处于可运行但没有获得足够调度的状态。

### 计算

```text
main RUNNABLE
→ sortLargeList
→ buildPageData
→ Activity.onCreate
```

继续看数据规模、循环次数和算法复杂度，并确认它为什么进入启动、输入或组件生命周期的关键路径。

### IO

```text
main RUNNABLE
→ FileOutputStream.write
→ Bitmap.compress
→ saveToLocalAlbum
→ CameraClickActivity.confirm
```

这条快照说明主线程采样时位于图片压缩或文件写入。还要结合相似样本、源码线程边界、文件大小和修复结果，证明它足以造成超时。

### Binder

```text
main RUNNABLE
→ BinderProxy.transactNative
→ BinderProxy.transact
→ 某系统服务接口
→ 业务代码
```

“Binder”只是等待边界。继续确认调用了哪个远端服务，以及远端线程池、服务实现或系统资源为什么没有及时返回。

## BLOCKED：谁拿着主线程需要的锁？

`BLOCKED` 通常表示线程正在等待进入 Java `synchronized` monitor。

```text
main BLOCKED
waiting to lock A
held by thread 58
```

下一步切换到线程 58：它是在锁内执行慢 IO，还是继续等待另一把锁？每发现一条锁依赖，都沿持锁线程继续追。

只有形成下面的闭环，才能判断 AB-BA 死锁：

```text
main 持有 B，等待 A
thread 58 持有 A，等待 B
```

只看到主线程 `BLOCKED`，最多只能证明当前锁等待，不能直接写成死锁。

## WAITING：谁负责让条件成立？

`WAITING` 表示线程等待某个条件，不等于等待进入 `synchronized`。

| 栈或 API | 等待什么 | 下一步查谁 |
|---|---|---|
| `Object.wait()` | 共享状态变化 | 修改状态并通知的线程 |
| `CountDownLatch.await()` | 一组任务完成 | 负责 `countDown()` 的任务 |
| `Future.get()` | 异步结果 | 执行 Future 的线程或线程池 |
| `Thread.join()` | 另一线程退出 | 被 join 的线程 |

看到 `CountDownLatch.await()` 后，应检查任务是否提交、线程池是否有空闲线程，以及负责 `countDown()` 的任务是否反过来等待主线程。

## NATIVE：具体停在哪个 native 调用？

`NATIVE` 只说明采样时线程进入了 native 层。必须继续阅读具体函数。

| native 栈 | 常见含义 | 继续检查 |
|---|---|---|
| `nativePollOnce` | Looper 等待消息 | 是否晚采样、目标线程是否正确 |
| `transactNative` | 同步 Binder | 调用的远端服务及其处理线程 |
| `read/write/fsync` | 文件或设备 IO | Java 业务入口和设备等待 |
| `futex/pthread_mutex` | native 锁等待 | 持锁线程 |
| `pthread_join` | 等待线程退出 | 被等待线程 |

### IJK：`pthread_join` 后面应该查谁？

```text
main
→ IjkMediaPlayer.release
→ SDL_WaitThread
→ pthread_join

audio thread
→ AudioTrack.write
→ AudioTrack::obtainBuffer
```

主线程等待音频线程退出；音频线程卡在阻塞式写入，无法及时检查退出标记。最终问题是 UI 线程同步执行了一个没有稳定时间上界的释放流程。

## 四种状态看完后，再归并结果

### A：责任线程自己执行太久

常见于业务计算、图片处理、文件或数据库 IO。Camera 主线程保存图片属于这一类。

需要回答：它为何进入限时职责路径，哪个步骤失去时间上界，应该在哪个调用边界缩短或迁移？

### B：责任线程正在等待别人

常见于 Java monitor、Latch、Future、join、native 锁和同步 Binder。

需要继续找到负责释放锁、完成条件或返回结果的执行单元，直到依赖链落到最终责任方。极验 AB-BA 和 IJK `pthread_join` 属于这一类。

### C：当前样本无法解释超时

只有 `nativePollOnce`、堆栈缺失或采样过晚时，不强行归因。回到同一聚类换代表样本，必要时补连续采样或 Perfetto/system trace。

C 类不是“系统问题”，而是当前证据不足。

## 三个典型判断

1. 主线程位于 `FileOutputStream.write()`：能提出主线程 IO 假设，不能仅凭一次快照证明它持续超过阈值。
2. 主线程等待锁 A：直接阻塞点是锁 A，最终责任方要看持锁线程的完整栈。
3. 主线程位于 `nativePollOnce`：当前栈不能解释超时，应检查采样时机或更换同聚类样本。

## 常见误区

1. 把 `RUNNABLE` 直接翻译成 CPU 满载。
2. 看到 `BLOCKED` 就停止，不检查持锁线程。
3. 把 `WAITING` 当成 Java monitor 竞争。
4. 看到 `NATIVE` 就认为无法分析或属于系统问题。
5. 只写直接阻塞点，没有继续追最终责任方。

## 本篇自测

1. RUNNABLE 栈顶是 `FileOutputStream.write()`，现在能证明什么？
2. 主线程等待锁 A，为什么必须查看持锁线程？
3. `CountDownLatch.await()` 与 `BLOCKED` 的追踪方向有什么不同？
4. `pthread_join` 后应该继续检查哪条线程？
5. A、B、C 三类分别表示什么？

## 一句话总结

线程状态只决定第一步追踪方向；真正的责任方藏在完整执行链或等待链的终点。
