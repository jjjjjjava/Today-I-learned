# 01｜线上出现一批 ANR，先做什么？

> 掌握状态：`3/4`。已掌握双入口、共性归因和爆发归因；正在学习如何区分统计线索、相关性与技术根因。

## 本篇只解决一个问题

线上出现一批 ANR，应该先打开一条堆栈，还是先看指标和分布？

答案取决于入口：日常看板处理长期存量，告警机器人处理短期爆发。两者最终都要把一批事件收敛成主要聚类，再选择代表 issue 做单点归因。

```text
日常看板 → 共性归因 ┐
                    ├→ 主要聚类 → 代表 issue → 单点归因
告警机器人 → 爆发归因 ┘
```

## 日常看板和告警机器人有什么不同？

日常看板面对已经积累一段时间的存量问题。首问是：这些问题共同集中在哪里，哪个问题值得优先解决？

告警机器人面对正在上涨的问题。首问是：这是真实爆发吗，影响是否仍在扩大，要不要先止损？

随机打开一条堆栈，只能解释一个样本。入口判断错误，可能修到低频个案，也可能在影响扩大时错过止损窗口。

## 共性归因原则

共性归因用于处理存量 issue。它不直接寻找技术根因，而是寻找最值得优先分析的边界。

第一层看业务和环境：

```text
版本 / 机型 / 系统 / 地区 / 企业 / 页面
```

第二层看技术特征：

```text
ANR reason / 主线程栈 / 公共业务调用链
```

切片不是把每个维度单独看一遍，而是逐步缩小范围。例如先发现某页面集中，再检查它是否集中于特定版本、机型或同一条公共栈。

### Camera：页面集中以后看什么？

抽样发现大量事件来自 `CameraClickActivity`。批量聚类后仍明显集中于该页面，因此拍照确认路径应被优先检查。

代表 issue 的主线程经过：

```text
CameraClickActivity.confirm
→ saveToLocalAlbum
→ Bitmap.compress
→ FileOutputStream.write
```

页面集中只确定调查范围。线程现场和源码线程边界，才把结论推进到“图片压缩和文件写入位于主线程”。

### 页面不集中，还能归并吗？

IJK 案例分布在多个视频页面，机型也不集中，但公共栈都进入：

```text
VideoPlayChildView.stopPlay
→ IjkMediaPlayer.release
```

此时页面只是不同触发入口，公共播放器组件才是主要聚类。

## 爆发归因流程

爆发归因先回答影响是否扩大，再回答为什么现在上涨。

### 第一步：确认是不是真实爆发

同时看事件次数、影响设备数或用户数、用户率和上涨持续性。

Bugly 每 50 分钟形成一个时间桶。需要区分单桶尖峰与多个时间桶持续上涨，也要避免把一个用户重复触发很多次误判成影响面扩大。

活跃用户、上报覆盖率或统计口径变化，也可能让绝对事件数上涨。因此事件数不能单独作为爆发结论。

### 第二步：影响扩大时先止损

如果问题紧随灰度、业务开关、配置或 SDK 变更出现，可以暂停放量、关闭开关或执行安全回滚。

止损不要求技术根因已经完全确认。它只回答：怎样阻止新增影响，并为后续判断提供一次反向实验。

### 第三步：寻找增量来自哪里

不要只找绝对量最大的分组。老版本可能一直占比最高，但这次上涨来自一个刚放量的小版本。

```text
找到指标拐点
→ 按版本、机型、系统、企业、地区、页面和公共栈切片
→ 比较各分组相对自身历史基线的增量
→ 找到贡献增量最大的聚类
→ 对齐近期变更
```

### “茉莉奶白”：一次告警怎样收敛？

```text
机器人告警
→ 事件次数与影响设备数持续上涨
→ 企业维度的相对增幅最大
→ 增量集中于“茉莉奶白”
→ 对齐近期业务开关
→ 关闭开关止损
→ 对应指标逐渐回落
```

企业集中提供统计线索；开关和指标在时间、人群上重合，形成相关性；代表 issue 的现场、源码路径和止损后的回落，才能继续增强因果判断。

## 线索、相关性和技术根因差在哪里？

| 结论 | 能说明什么 | 还不能说明什么 |
|---|---|---|
| 统计线索 | 某版本、企业、页面或公共栈更集中 | 内部为什么超时 |
| 相关性 | 指标变化与一次变更在时间和人群上重合 | 变更是否就是直接原因 |
| 技术根因 | 现场和源码解释了超时，修复实验符合预期 | 未覆盖人群是否同样成立 |

```text
集中 ≠ 相关
相关 ≠ 根因
根因需要机制证据与反向验证
```

## 怎样选择代表 issue？

代表 issue 应来自目标时间窗口、目标版本和主要聚类，现场信息还要足够完整。不要从全量数据中随手挑一条“看起来明显”的堆栈。

如果第一个样本只有 `nativePollOnce`、堆栈缺失或抓取过晚，应继续在同一聚类中换样本，而不是换掉整个调查方向。

## 常见误区

1. 随机打开一条堆栈，把低频个案当成主要问题。
2. 只看事件次数，不看影响设备数和用户率。
3. 某企业或页面集中，就直接写成技术根因。
4. 等根因完全确定后才止损，让影响继续扩大。
5. 只看绝对量，不比较各分组相对自身基线的增量。
