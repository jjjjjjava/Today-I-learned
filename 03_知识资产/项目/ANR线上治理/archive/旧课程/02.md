## 正文内容

经过共性归因或爆发归因，我们已经把范围收敛到某个聚类、人群、页面或代码分支。接下来要选择一条有代表性的 issue，进入**单点归因 SOP**。

单点归因的完整路径是：

```text
1. 确定 ANR 类型
2. 根据类型确定观察线程
3. 判断当前堆栈是不是有效现场
4. 根据线程状态和调用栈判断：执行太久，还是等待太久
5. 沿调用链、锁链或 Binder 链追到真正责任方
6. 回到源码修改，并验证对应问题是否下降
```

本篇只展开前三步。后续再处理 RUNNABLE、BLOCKED、WAITING、锁链和 Binder 链。

后续在这里插入你已经学过的 ANR 原理模块，至少承接以下内容：

- 系统为什么需要监控应用响应；
- 不同组件分别由什么机制设置超时；
- 超时后系统如何进入 ANR 处理；
- 为什么 ANR 类型代表系统当时在等待哪项职责完成。

当前课程直接使用这个模块的结论：

> **ANR 不是一个统一的“主线程超时事件”。系统等待的职责不同，ANR 类型不同，真正应该观察的线程也可能不同。**

### 第一步：先确定 ANR 类型

拿到一条 issue 后，先看平台提供的 reason、subject、组件名或类型标签，确认系统当时在等待什么。

常见类型包括：

- Input dispatch timeout；
- No focused window；
- BroadcastReceiver timeout；
- Execute Service 或前台服务启动超时；
- ContentProvider not responding；
- JobService 响应超时。

这一步不能跳过。因为“看到 ANR 就直接看主线程”隐含了一个未经验证的假设：这次超时职责一定由主线程完成。这个假设在很多场景成立，但不是全部。

正确路径是：

```text
reason / subject
→ ANR 类型
→ 系统在等待哪项职责
→ 哪条线程负责完成该职责
```

### 第二步：类型决定首要观察线程

| ANR 类型 | 首要观察对象 | 原因或注意点 |
|---|---|---|
| Input dispatch timeout | 主线程 | 主线程需要消费输入事件并推进界面响应 |
| No focused window | 主线程与窗口状态 | 不一定是线程卡死；还可能是首帧过慢或窗口不可获得焦点 |
| 同步 BroadcastReceiver | 执行 `onReceive()` 的线程 | 默认通常是主线程；使用自定义 Handler 注册后可以在其他线程 |
| `goAsync()` 异步广播 | 真正处理异步任务的工作线程或线程池 | 主线程返回不代表广播任务已经调用 `finish()` 完成 |
| Execute Service / 前台服务启动 | 主线程 | 重点检查冷启动及 `onCreate()`、`onStartCommand()`、`onBind()` 路径 |
| ContentProvider not responding | Provider 的 Binder 线程，或启动阶段的主线程 | 慢查询通常观察 Binder 线程；进程冷启动慢时观察主线程 |
| JobService 响应超时 | 主线程 | 检查调度回调是否被主线程其他任务阻塞 |

所以，“锁定观察对象：主线程”应改成：

> **先确认 ANR 类型，再锁定该类型对应的责任线程；Input、Service 等类型通常优先观察主线程。**

这不是降低主线程的重要性，而是避免在 BroadcastReceiver、ContentProvider 等场景中看错对象。

### 第三步：判断当前堆栈是不是有效现场

确定观察线程后，再看它的堆栈是否能解释超时。

如果主线程出现下面的调用：

```text
android.os.MessageQueue.nativePollOnce
android.os.MessageQueue.next
android.os.Looper.loop
android.app.ActivityThread.main
```

说明**采集堆栈这一刻，主线程正在消息队列中等待新消息**，没有执行 Java 层业务任务。

在很多 Input dispatch 或 Service ANR 中，这常常说明没有取到真正阻塞发生时的位置，例如：

1. ANR 已经触发，但等到平台抓取堆栈时，主线程已经恢复并回到消息循环；
2. 当前展示的是主线程，但这类 ANR 真正应该观察的是 Receiver 工作线程或 Binder 线程；
3. 进程此前可能因系统负载得不到调度，恢复后抓到的主线程已经空闲。

因此可以先形成这个工作判断：

> **`nativePollOnce` 常常说明取到了错误的位置或错误的观察线程，当前主线程栈无法直接支持业务代码归因。**

但不要把它扩大成：

> `nativePollOnce` 出现，所以整条 issue 一定无效。

是否还能继续分析，必须结合前面已经确认的 ANR 类型。

### 同一个 nativePollOnce，处理方式为什么不同

#### Input dispatch / Service

这两类通常重点观察主线程。如果主线程已经处于 `nativePollOnce`，较常见的是堆栈抓晚了。当前样本通常无法直接指出业务根因，应寻找同聚类中的其他有效 issue、更多采样或系统 trace。

#### BroadcastReceiver

如果 Receiver 在自定义线程执行，或者调用 `goAsync()` 后把任务交给线程池，主线程处于 `nativePollOnce` 可以完全正常。此时应转而检查 Receiver 工作线程、任务队列以及 `PendingResult.finish()` 是否及时调用。

#### ContentProvider

Provider 进程已经启动后，查询可能由 Binder 线程执行。主线程空闲不代表 Provider 查询正常，应检查 Binder 线程是否卡在数据库、文件 IO、锁或其他 Binder 调用。

所以更准确的现场判断是：

```text
nativePollOnce
→ 当前主线程栈信息量低
→ 回看 ANR 类型
→ 主线程本应负责：考虑晚采样，换有效样本
→ 其他线程负责：转看 Receiver、Binder 或工作线程
```

### 本篇形成的单点归因开头

当前可以把单点归因前三步固定为：

```text
拿到代表 issue
→ 查看 reason / subject，确定 ANR 类型
→ 根据类型锁定责任线程
→ 检查责任线程堆栈
→ 出现 nativePollOnce 时，判断是晚采样还是看错线程
→ 当前样本无法归因就换样本或补证据，不强行下结论
```

这一步完成后，才进入下一阶段：观察责任线程是 RUNNABLE、BLOCKED、WAITING 还是其他状态，并结合栈内容判断它到底在忙什么、等什么。
