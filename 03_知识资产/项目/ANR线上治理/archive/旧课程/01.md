# ANR 线上治理：从入口、切片到单点归因

> 归档说明：这是分层重构前的课程原文，保留案例、学习语境与历史内容；当前入口见 [[../../syllabus]]。

> 复习目标：面对线上 ANR，能够先判断从哪个入口进入，再用共性归因或爆发归因缩小范围，最后选择代表 issue 完成单点归因。

## 1. 概览

### 1.1 入口

实际工作中，ANR 主要从两个入口进入我们的视野：

1. **日常线上看板**：我们主动查看一段时间内积累的 ANR。
2. **告警机器人**：某项 ANR 指标在短时间内出现异常变化，系统主动告警。

入口不同，最先要回答的问题也不同。日常看板面对的是一批存量 issue，要先寻找共性；机器人告警面对的是突然上涨的指标，要先判断是否发生了真实爆发。

### 1.2 切片

一般来说，我们会先做共性归因或爆发归因，通过版本、机型、系统、地区、企业、页面和调用栈等维度排除无关影响因子，逐步缩小排查范围。

切片结果只是定位线索，不是最终根因。

### 1.3 单点归因

无论从哪个入口开始，最后都要选择一个有代表性、现场有效的 issue，结合堆栈和代码完成根因定位与验证。

```text
日常线上看板 → 共性归因 ┐
                        ├→ 代表 issue → 单点归因 → 修复与验证
告警机器人   → 爆发归因 ┘
```

## 2. 共性归因

日常线上看板中，我们面对的是一批已经积累起来的 issue。一个常见错误是随机打开一条堆栈，结合代码完成单点归因，然后解决了一个低频个案，却错过了影响面最大的聚类。

因此，第一步应该先问：

> 这批 issue 有没有共同的性质？

常见的切片维度包括：

1. **集中在低端机**：资源紧张可能放大某段临界代码中的 IO、计算、内存抖动或线程调度问题。
2. **集中在某个地区或企业**：可能存在地区配置、企业配置或定制化代码分支。
3. **集中在某个页面**：优先检查该页面进入、渲染、保存和销毁等路径中的主线程工作。
4. **页面分散，但调用栈存在公共方法**：公共组件、基础库或三方 SDK 可能是共同入口。

必须注意：集中在某个维度，只能说明排查应该优先看哪里，不能直接证明这个维度就是技术根因。

### 2.1 CameraClickActivity：页面聚类是怎样发现的

最开始抽样查看了几个 ANR，发现当前页面都是 `CameraClickActivity`。为了判断这是不是偶然现象，我们委托基础平台那边通过接口拉取某个时间窗口内的 ANR 样本。

从每条样本中提取当前 Activity 等页面字段，再交给 AI 做归纳分析，发现样本大致都集中在 `CameraClickActivity`。随后再次抽样检查原始堆栈，发现这些样本还具有相似的调用路径。

```text
先抽样检查几个 issue
→ 当前页面都是 CameraClickActivity
→ 接口拉取某个时间窗口内的 ANR 样本
→ 提取每条样本的当前 Activity
→ 交给 AI 归纳页面分布
→ 发现样本大致集中在 CameraClickActivity
→ 回到原始样本继续抽样
→ 确认它们具有相似调用路径
```

这里，AI 负责辅助整理大批数据，抽样回看原始堆栈负责验证结果。页面聚类将范围缩小到了 `CameraClickActivity`，但真正的根因仍要通过代表 issue 和代码完成单点归因。

### 2.2 CameraClickActivity：单点根因与修复

抽取代表 issue 后，发现主线程阻塞在

```text
CameraClickActivity.confirm
→ observeOn(AndroidSchedulers.mainThread())
→ saveToLocalAlbum
→ CameraBitmapUtils.saveBitmap
→ Bitmap.compress
→ FileOutputStream.write
```

`confirm` 流程切回主线程后继续调用 `saveToLocalAlbum`。其内部执行图片压缩和文件写入。当图片较大或磁盘 IO 较慢时，主线程会阻塞在 `Bitmap.compress` 或 `FileOutputStream.write`，导致 Looper 无法及时响应并触发 ANR。

这个问题的根因不是“图片压缩比较慢”，而是**耗时的图片压缩和文件 IO 被放在了主线程**。

修复时对比了三种方案：

- 只优化 `saveBitmap`：可以降低部分耗时和资源泄漏风险，但只要仍在主线程调用，就无法根治 ANR。
- 让工具方法内部异步：调用点改动小，但会改变同步语义，调用方难以确定保存完成时机，容易打乱 `finish`、图片回收和媒体库刷新的顺序。
- 调整调用链的线程边界：保持保存方法的同步语义，在 IO 线程完成压缩、写入和媒体库刷新，完成后再回到主线程更新页面。

最终选择第三种方案：使用 `Schedulers.io()` 执行图片压缩、文件写入和媒体库刷新，完成后再通过 `AndroidSchedulers.mainThread()` 执行事件通知、`finish` 或 `onBackAction`。

同时将 `FileOutputStream` 改为 `use { }` 自动关闭，避免压缩或刷新异常时文件流没有被正确释放。

#### 面试精简表达

> 我们先对线上 ANR 做页面聚类，发现问题明显集中在 `CameraClickActivity`。抽取代表 issue 后，主线程堆栈显示阻塞在 `FileOutputStream.write`。
>
> 回溯代码发现，拍照确认流程通过 `observeOn` 切回主线程后，又执行了 `Bitmap.compress` 和文件写入。图片较大或磁盘较慢时，就会阻塞主线程并触发 ANR。
>
> 修复时，我们没有让底层工具方法偷偷异步，而是调整整个调用链的线程边界：压缩、写文件和刷新媒体库放到 IO 线程，完成后再回到主线程执行事件通知和页面退出。这样既根治了主线程 IO，也保持了原有业务顺序。

修改后执行 `:cameravideolib:compileDebugKotlin` 编译通过，后续多个观察阶段也没有再发现相同的主线程阻塞栈。

### 2.3 共性分析也决定验证范围

共性分析不仅帮助定位，还会影响修复后的验证范围：

- 如果问题在人群和设备上分布均匀，可以随机选择验证样本。
- 如果明显集中在某款机型，修复后的观察应优先覆盖该机型。
- 如果集中在某个地区或企业，应确认修复版本已经到达这部分用户，并单独观察对应聚类。

## 3. 爆发归因

机器人告警一般意味着某类问题从某个时间点开始持续、稳定地上升。此时第一步不是立即打开一条堆栈，而是判断这是不是一次影响范围正在扩大的真实爆发。

### 3.1 确认

首先确认 ANR 事件量和受影响用户数是否同步、稳定地上升。

我们曾经遇到过一次告警，事件量看起来增长很快，但实际上只是一个用户在短时间内触发了几十次 ANR。后来了解到，该用户可能开启了作弊或破解软件，并不代表大量普通用户受到了影响。

因此，不能只看事件量。一个用户产生 100 次 ANR，与 100 个用户分别产生一次 ANR，代表的影响面完全不同。

### 3.2 止损

如果告警发生在版本灰度、开关大规模开启或其他重要变更之后，并且影响仍在不断扩大，应优先考虑：

- 暂停继续放量；
- 关闭相关开关；
- 问题严重时执行安全回滚。

止损不需要等到技术根因完全确定。它的首要目标是阻止影响继续扩大。

### 3.3 多维切片

完成确认和必要的止损后，再按版本、机型、系统、地区、企业和页面等维度切片，观察哪个参数组相对自身历史基线的增幅最大。

如果某个地区或企业的增幅特别明显，可以提出假设：本次问题可能与该人群命中的配置、开关或代码分支有关。接下来继续检查：

- 该群组与正常群组的配置差异；
- 最近是否修改过相关开关或代码；
- 代表 issue 是否经过对应业务路径；
- 撤销相关变更后，指标是否回落。

### 3.4 “茉莉奶白”企业开关案例

我们组曾处理过一次由告警机器人发现的 ANR 爆发。确认事件量和受影响用户数都在持续上升后，我们对版本、机型、系统、地区、企业和页面等参数进行切片。

企业维度的相对增幅最明显，并进一步集中在“茉莉奶白”企业。结合近期变更排查后，发现本次版本开启了一个相关业务开关。

关闭开关后，ANR 指标逐渐回落并恢复稳定。这说明本次爆发与该开关控制的业务路径高度相关。

```text
告警机器人发现指标上涨
→ 确认事件量和受影响用户数持续上升
→ 多维切片
→ 企业维度相对增幅最大
→ 进一步集中在“茉莉奶白”企业
→ 对照近期变更，发现本次版本开启了相关开关
→ 关闭开关止损
→ ANR 指标逐渐回落并恢复稳定
```

“集中在茉莉奶白”只是定位线索。开启开关后指标上涨、关闭后逐渐回落，才进一步加强了因果判断。如果要定位开关内部更具体的技术根因，仍然需要选择代表 issue 进入单点归因。

### 3.5 难处理的爆发问题

爆发归因中有一类问题特别难处理：停止放量或关闭开关后，指标仍然持续上升。

如果切片也没有明显特征，或者多个 ANR 聚类同时上涨，就不能强行得出结论。此时通常需要联合其他团队，补充系统 trace、服务端变更、设备状态或基础设施指标，一起扩大证据范围。

## 4. 单点归因

共性归因和爆发归因的作用，都是排除无关影响因子、缩小排查范围。最终仍然要选择一个有代表性、现场有效的 issue，结合堆栈和代码完成根因定位。

单点分析要依次回答下面五个问题：

1. **这个堆栈是不是有效现场？**
2. **这是什么类型的 ANR？**
3. **这个类型应该重点观察哪个线程？**
4. **目标线程正在执行什么，或者正在等待什么？**
5. **沿调用链、锁链或 Binder 链继续追踪后，真正的责任方在哪里？**

最终要形成一条可以复查的因果链：

```text
系统为什么判定超时
→ 哪个线程没有及时完成职责
→ 它正在执行或等待什么
→ 谁造成了这次执行或等待
→ 哪段自有代码、三方代码或系统状态应该负责
```

因此，三个阶段分别回答不同的问题：

- **共性归因**：这批存量 issue 应该优先看哪里？
- **爆发归因**：为什么现在突然变多，是否需要先止损？
- **单点归因**：这个代表 issue 具体为什么发生？

只有完成单点证据链，并在修改后观察指标或同类堆栈是否消失，才能真正闭环一次 ANR 治理。
