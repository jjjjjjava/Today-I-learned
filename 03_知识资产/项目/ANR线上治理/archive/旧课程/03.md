### 正确答案

**第 1 题：类型为什么必须在前？**

> ANR 类型说明系统在等待哪项职责完成；职责决定责任线程。Input 和 Service 通常重点看主线程，同步 Receiver 看实际执行 `onReceive()` 的线程，`goAsync()` 看工作线程，ContentProvider 慢查询可能看 Binder 线程。因此不能机械固定观察主线程。

**第 2 题：如何描述 nativePollOnce？**

> 采样这一刻主线程处于消息队列空闲等待，当前栈没有直接业务归因价值。可能是抓取偏晚、观察线程选错或系统调度问题；没有更多证据时不能在这些原因中强行选择一个。

**第 3 题：goAsync() 后看谁？**

> 看真正执行异步任务的线程或线程池，沿提交关系确认它是否承担该 Receiver 的工作，再检查阻塞点、队列和 `finish()` 调用路径。

## 正文内容

完成前面三步后，我们已经知道：

```text
这是什么类型的 ANR
→ 应该观察哪条线程
→ 当前堆栈是否值得继续分析
```

接下来进入单点归因的第四步：**结合线程状态与调用栈，判断责任线程是在执行太久，还是等待太久。**

### 一、状态、栈和职责必须一起看

一条线程信息通常包含三层含义：

1. **线程职责**：系统为什么在等它，例如主线程要响应输入、Receiver 工作线程要完成异步广播。
2. **线程状态**：RUNNABLE、BLOCKED、WAITING 等。
3. **调用栈**：它具体执行到了哪段代码、正在等待哪个同步原语或跨进程调用。

这三层不能拆开使用。

例如：

```text
main  RUNNABLE
```

只能说明 JVM 视角下线程处于可运行状态，不能说明它一定正在持续占用 CPU。

再加上调用栈：

```text
main  RUNNABLE
→ FileOutputStream.write
→ saveImageToGallery
→ CameraClickActivity
```

才得到一个具体方向：主线程采样时正在执行保存相册的文件 IO。

因此判断公式是：

> **线程职责 + 线程状态 + 调用栈 = 当前可提出的根因假设。**

它仍然是“假设”，证据强度还要结合持续时间、重复样本、源码路径和修复结果。

### 二、RUNNABLE：可能在执行，也可能卡在 native 调用

`RUNNABLE` 容易被误读为“线程正在占满 CPU”。实际上，它可能处于以下情况：

- 正在执行 Java/Kotlin 计算；
- 可以运行但暂时没有被 CPU 调度；
- 进入 native 方法执行文件 IO、数据库或图片处理；
- 进行同步 Binder 调用；
- 在某些内核调用中等待返回，但 JVM 仍把它显示为 RUNNABLE。

所以看到 RUNNABLE 后，继续读栈顶和业务调用链。

#### 栈顶是计算

```text
main  RUNNABLE
→ sortLargeList
→ buildPageData
→ Activity.onCreate
```

方向是主线程计算过重。接下来检查数据规模、算法复杂度、循环以及它是否位于启动或输入响应的关键路径。

#### 栈顶是 IO

```text
main  RUNNABLE
→ FileOutputStream.write
→ saveImageToGallery
→ CameraClickActivity
```

方向是主线程阻塞 IO。这与 `CameraClickActivity` 案例一致：页面聚集负责选出排查范围，有效单点栈把问题指向保存相册路径，源码再确认该调用运行在主线程。

#### 栈顶是 Binder

```text
main  RUNNABLE
→ BinderProxy.transactNative
→ BinderProxy.transact
→ 某系统服务或远程服务接口
```

方向是同步 Binder 调用返回过慢。此时不能只说“主线程 Binder 导致 ANR”，还要继续判断远端进程、Binder 线程池或 system_server 为什么没有及时返回。

因此 RUNNABLE 的工作结论应写成：

> **责任线程采样时正在某条调用路径中；根据栈顶判断计算、IO 或 Binder 方向，再用更多证据确认它是否持续得足够久。**

### 三、BLOCKED：正在竞争 Java monitor

`BLOCKED` 通常表示线程正在尝试进入一个 `synchronized` monitor，但锁被其他线程持有。

典型 trace 会给出类似信息：

```text
main  BLOCKED
waiting to lock <0x0fd09ed5>
held by thread 58
```

这时能确定的直接原因是：

> 主线程需要锁 A，但锁 A 当前由线程 58 持有，所以主线程无法继续执行。

但线程 58 才是下一步真正要看的对象：

- 它是否在锁内执行耗时 IO 或计算？
- 它是否在等待另一把锁？
- 它是否又通过某条依赖链等待主线程？
- 它持锁的代码是否属于自有代码或三方 SDK？

所以 `BLOCKED` 不等于“找到根因”。它只是给出了第一条明确的依赖边：

```text
main → 等锁 A → A 由线程 58 持有
```

下一篇会从这里继续，完整追踪极验案例中的 A、B 两把锁和 58、54 两条线程。

### 四、WAITING：在等一个条件，不一定是等 synchronized 锁

`WAITING` 表示线程正在等待某个条件成立。它与 `BLOCKED` 的排查方向不同：

- `BLOCKED` 是为了进入 `synchronized` 临界区而等待获得锁，重点查“谁持有这把锁”；
- `WAITING` 是等待某个状态改变、任务完成或线程结束，重点查“谁负责让条件成立”。

常见的等待条件可以归纳为以下四类：

| 等待的条件 | 常见栈/API | 谁负责让它继续 |
| --- | --- | --- |
| 共享状态改变 | `Object.wait()` | 修改共享状态后调用 `notify()` / `notifyAll()` |
| 一组任务完成 | `CountDownLatch.await()` | 一个或多个任务调用 `countDown()` |
| 异步结果完成 | `Future.get()` / `CompletableFuture.get()` | 执行任务的线程完成、失败或取消 |
| 另一线程结束 | `Thread.join()` | 被 `join` 的线程退出 |

#### 案例：主线程等待 IJK 音频线程退出

**共性归因**

线上 5.32.01 版本存在一批视频场景 ANR。按页面和机型切片后，没有发现单一影响因素：`VideoActivity`、`VideoSplitAllActivity` 等多个 Activity 都有同类问题，机型分布也较分散。

继续比较调用栈，发现不同页面最终都经过同一条公共组件路径：

```text
VideoPlayChildView.onDetachedFromWindow
VideoPlayChildView.stopPlay
IjkPlayView.stopPlayback
IjkMediaPlayer.release
```

所以 Activity 只是触发场景，真正应该进入单点归因的是公共组件 `VideoPlayChildView` 和 `IjkPlayView` 的播放器释放逻辑。

**单点归因**

代表 issue 中，主线程在 RecyclerView 重新布局、回收子 View 时触发 `onDetachedFromWindow()`，随后同步释放 IJK 播放器：

```text
main
→ IjkMediaPlayer.release
→ ijkmp_shutdown_l
→ ffp_wait_stop_l
→ SDL_AoutCloseAudio
→ SDL_WaitThread
→ pthread_join
```

完整线程 dump 同时显示，IJK 音频写入线程停在：

```text
Thread-444
→ AudioTrack.write
→ AudioTrack::obtainBuffer
→ ClientProxy::obtainBuffer
```

`pthread_join` 表示主线程正在等待音频线程退出。IJK 虽然设置了退出标记，但音频线程必须先从阻塞式 `AudioTrack.write()` 返回，才能重新检查标记并结束。

这里平台把主线程显示为 Native，而不是 Java 的 `WAITING`。但从依赖关系看，它仍属于“等待另一线程结束”：直接原因是主线程阻塞在 `pthread_join`，触发因素是音频线程卡在 `AudioTrack.write()`，应用侧根因是在主线程执行了没有时间上界的播放器释放。

**修复**

提交 `1c07c850` 没有删除 `pthread_join`，而是调整播放器释放的线程边界：

```java
IMediaPlayer player = mMediaPlayer;
mMediaPlayer = null;

new Thread(() -> {
    player.stop();
    player.release();
}).start();
```

主线程先保存旧播放器引用并清空成员字段，立即更新页面和播放状态；后台任务继续持有局部变量 `player`，负责执行可能阻塞的 `stop()` 和 `release()`。

严格来说，Java 没有语言级所有权转移。这里表示业务责任转移：UI 组件不再提供旧播放器的操作入口，后台任务接管它的最终释放。即使 `pthread_join` 仍然等待较久，阻塞的也是释放线程，不再是主线程。

**面试表达**

> 我们先做共性切片，发现 ANR 分布在多个视频 Activity 和多种机型，但公共堆栈都落到 `VideoPlayChildView`，因此把排查范围收敛到公共播放器组件。
>
> 单点 trace 显示，主线程释放 IJK 播放器时阻塞在 `pthread_join`；被等待的音频线程停在 `AudioTrack.write()`，无法及时返回并响应退出标记。
>
> 修复没有强行移除 `pthread_join`，而是先让 UI 放弃旧播放器，再把完整的 `stop()`、`release()` 放到后台线程。这样保留正常资源回收流程，同时切断主线程对慢退出音频线程的同步依赖。

下面是一种“等后台结果准备好”的协作写法。`lock` 是两条线程共用的同一个对象，`configReady` 是共享状态。

主线程：

```java
synchronized (lock) {
    while (!configReady) {
        lock.wait();
    }
}
```

主线程的意思是：

> 我先拿着 `lock` 检查配置是否准备好；如果没有，就释放 `lock` 并进入等待。等别人通知后，我再拿到 `lock`，重新检查 `configReady`。

后台线程：

```java
synchronized (lock) {
    configReady = true;
    lock.notifyAll();
}
```

后台线程拿到同一个 `lock` 后，把 `configReady` 改为 `true`，再通过 `notifyAll()` 通知等待线程。完整过程是：

```text
主线程拿到 lock
→ 发现 configReady == false
→ wait() 释放 lock，主线程进入 WAITING
→ 后台线程拿到 lock
→ 设置 configReady = true
→ notifyAll() 通知等待线程
→ 后台线程退出 synchronized，释放 lock
→ 主线程重新拿到 lock
→ 再次检查 configReady，条件成立后继续执行
```

这里使用 `while` 而不是 `if`，是因为线程被唤醒后仍然需要重新检查条件是否真的成立。

因此，线上排查可以记成：

```text
BLOCKED → 沿锁依赖寻找持锁线程
WAITING → 沿条件依赖寻找完成条件的责任线程
```

例如看到 `CountDownLatch.await()`，就继续检查谁负责调用 `countDown()`、任务是否成功提交、线程池是否有机会执行，以及负责完成条件的线程是否又在等待主线程。

### 五、平台显示 Native 时仍然要看具体 native 栈

采样时，线程已经从 Java/Kotlin 调用栈进入了 native 层。

#### MessageQueue.nativePollOnce

```text
main
→ MessageQueue.nativePollOnce
→ MessageQueue.next
→ Looper.loop
```

这通常意味着：

> 采样这一刻，主线程没有正在处理的消息，而是在等新消息。

#### BinderProxy.transactNative

```text
main
→ BinderProxy.transactNative
→ BinderProxy.transact
→ PackageManager.getPackageInfo
→ 业务代码
```

这里是业务代码同步调用系统服务，然后进入 Binder 的 native 实现，等待远端返回。

含义可能是：

```text
主线程
→ 同步 Binder 请求
→ system_server 或其他进程处理
→ 对端迟迟没有返回
→ 主线程卡在 transactNative
```

这类 Native 栈可能非常有价值。需要继续检查调用了什么服务，以及对端为什么没有及时返回。

#### native 文件读写

```text
main
→ read / write / fsync
→ FileInputStream / FileOutputStream
→ 业务代码
```

可能是 Java 文件 API 最终进入 native 系统调用，也可能是 App 或 SDK 的 `.so` 在读写文件。

这说明线程可能在等待磁盘或设备 IO，不代表它正在执行大量 C++ 计算。

#### futex、pthread_mutex

```text
main
→ futex_wait
→ pthread_mutex_lock
→ 某个 native 方法
→ 某 SDK 接口
```

这表示线程可能在 native 层等待锁。此时要找哪个线程持有 native 锁，以及持锁线程正在做什么。

因此，排查 Native 栈时要同时看两部分：

```text
native 栈顶：当前具体在 poll、transact、read、futex，还是计算？
Java 调用链：是谁把线程带进这个 native 方法的？
```

### 六、把状态归并成三个实际排查方向

在线上排查时，不必停留在背线程枚举，可以把它们归并成三个工作方向：

#### A. 责任线程自己在执行

常见信号：RUNNABLE，栈中出现业务计算、IO、图片处理、数据库或 Binder。

```text
责任线程
→ 当前执行什么
→ 为什么这段工作会这么久
→ 能否移出关键线程或缩短关键路径
```

#### B. 责任线程在等待其他执行单元

常见信号：BLOCKED、WAITING，栈中出现 monitor、Latch、Future、join 等。

```text
责任线程
→ 在等待什么条件或资源
→ 谁负责释放锁或完成条件
→ 那个线程为什么没有完成
```

#### C. 当前样本不能解释超时

常见信号：责任线程 `nativePollOnce`、缺失栈、采样过晚，或者只有系统因素假设但没有系统证据。

```text
不强行归因
→ 换同聚类样本
→ 检查其他责任线程
→ 有条件时补系统 trace
→ 平台没有相关信息时明确记录“证据不足”
```

### 七、单点归因 SOP 更新到第四步

现在完整路径已经推进到：

```text
确定 ANR 类型
→ 确定责任线程
→ 判断堆栈是否有效
→ 同时看线程状态与调用栈
   ├─ RUNNABLE：追计算、IO、Binder 等执行路径
   ├─ BLOCKED：找锁地址与持锁线程
   ├─ WAITING：找完成等待条件的责任方
   └─ 当前栈无法解释：换样本或补证据
```

下一步不是立即修改主线程代码，而是沿已经暴露出的依赖关系继续向下追：持锁线程在做什么、等待条件由谁完成、Binder 远端为什么没返回。只有追到不能再向下解释的责任代码，根因链才闭合。
