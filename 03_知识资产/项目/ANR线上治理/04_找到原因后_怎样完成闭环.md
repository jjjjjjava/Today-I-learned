# 04｜找到原因后，怎样完成闭环？

> 掌握状态：`0/3`。本篇关注线程边界、验证范围和指标闭环。

## 本篇只解决一个问题

已经找到责任代码。怎样修复而不破坏业务顺序，并证明线上问题真的下降？

## Camera：把 `saveBitmap()` 改成异步就够了吗？

Camera ANR 已定位到主线程图片压缩和文件写入。最直接的想法，是让 `saveBitmap()` 在内部偷偷切到异步线程。

这会改变方法原有的同步语义。调用方不知道保存何时完成，`finish()`、图片回收、媒体库刷新和事件通知可能发生乱序。

真正需要一起调整的是整条调用链：

```text
IO 线程：压缩 → 写文件 → 刷新媒体库
主线程：结果通知 → finish / onBackAction
```

耗时工作离开主线程，调用方仍能明确知道成功、失败和取消发生在什么时候。文件流使用 `use {}` 等方式关闭，但资源释放不能代替线程边界修复。

## 调整线程边界前，先保留哪些业务顺序？

需要从当前调用链中回答：

- 哪些工作必须完成后才能退出页面？
- 哪些对象只能在主线程访问？
- 后台任务需要独立持有哪些资源？
- 失败、取消和重复触发时怎样收尾？

异步不是把耗时方法随手包进线程池。切换位置应拥有完整业务语义，能表达任务开始、结果返回、失败和资源释放。

## IJK：为什么要转移释放责任？

IJK 的直接现场是主线程在 `pthread_join` 等待音频线程退出。问题不是 `pthread_join` 这个函数存在，而是 UI 线程同步执行了退出时间无上界的释放流程。

```java
IMediaPlayer player = mMediaPlayer;
mMediaPlayer = null;

new Thread(() -> {
    player.stop();
    player.release();
}).start();
```

主线程先清空 UI 对旧播放器的操作入口，后台释放任务持有局部引用。即使音频线程退出较慢，等待也不再占用 UI 职责。

这里是业务责任转移，不是 Java 语言级所有权转移。仍要处理重复释放、页面销毁和后台任务异常。

## 验证范围为什么要跟着原聚类走？

修复前在哪里发现共性，修复后就在哪里验证。

| 原聚类 | 修复后重点观察 |
|---|---|
| 特定版本 | 修复版本覆盖率、旧版本是否隔离 |
| 特定机型 | 目标机型用户率和同类堆栈 |
| 特定企业或地区 | 配置、开关和版本是否覆盖目标人群 |
| 特定页面 | 页面访问量、ANR 用户率和调用栈 |
| 公共组件栈 | 跨页面检查同一公共调用链是否消失 |

原问题集中于某款机型，只观察全量均值可能完全看不到变化。修复版本还没覆盖目标用户时，短期“零新增”也不能证明修复有效。

## Camera 修复后应该验证什么？

先验证代码和业务行为：

- 主线程不再执行图片压缩、文件写入和媒体库刷新；
- 保存完成后才执行依赖结果的页面退出或通知；
- 保存失败、页面销毁、重复点击和任务取消能正确收尾；
- 后台任务没有继续持有已失效的 Activity 或 View。

再验证线上结果：目标版本获得足够曝光后，观察 `CameraClickActivity` 聚类、主线程 IO 栈和用户率是否下降。

## 怎样形成一条可复查的因果链？

Camera 案例可以写成：

```text
事件集中于 CameraClickActivity
→ 代表 issue 主线程位于 Bitmap.compress / FileOutputStream.write
→ 源码确认保存流程运行在主线程
→ 压缩、写入和媒体库刷新迁入 IO 线程
→ 原页面与同类主线程 IO 栈下降
```

“茉莉奶白”案例可以写成：

```text
告警后事件次数和影响设备数持续上涨
→ 增量集中于目标企业
→ 时间线对齐新业务开关
→ 关闭开关止损
→ 目标企业指标逐渐回落
```

如果缺少有效单点现场，第二条只能证明开关控制的路径与问题相关，不能凭空补出路径内部的技术根因。

## 修复上线后指标没有下降怎么办？

按原因由外到内检查：

```text
修复版本是否覆盖目标人群
→ 统计窗口和样本量是否足够
→ 原聚类是否被新的签名拆散
→ 修复是否只移动了表面阻塞点
→ 回到主要聚类重新选择代表 issue
```

指标没有下降是一条反证。它说明覆盖、口径、归因或修复至少有一项需要重查。

## 三个典型判断

1. 编译通过且线下不再复现：只能证明基本行为，不代表线上已经闭环。
2. 全量 ANR 下降但原聚类不变：不能证明当前修复有效，可能是流量或其他问题变化。
3. 原聚类下降但新栈上涨：需要判断耗时是否被转移到新的同步等待点。

## 常见误区

1. 底层同步方法偷偷异步，破坏调用方语义。
2. 只减少耗时，没有切断关键线程上的无界执行或等待。
3. 原问题集中于特定人群，修复后只看全量均值。
4. 修复版本尚未覆盖目标用户，就用“零新增”证明有效。
5. 指标下降后，把统计相关性描述成已证明的内部根因。
