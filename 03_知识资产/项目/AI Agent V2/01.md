# 模块一 · 项目口径与主链路：把 AI Agent V2 讲成一个工程项目

> 前置知识：Flutter 页面路由、ValueNotifier、Stream/SSE 基本概念、分层架构基本概念
> 难度：进阶
> 预计阅读时间：15 分钟
> 阅读方式：正文是你面试要讲的项目主线；`机制注脚` 是面试官继续追问时用来兜底的解释。

## 正文内容

## 1. 先定项目口径：它不是“一个聊天页”，而是门店 AI Agent 前端执行台

面试里不要把这个项目说成“我做了一个 AI 聊天页面”。这个说法太轻，听起来像普通 IM UI。更准确的项目口径是：

> 我参与了 Flutter 混合栈里的 AI Agent V2 模块，它面向门店经营场景，把后端 agent 的流式输出、工具调用、检测报告、定时任务配置、用户确认 interrupt、多模态附件输入整合成一个前端执行台。用户不只是聊天，还能在同一个会话里完成“即拍即检、无人值守规则、门店设备绑定、定时检测任务确认、查看执行报告”等闭环操作。

这句话里有三个面试加分点：

| 关键词 | 面试含义 |
|---|---|
| AI Agent 前端执行台 | 不是普通聊天 UI，而是承接 agent 任务执行过程 |
| 流式输出 + 工具调用 + interrupt | 有复杂状态机和人机协作，不只是接口请求 |
| Flutter 混合栈 | 路由、参数、Native 图片/文件选择、token/header 都需要和宿主协同 |

如果面试官只给你 30 秒，可以这样说：

> 这个模块是门店 AI 助手的 V2 版本。我主要把后端 AGUI/SSE 事件流，在 Flutter 端建模成一条可渲染的时间线：里面既有用户消息、AI 流式文本，也有工具调用进度、需要用户确认的 interrupt 卡片和本地业务卡片。入口通过 FlutterBoost 路由进来，`AgentPageFactory` 解析参数并完成依赖装配，`ChatController` 消费 SSE 事件维护状态，页面只负责按 `ChatItem` 类型渲染不同组件。

## 2. 入口链路：从 FlutterBoost 路由到聊天页

源码入口不是直接 new 页面，而是经过一层工厂：

```text
old_module.dart
  -> _buildAgentChatPageV2(arguments)
  -> AgentPageFactory.createChatPage(arguments)
  -> _parseArguments(arguments)
  -> ServiceLocatorV2.setup(agentId, forwardedProps, threadId)
  -> AgentChatPageV3(controller, params)
```

对应源码：

- `lib/app/route/old/old_module.dart`：老路由表中把 AI Agent V2 页面委托给 `AgentPageFactory`
- `ai_agent_v2/presentation/pages/agent_page_factory.dart`：解析 `agentId / user_id / store_id / camera_id / threadId`
- `ai_agent_v2/application/di/service_locator_v2.dart`：创建 `AguiClient` 和 `ChatController`
- `ai_agent_v2/presentation/pages/chat_page_v3.dart`：真正的聊天页面

面试时可以这样解释这一层：

> 我们没有在页面里散落解析路由参数和创建依赖，而是用 `AgentPageFactory` 统一处理。这样 FlutterBoost/Native 传来的参数先被归一化，比如 `store_id/storeId`、`camera_id/cameraId` 这种命名差异会在入口层消化；然后由 `ServiceLocatorV2` 创建 AGUI client 和 controller，页面拿到的是已经可用的 controller。

这里的 `forwardedProps` 很关键，它会随每次 agent 请求带给后端：

```text
user_id
store_id
camera_id
lang
```

这些字段决定了后端 agent 在哪个用户、门店、摄像头和语言上下文里执行任务。

## 3. 四层架构：每一层解决什么问题

`ai_agent_v2` 目录按职责拆成四层：

```text
ai_agent_v2/
  core/              核心状态模型、事件模型、解析器、控制器
  application/       简化依赖注入
  infrastructure/    AGUI/SSE client、REST repository、API path
  presentation/      页面、Widget、Interrupt 策略卡片
```

### 3.1 Core：把后端事件翻译成前端领域状态

Core 里最重要的是三类模型：

| 模型 | 作用 |
|---|---|
| `AguiEvent` | 对后端 SSE 事件做强类型建模，例如 `TextDelta`、`ToolCallStart`、`InterruptArrived` |
| `ChatItem` | 对页面时间线做强类型建模，例如 `UserMessage`、`AssistantMessage`、`ToolCallItem`、`InterruptItem` |
| `ToolCallState` | 单独维护工具调用的执行中、完成、错误、取消等状态 |

这里最值得讲的是 **SSE 事件模型和 UI 时间线模型分开**。

后端发来的事件是过程态：

```text
TEXT_MESSAGE_START
TEXT_MESSAGE_CONTENT
TEXT_MESSAGE_CONTENT
TEXT_MESSAGE_END
TOOL_CALL_START
TOOL_CALL_ARGS
TOOL_CALL_END
TOOL_CALL_RESULT
CUSTOM on_interrupt
```

页面需要的是结果态/展示态：

```text
UserMessage
AssistantMessage
ToolCallItem
InterruptItem
InstantCaptureItem
UnattendedGuardItem
```

> 机制注脚：为什么不直接拿后端事件渲染 UI？
> 因为后端事件是“流式过程”，一个完整 AI 回复可能被拆成几十个 delta；工具调用参数也可能分片到达。如果 UI 直接消费原始事件，页面会到处处理半包、拼接、去重、完成态。`ChatController` 先把事件折叠成稳定的 `ChatItem` 时间线，Widget 才能只关心“我现在应该渲染哪种 item”。

### 3.2 Infrastructure：处理两类网络通道

基础设施层有两类通道：

| 通道 | 类 | 用途 |
|---|---|---|
| AGUI/SSE | `AguiClient` | 实时对话、工具调用、历史连接、interrupt resume |
| REST | `TaskRepository`、`StoreDeviceRepository` | 定时任务列表、执行历史、门店/设备列表 |

这个拆分面试里很好讲：

> 实时对话是长连接式的 SSE，因为要持续接收 token delta、工具调用进度和 interrupt；任务列表、执行历史、门店设备查询是普通查询，走 REST repository 更简单，也复用项目里的 `AuthNetworkManager` token 注入能力。

`AguiClient` 负责的事情包括：

- 构造 `agent/run`、`agent/connect` 请求体
- 设置 `accept: text/event-stream`
- 带上 `ovo-access-token`
- 把 HTTP response stream 按 SSE 的 `data: {...}` 行解析成 `Map`
- 处理 UTF-8 半包、请求超时、SSE 空闲超时
- debug 模式把 SSE 请求/响应上报到调试端点，方便 Charles 抓包

### 3.3 Application：简化版依赖注入

`ServiceLocatorV2` 只注册两个对象：

```text
AguiClient
ChatController
```

它每次 setup 前会 dispose 旧 controller/client 并 clear 容器。这说明 V2 的依赖图很克制：页面不需要知道 client 怎么创建，也不需要自己管理旧连接资源。

面试表达：

> V2 没有继续堆复杂全局状态，而是收敛成一个页面级 controller。依赖注入层只做对象装配和生命周期清理，保持模块边界简单。

### 3.4 Presentation：按时间线 item 做分发渲染

`AgentChatPageV3` 里核心渲染逻辑是：

```text
ValueListenableBuilder<List<ChatItem>>
  -> ListView.builder
  -> _buildItem(item)
```

`_buildItem` 根据 sealed class 类型分发：

| `ChatItem` | Widget |
|---|---|
| `UserMessage` | 用户消息/图片/文件展示 |
| `AssistantMessage` | `StreamingTextBubble` |
| `ToolCallItem` | `ToolCallWidget` |
| `InterruptItem` | `StoreDeviceSelectorCard` 或 `InterruptCard` |
| `InstantCaptureItem` | 即拍即检本地卡片 |
| `UnattendedGuardItem` | 无人值守本地卡片 |

这就是 V2 设计里最核心的前端抽象：**消息列表不是字符串数组，而是一条混合业务时间线**。

## 4. 主数据流：用户发一句话后发生什么

把链路压成一张图：

```text
用户输入
  -> AgentChatPageV3 调 controller.sendMessage/sendMessageWithAttachments
  -> ChatController 先把 UserMessage 加入时间线
  -> 确保 threadId
  -> AguiClient 构造 agent/run 请求
  -> POST /ovopark-agent/run，accept: text/event-stream
  -> AguiClient 解析 SSE data 行
  -> EventParser 把 raw Map 转成 AguiEvent
  -> ChatController 根据事件更新 ChatItem 时间线和内容缓存
  -> ValueListenableBuilder/ListView 渲染新增 item
  -> StreamingTextBubble/ToolCallWidget 展示文本增量和工具调用状态
```

这里有两个细节值得面试主动说：

### 4.1 发送请求时只发送当前消息

`AguiClient.sendMessage` 构造请求体时，`messages` 里只放当前用户消息，`state` 为空。代码注释写得很清楚：后端通过 `threadId` 自己维护对话历史。

面试表达：

> 我们没有每次把全量历史消息传给后端，而是用 `threadId` 让后端维护上下文，前端只发送当前输入。这可以降低请求体大小，避免移动端反复序列化历史消息，也减少多模态附件重复上传/引用的复杂度。

### 4.2 时间线和流式内容分开维护

`ChatController` 里有两套状态：

```text
messages: ValueNotifier<List<ChatItem>>
_messageContents: Map<messageId, String>
_toolCallStates: Map<toolCallId, ToolCallState>
```

`messages` 管“列表里有哪些 item”，`_messageContents` 管“某条 assistant 消息当前累计到什么文本”，`_toolCallStates` 管“某个工具调用执行到什么状态”。

> 机制注脚：为什么不每来一个 token 就替换整个消息列表？
> 流式输出的 delta 频率很高。如果每个 delta 都把整个 `List<ChatItem>` 重建并触发列表级刷新，滚动列表和复杂卡片都会承压。V2 的做法是：只有出现新消息骨架、新工具调用、interrupt 这种结构变化时才改时间线；文本内容和工具状态放在按 id 查询的缓存里，让对应 widget 自己更新/读取。

## 5. 历史恢复：不是“拉列表”，而是连接 thread 后消费快照

页面初始化时有两种情况：

```text
有 threadId
  -> initSession(threadId)
  -> connectToThread(threadId)

无 threadId
  -> initSession()
  -> loadHistory()
  -> getConversations()
  -> 取最新 threadId
  -> connectToThread(threadId)
```

`connectToThread` 不是普通 REST 拉历史，而是走 AGUI 的 `agent/connect`，随后等待第一个 `MESSAGES_SNAPSHOT`。拿到快照后，`MessageSnapshotConverter` 把历史消息转换成：

- `ChatItem` 列表
- assistant 文本缓存
- tool call 状态缓存

面试表达：

> 历史消息不是简单 JSON 列表渲染，因为历史里也可能包含 assistant 消息、tool call、tool result 和多模态内容。我们用 `MessageSnapshotConverter` 做一次归一化，把历史态转换成和实时态相同的 `ChatItem` 时间线，这样 UI 不需要区分“历史消息”和“实时消息”两套渲染逻辑。

## 6. Interrupt：AI Agent 项目里最有辨识度的难点

普通聊天页只有“用户问、AI 答”。Agent 项目不同：AI 可能要创建任务、删除标准、绑定门店设备，这些操作有副作用，不能直接执行，必须让用户确认。

后端通过 `CUSTOM` 事件里的 `on_interrupt` 表示“执行暂停，需要用户决策”。前端流程是：

```text
CUSTOM on_interrupt
  -> EventParser.parseCustomEvent()
  -> InterruptArrived
  -> ChatController 添加 InterruptItem
  -> AgentChatPageV3._buildInterruptWidget()
  -> StoreDeviceSelectorCard 或 InterruptCard
  -> 用户确认/取消
  -> controller approve/reject
  -> AguiClient.resumeWithConfirmation()
  -> 后端 agent 继续执行
```

`InterruptCard` 本身只负责外壳，具体内容和按钮交给策略：

```text
InterruptStrategyFactory
  create_scheduled_task / update_scheduled_task -> TaskConfirmationStrategy
  delete_scheduled_task -> TaskDeletionStrategy
  create_standard / update_standard -> EditableListStrategy
  delete_standard -> StandardDeletionStrategy
```

面试表达：

> Interrupt 是我觉得这个模块最像 agent 产品的地方。它把 AI 的自动执行和人的最终决策接起来：后端执行到需要确认的节点就暂停，前端把 interrupt 渲染成结构化卡片，用户确认后再用 resume 命令恢复 run。这样既保留 AI 的自动化能力，又把有副作用的操作放在人类确认之后。

## 7. 这项目的 2 分钟面试主线

你可以按这个版本背：

> 我做过一个 Flutter 混合栈里的 AI Agent V2 模块，场景是门店 AI 助手。它不是普通聊天页，而是一个 agent 前端执行台：用户可以发文本、图片、文件，后端通过 AGUI/SSE 流式返回 AI 文本、工具调用进度、检测报告，以及需要用户确认的 interrupt 卡片。
>
> 架构上我把它拆成四层：presentation 负责页面和卡片渲染；core 负责 `AguiEvent`、`ChatItem`、`ChatController` 这些核心状态；infrastructure 负责 AGUI SSE client 和 REST repository；application 只做简化依赖注入。入口由 FlutterBoost 老路由进入 `AgentPageFactory`，统一解析 `agentId/userId/storeId/cameraId/threadId`，再通过 `ServiceLocatorV2` 创建 `AguiClient` 和 `ChatController`。
>
> 核心难点是流式事件状态机。后端发来的不是一条完整消息，而是一串 `TEXT_MESSAGE_*`、`TOOL_CALL_*`、`CUSTOM on_interrupt`、`MESSAGES_SNAPSHOT` 事件。我没有让 UI 直接消费原始 Map，而是先用 `EventParser` 转成强类型事件，再由 `ChatController` 折叠成一条 `ChatItem` 时间线。这个时间线里可以混合用户消息、AI 流式消息、工具调用、确认卡片和本地业务卡片，页面只按 item 类型分发渲染。
>
> 另一个重点是 interrupt 人机协作。比如创建定时检测任务、删除标准、绑定门店设备这类有副作用操作，后端 agent 会发 interrupt 暂停执行，Flutter 端渲染成策略化卡片，用户确认后再通过 `resumeWithConfirmation` 让后端继续执行。这样既能体现 AI 自动化，又能控制风险。

## 8. 高频追问的第一层回答

### 8.1 为什么从旧 MVI 改成事件驱动？

可以回答：

> 这个模块的状态不是传统表单状态，而是后端持续推送的事件流。V2 更适合用事件驱动：`AguiClient` 产生事件，`EventParser` 归一事件，`ChatController` 折叠事件成 UI 时间线。相比把所有东西塞进一个 MVI store，这个模型更贴近 SSE 的过程态，也更容易按事件类型扩展。

### 8.2 为什么不用一个 Message model？

可以回答：

> 因为页面不是单一消息流，而是混合时间线。AI 回复、工具调用、interrupt、本地功能卡片在交互和生命周期上完全不同。用 sealed class 建模后，编译期就能约束每种 item 的渲染分支，也避免到处判断 `type` 字符串。

### 8.3 为什么实时对话走 SSE，任务列表走 REST？

可以回答：

> SSE 适合后端单向持续推送，正好符合 AI 文本 delta、工具调用进度、interrupt 这种场景；任务列表和执行历史只是查询，没有持续推送需求，走 REST repository 更简单，也能复用已有鉴权网络层。

### 8.4 为什么历史消息要单独 converter？

可以回答：

> 历史快照里的消息结构和实时事件不同，但最终 UI 应该复用同一条 `ChatItem` 时间线。`MessageSnapshotConverter` 的价值就是把历史态转换成实时态同构的数据，避免 UI 写两套渲染逻辑。
