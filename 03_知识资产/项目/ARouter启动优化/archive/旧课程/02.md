## 1. ARouter 原理

第一轮的根因发生在“加载路由表”，但要真正讲清它，必须先把生成、加载、使用三段串起来：

```text
编译期生成路由表
→ App 初始化时找到并注册路由表
→ 运行时根据 path 查表并完成跳转
```

其中：

- **APT** 解决“路由表从哪里来”。
- **`LogisticsCenter.init()`** 解决“路由表怎样进入运行时仓库”。
- **`navigation()`** 解决“一个 path 怎样变成真正的 Activity、Fragment 或 Provider”。

本次 7～8 秒劣化发生在第二段，但第一段决定有哪些生成类，第三段决定这些生成类为什么必须被正确装载。

### 1.1 路由表跳转：path 怎样变成目标 Class

#### 1.1.1 ARouter 为什么需要路由表

传统页面跳转直接引用目标类：

```kotlin
Intent(context, UserLoginActivity::class.java)
```

调用方因此必须依赖目标模块。ARouter 改成：

```kotlin
ARouter.getInstance()
    .build("/user/login")
    .withBundle("data", bundle)
    .navigation()
```

调用方只知道字符串 `path`，不知道 `UserLoginActivity.class`。这实现了模块解耦、动态跳转和统一拦截，但也引入一个必要条件：运行时必须存在一张可以完成间接寻址的路由表。

```text
/user/login → UserLoginActivity.class
```

#### 1.1.2 `build(path)`：创建 Postcard

`build("/user/login")` 会创建一个 **Postcard**。它代表本次跳转请求，此时主要保存：

```text
path
group
Bundle 参数
flags
动画等跳转配置
```

如果没有显式指定 group，通常会从 path 的第一段提取：

```text
/user/login → group = user
```

此时 Postcard 还不知道最终目标 Class，也不知道路由类型。

#### 1.1.3 `navigation()`：进入 completion

调用 `navigation()` 后，主线会进入：

```text
LogisticsCenter.completion(postcard)
```

`completion()` 的核心任务是：

> 根据 `path` 找到对应的 `RouteMeta`，再用 `RouteMeta` 补全 `Postcard`。

**RouteMeta** 是一条路由元信息，核心字段包括：

```text
destination：目标 Class
type：Activity、Fragment、Provider 等类型
path：完整路由地址
group：路由分组
priority / extra：优先级及扩展信息
```

补全后的 Postcard 才拥有：

```text
destination = UserLoginActivity.class
type = ACTIVITY
```

最后根据 `type` 执行对应操作：

```text
ACTIVITY → 组装 Intent、写入 extras、startActivity()
FRAGMENT → 创建 Fragment、设置 arguments、返回实例
PROVIDER → 获取或创建服务实例
```

#### 1.1.4 Warehouse：为什么要分 Root 和 Group

ARouter 的运行时路由仓库叫 **Warehouse**。和页面路由直接相关的两个结构是：

```text
groupsIndex：group → Group Class
routes：path → RouteMeta
```

例如：

```text
groupsIndex["user"] = ARouter$$Group$$user.class
routes["/user/login"] = RouteMeta(UserLoginActivity.class)
```

#### 1.1.5 completion 的查表过程

`completion(postcard)` 首先查询：

```text
Warehouse.routes[path]
```

如果能找到 RouteMeta，就直接补全 Postcard。如果找不到，通常说明对应 group 还没有加载：

```text
routes["/user/login"]
→ 找不到
→ 从 path 得到 group = user
→ groupsIndex["user"]
→ 找到 ARouter$$Group$$user.class
→ 反射创建 Group 实例
→ Group.loadInto(Warehouse.routes)
→ 再次执行 completion(postcard)
→ 找到 RouteMeta，补全 Postcard
```

#### 1.1.6 分组懒加载的意义

初始化时并不会把所有 `path → RouteMeta` 全量写入 `routes`，而是先加载较小的：

```text
group → Group Class
```

真正访问某个 group 时，才把该组的具体路由写入 `routes`。这就是分组懒加载。

因此 Root 和 Group 的职责不同：

| 生成类 | 保存内容 | 加载时机 |
|---|---|---|
| Root | `group → Group Class` | ARouter 初始化时 |
| Group | `path → RouteMeta` | 第一次访问对应 group 时 |
| Provider | Provider 服务映射 | 初始化注册索引 |
| Interceptor | 拦截器索引 | 初始化注册索引 |

这也解释了一个关键点：插件初始化时需要直接注册 Root、Provider、Interceptor，但不需要全量注册所有 Group；Group 已经由 Root 间接索引，并保持懒加载。

### 1.2 路由表生成：`@Route` 怎样变成 Root 和 Group

运行时查的 RouteMeta 并不是启动时动态分析业务类得到的，而是在编译期生成。

#### 1.2.1 RouteProcessor 扫描 `@Route`

业务页面声明：

```kotlin
@Route(path = "/user/login")
class UserLoginActivity : Activity()
```

Java 注解处理阶段会调用 ARouter 的 `RouteProcessor`。Kotlin 项目通常通过 kapt 接入这个 Java 注解处理器。

编译器会把当前轮次的信息封装在 **RoundEnvironment** 中。处理器通过：

```java
roundEnv.getElementsAnnotatedWith(Route.class)
```

取得所有被 `@Route` 标注的 **Element**。

Element 不是运行时的 `UserLoginActivity.class`，而是编译期对该类型的结构化描述。处理器可以从中取得：

```text
类型名和包名
父类与实现接口
注解
成员信息
```

#### 1.2.2 生成 RouteMeta

`RouteProcessor` 会结合注解与类型工具提取：

```text
@Route：path、group、priority、extra
Element：destination、Activity/Fragment/Provider 等目标类型
```

然后将它们封装成 RouteMeta，并按 group 整理：

```text
user group
├── /user/login → RouteMeta(UserLoginActivity.class)
└── /user/profile → RouteMeta(UserProfileActivity.class)
```

#### 1.2.3 JavaPoet 生成路由表 Java 类

APT 负责扫描和分析，**JavaPoet** 负责生成 Java 源文件。核心生成类包括：

```text
ARouter$$Group$$user
    loadInto(routes)：写入 path → RouteMeta

ARouter$$Root$$app
    loadInto(groupsIndex)：写入 group → Group Class

ARouter$$Providers$$app
    loadInto(providersIndex)：写入 Provider 服务映射
```

拦截器由对应的注解处理链生成 `ARouter$$Interceptors$$...`，运行时同样需要进入拦截器索引。

完整生成链是：

```text
@Route
→ RouteProcessor 扫描
→ RoundEnvironment 提供当前轮次元素
→ 解析 Element 与注解
→ 封装 RouteMeta
→ 按 group 整理
→ JavaPoet 生成 Group / Root / Provider 等 Java 类
→ Java/Kotlin 编译产出 Class
→ 后续进入 Dex
```

到这里，路由表已经“存在于安装包中”，但 ARouter 初始化仍然要解决一个问题：**怎样找到这些生成类并调用 `loadInto()`？**

### 1.3 路由表加载：插件注册与 Dex 扫描两条路径

初始化入口是：

```text
ARouter.init(application)
→ LogisticsCenter.init(context, executor)
```

`LogisticsCenter.init()` 先调用：

```text
loadRouterMap()
```

它把加载过程分成两条路径。

#### 1.3.1 插件注册路径

`loadRouterMap()` 是框架为 Gradle 插件预留的注册入口。没有插桩时，它基本是空的；插桩成功后，其中会出现：

```java
register("com.alibaba.android.arouter.routes.ARouter$$Root$$app");
register("com.alibaba.android.arouter.routes.ARouter$$Providers$$app");
register("com.alibaba.android.arouter.routes.ARouter$$Interceptors$$app");
```

`register()` 根据类名加载生成类，实例化后调用对应的 `loadInto()`，把索引写入 Warehouse，并让 `registerByPlugin` 标记插件注册已经生效。

```text
loadRouterMap()
→ register(生成类名)
→ Class.forName / 创建实例
→ loadInto(Warehouse 对应索引)
→ registerByPlugin = true
→ 跳过 Dex 扫描
```

这条路径不是“运行时不加载路由表”，而是“不再运行时搜索路由表”。启动时仍会执行必要的注册和 `loadInto()`，只是省掉打开并遍历 Dex 的发现成本。

#### 1.3.2 默认 Dex 扫描路径

如果 `loadRouterMap()` 没有被成功插桩，`registerByPlugin` 为 false，ARouter 就回退到 Dex 扫描：

```text
获取 APK 中所有 Dex 路径
→ 逐个打开 Dex
→ DexFile.entries() 枚举全部类名
→ 按 com.alibaba.android.arouter.routes 包名前缀筛选
→ 再按生成类名前缀区分 Root、Provider、Interceptor
→ 反射创建实例
→ 调用 loadInto()
→ 写入 Warehouse
```

这里有两层字符串判断：

```text
第一层：className.startsWith("com.alibaba.android.arouter.routes")

第二层：
ARouter$$Root$$...         → Root
ARouter$$Providers$$...    → Provider
ARouter$$Interceptors$$... → Interceptor
```

因此，默认模式确实主要依靠**类的全限定名**做包名和生成类名前缀匹配，不会像插件那样用 ASM 读取 Class 接口。

但真正昂贵的不是 `startsWith()`：为了执行这几个很轻的字符串判断，前面必须先找到所有 Dex、打开它们，并枚举其中的全部类名。项目 Dex 越多、类越多，发现少量路由表类付出的全量扫描成本越高。

本项目 APK 体量超过 400MB，同时 Dex 和类规模较大。这个项目事实用于说明扫描成本为何被放大；它不等于“Dex 文件本身有 400MB”。

这就是 Profiler 中：

```text
ClassUtils.getFileNameByPackageName
→ DexFile.openDexFile
→ openDexFileNative ≈ 7.6 秒
```

的机制来源。

#### 1.3.3 SP 缓存为什么不是根治

ARouter 会缓存上一次 Dex 扫描得到的**生成类名集合**。它缓存的不是完整 RouteMeta，也不是另一个路由表生成方案。

```text
首次安装 / App 版本变化 / Debug 场景
→ 重新扫描 Dex
→ 保存生成类名集合到 SP

版本未变化且缓存有效
→ 从 SP 读取类名集合
→ 仍然 Class.forName、实例化并 loadInto()
```

SP 能减少重复扫描，却无法覆盖新安装、升级后首次启动以及频繁安装的调试场景。这也是为什么只跑多轮中位数、把首轮当 warm-up，可能把劣化隐藏掉。

## 2. 升级 AGP 和 Gradle 为何导致劣化

### 2.1 升级前的快速路径

故障前的路径是：

```text
编译期插件收集路由表类
→ 插桩 LogisticsCenter.loadRouterMap()
→ 运行时直接 register()
→ registerByPlugin 生效
→ 跳过 Dex 扫描
```

### 2.2 升级后回退到 Dex 扫描

Gradle/AGP 升级后，旧插件依赖的 Transform 接入方式不再适用，`loadRouterMap()` 没有被正常插入注册逻辑。运行时于是变成：

```text
loadRouterMap() 没有完成注册
→ registerByPlugin = false
→ LogisticsCenter.init() 进入默认分支
→ ClassUtils.getFileNameByPackageName()
→ 打开并遍历 Dex
→ openDexFileNative 出现 7～8 秒聚合耗时
```

### 2.3 根因证据链

完整证据链不能只说“Profiler 看到了 native 方法”，而要四层闭合：

1. **线上指标**：增量集中在 `task_arouter.init`。
2. **线下调用栈**：耗时属于 `ARouter.init → LogisticsCenter.init → DexFile`。
3. **源码与构建链**：只有插件注册失效时才会回退这条 Dex 路径；相关 issue 也确认旧插件存在新 AGP 兼容问题。
4. **修复反证**：恢复兼容插件后，`openDexFileNative` 大块消失，Benchmark 与灰度指标回落。

## 3. 方案设计

### 3.1 三个候选方案

| 方案 | 能否消除 Dex 扫描 | 主要问题 | 结论 |
|---|---|---|---|
| 异步初始化 | 不能 | 成本仍在；首个路由请求可能早于初始化完成，需要等待或兜底 | 不治本 |
| 更换路由框架 | 可以绕开 | 页面、Provider、Interceptor、多模块调用迁移范围大，回归风险高 | 成本过高 |
| 恢复插件注册 | 可以 | 需要解决新 AGP 的构建兼容 | 最贴近根因 |

### 3.2 最终选择

第一轮最终选择支持新 AGP Artifacts API 的插件，拉取源码验证后接入。其本质没有改变 ARouter 的运行时语义：

```text
默认模式：运行时扫描 Dex，发现路由表类
插件模式：编译期收集路由表类，运行时直接 register
```

变化的只是“发现类名”发生在什么时候。完整的插件扫描与 ASM 插桩实现放在下一篇，与 Java 21 的第二轮故障一起讲透。

## 4. 结果验证

验证要从运行路径、功能、对照实验和线上指标四层闭合，不能只说“启动变快了”。

### 4.1 运行路径验证

`loadRouterMap()` 本身无论是否插桩都能正常执行，所以“方法调用成功”不是插件生效的证据。需要确认其中的 `register()` 真正被执行。

```text
loadRouterMap() 执行 register()
→ registerByPlugin 被置为 true
→ 不进入 ClassUtils.getFileNameByPackageName()
→ 不再打开和遍历 Dex
```

运行时可通过断点确认 `register()` 和标记位变化，并确认调用栈没有进入 Dex 扫描分支。

### 4.2 功能回归

路由表发现方式改变后，需要回归所有依赖 Root、Provider 和 Interceptor 注册的能力：

```text
页面路由跳转
Provider 注册与获取
Interceptor 注册与执行
多模块路由表完整性
Debug / Release 与目标 variant 构建
```

### 4.3 ABC 控制变量实验

| 版本 | 构建环境 | ARouter 插件状态 | 作用 |
|---|---|---|---|
| A | 旧 Gradle/AGP | 插件正常 | 原稳定基线 |
| B | 新 Gradle/AGP | 插桩失效 | 灰度故障版本 |
| C | 新 Gradle/AGP | 插桩修复 | 修复版本 |

- `B → C`：Gradle/AGP 环境相同，主要变量是插桩是否生效，用来隔离 ARouter 修复收益。
- `A → C`：两者都走正常插件路径，用来观察 Gradle/AGP 升级后是否还有剩余差异。

例如 A、B、C 的 LOW 档 P90 分别约为 `4.5s`、`12.8s`、`4.7s`。`B → C` 说明约 8 秒的 ARouter 劣化基本被消除；`A → C` 仍有约 0.2 秒差异，只能说回到预算范围。

三组实验需要保持设备档位、构建类型、启动入口、统计终点和数据状态一致，否则无法隔离变量。

### 4.4 Profiler、Benchmark 与灰度

- CPU Profiler 中原来约 7.6 秒的 `openDexFileNative` 大块消失，用于验证执行路径改变。
- 重新构建 Benchmark 包并多轮测试；相对升级前基准包，修复版 P50 只增加约 200ms，处于本次升级预算内。
- 重新分级灰度后，冷启动耗时和 `task_arouter.init` 恢复到正常范围。

Profiler 负责解释方法路径，Benchmark 负责同环境对比，灰度负责验证真实用户结果。三类数据不能直接混为同一组绝对值。

## 5. 第一轮小结

### 5.1 面试表达

> Gradle/AGP 升级后，我们在灰度发现 `task_arouter.init` 的 P90 相对历史版本新增约 8.3 秒。低端机复现后，通过 CPU Profiler Sampling 定位到 `ARouter.init → LogisticsCenter.init → openDexFileNative`，其中 Dex 打开聚合耗时约 7.6 秒。沿源码确认 ARouter 初始化有插件注册和运行时 Dex 扫描两条路径：正常情况下，插件会把 Root、Provider、Interceptor 等生成类写进 `loadRouterMap()`，运行时直接 `register()`；升级后旧 Transform 插桩失效，`registerByPlugin` 没有生效，因此回退到打开所有 Dex、枚举全部类名、按包名和生成类名前缀筛选的慢路径。我们比较了异步初始化、更换框架和恢复插件三种方案，最终接入兼容新 AGP Artifacts API 的插件，把路由表发现重新前移到编译期。修复后 `openDexFileNative` 耗时块消失，Benchmark 回到升级预算内，重新灰度后冷启动和 ARouter Task 指标恢复正常。

这一轮最重要的不是背“Dex 扫描很慢”，而是能串起：

```text
@Route 如何生成路由表
→ 初始化为什么要发现路由表
→ 插件路径如何直接注册
→ 插桩失效为什么回退 Dex 扫描
→ 运行时 path 如何最终查到 RouteMeta
```

## 思考题
