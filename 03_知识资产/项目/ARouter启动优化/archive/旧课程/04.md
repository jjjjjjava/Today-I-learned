### 你的回答评估

**第 1 题：要先收集全部路由表字节码文件，否则会遗漏后续出现的 Class。——✅ 核心正确**

更精确的说法是：插桩依赖完整的“路由表类名集合”。遍历顺序不确定，如果先遇到 `LogisticsCenter.class` 就立即插桩，只能写入当时已经收集到的类名，后续出现的 Root、Provider、Interceptor 将缺少对应 `register()`。

**第 2 题：Dex 用前缀匹配；插件先过滤再用 Visitor 找接口；Group 用于懒加载。——⚠️ 基本正确，校准两个术语**

运行时 Dex 扫描先按类全限定名的包名前缀过滤，再按生成类名前缀分类。插件先按 Class Entry 包路径筛候选类，再由 `ClassReader → ScanClassVisitor.visit()` 检查接口。Root 对应的准确接口名是 `IRouteRoot`，不是 `IRoot`。Group 不是“没意义”，而是很重要：Root 已经间接索引它，因此不需要在初始化时直接注册，才能保留懒加载。

**第 3 题：升级 ASM 9.7、改 ASM9、移除废弃 API。——⚠️ 前两项正确，第三项需要纠正**

这个项目记录中的第三项不是泛化的“移除废弃 API”，而是确保插件运行时 classpath 真正加载新版 ASM。只修改依赖声明或 Visitor 常量，如果运行时仍因依赖冲突加载旧 `ClassReader`，major version 65 异常仍然存在。

### 正确答案

**第 1 题：为什么不能立即修改 LogisticsCenter？**

> 插桩结果依赖扫描全部 Class 后得到的完整 Root、Provider、Interceptor 类名集合，而 Class 遍历顺序不确定。必须先缓存 `LogisticsCenter.class`，完成全量扫描，再一次性插入全部 `register()`；否则会静默漏注册后出现的路由表类。

**第 2 题：运行时扫描与插件扫描有什么区别？**

> 运行时通过 `DexFile.entries()` 枚举类全限定名，先按 routes 包名前缀过滤，再按 `ARouter$$Root$$` 等生成类名前缀分类。插件处理 Class Entry，先按 `com/alibaba/android/arouter/routes/` 路径过滤，再通过 ASM 检查 `IRouteRoot`、`IProviderGroup`、`IInterceptorGroup`。Group 由 Root 的 `group → Group Class` 间接索引，保留首次访问时的懒加载。

**第 3 题：Java 21 修复的三个层次是什么？**

> 第一，将 asm、asm-commons、asm-tree 统一升级到 9.7，让 `ClassReader` 能读取 major version 65；第二，将 Visitor API 从 ASM7 调整到 ASM9；第三，确认 Gradle 插件运行时 classpath 实际解析到新版 ASM，而不是被传递依赖或打包方式换回旧版本。

## 正文内容

## 1. 这个项目真正的主线

四篇笔记的信息很多，但面试时不能从 APT 开始平铺源码。主线只有一句话：

> 构建环境升级破坏了 ARouter 的编译期注册链，导致第一轮出现运行时 Dex 扫描和启动劣化；恢复链路后，Java 21 又暴露插件字节码解析能力不足，我们进一步修复 ASM 兼容并回馈上游。

两轮问题发生在不同阶段：

| 轮次 | 触发变化 | 故障阶段 | 表现 | 根因 |
|---|---|---|---|---|
| 第一轮 | Gradle/AGP 升级 | App 运行时 | 启动 P90 增量约 8.3 秒 | 插桩失效，回退 Dex 扫描 |
| 第二轮 | Java 21 升级 | 构建期 | major version 65 构建失败 | 旧 ASM 无法解析新 Class |

共同交点是：

```text
编译期生成的路由表
→ 插件能否正确发现并写入注册逻辑
→ 运行时能否低成本装载到 Warehouse
```

## 2. 2～3 分钟完整面试话术

> 这是一次典型的版本增量启动劣化，我们前后处理了两轮。
>
> 第一轮发生在 Gradle/AGP 升级后。新版本灰度时，我们发现启动耗时异常，沿统一埋点下钻到 `stage_app_init`，其中 `task_arouter.init` 的 P90 相对历史版本新增约 8.3 秒，已经超过升级预算，所以先暂停放量。线下统一为杀进程保留数据、相同入口冷启动、首帧完成作为终点，并选择低端机放大问题。因为这是秒级单点异常，我先用 CPU Profiler 的 Sampling 模式快速看调用栈，定位到 `ARouter.init → LogisticsCenter.init → DexFile.openDexFile → openDexFileNative`，其中 native 打开 Dex 的聚合耗时约 7.6 秒。
>
> 继续看 ARouter 源码后确认，它初始化路由表有两条路径。正常情况下，Gradle 插件会在编译期收集 APT 生成的 Root、Provider、Interceptor 等路由表类，并向 `LogisticsCenter.loadRouterMap()` 插入 `register()`；运行时直接把索引加载到 Warehouse，`registerByPlugin` 生效后跳过 Dex 扫描。AGP 升级后旧插件的 Transform 接入方式失效，`loadRouterMap()` 没被正确插桩，于是回退到打开所有 Dex、枚举全部类名、按包名和生成类名前缀筛选的慢路径。真正昂贵的不是字符串匹配，而是打开 Dex 和遍历全部类名。
>
> 我们比较了异步初始化、更换路由框架和恢复插件三种方案。异步只转移扫描成本，还会引入路由可用时机问题；更换框架改造和回归范围过大；最终选择兼容新 AGP Artifacts API 的插件，把路由表发现重新前移到编译期。修复后 Profiler 中原来的 `openDexFileNative` 大块消失，Benchmark 相对升级前基准的 P50 只增加约 200 毫秒，处于预算内；重新灰度后冷启动和 ARouter Task 指标恢复正常。
>
> 第二轮发生在项目升级 Java 21 后，构建报 `Unsupported class file major version 65`。我梳理插件源码后确认：插件通过 Artifacts API 获取 `allDirectories` 和 `allJars`，先按 routes Class Entry 路径过滤，再用 ASM 检查实现的 `IRouteRoot`、`IProviderGroup`、`IInterceptorGroup`；扫描全部 Class 后缓存并修改 `LogisticsCenter.class`，通过 `ClassReader → ClassVisitor → MethodVisitor → ClassWriter`，在 `loadRouterMap()` 的 `RETURN` 前插入 `LDC + INVOKESTATIC register`。
>
> Java 21 对应 Class major version 65，旧 ASM 在 `ClassReader` 读取文件头时就不认识，所以还没进入 Visitor 就抛错。我们 fork 插件，将 asm、asm-commons、asm-tree 升到 9.7，把 API 调整为 ASM9，并确认插件运行时真正解析到新版依赖。修复后发布自维护版本，同时提交上游 PR 并被接受。
>
> 最后我们不只验证“能编译、启动变快”，还检查目标 variant 的 `loadRouterMap()` 是否包含完整 `register()`、升级首启/缓存失效场景下 `registerByPlugin` 是否生效，并回归页面、Provider、Interceptor 和多模块路由。这次最终沉淀的是一套增量劣化治理闭环：灰度发现、暂停放量、统一口径、工具归因、源码定位、治本修复、Benchmark、重新灰度，再把首次启动场景和构建产物校验回填防线。

## 3. 面试官追问时怎样下钻

不要在主线里一次讲完所有源码。面试官问到哪一层，再进入对应链路：

| 追问 | 回答抓手 |
|---|---|
| ARouter 为什么需要路由表？ | `path` 替代 Class 引用，需要 `path → RouteMeta → destination` 的间接寻址 |
| 一次跳转怎么完成？ | `build → Postcard → navigation → completion → RouteMeta → type` |
| Root 和 Group 为什么分开？ | `groupsIndex` 先装 Root，`routes` 按 group 懒加载 RouteMeta |
| 路由表从哪来？ | `@Route → RouteProcessor → Element → RouteMeta → JavaPoet` |
| Dex 扫描具体扫什么？ | `DexFile.entries()` 枚举类名，包名前缀过滤，生成类名前缀分类 |
| 为什么前缀匹配也会耗时？ | 匹配很轻；打开多个 Dex、遍历全部类名很重 |
| 插件怎样识别类型？ | Entry 路径筛候选，ASM 根据三个实现接口分类 |
| 为什么缓存 LogisticsCenter？ | 遍历顺序不确定，必须拿到完整类名集合再统一插桩 |
| ASM 具体插了什么？ | `RETURN` 前执行 `LDC className + INVOKESTATIC register` |
| 为什么 Java 21 会失败？ | `ClassReader` 不认识 major version 65，失败发生在 Visitor 之前 |
| 怎么证明插件真的生效？ | 产物有 register、运行时 `registerByPlugin=true`、缓存失效仍无 Dex 扫描 |

原则是：先回答问题本身，再补一层机制，不主动把所有知识一次倾倒出来。

## 4. 证据要分层，不能用一个“快了”包办全部结论

这个案例的证据可以分成五层：

```text
现象证据：灰度 P90 相对历史版本新增约 8.3 秒
归属证据：增量集中在 task_arouter.init
方法证据：Profiler 命中 openDexFileNative 约 7.6 秒
机制证据：插桩缺失 → registerByPlugin=false → 回退 Dex 扫描
反证与结果：恢复插桩后 native 大块消失，Benchmark 与灰度恢复
```

其中：

- 灰度正常证明用户侧结果恢复，但不能单独证明内部一定走插件路径。
- 没有 `openDexFileNative` 也不能单独证明插件生效，因为可能命中 SP 缓存。
- 构建成功不能证明插桩完整，因为目标 variant、类名收集或 `register()` 产物仍可能有问题。

最稳的验证是“产物 + 运行路径 + 功能 + 指标”四层同时成立。

## 5. 从个案抽象出的增量劣化治理闭环

```text
1. 灰度发现版本增量异常
2. 暂停放量，控制影响面
3. 统一场景、设备、入口和终点
4. 按问题量级选择工具，定位主要调用栈
5. 沿源码与构建链找到条件变化
6. 比较方案，选择消除根因的路径
7. 用对照版本、Benchmark、产物和功能回归验证
8. 重新灰度，确认真实用户指标恢复
9. 把漏网条件回填到 CI 和兼容矩阵
10. 将通用修复回馈上游
```

它和普通的存量优化不同：

```text
增量治理：先回答“新版本为什么比旧版本差”，目标是恢复基线
存量治理：再回答“稳定版本还能怎样继续变快”，目标是降低水位
```

不要把二者混在一起，否则既难隔离因果，也难证明本次改动解决了什么。

## 6. 防复发矩阵

### 6.1 启动场景

```text
clean install first launch
upgrade first launch
cache-hit cold start
```

首次安装和升级后第一次启动必须单独统计，不能一律当作 warm-up 丢弃。否则 SP 缓存会让后续样本看起来正常，掩盖真实升级用户的第一次扫描。

### 6.2 指标预算

```text
startup.stage.app_init
startup.task.arouter.init
```

总启动指标用于判断用户影响，ARouter Task 用于判断增量贡献。预算只有在测试确实执行到风险路径时才有意义。

### 6.3 构建产物

```text
目标 variant 确实执行插件任务
Root / Provider / Interceptor 收集数量合理
loadRouterMap() 存在完整 register() 列表
registerByPlugin 路径在缓存失效场景生效
```

### 6.4 兼容矩阵

```text
AGP / Gradle 版本
Java Class major version
ASM 解析版本与 Visitor API
插件运行时依赖解析结果
Debug / Release / Benchmark 目标 variant
```

### 6.5 功能回归

```text
普通页面路由
Provider 注册与获取
Interceptor 注册与执行
多模块路由完整性
Group 懒加载
```
