 # 引子：一次启动增量劣化，两轮修复

> 前置知识：知道 Android 冷启动包含 Application 初始化和首帧展示阶段。
> 难度：进阶
> 预计阅读时间：6 分钟

## 正文内容

## 1. 背景：这不是“App 一直很慢”

这个项目要先定性：它不是降低稳定版本的存量启动水位，而是治理一次**版本增量劣化**。

## 2. 线上预定位

这个问题最初是 Leader 在灰度监控中发现的。候选版本的启动 P90，从稳定版约 4.5 秒上升到 12.8 秒，相对增加约 8.3 秒。

因为 ARouter 存在 SP 缓存，我们没有认为所有启动都会劣化，而是进一步聚合 P90 尾部的慢启动样本。沿启动埋点下钻后，发现异常主要集中在 stage_app_init，其中 task_arouter.init 在慢样本中高频出现，而且耗时贡献最大。团队因此先暂停了灰度。

我接手后负责线下复现和技术归因
## 3. 线下复现

### 3.1 工具和 TTFD 选取

线下复现首先统一口径：

```text
杀掉进程但保留应用数据
→ 从相同入口执行冷启动
→ 以首帧完成作为启动终点
```

选择低端机，是因为较弱的 CPU 和 I/O 更容易放大 Dex 打开、类名遍历等成本，让增量问题稳定显形。

工具上选择 Android Studio CPU Profiler 的 **Sampling 模式**，采样间隔设置为：

```text
1000 μs ≈ 1 ms
```

采样线程会周期性抓取各线程的**调用栈**。之所以没有一开始就使用更重的插桩或 Perfetto，是因为当前任务已经新增接近 10 秒，目标只是快速回答：

> 启动阶段是否存在一个秒级的重量级调用栈，它属于哪条初始化链路？

### 3.2 归因分析：找到 openDexFileNative

火焰图中，启动阶段最大的聚合耗时块是：

```text
openDexFileNative ≈ 7.6 秒
```

沿调用栈向上追踪，可以确认它属于 ARouter 初始化链路：

```text
ARouter.init
→ LogisticsCenter.init
→ 获取 APK 中的 Dex 路径
→ DexFile.openDexFile
→ openDexFileNative
```

这一步只形成一个初步判断：ARouter 初始化正在打开 Dex，而且它与线上 `task_arouter.init` 的异常方向一致。它还不能直接回答三个更深的问题：

1. ARouter 为什么需要找到路由表，路由表又是怎么生成和使用的？
2. Gradle/AGP 升级为什么会让它从快速路径退回 Dex 扫描？
3. `openDexFileNative` 为什么会耗时数秒，真正昂贵的是哪一步？

这些问题构成第一轮优化的完整原理链。

## 4. 小结

### 4.1 两轮问题的地图

整个项目后来经历了两轮处理
第一轮是：使用插件加载模式进行字节码插桩替代原有的openDexFile进行路由表加载，最终让线上增量劣化回落
第二轮处理是：后来项目升级到 Java 21，构建阶段又出现：Unsupported class file major version 65，我们修改插件源码，解决了问题，
修复完成后，将插件版本发布到 JitPack，并作为项目的自维护插件接入，同时将 修复提交给上游项目。PR 最终被接受，上游作者也对贡献进行了致谢。
### 4.2 面试转场与开场版本

完成两轮问题的总览后，可以先询问面试官：

> 这个问题我一共做过两轮处理。您想两轮都听，还是先聚焦其中一轮？

如果进入第一轮，再用一句话引出原理：

> 介意我先简单扩展一下 ARouter 的路由表生成、加载和使用原理吗？这是后续归因的基础。

如果面试中只给 30 秒介绍背景，可以这样说：

> 这是一次构建升级引起的启动增量劣化。Gradle/AGP 升级后，我们在灰度发现 `task_arouter.init` 的 P90 相对历史版本新增约 8.3 秒，于是暂停放量，在低端机按统一冷启动口径复现。
> 通过 CPU Profiler Sampling 定位到 ARouter 初始化中的 `openDexFileNative`，聚合耗时约 7.6 秒。沿源码确认是旧插件插桩失效后，ARouter 回退到了运行时 Dex 扫描。
> 第一轮我们恢复了兼容新 AGP 的编译期注册；后来升级 Java 21，又二轮修复了旧 ASM 无法读取 major version 65 的问题。这两轮最终形成了一套从灰度发现、工具归因、源码定位、治本修复到 Benchmark 和灰度验收的增量劣化治理闭环。

这段开场只负责把故事立住。下一篇会完整展开第一轮：从一次 `navigation()` 为什么需要路由表开始，一直讲到 APT 生成、Warehouse 加载、Dex 扫描退化、方案选择和验证结果。

## 思考题

1. 为什么这里必须说“P90 相对历史版本新增约 8.3 秒”，而不能直接说“P90 是 8.3 秒”？这两个说法分别对应什么治理目标？
2. Profiler 中的 `openDexFileNative ≈ 7.6 秒`，为什么不能直接拿来和线上 P90 的 8.3 秒做等式？两组数据分别承担什么证据职责？
3. 如果你只知道 `openDexFileNative` 很慢，还缺少哪些证据，才能得出“AGP 升级导致 ARouter 插桩失效并回退 Dex 扫描”的完整根因结论？
