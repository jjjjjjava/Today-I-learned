# 模块一 · 优化口径与问题定位：为什么 Profiler 先行，为什么区间选 attachBaseContext → 首页可见

> 前置知识：冷启动大致分进程创建 / 主线程 / Application / Activity / 渲染五段；ARouter 是组件化路由框架（本篇会补背景）
> 难度：进阶
> 预计阅读时间：12 分钟
> 阅读方式：本篇是「项目骨架 + 🔧 机制注脚」融合体。**正文是你面试要讲的项目主线**，`🔧 机制` 框是被追问原理时垫底用的。

## 1. 项目骨架：先圈区间，再谈优化

这个问题的起点很「真实」——不是立项的专项优化，而是我日常打 debug 包时发现的：小米 8 这类设备上，App 冷启动到首页可见经常要 **10s 左右**，体感明显异常。

启动优化最容易犯的错，是上来就改代码——异步初始化、删 SDK、懒加载一通操作，然后「感觉快了」。问题是：**没有一个可分析、可复现、可对比的区间，你既证明不了优化有效，也圈不出到底是哪段业务链路卡住了启动。** 所以第一步是定区间。

### 1.1 主统计区间

```text
Application.attachBaseContext()  →  首页可见
```

- **起点 `attachBaseContext()`**：从这里开始进入**业务代码更可控**的启动阶段。
- **终点「首页可见」**：取 `HomeOldActivity.onWindowFocusChanged(true)` 附近，覆盖「从业务初始化到首页真正展示出来」的全过程。

> **面试一句话：** 这次不是为了做线上严格 TTFD 指标，而是为了在本地复现启动慢时，圈定一个**业务可控**的启动区间，再抓 trace 找主要耗时点。所以我把区间定为 `Application.attachBaseContext()` 到首页可见。

### 1.2 为什么起点不从「点击图标」算、终点不停在 onCreate/onResume

这是两个高频追问点，得能接住：

- **起点为何是 `attachBaseContext()` 而不是点击图标？** 完整冷启动还包括 AMS 创建进程、Zygote fork、`ActivityThread.main()` 前后等**系统阶段**，这些受系统调度、进程创建、设备状态影响，**不是业务代码能优化的可控区间**。从 `attachBaseContext()` 起才进入 Application → ContentProvider → Activity 这条业务相对可控的链路。量的是「我能改的那段」。

- **终点为何不停在 `onCreate()` / `onResume()`？** 那些只是生命周期节点，到了 `onResume()` 首页内容也未必真画出来了。取 `onWindowFocusChanged(true)` 附近，是为了贴近「首页真正展示出来」的用户体感，而不是「代码跑到某个回调」。

> 🔧 **机制注脚：`onResume()` ≠「画出来了」。** `onResume()` 只代表 Activity 进入前台、生命周期回调走到这。真正的像素要等 `ViewRootImpl` 跑完一次 `performTraversals()`（measure/layout/draw）并提交渲染线程。`onWindowFocusChanged(true)` 发生在窗口获得焦点、首帧绘制时机附近，比 `onResume()` 更贴近「看见」。（这条渲染链路本课不展开，已在「首页启动优化」课题里讲透。）

## 2. 项目骨架：第一层归因工具为什么选 Profiler，而不是 Perfetto

定完区间，下一步是选**第一层归因工具**。这里我选了 **Android Studio Profiler / Method Trace**，而不是 Perfetto。

### 2.1 选 Profiler 的理由

这次的第一目标很明确：

```text
到底被哪个方法卡住了，为什么卡这么久？
```

因为是 **10s 级**的异常慢，我不追求精细化追踪，只想**快速定位是否存在一个秒级的重量级任务**。相比 Perfetto、线上指标平台或大量业务埋点，Profiler 使用成本最低、反馈最快，能直接看到启动阶段的方法调用栈和耗时分布。

### 2.2 Profiler 的局限（必须主动说，否则像不懂）

| 维度 | 说明 |
|---|---|
| 不等价线上真实耗时 | Method Trace / Profiler 本身有**采样或插桩开销** |
| 不适合判断小收益 | 几十毫秒、几百毫秒级的精细收益用它判断不可靠 |
| 适合什么 | **秒级瓶颈**的第一层归因——判断「有没有单个重量级任务」 |

> **面试表达：** Profiler 不能直接等价线上真实耗时，也不适合判断很小的收益。但这次是 10s 级异常慢，我先用它判断是否存在秒级重量级任务。如果发现耗时分散、或目标是几百毫秒级优化，我会再切到 **Perfetto + 统一口径**做精细化统计。

这句话很重要：它表明你**知道工具边界**，是「按问题量级选工具」，而不是「只会一个工具」。

> 🔧 **机制注脚：我用的是「采样模式」抓 trace，而不是插桩模式。** 采集这段 trace 实际调的是：
>
> ```java
> Debug.startMethodTracingSampling(
>     traceFile.getAbsolutePath(),
>     8 * 1024 * 1024,   // buffer 8MB
>     1000               // 采样间隔，单位微秒：每 1000μs(=1ms) 采一次
> );
> ```
>
> Android 的 Method Trace 有两种模式，开销和精度不同：
>
> | 模式 | API | 原理 | 取舍 |
> |---|---|---|---|
> | 采样 (Sampling) | `Debug.startMethodTracingSampling()` | 一个采样线程**每隔固定间隔**抓一次各线程调用栈 | 开销小、不扭曲时序；代价是**比间隔短的方法可能被漏采** |

## 3. 🔧 机制注脚：ARouter 是什么、解决什么（项目背景）

后面归因会发现瓶颈落在 ARouter 初始化上，所以这里先把 ARouter 的背景垫一层——面试官多半会顺口问「ARouter 是干嘛的、为什么要用它」。

### 3.1 核心思想：用 path 间接寻址替代 Class 引用

传统跳转直接依赖目标类：

```kotlin
startActivity(Intent(this, ShopDetailActivity::class.java))  // 直接 Class 引用
```

ARouter 改成用一个字符串 `path` 间接寻址：

```kotlin
ARouter.getInstance().build("/shop/shopDetail").navigation()  // path 间接寻址
```

调用方不再拿 `ShopDetailActivity.class`，而是拿 `/shop/shopDetail` 去**路由表**里查目标，再完成跳转。

### 3.2 解决的三个问题

| 能力 | 说明 |
|---|---|
| **模块解耦** | 调用方不必 `import` 目标模块的类，只依赖 ARouter + 约定 `path`，业务模块间不再强依赖 |
| **动态跳转** | 服务端 / 运营 / Push / H5 可下发字符串 `path`，客户端按 `path` 找页面跳转 |
| **统一拦截** | 跳转前统一执行拦截逻辑（如登录校验），未登录就中断并跳登录页，不必每个入口重复写 |

### 3.3 一条三步链路（后续模块的地图）

ARouter 的工作链路就三步，记住它，后面 Trace 归因和 register 插桩都挂在这条链上：

```text
编译期生成路由表  →  App 初始化时加载路由表  →  运行时根据 path 查表跳转
   （APT 生成）        （ARouter.init 装进 Warehouse）     （navigation 查表）
```

> 🔧 本课的核心瓶颈，就出在**第二步「初始化时加载路由表」**：ARouter 默认用「运行时扫描 dex」找编译期生成的路由表类，项目体量大时这一步是秒级的。模块二会沿 Profiler 调用栈把它揪出来，模块三再讲怎么用字节码插桩绕过它。

> **面试一句话（背景版）：** ARouter 是组件化路由框架，核心是用 `path` 代替直接 `Class` 引用——编译期 APT 生成路由表，初始化时加载到运行时仓库，运行时按 `path` 查表跳转，从而实现解耦、动态跳转和统一拦截。我这次优化动的就是「初始化时加载路由表」这一步。

## 思考题

1. 面试官追问：「你从 `attachBaseContext()` 算，那点击图标到 `attachBaseContext()` 这段难道就不优化了？」——你怎么回答，既守住口径、又不显得在甩锅？
2. 同样是启动优化，「首页启动优化」那个项目用的是 Perfetto + 业务 marker，这个 ARouter 项目却用 Profiler。两者口径起点（`bindApplication` vs `attachBaseContext`）和工具选择都不同，背后的判断依据分别是什么？（提示：问题量级、目标精度）
3. ARouter 用 `path` 替代 `Class` 引用换来了解耦，但天下没有免费的午餐——这种「间接寻址」在**启动期**可能引入什么代价？（这题其实就是模块二要归因的瓶颈，先猜猜看）
