# 04｜Java 21 让插件再次失效，怎样修复？

## 本篇只解决一个问题

第一轮已经恢复编译期注册。项目升级 Java 21 后，构建为什么再次失败，怎样证明插件已经完整兼容？

## 这次还是启动性能问题吗？

升级 Java 21 后，插件处理 Class 产物时出现：

```text
Unsupported class file major version 65
```

这次故障发生在 APK 生成之前，是构建期字节码解析失败，不是运行时路由查找，也不是第二次启动性能劣化。

两轮问题发生在同一条注册链的不同位置：

| 轮次 | 变化 | 故障阶段 | 结果 |
|---|---|---|---|
| 第一轮 | AGP 升级 | 插件没有正确处理目标 Class | 运行时回退 Dex 扫描 |
| 第二轮 | Java 21 升级 | 旧 ASM 无法解析新 Class | 构建直接失败 |

## major version 65 表示什么？

`.class` 文件头中的 major version 表示 Class 格式版本：

```text
Java 17 → major version 61
Java 21 → major version 65
```

插件中的 ASM `ClassReader` 读取 Class 文件头时，会先确认当前解析器是否支持该版本。

旧 ASM 不认识 major version 65，因此执行顺序是：

```text
ClassReader 读取文件头
→ 校验 major version
→ 发现版本超出支持范围
→ 直接抛异常
```

此时还没有进入 `ClassVisitor`、`MethodVisitor` 或 D8。因此问题不是接口识别、`register()` 指令或路由逻辑错误。

## 为什么只把 `ASM7` 改成 `ASM9` 不够？

`Opcodes.ASM7` 或 `ASM9` 表示 Visitor 使用的 API 级别；真正负责读取 Class 文件头的是插件运行时加载的 `ClassReader`。

如果代码把 Visitor 常量改成 ASM9，但插件运行时仍加载旧 ASM Jar，旧 `ClassReader` 依然无法识别 major version 65。

需要同时解决解析器版本、Visitor API 和插件运行时依赖三个层次。

## 三层修复分别做了什么？

### 第一层：升级完整 ASM 依赖族

```kotlin
implementation("org.ow2.asm:asm:9.7")
implementation("org.ow2.asm:asm-commons:9.7")
implementation("org.ow2.asm:asm-tree:9.7")
```

三个模块保持同一版本，避免核心解析、工具类和 Tree API 之间出现版本错配。

### 第二层：Visitor API 调整为 ASM9

```text
Opcodes.ASM7 → Opcodes.ASM9
```

这让 Visitor 按新的 ASM API 级别工作，但它不能代替第一层解析器升级。

### 第三层：确认运行时真正加载新版 ASM

Gradle 插件拥有自己的运行时 classpath。即使源码声明 ASM 9.7，依赖冲突、传递依赖选择或打包方式仍可能让运行时加载旧版本。

所以要确认：

```text
插件声明 ASM 9.7
→ 运行时依赖解析结果确实为 ASM 9.7
→ ClassReader 能读取 major version 65
→ 后续扫描与插桩继续执行
```

## 构建恢复后，应该检查哪些产物？

“不再报错”只证明 `ClassReader` 已经越过最初异常，还不能证明插桩结果正确。

继续检查：

- Root、Provider、Interceptor 类名集合是否完整；
- Group 是否仍保持按需加载，没有被错误直接注册；
- 目标 variant 的 `loadRouterMap()` 是否包含完整 `register()`；
- 修改后的 `LogisticsCenter.class` 是否正确交给 D8；
- Release 与 Benchmark 等目标变体是否真正执行插件任务。

运行时还要确认 `registerByPlugin` 生效、不进入 Dex 扫描，并回归普通页面、Provider、Interceptor 和多模块路由。

## 两轮修复最后得到什么结果？

第一轮恢复兼容新 AGP 的编译期注册；第二轮补齐 Java 21 和新版 ASM 支持。

修复后的插件发布到 JitPack，项目接入自维护版本。同时将 Java 21 兼容修改提交上游，PR 最终被接受。

线上 LOW 档 P90 最终回到原有范围：

```text
原稳定版：约 4.5s
升级候选版：约 12.8s
修复版：约 4.5s
```

准确结论是：构建升级引入的约 8.3s ARouter 增量被消除，启动恢复原基线。原本约 4.5s 的存量仍属于后续启动治理。

## 怎样让同类问题在灰度前失败？

### 检查目标 variant 的插桩产物

构建任务必须覆盖 Release、Benchmark 等实际交付或验收变体。CI 直接检查 `loadRouterMap()` 中的 `register()` 数量和内容，避免再次出现“构建成功但没有插桩”。

### 保留 Stage 和 Task 预算

```text
startup.stage.app_init
startup.task.arouter.init
```

总启动指标观察用户体验，ARouter Task 观察该组件是否重新产生异常增量。

### 建立构建兼容矩阵

```text
Gradle / AGP 版本
Java Class major version
ASM 解析版本
Visitor API
插件运行时 classpath
Release / Benchmark / 目标 variant
```

每次升级其中一层，都要重新验证完整扫描、插桩产物和运行路径。

### 固定路由功能回归

```text
普通页面路由
Provider 注册与获取
Interceptor 注册与执行
多模块路由完整性
Group 懒加载
```

性能恢复但注册列表不完整，可能只是把启动问题换成线上路由缺失。

## 三个典型判断

1. Java 21 构建不再报错：只能证明解析阶段恢复，不能证明注册列表完整。
2. Visitor 使用 ASM9：如果运行时仍加载旧 ASM，major version 65 错误仍可能存在。
3. 灰度 P90 恢复：证明用户结果恢复，但产物和功能检查仍用于确认内部路径完整。

## 常见误区

1. 把第二轮描述成运行时路由失败。
2. 认为 major version 65 是 D8 转 Dex 时才出现的问题。
3. 只修改 `Opcodes.ASM9`，不升级实际解析器。
4. 只修改依赖声明，不确认插件运行时 classpath。
5. 构建通过后，不检查最终 `register()` 产物。
6. 把恢复原基线描述成消除了全部启动存量。

## 一句话总结

Java 21 修复不只是升级一个常量，而是让解析器、Visitor、运行时依赖和目标 variant 重新形成可验证的完整插桩链。
