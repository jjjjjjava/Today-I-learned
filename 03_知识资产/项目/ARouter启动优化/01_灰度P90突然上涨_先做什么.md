# 01｜灰度 P90 从 4.5s 涨到 12.8s，先做什么？

## 本篇只解决一个问题

候选版本启动明显变慢。怎样先控制影响，再把问题收敛到可以线下分析的调用链？

## 这是存量慢，还是新版本引入的劣化？

灰度期间，LOW 档设备的启动 P90 出现明显变化：

```text
原稳定版：约 4.5s
升级候选版：约 12.8s
相对增加：约 8.3s
```

这不是“应用一直很慢”，而是候选版本相对稳定版突然变差，属于增量劣化。

两类任务的目标不同：

```text
增量治理：解释新版本为什么变差，先恢复原基线
存量治理：解释稳定版本还能怎样变快，继续降低水位
```

本次第一目标不是把原有 4.5s 全部优化掉，而是找出新增约 8.3s 来自哪里。

## 为什么先暂停灰度？

候选版已经显著突破启动预算，而且问题仍可能随着放量扩大。团队先暂停灰度，控制新增影响，再进入技术归因。

暂停放量只表示当前版本不适合继续扩大，不代表技术根因已经确定。

## 怎样从总启动下钻到 ARouter？

线上统一埋点显示：

```text
startup.total
└── startup.stage.app_init
    └── startup.task.arouter.init
```

`stage_app_init` 说明增量主要集中在应用初始化阶段；`task_arouter.init` 则是该阶段横向对比中贡献最大的任务。

这一步把调查范围从“整个启动很慢”缩到“ARouter 初始化异常”。它还不能证明 ARouter 内部究竟在执行什么。

## 为什么这次先用 CPU Profiler？

线上已经把范围缩到 `arouter.init`，异常又接近 8 秒。当前最需要回答的是：ARouter 内部是否存在一个秒级重量级调用栈？

因此选择 Android Studio CPU Profiler 的 Sampling 模式，采样间隔约 `1000 μs`。

Profiler 能快速呈现周期性采集到的调用栈，适合定位这种秒级单点异常。它不适合直接证明几十毫秒级收益，也不能替代线上指标。

线下使用代表性低端机，固定构建类型、启动入口、账号、页面数据和启动终点，让 Dex 打开、类名遍历等成本更容易显形。

## 火焰图中最大的耗时块是什么？

本地整体 Trace 约 9.74s，其中最大的聚合耗时块是：

```text
openDexFileNative ≈ 7.603s
```

沿调用栈向上追：

```text
ARouter.init
→ LogisticsCenter.init
→ ClassUtils.getFileNameByPackageName
→ DexFile.openDexFile
→ openDexFileNative
```

这说明耗时不是一个孤立的系统 native 方法，而是由 ARouter 初始化过程触发的 Dex 打开和路由表发现路径。

当前可以提出假设：

```text
编译期 register 链可能失效
→ loadRouterMap 没有完成注册
→ registerByPlugin=false
→ 运行时回退 Dex 扫描
```

Profiler 只能证明候选版本执行了 Dex 扫描。AGP 为什么导致注册失效，还需要源码、构建产物和修复后的反向结果。

## 线上 8.3s 和本地 7.603s 为什么不能画等号？

线上约 8.3s 是大量真实用户样本中，候选版 P90 相对稳定版的差值。

本地约 7.603s 是指定低端机、指定构建和 Sampling 工具下，`openDexFileNative` 的聚合采样结果。

两者方向互相印证，但设备、人群、统计方式和工具开销不同。线上数据证明影响范围，本地调用栈解释主要执行路径。

## 三个典型判断

1. 候选版 P90 为 12.8s：这是绝对水位；新增约 8.3s 才是本次增量。
2. `arouter.init` 是增量最大的 Task：可以确定调查优先级，不能单独证明 Dex 扫描。
3. Profiler 看到 `openDexFileNative`：可以确认执行路径，不能把 7.603s 直接当成线上收益。

## 常见误区

1. 把“P90 新增约 8.3s”说成“P90 是 8.3s”。
2. 把构建升级后的全部变化笼统归因给 Gradle。
3. Stage 高就直接认定内部技术根因。
4. 把 Profiler 聚合时间当成线上分位数。
5. 看到 native 方法就把问题归给 Android 系统。

## 本篇自测

1. 为什么本项目首先属于增量治理？
2. 4.5s、12.8s 和 8.3s 分别表示什么？
3. Stage 与 Task 各自把问题推进了哪一步？
4. 为什么这次先用 Profiler，而不是先做精细 Perfetto 分析？
5. 从 `openDexFileNative` 到完整根因还缺哪些证据？

## 一句话总结

先用灰度数据确认增量并暂停放量，再沿 Stage、Task 和调用栈把 8 秒级异常收敛到 ARouter 的 Dex 扫描路径。
