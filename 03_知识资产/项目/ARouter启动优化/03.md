### 正确答案

**第1题：** 把 `ARouter.init()` 丢到子线程，7.6s 会消失吗？带来什么新问题？
> **不会消失。** dex 扫描的 CPU / IO 成本还在，异步只是把它从主线程挪到子线程——总耗时、总功耗不减，设备繁忙时甚至更久。新问题是**路由可用时机**：主线程启动流程跑完、业务马上要 `navigation` 跳转时，子线程的 init 可能还没结束，`Warehouse` 还没装好，查不到 `RouteMeta` → 跳转失败，或得加额外等待 / 兜底。所以异步是「**藏**」不是「**治**」——这正是本篇否决异步方案的理由。

**第2题：** 采样模式会漏掉「几万次、每次几微秒的短方法累加成的 1s」吗？
> **会严重低估甚至漏掉。** 采样每 1ms 抓一次栈，某方法被命中的概率正比于它「在采样那一刻正好在栈上」的时长。持续 7.6s 的 `openDexFileNative` 几乎每次采样都在栈顶，必然显形；但单次几微秒的短方法远短于 1ms 间隔，绝大多数采样时刻它不在执行，即便总量累加到 1s，也只是偶发被采到，**统计上被低估、调用次数也测不准**。这种「高频短方法累加型」瓶颈得用**插桩**（精确计次）或 Perfetto——呼应模块一「采样不适合判断细粒度」。

**第3题：** 自测题——串「路由表哪来 → 启动卡哪步 → 装进哪个结构」。
> 参考串法：① **哪来**：编译期 APT `RouteProcessor` 扫 `@Route`，JavaPoet 生成 `ARouter$$Root/Group/Providers$$xxx` 类，埋进 dex；② **卡哪**：启动 `ARouter.init` 时，默认靠**运行时扫描 dex** 去找这些生成类（`openDexFileNative` 7.6s 卡这）；③ **装哪**：找到后反射 `loadInto`，把 `group→Group Class` 装进 `Warehouse.groupsIndex`，真正访问某 path 时再懒加载该组 `path→RouteMeta` 进 `Warehouse.routes`。串不顺处就是薄弱点。

## 正文内容

## 1. 项目骨架：现有两条加载路径，决定了方案空间

读 ARouter 源码后，路由表加载其实有**两条路径**，方案选型就在这两条路径里做文章：

| 路径 | 入口 | 行为 |
|---|---|---|
| **默认 dex 加载** | `ClassUtils.getFileNameByPackageName()` | 打开 dex、遍历类名、筛 `routes` 类（模块二的 7.6s 元凶） |
| **插件注册** | `LogisticsCenter.loadRouterMap()` | **默认是空壳**；被插件插桩后执行 `register(...)`，直接注册生成类、**跳过 dex 扫描** |

关键洞察：`loadRouterMap()` 这条路径**框架早就预留好了**，只是默认空着——它依赖字节码插桩来「填内容」。这决定了最优方案不是另起炉灶，而是**把这条预留路径激活**。

## 2. 项目骨架：三方案取舍

### 2.1 异步初始化 —— 否决

把 init 挪到子线程。**否决理由**（02 思考题已推导）：没有消除 dex 扫描成本，只是搬运；还引入**路由可用时机**问题——业务要跳转时 init 可能没跑完，跳转失败或要兜底。是「藏」不是「治」。

### 2.2 更换路由框架 —— 否决

换掉 ARouter 自然绕开它的扫描机制。**否决理由**：项目已**大量**使用 ARouter（页面跳转、Provider、Interceptor、多模块路由），替换成本和回归风险都很高，性价比差。

### 2.3 接入 register 插件 —— 选定

**选定理由**：它最贴近根因。不再依赖启动期 dex 扫描，而是用字节码插桩让预留的 `loadRouterMap()` 生效，把「找路由表类」这件事**前移到编译期**准备好。

本质一句话（面试主线必背）：

> **把「启动期打开 dex、遍历类名找 routes 类」替换成「运行时执行 `loadRouterMap()` 里几行简单的 `register(...)` 方法调用」——重扫描从运行时挪到编译期，启动时不再逐个开 dex，所以耗时明显缩短。**

接下来三段 🔧 回答面试官必然追问的「这个插桩到底怎么做的」。

## 3. 🔧 机制注脚一：为什么非得用 ASM，不能直接改代码

插件介入的时机，决定了它**只能改字节码**：

```text
ARouter 插件干活时，源码已经被编译成 .class 字节码，不再是 .java
```

于是想往 `loadRouterMap()` 里插 `register("xxx")`：

- ❌ 不能像写业务代码一样改 `.java`——源码阶段早过了；
- ❌ 不能把 `.class` 当文本，搜 `loadRouterMap` 字符串再拼内容——`.class` 是结构化二进制（常量池、方法表、字节码指令、栈帧帧）。

要安全地「找到某方法、在它的 `return` 指令前插入新的调用指令」，就需要 **ASM** 这种能读懂、改写字节码结构的工具。

> 一句话：**ASM 在 class 后处理阶段，结构化地修改 `.class`，把 `register("生成类名")` 插进 `loadRouterMap()`。**

## 4. 🔧 机制注脚二：插件怎么挂进构建流程

要理解插桩发生在哪，先看 Android 从点击运行到出包的四个阶段：

```text
① 配置阶段   Gradle 读配置，AGP 创建 debug/release 等 variant
             ARouterPlugin 在这阶段为每个 variant 注册 TransformAllClassesTask
② 编译阶段   JavaCompile/KotlinCompile 编译源码
             Javac 跑 RouteProcessor（APT）生成 ARouter$$Root$$xxx 等 .java → 再编成 .class
③ 字节码后处理  AGP 汇总该 variant 所有 class
             TransformAllClassesTask 接管，扫路由表 class，对 LogisticsCenter.class 做 ASM 插桩
④ Dex/打包   D8 把处理后的 class 转 dex，打包 APK/AAB
```

记牢这条边界（面试高频）：

```text
RouteProcessor（APT）= 阶段②，处理「源码和注解」，生成路由表类
ASM 插桩            = 阶段③，处理「已编译的 .class 字节码」，把路由表类注册进初始化逻辑
```

插件**怎么接管 class**——核心是 AGP 的 **Artifacts API**，在 class 进 D8 之前截下 `CLASSES` 产物：

```kotlin
variant.artifacts.forScope(ScopedArtifacts.Scope.ALL)
    .use(taskProvider)              // TransformAllClassesTask
    .toTransform(
        ScopedArtifact.CLASSES,
        TransformAllClassesTask::allJars,        // jar 形式的 class
        TransformAllClassesTask::allDirectories, // 目录形式的 class
        TransformAllClassesTask::output          // 处理后输出
    )
```

所以它**不是「编译结束回调」，而是插进了 AGP 的 class artifact 管线**——拿到全量 class，处理完输出新的一份给 D8。

## 5. 🔧 机制注脚三：具体插哪两步 + 为什么要复制 class

插桩任务做两件事：**先扫描收集，再定点插入**。

**第一步：扫描路由表 class，收集生成类名。** 只扫 `com/alibaba/android/arouter/routes/` 包，用 ASM `ClassReader` 读 class，在 `ScanClassVisitor` 里看它实现了哪个接口：

```text
IRouteRoot        → 这是 Root 路由表
IInterceptorGroup → 这是 Interceptor 路由表
IProviderGroup    → 这是 Provider 路由表
```

扫完就知道「有哪些生成类、各是什么类型」。

**第二步：ASM 定点插桩 `loadRouterMap()`。** 目标固定是 `LogisticsCenter.class` 的 `loadRouterMap()` 方法：

```text
ClassReader 读 LogisticsCenter.class
  → ClassVisitor 找到 loadRouterMap 方法
  → MethodVisitor 遍历指令，在 return 前插入 register 调用
  → ClassWriter 输出修改后的字节码
```

插入的等价代码：

```java
LogisticsCenter.register("com.alibaba.android.arouter.routes.ARouter$$Root$$app");
LogisticsCenter.register("com.alibaba.android.arouter.routes.ARouter$$Interceptors$$app");
LogisticsCenter.register("com.alibaba.android.arouter.routes.ARouter$$Providers$$app");
```

运行时执行 `loadRouterMap()` 就直接注册这些类，不必再扫 dex。

> **追问「为什么任务要把其他 class 原样复制？」** `TransformAllClassesTask` 是 transform 任务——它**消费**旧的 `CLASSES`，就**必须产出一份完整的新 `CLASSES`**。所以不能只改 `LogisticsCenter.class`，其余 class 必须原样复制到输出，否则后续 D8 拿不到完整 class、或出现重复 entry。处理策略是：普通 class 原样复制；路由表 class 扫描后原样复制；`LogisticsCenter.class` 先缓存不复制原版，最后写入插桩后的版本。

## 6. 收束：方案的「前移」本质

```text
默认方案：编译期生成路由表类 →【运行时扫 dex 找它们】→ loadInto → Warehouse
插件方案：编译期生成路由表类 →【编译期 ASM 把它们写进 loadRouterMap】→ 运行时直接 register → Warehouse
                                          ↑
                              重活从「运行时扫描」前移到「编译期插桩」
```

> 顺带回收一个旧追问：**SP 缓存为什么不算根治？** 它只缓存「上次扫到的类名集合」，仍属于 dex 扫描这条路线的优化；新安装 / 包更新 / debug 频繁安装时缓存失效就回退扫 dex。而 register 插桩是直接换了路线，不依赖缓存命中——这也是我打 debug 包反复触发 10s 时，唯一稳定有效的根治办法。

理论闭环了。但工程落地远没这么顺——模块四讲三个真实的坑：原版插件不兼容 AGP8、Java 21 的 `Unsupported class file major version 65`、以及「编译通过但插桩根本没生效」的 variant 命名坑。
