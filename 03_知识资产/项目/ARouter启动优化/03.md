### 正确答案

**第 1 题：从 `@Route` 到 `startActivity()` 的完整链路**

> `RouteProcessor` 在编译期扫描 `@Route`，生成 Group 的 `path → RouteMeta` 和 Root 的 `group → Group Class`。初始化时注册 Root，把分组索引写进 `Warehouse.groupsIndex`。运行时 `build(path)` 创建 Postcard，`navigation()` 进入 `completion()`；先查 `Warehouse.routes`，找不到就从 `groupsIndex` 取得 Group Class，反射调用 `loadInto(routes)`，再次查到 RouteMeta，补全 Postcard 的 `destination/type`，最后组装 Intent 并 `startActivity()`。

**第 2 题：为什么不在初始化时注册全部 Group？**

> Root 已经提供了 Group 的间接索引。Group 的职责是把某个分组下的具体 RouteMeta 按需写入 `routes`。启动时全量加载 Group 会破坏分组懒加载，把所有分组的反射与路由对象创建成本提前到启动期。

**第 3 题：证明插件路径生效的最小闭环**

> 构建期确认目标 variant 处理后的 `LogisticsCenter.loadRouterMap()` 中存在完整 `register()` 列表；运行时在清除/失效 ARouter 路由类名 SP 缓存或升级首启场景下，确认 `register()` 被执行、`registerByPlugin` 为 true，且没有进入 `ClassUtils.getFileNameByPackageName → openDexFileNative`；最后用路由功能回归和灰度指标确认结果。灰度正常能证明用户结果恢复，但单独不能证明内部一定走了哪条路径。

## 1. 插件模式原理介绍

插件模式的目标，是在 Java/Kotlin 源码编译完成后接管 Class 产物，先收集路由表类，再修改 `LogisticsCenter.loadRouterMap()`，最后将完整 Class 集合交给 D8。

### 1.1 Artifacts API 接入与构建边界

整个构建链可以压成四段：

```text
1. 配置阶段
   Gradle 读取配置，AGP 创建 variant
   插件为目标 variant 注册 Class 处理任务

2. 源码编译阶段
   Java / Kotlin 源码被编译
   APT RouteProcessor 生成路由表 Java，再编译成 Class

3. 字节码后处理阶段
   插件取得当前 variant 的全部 Class 产物
   扫描路由表 Class，并用 ASM 修改 LogisticsCenter.class

4. Dex 与打包阶段
   D8 将处理后的 Class 转成 Dex
   最终生成 APK / AAB
```

两项技术的边界必须说准：

```text
APT：处理源码、注解和 Element，生成路由表源码
ASM：处理已经编译完成的 .class，修改 loadRouterMap() 的字节码
```

APT 不负责修改 `LogisticsCenter.class`，ASM 也不负责扫描业务源码中的 `@Route`。前者生产路由表，后者把路由表的注册调用写进初始化入口。

#### 1.1.1 插件怎样取得当前 variant 的全部 Class

兼容新 AGP 的插件通过 **Artifacts API** 接入 Class artifact 管线，而不是继续依赖旧 Transform API。

核心关系可以表示为：

```kotlin
variant.artifacts
    .forScope(ScopedArtifacts.Scope.ALL)
    .use(taskProvider)
    .toTransform(
        ScopedArtifact.CLASSES,
        TransformAllClassesTask::allJars,
        TransformAllClassesTask::allDirectories,
        TransformAllClassesTask::output
    )
```

AGP 把 Class 产物分成两种输入：

```text
allDirectories：目录形式的 Class
allJars：Jar 形式的 Class
```

任务消费旧的 `CLASSES`，必须输出一份新的、完整的 `CLASSES`，后续 D8 只使用这份输出。因此任务不是“找到一个 Class 就原地改一下”，而是：

```text
遍历全部输入
→ 普通 Class 原样复制
→ 路由表 Class 扫描后原样复制
→ LogisticsCenter.class 暂存，最后写入修改后的版本
→ 输出完整 Class 集合给 D8
```

如果其他 Class 没有复制到输出，D8 得不到完整产物；如果原始与修改后的 `LogisticsCenter.class` 都写入，还可能出现重复 Entry。

### 1.2 路由表 Class 扫描

#### 1.2.1 Class Entry 路径只负责筛选候选类

插件遍历 Jar Entry 或目录 Class 时，先根据路径筛选：

```text
entryName.startsWith("com/alibaba/android/arouter/routes/")
```

这一步只说明 Class 位于 ARouter 生成类的固定包下。它不是直接根据：

```text
ARouter$$Root$$
ARouter$$Providers$$
ARouter$$Interceptors$$
```

这些类名前缀确定最终类型。

这和运行时 Dex 扫描不同：

| 模式 | 第一层过滤 | 最终类型识别 |
|---|---|---|
| 运行时 Dex 扫描 | 类全限定名的包名前缀 | 生成类名前缀 |
| 编译期插件扫描 | Class Entry 包路径 | Class 实现的接口 |

#### 1.2.2 ClassReader 与 ScanClassVisitor 识别接口

候选 Class 会交给 ASM：

```text
ClassReader
→ ScanClassVisitor.visit(..., name, ..., interfaces)
```

`visit()` 能取得当前 Class 的内部类名 `name` 和它实现的接口 `interfaces`。插件关注三个接口：

```text
IRouteRoot        → Root 列表
IProviderGroup    → Provider 列表
IInterceptorGroup → Interceptor 列表
```

所以完整判断是：

```text
包路径筛选候选 Class
→ ClassReader 解析
→ visit() 检查 interfaces
→ 把 name 收集进对应列表
```

Group 实现的是 `IRouteGroup`，但插件不把所有 Group 直接写进 `loadRouterMap()`，因为 Root 已经保存 `group → Group Class`，具体 Group 要继续保持运行时懒加载。

### 1.3 LogisticsCenter 插桩

#### 1.3.1 为什么必须先扫描全部 Class

插件还要从全部输入中定位：

```text
com/alibaba/android/arouter/core/LogisticsCenter.class
```

找到后不会立即插桩，而是先缓存原始字节码。原因是 Class 遍历顺序不确定：

```text
可能先遇到 LogisticsCenter.class
→ 当时只收集到一部分 Root / Provider / Interceptor
→ 如果立即插入 register()
→ 后面才遇到的路由表类会永久遗漏
```

正确过程必须分成两阶段：

```text
阶段一：扫描全部 Class
├── 收集完整 Root / Provider / Interceptor 类名
├── 缓存 LogisticsCenter 原始字节码
└── 复制其他 Class

阶段二：统一修改 LogisticsCenter.class
├── 使用完整类名集合插入 register()
└── 输出修改后的 LogisticsCenter.class
```

这里缓存的目的不是性能优化，而是解决**遍历顺序与全量信息依赖**：插桩结果依赖全部扫描结果，所以必须等信息完整后再生成。

#### 1.3.2 ASM 怎样修改 loadRouterMap

##### 1.3.2.1 Visitor 链各自负责什么

修改目标时使用：

```text
ClassReader
→ ClassVisitor
→ MethodVisitor
→ ClassWriter
```

职责分别是：

| 组件 | 职责 |
|---|---|
| `ClassReader` | 解析 `LogisticsCenter.class` 的结构和方法字节码 |
| `ClassVisitor` | 遍历类，并在 `visitMethod()` 中找到 `loadRouterMap()` |
| `MethodVisitor` | 遍历目标方法的 JVM 指令，在返回点插入新指令 |
| `ClassWriter` | 输出修改后的 Class 字节数组 |

目标方法是无参、返回 void：

```text
loadRouterMap()V
```

##### 1.3.2.2 为什么在 RETURN 前插入

原始 `loadRouterMap()` 基本是空方法，最终执行 `RETURN`。`MethodVisitor.visitInsn(opcode)` 遍历到 void 方法的：

```text
Opcodes.RETURN
```

时，在它前面为每个收集到的生成类插入一次 `register()` 调用。这样无论源码方法体里原先有什么逻辑，只要正常返回，注册调用都会在退出前执行。

##### 1.3.2.3 两条关键 JVM 指令

Java 等价代码是：

```java
LogisticsCenter.register(
    "com.alibaba.android.arouter.routes.ARouter$$Root$$app"
);
```

ASM 插入的不是 Java 源码，而是 JVM 指令。

第一步，用 `LDC` 把类名字符串压入当前方法的操作数栈：

```kotlin
methodVisitor.visitLdcInsn(className)
```

第二步，调用静态方法：

```kotlin
methodVisitor.visitMethodInsn(
    Opcodes.INVOKESTATIC,
    "com/alibaba/android/arouter/core/LogisticsCenter",
    "register",
    "(Ljava/lang/String;)V",
    false
)
```

五个参数分别表示：

```text
INVOKESTATIC：静态方法调用
owner：LogisticsCenter 的 JVM 内部类名
name：register
descriptor：(Ljava/lang/String;)V
isInterface：false
```

方法描述符：

```text
(Ljava/lang/String;)V
```

表示接收一个 `java.lang.String` 参数，返回 `void`。`LDC` 先把这个 String 压栈，`INVOKESTATIC` 再从栈中消费它作为参数。

最后 `ClassWriter` 输出修改后的 `LogisticsCenter.class`，替换原始版本，再交给 D8。

#### 1.3.3 从编译期插桩到运行时生效

完整链路如下：

```text
@Route / @Interceptor 等注解
→ APT 生成 Root / Group / Provider / Interceptor Class
→ AGP Artifacts API 把 allJars / allDirectories 交给插件
→ 路径筛选候选类
→ ClassReader + interfaces 识别 Root / Provider / Interceptor
→ 收集完整类名集合
→ ASM 修改 LogisticsCenter.loadRouterMap()
→ 在 RETURN 前插入 register(类名)
→ ClassWriter 输出修改后的 Class
→ D8 生成 Dex并打包
```

运行时：

```text
ARouter.init
→ LogisticsCenter.init
→ loadRouterMap
→ register(生成类名)
→ 反射实例化并 loadInto(Warehouse)
→ registerByPlugin = true
→ 跳过 ClassUtils.getFileNameByPackageName
→ 不再打开并遍历 Dex
```

插件消除的是“运行时发现生成类”的成本，不是删除 `loadInto()`，也不是把全部 Group 提前加载。

## 2. 为何有问题

第一轮接入兼容新 AGP 的插件后，ARouter 恢复了编译期注册。后来项目从 Java 17 升级到 Java 21，构建阶段又出现：

```text
Unsupported class file major version 65
```

这次异常发生在生成 APK 之前，不是 ARouter 运行时查表失败，也不是 D8 转 Dex 失败，而是插件读取编译后的 Class 时失败。

定位时需要回答三件事：APT 生成的 Class 何时进入插件，插件如何识别并修改 `LogisticsCenter.class`，以及 ASM 为何在进入 Visitor 之前就抛错。

### 2.1 Class 文件的 major version

`.class` 文件头包含 major version，用来表示该 Class 格式对应的 Java 版本。关键对应关系是：

```text
Java 17 → major version 61
Java 21 → major version 65
```

### 2.2 旧 ASM ClassReader 无法解析 Java 21

ASM 的 `ClassReader` 构造时要先读取并校验这个版本，确认当前 ASM 是否支持解析该格式。原插件使用的 ASM 较旧，不认识 major version 65，于是抛出：

```text
Unsupported class file major version 65
```

异常发生顺序是：

```text
读取 Class 文件头
→ 检查 major version
→ 发现超出旧 ASM 支持范围
→ 直接抛异常
```

此时还没有进入：

```text
ScanClassVisitor.visit()
ClassVisitor.visitMethod()
MethodVisitor.visitInsn()
ClassWriter
```

所以根因不是：

- ARouter 的路由逻辑错误；
- 接口识别规则失效；
- `register()` 指令写错；
- D8 打包不支持。

准确根因是：

> 插件运行时使用的旧 ASM `ClassReader` 无法解析 Java 21 生成的 Class 文件。

## 3. 解决方案

我们 fork 插件后做了三项核心修改。

### 3.1 升级完整 ASM 依赖族

```kotlin
implementation("org.ow2.asm:asm:9.7")
implementation("org.ow2.asm:asm-commons:9.7")
implementation("org.ow2.asm:asm-tree:9.7")
```

三个模块保持同一版本，避免核心解析、工具类和 Tree API 之间出现版本错配。

### 3.2 Visitor API 调整为 ASM9

```text
Opcodes.ASM7 → Opcodes.ASM9
```

这里的 API 常量表示 Visitor 按哪个 ASM API 级别工作。它和 `ClassReader` 能否解析 major version 是相关但不同的两层：只改常量、仍运行旧 ASM Jar，无法让旧 `ClassReader` 突然认识 Java 21。

### 3.3 确保插件运行时真正解析到新版 ASM

Gradle 插件有自己的运行时 classpath。即使源码声明了 ASM 9.7，如果依赖冲突、传递依赖选择或打包方式导致运行时仍加载旧 ASM，异常依然存在。

因此验证不能停在“依赖文件改了”，还要确认：

```text
插件编译依赖是 ASM 9.7
→ 插件运行时 classpath 实际解析到 ASM 9.7
→ ClassReader 能读取 major version 65
→ 后续扫描与插桩链真正执行
```

### 3.4 Debug 变体构建耗时优化

后续部分同事反馈 Debug 构建较慢。因此为 Debug 变体增加判断，在日常调试时跳过 Artifacts 字节码插桩任务，减少对全量 Class 产物的处理。

Debug 跳过插桩是构建效率选项，不能用于证明生产修复效果。Release 和用于性能验收的 Benchmark 变体必须显式启用插桩。

## 4. 闭环

### 4.1 Java 21 构建与插桩验证

第二轮的验证分四层：

1. **解析层**：Java 21 Class 能通过 `ClassReader`，不再出现 major version 65 异常。
2. **收集层**：Root、Provider、Interceptor 类名集合完整，Group 不被错误地全量注册。
3. **产物层**：目标 variant 的 `LogisticsCenter.loadRouterMap()` 中存在完整 `register()` 调用，处理后的 Class 能继续交给 D8。
4. **运行层**：升级首启/缓存失效条件下 `registerByPlugin` 生效，不进入 Dex 扫描；页面、Provider、Interceptor 和多模块路由均正常。

“构建成功”只覆盖第一层和部分打包链路，不等于插桩目标正确、类名收集完整或运行时真的跳过 Dex 扫描。

### 4.2 自维护插件发布

修复完成后，将插件版本发布到 JitPack，并作为项目的自维护插件接入，使项目可以在 AGP 8 和 Java 21 环境下继续使用编译期注册路径。

### 4.3 上游回馈

同时将 Java 21 兼容修复提交给上游项目。PR 最终被接受，上游作者也对贡献进行了致谢。

### 4.4 第二轮面试表达

> 第一轮恢复编译期注册后，项目升级 Java 21 又出现 `Unsupported class file major version 65`。为了定位，我把插件链路拆成四段：APT 先生成路由表 Class；AGP Artifacts API 把当前 variant 的 `allDirectories` 和 `allJars` 交给插件；插件先按 `com/alibaba/android/arouter/routes/` 路径筛候选类，再用 ASM `ClassReader` 检查实现接口，收集 Root、Provider、Interceptor；扫描全部 Class 后，再用 `ClassVisitor` 和 `MethodVisitor` 找到 `LogisticsCenter.loadRouterMap()`，在 `RETURN` 前插入 `LDC + INVOKESTATIC register`，最后由 `ClassWriter` 输出给 D8。Java 21 的 Class major version 是 65，旧 ASM 在读取文件头时就不认识，因此甚至还没进入 Visitor。我们 fork 插件，将 asm、asm-commons、asm-tree 升到 9.7，把 API 调整到 ASM9，并确认插件运行时真正使用新版依赖。修复后发布自维护版本，同时向上游提交 PR 并被接受。
