### 正确答案

**第1题：** 为什么 `loadRouterMap()` 只 register `Root / Interceptors / Providers`，不 register `Group`？
> 因为 **Group 是懒加载的**。init 时只 register Root，`Root.loadInto()` 把 `group→Group Class` 装进 `Warehouse.groupsIndex`；Group 类本身**不在启动时注册**，而是真正访问某个 `path`、`routes` 里没有时，才按 group 从 `groupsIndex` 找到对应 Group Class，反射加载、`loadInto(routes)`。所以 Group 的加载入口是「按需触发」，不该在启动时全量 register。只有 `Root / Interceptors / Providers` 这些「启动就要全量装进 `Warehouse` 索引」的才需要 register。这正是分组懒加载的体现——插桩只替代了「全量索引的装载」，没破坏懒加载。

**第2题：** 为什么偏偏插 `loadRouterMap()` 这个「默认空壳」方法？体现什么设计意图？
> `loadRouterMap()` 是 `LogisticsCenter.init()` 里**专门留给插件填注册逻辑的钩子**：默认空 → 回退 dex 扫描；被插桩填了 `register(...)` → 走插件注册并跳过扫描（配合 `registerByPlugin` 标志判断）。作者预留它体现**插桩友好 / 开闭**设计——把「是否走插件注册」做成一个**可被字节码填充的开关方法**，插件无需改动 init 主流程，只往这**一个固定方法**插指令，插桩目标固定、风险最小、向后兼容（没插件也能正常跑）。

**第3题：** 某模块路由表类忘实现 `IProviderGroup`（或包名写错没落在 `routes` 包下），会怎样？编译期还是运行时暴露？
> 插桩扫描只认「`routes` 包下 + 实现了指定接口」的类。包名错或没实现接口 → **扫描收集不到它** → `loadRouterMap()` 里不会为它插 `register` → 运行时它不会被注册进 `Warehouse`。**编译期不报错**（插桩是「尽力收集」，无强校验），所以编译期发现不了；要到**运行时** `navigation` 那个 path 时，`Warehouse` 查不到 `RouteMeta`、跳转失败（走降级或报找不到路由）才暴露。这是插桩方案的隐患——**静默丢失**，得靠功能回归覆盖。（实务里 APT 生成的类一定实现正确接口，真正风险在包名 / 混淆 keep 配置。）

## 正文内容

## 1. 项目骨架：落地不是「接一个现成插件」

方案选定 register 插桩后，真正落地踩了三个坑。这段在面试里值钱，不在于「我会插桩」，而在于**每一步排查都不是凭感觉，而是查证据、补日志、定位到根因**。

### 1.1 坑一：原版 arouter-register 不兼容 AGP8

阿里官方确实有 `arouter-register` 插件，但**太老了，2021 年后就不维护**，不兼容当前项目的 AGP8 环境。

> **关键细节（面试一定要说）：** 这个判断不是凭空猜的——我**先查了 GitHub issue**，确认社区里已经有人反馈 AGP8 兼容问题，所以没有在原插件上硬接，而是去找兼容 AGP8 的替代。

这一步体现的是「**先验证再动手**」：不假设、不在一个已知死路上耗。

### 1.2 坑二：Java 21 字节码读取失败

换用一个兼容 AGP8 的三方 ARouter 插件、把源码接进项目验证后，又撞上：

```text
Unsupported class file major version 65
```

这个错在**插件源码执行过程中**暴露：插件用 ASM 的 `ClassReader` 读编译后的 class 时失败了。

> 🔧 **机制注脚：为什么是「major version 65」？**
> 插件处理的是 `.class` 字节码，不是 Java 源码。ASM 的 `ClassReader` 读 class 文件时，**必须先认识 class 文件头里的 major version**。版本对应关系：
>
> ```text
> Java 17 → major version 61
> Java 21 → major version 65
> ```
>
> 插件内部用的 ASM 版本太旧，**不认识 Java 21 编译出来的 class 版本号**，所以一读字节码就抛 `Unsupported class file major version 65`（Java 17 环境则是 61）。
> **根因一句话：旧 ASM 的 `ClassReader` 读不懂新版本 JDK 编译的 class 文件头。** 修复方向：确保插件运行时真正使用支持新 class version 的 ASM。

于是我 **fork 了插件自己修**，主要三件事：

```text
① 升级 ASM 版本（如 asm / asm-commons / asm-tree 升到 9.7），支持 Java 21 class
② 检查 ASM API 常量，例如 Opcodes.ASM7 → ASM9
③ 确保插件运行时真正使用正确的 ASM 依赖（不是编译能过就行，运行时也得是新版）
```

修复后**发布自己的 ARouter Gradle 插件**供项目接入，并把修复 **提了 PR 给对方项目**。

> **亮点（面试加分，但别吹）：** 对方是百星级开源项目，作者邮件回复致谢，并在项目里对我的贡献做了致谢。这条证明的是「我能改到上游、修的是真根因」，不是面子话。

### 1.3 坑三：编译通过 ≠ 优化生效

这是最容易被忽视、也最能体现工程严谨的一坑。

接入自己修复的插件后，**项目能编译成功，但启动耗时没有明显下降**。

如果到这一步就以为「方案无效」，就前功尽弃了。我的处理是**继续看证据**：

```text
看构建日志 + 插件日志
  → 发现没有「插件应用到目标 variant」的日志
  → 说明字节码插桩任务根本没作用到当前构建变体
  → 在插件里补日志，结合 Gradle 编译过程排查
  → 定位到：variant 命名处理问题
```

根因：项目的变体名是**驼峰命名**，原插件在为变体配置任务 / 匹配任务时**没正确处理驼峰**，导致对应 variant 没走到插桩逻辑。

```text
修复 variant 命名兼容后 → loadRouterMap() 才真正被插桩
→ 方法里真插入了 register(...) → 运行时 ARouter init 才跳过 dex 扫描
```

> **这段的方法论才是核心：** 「编译通过」只代表插件**装上了**，不代表插桩**作用到了**。判断是否真生效，要看「插桩任务有没有作用到目标 variant」，而验证手段是**补日志看构建过程**，不是看启动快没快这个表象。

## 2. 项目骨架：回归验证——分场景看收益

性能验证**分首次冷启动和后续启动**两个场景看，因为它们走的加载路径不同。

### 2.1 首次冷启动（收益最明显）

首次启动没有可用的 SP 缓存，原方案必走 dex 扫描（开 dex、遍历类名）。插桩后变成 `loadRouterMap()` 里的几行 `register(...)` 调用：

| 指标          | 优化前     | 优化后          |
| ----------- | ------- | ------------ |
| ARouter 初始化 | ≈ 7.84s | **100ms 以内** |
| 整体冷启动       | ≈ 9.4s  | **≈ 1.54s**  |

### 2.2 后续启动（原本可能命中 SP 缓存）

后续启动原方案可能命中 SP 缓存，不一定每次重扫 dex。这个场景原方案大致是「一次 `SharedPreferences` 读取 + 遍历缓存中的 routes 类名 + 反射装载」，正常**几十毫秒级**（取决于路由表数量和设备 I/O）。插桩方案进一步变成直接执行 `register(...)`，通常压到**几毫秒到十几毫秒级**，并且**不受新安装 / 包更新 / debug 安装导致缓存失效的影响**。

> 所以收益不只是「快了」，而是**稳定的快**——消除了「缓存失效就回退秒级扫描」的尾部抖动。这正是模块二里我打 debug 包反复触发 10s 的根治。

### 2.3 功能回归清单

插桩动的是「路由表怎么注册」，所以回归重点是**所有依赖路由表的能力 + 各种构建变体**：

```text
✓ 普通页面路由跳转正常
✓ Provider 注册和获取正常
✓ Interceptor 注册和执行正常
✓ 多模块路由表没有缺失（呼应 03 思考题三：防静默丢失）
✓ debug / release 构建正常
✓ 不同 build variant 构建正常（呼应坑三的 variant 命名）
✓ AGP8 + Java21 环境下插件稳定可用
```
