## 上一篇思考题复盘

> 关键前置纠错（影响题 1）：**`RV` = RecyclerView，和 `RelativeLayout` 是两个控件。** 双重测量是 RelativeLayout 的行为；trace 里 `RV OnLayout 518ms` 是 RecyclerView。

### 你的回答评估
- **第 1 题**（ConstraintLayout 为何断崖式降）：⚠️ 你用"rv 关系型布局 2ⁿ"解释——机制对、但名字错（那是 RelativeLayout 不是 RecyclerView）。
- **第 2 题**（反射 vs 手写 new View）：❌ 你答"没太大差异"，错。
- **第 3 题**（P0 先打哪类、为何不先打 binder）：✅ 对，ViewPager 懒加载 + WebView。

### 正确答案
**第 1 题：** 深层嵌套 RelativeLayout 每层子 View 测两遍，n 层嵌套 ≈ 2ⁿ。换成 ConstraintLayout，它用**一次约束求解**确定所有相对关系，把"测量次数"从指数级压回近似线性——所以不是降一点，是**断崖式**消掉了重复测量。
> ⚠️ 这题前提是你的瓶颈来自**嵌套 RelativeLayout 的 measure**。若瓶颈是 RecyclerView 的 `RV OnLayout`，那要换的是"恢复懒加载 / 减首屏 item"，不是换 ConstraintLayout——**别把两个机制的药开混了**。

**第 2 题：** 有本质差异。XML inflate = `Class.forName` + **反射 newInstance** + 解析 `AttributeSet`/`TypedArray`（反射 + 属性解析双重开销）；手写 `new View()` = 直接构造 + setter，无反射无解析。单 View 差异小，首屏成百上千个累积就明显——这是 **X2C / AsyncLayoutInflater / Compose** 的动机。启发：首屏关键/高频 View 值得手写创建。

**第 3 题：** P0 先打 ViewPager 全量预加载 + WebView，因为**收益确定、改动聚焦**。不先打 binder 579 次：它**分散溯源到生命周期/系统服务/window/悬浮组件多处**，改动面大、收益不确定，是典型"看着吓人但不好下手"的指标，放后面。

## 正文内容

### 1. 总纲：首屏路径裁剪

```text
TTFD 前只做"用户第一屏可见且必须"的事。
非首屏 Tab、非首屏模块、WebView、通用悬浮组件、非必要初始化 —— 全部后置或按需加载。
```

按"收益确定性 + 改动聚焦度"分三级 P0/P1/P2。

### 2. P0：收益最确定、改动最聚焦

**① ViewPager 恢复懒加载**——移除启动期全量 `offscreenPageLimit = size`，冷启动只保证首页 Tab 可用，其余 Tab 切到再加载。直接砍掉非首屏 Fragment 的 inflate / RV layout。

**② WebView 移出启动路径**——删 XML 静态 WebView，换轻量 `FrameLayout` 占位，真正进 Web 场景再动态创建、用完按生命周期 destroy：
```kotlin
private var webView: WebView? = null
private fun ensureWebView() = webView ?: WebView(this).also {
    webView = it; webContainer.addView(it)
}
```

### 3. P1：继续减首屏 UI 压力（需更多回归）
- 首页模块首屏裁剪、分批渲染：TTFD 前只 add 首屏可见模块，其余首帧后分批 `addView`。
- BaseActivity 悬浮组件（巡店/客服/公告/录像）首帧后或按需创建。
> 面试表达：P1 和业务展示强相关，需和产品确认，用开关 + 回归控风险——别说"不知道业务逻辑"。

### 4. P2：Application 同步初始化瘦身（为什么排最后）

实测 `bindApplication wall = 220.5ms / self = 69.3ms`，相比 `inflate 700 / RV 518 / traversal 750`，**Application 阶段根本不是最大矛盾**，所以排 P2。后续把下载、OSS、缓存清理、埋点、非首屏 SDK 延迟到 Idle 或首帧后。

> 🔧 **机制：为什么 Application 阶段"看着该砍"但其实占比小、且砍不动多少。**
> `handleBindApplication` 在**主线程**串行做：创建 LoadedApk → `makeApplication`（反射 new Application）→ **`installContentProviders`（每个 Provider 反射 new + 同步 onCreate）** → `callApplicationOnCreate`。注意 **ContentProvider.onCreate 先于 Application.onCreate**，三方 SDK 夹带的 Provider（FirebaseInitProvider 等）会悄悄串行消耗启动时间（审查：`adb shell dumpsys package <pkg> | grep -i provider`）。
> 但**这些都串在主线程**——这也解释了"异步初始化为什么有天花板"：生命周期回调本身必须串行在主线程（Binder 线程只负责封消息、主线程 mH 串行处理），你能异步的只是 onCreate 里**你自己的**初始化逻辑，框架链路砍不动。本项目这段总共才 220ms，ROI 低，故 P2。

### 5. 验证：同口径复测（P0 后）

| 指标 | 优化前 | P0 后 | 变化 |
|---|---:|---:|---:|
| **TTFD** | ~2790ms | ~1774ms | **↓ 约 1016ms** |
| inflate | 106 次 / 700.8ms | 62 次 / 294.3ms | 少 44 次，↓406ms |
| RV OnLayout | 29 次 / 518.3ms | 18 次 / 178.4ms | 少 11 次，↓340ms |
| traversal | 750.1ms | 327.2ms | ↓423ms |
| layout | 516.1ms | 179.5ms | ↓337ms |
| WebView | 2 次 / 229.9ms | 0 | 从区间消失 |
| binder | 579 次 / 226.3ms | 382 次 / 183.5ms | 少 197 次 |

> 关键：必须**同口径**（同采集、同 TTFD SQL、同聚合）。数据证明是真少创建了 View、少做了 RV layout，不是时间波动。

### 6. 回归取舍：两个"治本不治标"的决策

P0 的低缓存提速了，但**暴露了被全量缓存掩盖的运行期问题**——这才是面试最出彩的部分（讲取舍）。

**6.1 门店页频繁切换重建** → 分阶段缓存
门店页是重页面（多层 Fragment / EventBus / RV / 缓存恢复）。低缓存下频繁切 Tab 会反复 destroy/recreate，出现 EventBus 早到、view 未 ready、白屏。

> 🔍 **怎么判断白屏是"生命周期时序"而非渲染/数据问题（面试追问高频）：**
> 1. **复现规律锁变量**：白屏只在**频繁来回切 Tab 后**出现，冷启动首次进门店页正常。同样的代码/布局/数据，唯一变量是"第 N 次销毁重建" → 排除静态布局/数据 bug，锁定**重建时序**。
> 2. **时间轴打点拿铁证**：在 Fragment `onAttach / onCreateView / onViewCreated / onResume` 及其数据源（EventBus、数据回调、adapter）都打**带时间戳的 log**；白屏时导出按时间排，发现 **数据/事件到达的时刻 _早于_ `onViewCreated`（view ready）**——事件来时消费方还没准备好被丢弃，等 view ready 时数据早来过且丢了，UI 拿不到数据 → 白屏。
> 3. **反证一锤定音**：数据其实正常返回了（排除"数据问题"）；一旦加回缓存让 Fragment 不重建，白屏消失 → 反向锁定病因是**重建时序**，不是渲染、不是数据。

**没有简单恢复 `offscreenPageLimit = size`**（那会抵消 P0），而是**分阶段缓存**：冷启动保持低缓存；首次进门店页后把主 ViewPager `offscreenPageLimit` 提到 3；兼顾启动性能与运行期稳定。

**6.2 "我的"页入口状态丢失** → 状态快照 + replay（揭晓你那个伏笔）
> 🔧 **本质：状态生产早于 UI 消费 ready。**
> 入口显隐 / 红点通过一次性 `EventBus.post(...)` 下发。低缓存后 `FragmentMineNew` 不再启动期提前创建，**事件发出时它还没创建 / 没注册 EventBus → 普通事件被丢弃** → 费用中心/审批等 item 加载不全。
>
> **这就是原开发者当初设 `offscreenPageLimit = 5` 的真实原因**——不是手滑，是用"提前创建所有 Fragment"**掩盖**这个时序 bug。但代价是回退了懒加载、加重冷启动。
>
> 治本方案（latest-wins 状态适合快照 replay，而非依赖一次性事件）：
> ```text
> ① HomeOldActivity 持有最新 MineEntryState
> ② API 回调先更新 MineEntryState（仍发原 EventBus，保实时链路）
> ③ FragmentMineNew 创建并 view ready 后，主动拉最新状态
> ④ applyMineEntryState(state) 统一应用显隐 + 红点
> ```
> EventBus 不再是唯一状态来源。

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 恢复 `offscreenPageLimit=5` | 改动小，Fragment 早创建 | 回退 P0，只是**掩盖**事件早发 | ✗ 不采用 |
| `MineEntryState` 快照 + replay | 保留低缓存收益，解决**状态早发本质** | 需改造状态同步 | ✓ 采用 |
