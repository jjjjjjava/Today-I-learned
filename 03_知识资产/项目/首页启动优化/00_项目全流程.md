# 首页启动优化 · 项目治理全流程

> 项目类型：冷启动存量治理
> 事实源：[[启动优化笔记]]
> 目标：能在 2～5 分钟内讲清发现、归因、治理、验证和持续守护闭环。


## 2. 项目叙事

### 引子

这是首页冷启动存量治理，不是某次版本突发劣化。产品希望 P50 降低 10%、P90 降低 30%；线上基线约为 P50 1.8s、P90 4.6s。

### 线上定位

从 `startup.total` 下钻到 `startup.stage.home_build`。Task TopN 指向 ViewPager 预加载和 WebView 初始化，因此第一假设是：首页创建和首屏渲染在 TTFD 前承担过多工作。

### 线下复现与口径

选择代表性低端机，固定 Release 包、账号、数据和启动场景，多轮运行 Benchmark。业务 TTFD 定义为：

```text
bindApplication → TTFD_HomeWorkDesk
```

终点发生在首页权限模块 View 添加并经历下一次 draw 后。

### Trace 与源码归因

业务 marker 定边界，Perfetto 解释区间。SQL 算得代表轮次 TTFD 约 2790ms；Wall/Self/Count 下钻后，主要成本为 `inflate`、`RV OnLayout`、`traversal` 和 WebView。

回到源码，根因是 ViewPager2 全量预加载非首屏 Tab、首页模块一次性添加多个 View、静态 XML WebView 提前触发 Chromium 初始化。

### 方案

- P0：恢复 ViewPager2 懒加载；WebView 改按需创建。
- P1：首页模块分批渲染；悬浮组件后置。
- P2：Application 初始化治理。本项目该阶段约 220ms，不是主矛盾。

### 验证、回归、灰度

代表 Trace TTFD 从约 2790ms 降到 1774ms。功能回归暴露门店页重建白屏和“我的”页一次性事件丢失；分别用分阶段缓存、状态快照加 replay 修复。

逐步灰度后，线上 P50 从 1.8s 降到 1.5s，P90 从 4.6s 降到 3.1s。最后更新 Benchmark、Stage 和 Task 预算。

## 4. 全流程评分

每项 0～2 分：

1. 结构：阶段完整，顺序稳定。
2. 因果：每个方案能对应根因。
3. 证据：区分线上、Benchmark、Trace 三层数据。
4. 取舍：能解释 P0/P1/P2 和回归决策。
5. 闭环：能讲到灰度、基线和预算。

某项失分，只提前对应阶段卡；不重置整棵知识树。
