### 正确答案

**第 1 题：TTFD 终点（等一次 draw 后打 marker）能不能代表"用户可点击"？**
> 不够。**"可见" ≠ "可交互"**。等一次 draw 只保证像素画出来了，但用户能点中，还需要：Surface 提交后 WMS / InputDispatcher 建好输入通道、且主线程空闲能取到 input 事件。要量"可点击"得用更靠后的指标（类似 TTI 可交互时间），它在 TTFD 之后。缺的机制就是 **draw → 提交 Surface → 建 input 通道 → 主线程取 input** 这一段。

**第 2 题：怎么守住"从 bindApplication 算"又不显得甩锅？**
> 表达成**「按可控性 + ROI 分层排优先级」**，不是"那段不管"。点击→`ActivityThread.main` 那段主要受系统调度、进程创建、设备状态影响，**业务可控度低**；但不是零手段——可做的有：减少 Application 之前的静态初始化 / 类加载、规范用 App Startup、Splash 策略、避免过早触发重类加载。只是收益和可控性不如 bindApplication 之后的首屏裁剪，所以**优先级靠后**，先吃确定性最高的那块。

**第 3 题：addView 后立刻打点为什么 TTFD 偏小？漏算了什么？**
> 漏算了 `addView → 创建 ViewRootImpl → requestLayout 注册 vsync → 等下一个 vsync → performTraversals（measure/layout/draw）→ 渲染提交` 这一整段。`addView` 只是把 View 交给 `WindowManager`、**对象层完成**，像素还没产生，距"用户看见"还差**一个 vsync 周期 + 一次完整 traversal**。立刻打点就把这段真实耗时漏掉，指标偏小且失真。

## 正文内容

模块一解决了"从哪到哪算"，这一篇解决第二个问题：**到底哪里慢、慢了多少。** 拆成三件事：选工具、算总时长、归因到具体方法。

### 1. 项目骨架：为什么是 Perfetto + 一个业务 marker

启动优化要回答两类问题，单一工具往往只覆盖一半：

```text
① 业务边界问题：从哪开始算、到哪算结束？  → 业务 marker 解决
② 耗时归因问题：到底哪里慢、慢多少？      → Perfetto 解决
```

所以本项目用 **Perfetto + 一个业务终点 marker** 的组合。各方案对比：

| 方案 | 能解决 | 主要问题 |
|---|---|---|
| 全链路业务打点 | 定义业务阶段 / 边界 | 看不到未打点路径和系统层、维护成本高 |
| AS Profiler / Method Trace | 局部方法级深挖 | 开销大、影响启动时序，不宜做主采集 |
| logcat 时间戳 | 简单、辅助验证 | 精度 / 覆盖不足，看不到系统 slice |
| 线上启动耗时平台 | 分位数 / 趋势监控 | 本项目未接入，本地归因仍需 trace |
| **Perfetto** | 系统级启动链路分析 | 不知业务"到哪算可用"，**需 marker 补边界** |

> **一句话：业务 marker 解决"终点在哪"，Perfetto 解决"中间发生了什么"。**

**Perfetto 原理（够答追问即可）**：它通过打开系统 tracing category，让系统把关键事件记成 trace。不是抓日志、也不是全 Java 方法栈，而是**系统数据源产生的 slice / 调度信息**。

```text
tracing category → system slice → .perfetto-trace → Perfetto UI / SQL → 业务 marker 补边界
```

常用 category 正好对应启动流程各段（追问时能落到机制）：

| Category | 关注 | 对应流程段 |
|---|---|---|
| `am` / `wm` | ActivityManager / WindowManager | 阶段1 进程、阶段4 Activity/Window |
| `gfx` / `view` | 绘制、layout、traversal | 阶段5 渲染 |
| `binder_driver` | 跨进程 binder | 阶段1/2/4 的 Binder 调用 |
| `dalvik` | ART、dex、类加载 | 阶段3 LoadedApk / 类加载 |
| `res` | 资源加载 | inflate 取资源 |

**采集两个关键点**：
- `-a com.kedacom.ovopark`：让 Perfetto 采到 App 内 `Trace.beginSection/endSection` 打的**自定义 marker**（你的 `sectionBegin/End` 本质就是它）。
- Android 10+ 非 debuggable 包要在 Manifest 配 `<profileable android:shell="true" />`，才允许 shell/profile 工具采自定义 section（不等于开放完整 debug）。

### 2. 项目骨架：用 SQL 算 TTFD，不肉眼估

抓到 `.perfetto-trace` 后，**不要在 UI 上拖时间轴肉眼估**。用 SQL 的理由：精确（基于时间戳）、可复现（同一条 SQL）、可对比（优化前后同口径）。

核心逻辑：在**目标进程**里找起止两个 slice，相减：

```sql
WITH app_slices AS (
  SELECT s.* FROM slice s
  JOIN thread_track tt ON s.track_id = tt.id
  JOIN thread t ON tt.utid = t.utid
  JOIN process p ON t.upid = p.upid
  WHERE p.name = 'com.kedacom.ovopark'   -- 限定目标进程，排除系统/他 App 同名 slice
),
start  AS (SELECT ts FROM app_slices WHERE name='bindApplication'    ORDER BY ts LIMIT 1),
finish AS (SELECT ts FROM app_slices WHERE name='TTFD_HomeWorkDesk'  ORDER BY ts LIMIT 1)
SELECT (finish.ts - start.ts) / 1000000.0 AS ttfd_ms FROM start, finish;
```

两个易错点：
- **必须限定 `p.name`**：一份 trace 里有系统进程、其他 App、目标 App 多线程，不限定会被同名 slice 干扰。
- **`ts` 单位是纳秒 ns**：所以除以 `1,000,000` 得毫秒。优化前实测 `≈ 2790ms`（2.79s）。

### 3. 项目骨架：Wall / Self / Count 归因法

定好区间后，导出区间内 slice，按耗时排序，但**不能只看 Wall**。三个指标：

| 指标 | 含义 | 用途 |
|---|---|---|
| **Wall** | slice 总耗时（含子任务） | 找影响面最大的区域 |
| **Self** | 扣掉子 slice 后自身耗时 | 判断是不是它自己真的重 |
| **Count** | 出现次数 | 单次慢 还是 次数多 |

组合判断（这张表是归因的核心方法论）：

| 特征 | 判断 | 优化方向 |
|---|---|---|
| Wall 高 + Self 高 + Count 少 | 单个重任务 | 异步 / 后置 / 换实现 |
| Wall 高 + Self 高 + Count 多 | 高频重任务 | 减次数 + 优化单次 |
| Wall 高 + **Self 低** + Count 多 | **容器型**，子任务多 | 继续下钻子 slice |
| Wall ≈ Self + Count 多 | 高频直接成本 | 合并 / 缓存 / 批量 / 延迟 |

⚠️ 聚合表里的 Wall **不能直接相加等于 TTFD**——slice 之间有嵌套和重叠。

### 4. 🔧 机制注脚：为什么 doFrame Wall 高、Self 低，不是根因

这是用上表"容器型"判断的真实一例，也是高频追问。实测：

```text
Choreographer#doFrame   Wall 753.7ms   Self 0.3ms   Count 10
```

> 🔧 **机制：`Choreographer#doFrame` 是"一帧的外层调度入口"，不是干活的人。**
> 每收到一个 vsync 信号，Choreographer 回调 `doFrame`，它内部**按序触发** input / animation / **traversal** 等回调；其中 `ViewRootImpl.performTraversals()` 才真正跑 `performMeasure / performLayout / performDraw`。所以 `doFrame` 的 Wall（753ms）是把它内部所有子任务都算进去的总时长，**Self 只有 0.3ms** 说明它自己几乎不耗时——真正的成本在它**嵌套调用**的 `traversal → inflate / measure / layout / draw`。
>
> 对应上表就是「Wall 高 + Self 低 + Count 多 → 容器型 → 继续下钻子 slice」。下钻进去，就是模块三要打的真正瓶颈：`inflate`、`RelativeLayout` 测量、`RV OnLayout`。

> **面试表达：** 我没有把 `doFrame` 当成根因——它 Self 只有 0.3ms，是每帧的外层调度壳子，Wall 高是因为它把内部 traversal、inflate、layout 都包进去了。真正要下钻的是它内部的子 slice。
