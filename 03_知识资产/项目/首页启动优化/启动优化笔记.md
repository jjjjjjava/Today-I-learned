# 首页冷启动存量治理笔记

> 本文不是孤立的 Perfetto 技巧笔记，而是“启动优化方法论”中存量治理路线的项目案例。

## 0. 接入启动优化方法论：这次为什么做、从哪里开始

### 0.1 案例定位：这是存量治理，不是版本突发劣化

启动性能治理分成两条线：

```text
增量劣化治理：阻止新代码继续抬高启动水位
存量启动优化：主动降低稳定版本已经存在的启动耗时
```

本项目没有从某个 MR 或新版本劣化开始，而是由产品提出阶段性体验目标，因此属于存量治理。

完整项目链路是：

```text
产品提出目标
→ 线上大盘确认问题和主要 Stage
→ 低端机放大并稳定复现
→ 定义本地 TTFD 口径
→ 多轮 Benchmark + 中位数 Perfetto 归因
→ 方案分级与实施
→ 同口径复测
→ 功能测试与回归修复
→ 逐步灰度
→ 线上同群对比
→ 更新基线和预算
```

后文原有的“启动优化第一步是定口径”仍然成立，但它指的是**进入本地实验后，第一步先定义测量口径，而不是先改代码**。

在它之前，还有产品目标和线上观测两个业务入口。

### 0.2 产品目标与线上基线

产品提出的目标是：

| 指标 | 优化前大盘 | 目标 |
| --- | ---: | ---: |
| P50 | 约 1.8s | 降低 10%，目标约 1.62s |
| P90 | 约 4.6s | 降低 30%，目标约 3.22s |

P50 代表多数用户的典型体验，P90 用来观察低端机、资源竞争和复杂用户状态形成的尾部体验。

这个目标不是直接拿来和单台测试机比较，而是用来判断投入价值，并作为最终灰度和全量后的验收目标。

### 0.3 线上先定位到 `startup.stage.home_build`

查看线上启动监控后，先从总启动耗时下钻，发现首页构建 Stage 的贡献尤其高。按埋点命名表示为：

```text
startup.total
└── startup.stage.home_build
    ├── startup.task.home.viewpager.preload
    ├── startup.task.home.webview.init
    └── startup.milestone.home.content_ready
```

`startup.stage.home_build` 覆盖 `HomeOldActivity` 创建、首页页面构建到首屏内容就绪这段关键路径。Task TopN 又表明 ViewPager 预加载和 WebView 初始化值得优先调查。

因此第一轮假设不是“Application 中的 SDK 太多”，而是：

> 首页创建和首屏渲染在 TTFD 前承担了过多工作。

线上 Stage/Task 只能把调查范围缩小到首页构建，并不能证明具体系统成本。进入本地 Perfetto 后，再沿 `android.view.LayoutInflater.inflate`、`RecyclerView#onLayout` 和 `ViewRootImpl#performTraversals` 判断 View 创建、布局和渲染为什么慢，最后回到源码证明根因。

### 0.4 为什么选择低端机复现

线上 P90 往往包含更多低端设备和资源竞争样本。低端机 CPU、存储和内存能力有限，同样的类加载、View 创建、布局和并发任务会被明显放大。

因此选择有代表性的低端机，固定 Release 包、账号、数据和启动场景，多轮执行冷启动 Benchmark。

这里的目的不是用单台低端机代替线上 P90，而是：

```text
放大问题信号
→ 降低单次偶然波动
→ 获得可重复的修改前后对照
→ 选出中位数轮次交给 Perfetto 解释根因
```

从这一步开始，才进入下一章的本地分析主线：先定 TTFD 口径，再改代码。

### 0.5 三组数据必须分层表达

本案例存在三组不同环境的数据，面试时不能混成一个“优化了 30%”：

| 数据层 | 优化前 | 优化后 | 变化 | 用途 |
| --- | ---: | ---: | ---: | --- |
| 个人手机多轮 Benchmark | 2.98s | 1.74s | 约下降 41.6% | 证明受控环境下优化有效 |
| 代表轮次 Perfetto TTFD | 约 2790ms | 约 1774ms | 约下降 36.4% | 解释目标 Slice 为什么下降 |
| 线上 P50 | 1.8s | 1.5s | 约下降 16.7% | 典型用户收益，达到 10% 目标 |
| 线上 P90 | 4.6s | 3.1s | 约下降 32.6% | 尾部用户收益，达到 30% 目标 |

因此准确结论是：

> 个人手机的受控 Benchmark 缩短约 41.6%；线上 P50 从 1.8s 降到 1.5s，P90 从 4.6s 降到 3.1s，两项目标均达成。

本地和线上降幅不要求一致：本地固定设备和环境，用来证明修改有效；线上包含不同设备、系统和用户状态，用来验证真实用户收益。

## 1. 启动优化口径：为什么先定义 TTFD

### 1.1 TTID 与 TTFD 的区别

启动优化的第一步不是直接改代码，而是先明确统计口径。否则后续即使看到耗时下降，也很难判断优化是否真正改善了用户体感。

本次复习中重点区分两个指标：

| 指标 | 含义 | 局限 |
| --- | --- | --- |
| TTID | Time To Initial Display，首帧可见 | 可能只是 Splash 或首页壳子，不代表核心业务可用 |
| TTFD | Time To Full Display，业务可用或关键业务内容可见 | 需要业务自己定义终点，口径设计要说明边界 |

**本项目选择 TTFD 作为主指标，是因为 TTID 只能说明首帧出现，不能说明用户已经看到首页工作台的核心模块。**

### 1.2 本项目的 TTFD 定义

本项目的 TTFD 定义为：

```text
TTFD = TTFD_HomeWorkDesk.ts - bindApplication.ts
```

起点是 Perfetto 系统 slice：

```text
bindApplication
```

选择 `bindApplication` 的原因是：从这里开始进入业务相对可控的 Application、ContentProvider、Activity 创建链路。点击图标、AMS 创建进程、`ActivityThread.main()` 前后的部分更多受系统调度、进程创建和设备状态影响，不是本轮业务代码优化的主要可控区间。

终点是业务 marker：

```text
TTFD_HomeWorkDesk
```

触发链路可以概括为：

```text
MainBodyFragment.initialize()
-> refreshDataByPrivilege()
-> presenter.getUserColumns()
-> onGetUserColumns()
-> 添加首页权限模块 View 到 llColumns
-> 等下一次 onDraw()
-> StartupTraceTracker.finish()
-> Trace.beginSection("TTFD_HomeWorkDesk") / endSection()
```

这里不能把终点简单说成 `getUserColumns()`。更准确的表达是：

**`getUserColumns()` 返回用户权限模块后，首页模块 View 被添加到容器，并经历下一次 draw 后，才打出 `TTFD_HomeWorkDesk` marker。**

这样统计的是首页工作台模块框架首次可见，而不是单纯接口返回或 View 添加完成。

### 1.3 为什么要等下一次 draw

如果在接口返回、View 创建或 `addView()` 后立即打点，统计到的只是数据或对象层面的完成，不代表用户真的看到了内容。

等待下一次 draw 的意义是：

- View 已经加入 View 树。
- 至少经历了一次绘制机会。
- 更接近“首页工作台模块框架首次可见”的用户感知。

### 1.4 口径局限与分层治理

这个 TTFD 口径有局限：它只代表首页工作台模块框架可见，不代表模块内部网络数据全部加载完成，也不代表所有模块都已经可以完整交互。

但这不是为了让数据更好看，而是为了把问题拆层：

| 层级 | 关注问题 | 优化方向 |
| --- | --- | --- |
| 第一层 | 首页框架什么时候可见 | View 创建、布局、WebView、初始化路径裁剪 |
| 第二层 | 各模块内部数据什么时候可用 | 接口耗时、缓存命中、并发调度、局部渲染 |

首页进入时可能有三四十个接口。如果把所有业务数据加载完成作为 TTFD 终点，指标会强依赖网络状态、后端耗时、接口并发和缓存命中情况，导致波动较大，也难以判断到底是启动链路慢，还是某个接口慢。

**面试表达重点：当前 TTFD 解决的是“首页框架可见”这一层问题，模块内部数据加载要作为下一层指标继续治理。**

## 2. 工具选型：为什么是 Perfetto + 一个业务终点 marker

### 2.1 启动优化要回答的两个问题

启动优化本质上要回答两类问题：

1. 业务边界问题：从哪里开始算，到哪里算结束？
2. 耗时归因问题：到底哪里慢，慢了多少？

单一工具往往只能回答其中一部分，所以本项目最终采用：

```text
Perfetto + 一个业务终点 marker
```

### 2.2 各方案对比

| 方案 | 能解决什么 | 主要问题 |
| --- | --- | --- |
| 全链路业务打点 | 可以定义业务阶段和边界 | 看不到未打点路径和系统层行为，长期维护成本高 |
| Android Studio Profiler / Method Trace | 适合局部方法级深挖 | 开销较大，容易影响启动时序，不适合作为主采集工具 |
| logcat 时间戳 | 简单快速，适合辅助验证 | 精度和覆盖面不足，看不到系统 slice |
| 线上启动耗时平台 | 适合分位数、Stage 趋势和真实用户验证 | 能定位慢在哪个阶段，但本地根因仍需要 Benchmark 与 trace |
| Perfetto | 适合系统级启动链路分析 | 不知道业务上“到哪里算可用”，需要业务 marker 补边界 |

业务 marker 解决“终点在哪里”的问题，Perfetto 解决“中间发生了什么”的问题。

### 2.3 Perfetto 简要原理

Perfetto 是 Android 的系统级 tracing 工具。它通过打开系统 tracing category，让系统在运行过程中把关键事件记录成 trace 数据。

常用 category 包括：

| Category | 关注内容 |
| --- | --- |
| `am` / `wm` | ActivityManager、WindowManager 相关事件 |
| `gfx` / `view` | 绘制、View、layout、traversal |
| `binder_driver` | 跨进程 binder 调用 |
| `dalvik` | ART、dex、类加载 |
| `res` | 资源加载 |
| `sched` / `freq` / `idle` | 线程调度、CPU 频率和空闲状态 |

Perfetto 不是简单抓日志，也不是完整记录所有 Java 方法栈，而是记录系统 tracing 数据源产生的 trace event / slice / 调度信息。

一句话记忆：

```text
tracing category -> system slice -> .perfetto-trace -> Perfetto UI / SQL -> 业务 marker 补边界
```

### 2.4 `-a 包名` 与 `profileable`

采集命令中需要带上：

```bash
-a com.kedacom.ovopark
```

它的作用是让 Perfetto 采集目标 App 中通过 `Trace.beginSection/endSection` 打出的自定义 marker。

如果 Android 10+ 的非 debuggable 包无法在 Perfetto 中看到 App 自定义 marker，需要在 Manifest 中配置：

```xml
<profileable android:shell="true" />
```

它允许 shell/profile 工具采集 App 自定义 trace section，但不等同于开放完整 debug 能力。

## 3. 数据计算与 Slice 分析方法

### 3.1 为什么用 SQL 计算 TTFD

抓到 `.perfetto-trace` 后，不建议只在 Perfetto UI 上肉眼拖时间轴估算耗时。

原因：

- 精确性更好：SQL 直接基于时间戳计算。
- 可复现：同一条 SQL 可以重复计算。
- 便于对比：优化前后可以使用同一口径比较。

本项目 SQL 计算逻辑是：

```sql
WITH app_slices AS (
  SELECT s.*
  FROM slice s
  JOIN thread_track tt ON s.track_id = tt.id
  JOIN thread t ON tt.utid = t.utid
  JOIN process p ON t.upid = p.upid
  WHERE p.name = 'com.kedacom.ovopark'
),
start AS (
  SELECT ts
  FROM app_slices
  WHERE name = 'bindApplication'
  ORDER BY ts
  LIMIT 1
),
finish AS (
  SELECT ts
  FROM app_slices
  WHERE name = 'TTFD_HomeWorkDesk'
  ORDER BY ts
  LIMIT 1
)
SELECT
  (finish.ts - start.ts) / 1000000.0 AS tffd_ms
FROM start, finish;
```

这里需要从 `slice` 关联到 `process`，并限制：

```sql
p.name = 'com.kedacom.ovopark'
```

因为同一份 trace 里可能包含系统进程、其他 App 进程和目标 App 的多个线程事件。限定目标进程可以避免其他进程的同名 slice 或系统活动干扰结果。

### 3.2 时间戳单位

Perfetto 中 `ts` 的单位是纳秒 ns。

本次优化前数据：

```text
bind_application_ts = 790291535603783
tffd_finish_ts = 790294325733418
```

换算：

```text
790294325733418 - 790291535603783 = 2,790,129,635 ns
2,790,129,635 / 1,000,000.0 = 2790.129635 ms
```

所以优化前 TTFD 约为：

```text
2790.13ms，约 2.79s
```

### 3.3 Wall / Self / Count 分析法

拿到 TTFD 区间后，分析流程是：

```text
定区间 -> 导 slice -> 按 Wall 排序 -> 看 Self 和 Count -> 分类 -> 回源码
```

三个核心指标：

| 指标 | 含义 | 用途 |
| --- | --- | --- |
| Wall Duration | slice 总耗时，包含子任务 | 找影响面最大的区域 |
| Self Duration | 扣除子 slice 后自身耗时 | 判断是不是自身真的重 |
| Count | 出现次数 | 判断是单次慢还是次数多 |

不能只看 Wall。比如 `Choreographer#doFrame` Wall 很高，但 Self 很低，说明它更像一帧调度的外层入口，真正耗时在它内部触发的 traversal、layout、inflate、RecyclerView layout、draw 等子任务。

### 3.4 组合判断

| 特征 | 判断 | 优化方向 |
| --- | --- | --- |
| Wall 高 + Self 高 + Count 少 | 单个重任务，自身就慢 | 异步、后置、替换实现，或拆出冷启动路径 |
| Wall 高 + Self 高 + Count 多 | 高频重任务 | 减少调用次数，同时优化单次成本 |
| Wall 高 + Self 低 + Count 多 | 容器型问题，内部子任务多 | 继续下钻子 slice |
| Wall 约等于 Self + Count 多 | 高频直接成本 | 合并、缓存、批量化或延迟 |

⚠️ 注意：聚合表中的 Wall 不能直接相加等于 TTFD，因为 slice 之间可能存在嵌套和重叠。

## 4. Trace 归因：首屏路径为什么过重

### 4.1 核心瓶颈总结

优化前核心数据：

| Slice | Wall | Self | Count | 判断 |
| --- | ---: | ---: | ---: | --- |
| `Choreographer#doFrame` | 753.7ms | 0.3ms | 10 | 掉帧结果，不是直接根因 |
| `traversal` | 750.1ms | 73.8ms | 10 | View 树遍历总成本高 |
| `inflate` | 700.8ms | 198.4ms | 106 | 首屏 View 创建数量过多 |
| `RV OnLayout` | 518.3ms | 235.6ms | 29 | RecyclerView/Layout 本身较重 |
| `layout` | 516.1ms | 4.1ms | 10 | 总成本高，但自身不是主要根因 |
| `WebView` | 229.9ms | 52.8ms | 2 | WebView 进入启动路径 |
| `binder transaction` | 226.3ms | 226.3ms | 579 | 启动期跨进程调用偏多 |

可以把瓶颈总结成三类：

1. **第一矛盾：首屏 UI 创建和布局过重。**
2. **第二矛盾：WebView 不应进入 TTFD 前路径。**
3. **第三矛盾：binder/system 调用偏多。**

### 4.2 ViewPager2 非首屏 Tab 提前创建

源码归因中发现 `HomeOldActivity.initViews()` 启动时存在类似逻辑：

```kotlin
for (i in 0..4) {
    initTab(i)
}
mContainer?.offscreenPageLimit = mListFragments.size
```

这会破坏 ViewPager2 默认懒加载效果。

本来 TTFD 前只需要首页 Tab 可用，但设置 `offscreenPageLimit = mListFragments.size` 后，非首屏 Tab 也可能提前创建或保留。非首屏 Fragment 一旦创建，就会带来：

- XML / View inflate
- RecyclerView 初始化
- measure / layout / traversal
- 资源加载

因此它能对应上 trace 里的：

```text
inflate 106 次
RV OnLayout 29 次
traversal/layout wall 偏高
```

优化方向是：冷启动阶段只保证当前首页 Tab 可用，其他 Tab 等用户切换时再加载。

### 4.3 首页模块一次性添加多个 View

另一个归因是首页工作台会在获取权限后一次性添加很多模块 View，例如 AI 助手、常用模块、待办、课程、资讯等。

`getUserColumns()` 本身可能只是缓存读取，但它返回后会触发模块 View 创建和添加。部分模块内部还有 RecyclerView，因此会进一步增加 `inflate`、`RV OnLayout` 和 `traversal/layout` 成本。

这一点在面试主线中不需要展开太碎，可以归入：

```text
首屏路径没有裁剪干净，TTFD 前做了过多首屏之外的 UI 工作。
```

### 4.4 WebView 静态写入 XML

`activity_home_change.xml` 中存在静态 WebView：

```xml
<WebView
    android:id="@+id/web"
    android:layout_width="wrap_content"
    android:layout_height="wrap_content"
    android:visibility="gone" />
```

`visibility="gone"` 只表示它不可见，不代表 XML inflate 时不会创建对象。

WebView 和普通 `TextView` / `Button` 不同，它是重量级组件。创建 WebView 实例时可能触发：

- WebView / Chromium 初始化
- `WebViewChromium.init`
- `AwBrowserProcess.start`
- 资源和 class loading

所以即使它不可见，只要静态写在首页 XML 里，就可能污染 TTFD。

优化方向：

```text
删除 XML 静态 WebView，改成轻量 FrameLayout 占位，真正进入 Web 场景时再动态创建 WebView 并 addView。
```

示例表达：

```kotlin
private var webView: WebView? = null

private fun ensureWebView(): WebView {
    return webView ?: WebView(this).also {
        webView = it
        webContainer.addView(it)
    }
}
```

### 4.5 其他首屏路径污染点

其他归因点可以一笔带过：

- BaseActivity 中通用悬浮组件同步创建，例如巡店、客服、公告、录像悬浮等。
- 部分系统调用、服务绑定、资源访问过早进入启动路径。
- binder transaction 次数偏多，说明启动期可能有非首屏必要系统调用或组件初始化过早发生。

总括表达：

```text
回源码后，我把问题归成三类：
第一是非首屏页面提前创建；
第二是重量级 WebView 进入启动路径；
第三是首页模块、悬浮组件和部分系统调用这些非首屏必要内容过早执行。
本质都是 TTFD 前做了太多首屏之外的工作。
```

## 5. 方案设计：首屏路径裁剪

### 5.1 什么是首屏路径裁剪

首屏路径裁剪的核心是：

```text
TTFD 前只做用户第一屏可见且必须的事情。
非首屏 Tab、非首屏模块、WebView、通用悬浮组件、非必要初始化全部后置或按需加载。
```

这能直接对应前面 trace 中的 UI 构建、布局、WebView、binder/system 调用偏多问题。

### 5.2 P0：收益最确定的改造

P0 做收益最明确、改动相对聚焦的点。

#### ViewPager2 恢复懒加载

冷启动阶段只保证首页 Tab 可用，不一次性创建所有 Tab。

优化点：

- 移除启动期全量 `offscreenPageLimit`。
- 保持 ViewPager2 默认懒加载，或最多设置为较小值。
- 修复懒加载后的 Fragment 首次加载时序，避免切到门店/管理页时 firstLoad 被提前消费。

#### WebView 移出启动路径

删除 XML 静态 WebView。

方案：

- XML 中用轻量 `FrameLayout` 占位。
- 真正进入 Web 场景时再创建 WebView。
- 用完后按生命周期 remove / destroy，避免泄漏。

### 5.3 P1：继续减少首屏 UI 压力

P1 涉及更多业务展示顺序和通用组件时机，所以需要更多回归。

包括：

- 首页模块首屏裁剪和分批渲染。
- TTFD 前只添加首屏可见模块。
- 非首屏模块首帧后分批 `addView`。
- BaseActivity 悬浮组件首帧后创建或按需创建。

这里不建议面试时说“不知道业务逻辑”，更稳的表达是：

```text
P1 和业务展示强相关，需要和产品、业务线确认，并通过开关和回归控制风险。
```

### 5.4 P2：Application 同步初始化瘦身

这次 trace 中：

```text
bindApplication wall = 220.5ms
self = 69.3ms
```

相比：

```text
inflate 700.8ms
RV OnLayout 518.3ms
traversal 750.1ms
```

Application 阶段不是最大矛盾，所以放到 P2。

后续可以把下载、OSS、缓存清理、机器人信息、埋点清理、非首屏 SDK 等延迟到 Idle 或首帧后。

## 6. 结果验证以及回归

### 6.1 二次性能验证

优化后必须用相同口径二次 Perfetto 验证：

- 同样的采集方式。
- 同样的 TTFD SQL。
- 同样的 TSV 聚合口径。
- 同样关注 Wall / Self / Count。

P0 前后核心对比：

| 指标 | 优化前 | P0 后 | 变化 |
| --- | ---: | ---: | ---: |
| TTFD | 约 2790ms | 约 1774ms | 下降约 1016ms |
| `inflate` | 106 次 / 700.8ms | 62 次 / 294.3ms | 少 44 次，Wall 降约 406ms |
| `RV OnLayout` | 29 次 / 518.3ms | 18 次 / 178.4ms | 少 11 次，Wall 降约 340ms |
| `traversal` | 750.1ms | 327.2ms | 降约 423ms |
| `layout` | 516.1ms | 179.5ms | 降约 337ms |
| `WebView` | 2 次 / 229.9ms | 0 | 从 TTFD 区间消失 |
| `binder transaction` | 579 次 / 226.3ms | 382 次 / 183.5ms | 少 197 次 |

这说明优化不是单纯时间波动，而是首屏路径里实际少创建了 View、少做了 RecyclerView layout，并且移除了 WebView 初始化成本。

### 6.2 回归问题一：门店页重页面频繁切换

P0 后，ViewPager2 低缓存让冷启动 TTFD 明显下降，但也暴露出运行期问题。

门店页是重页面，内部包含多层 Fragment、EventBus、RecyclerView、缓存恢复和补充数据请求。频繁切换底部 Tab 时，低缓存可能导致门店页反复 destroy / recreate。

典型问题：

- EventBus 事件早到。
- Fragment 尚未 attach 或 view 未 ready。
- adapter / RecyclerView 未 ready。
- 可见区位置为 `-1`。
- 出现白屏或刷新异常。

这说明问题不是单个刷新函数兜底能彻底解决的，而是低缓存导致重页面运行期生命周期不稳定。

### 6.3 门店页修正：分阶段缓存

没有简单恢复启动时全量缓存：

```kotlin
mContainer.offscreenPageLimit = mListFragments.size
```

因为这样会把启动期全量预加载带回来，抵消 P0 的 TTFD 优化收益。

最终采用分阶段缓存：

```text
冷启动阶段：
  保持 ViewPager2 默认低缓存，不提前创建所有 Tab。

首次进入门店页后：
  将主 ViewPager2 的 offscreenPageLimit 提升到 3。

后续频繁切 Tab：
  保留门店页和相邻高频页面，减少 create / destroy。
```

这个策略兼顾了启动性能和运行期稳定性。

### 6.4 回归问题二：“我的”页入口状态丢失

P0 后，首页 ViewPager2 从启动期全量缓存恢复为默认懒加载，“我的”页 `FragmentMineNew` 不再保证在启动阶段提前创建。

但费用中心、审批工作台、我的证件、权限等入口状态仍然通过一次性 EventBus 下发：

```text
HomeOldActivity API 回调完成
-> EventBus.post(ShowCrmCostCenterEvent / GetPrivilegesSuccessEvent)
-> FragmentMineNew 接收后更新入口显隐和红点
```

当 `FragmentMineNew` 尚未创建或尚未注册 EventBus 时，这些普通事件会被丢弃。

结果是：

```text
数据已经回来，但“我的”页入口状态没有被应用，
表现为费用中心 / 审批 / 证件等 item 加载不全。
```

之前通过启动期设置：

```kotlin
offscreenPageLimit = 5
```

可以提前创建 `FragmentMineNew`，从而掩盖这个时序问题。但这会回退 P0 懒加载优化，增加冷启动 Fragment 创建和 inflate 成本。

### 6.5 “我的”页修正：状态快照 + replay

这个问题本质是：

```text
状态生产早于 UI 消费 ready。
```

入口显隐、红点、未读数属于 latest wins 状态，适合做状态快照和 replay，而不是依赖一次性 EventBus。

最终方案：

1. `HomeOldActivity` 持有最新 `MineEntryState`。
2. API 回调先更新 `MineEntryState`。
3. 继续发送原 EventBus，保留实时通知链路。
4. `FragmentMineNew` 创建并 view ready 后，主动向 `HomeOldActivity` 拉取最新状态。
5. `FragmentMineNew.applyMineEntryState(state)` 统一应用入口显隐和红点状态。

这样 EventBus 不再是唯一状态来源。

对比两个方案：

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| 启动期恢复 `offscreenPageLimit = 5` | 改动小，Fragment 更早创建 | 回退 P0 优化，只是隐藏事件早发问题 | 不采用 |
| `MineEntryState` 状态快照 + replay | 保留低缓存收益，解决状态早发本质问题 | 需要改造状态同步方式 | 采用 |

### 6.6 最终回归结果

最终回归重点：

- 启动收益保留，TTFD 约降到 1774ms。
- `inflate` 和 `RV OnLayout` 的 Count / Wall 明显下降。
- WebView 从 TTFD 区间消失。
- 门店页频繁切换稳定性恢复。
- “我的”页入口状态不再依赖 Fragment 启动期提前创建。
- 首页首屏、Tab 首次加载、Web 入口、悬浮组件等功能回归通过。

### 6.7 逐步灰度与线上验证

本地测试和 Benchmark 通过后，不直接全量发布，而是逐步扩大灰度范围。

灰度阶段同时观察：

- 相同设备档位、启动场景和系统区间内的 P50、P90；
- `startup.stage.home_build` 及其 Task TopN；
- `startup.task.home.viewpager.preload`、`startup.task.home.webview.init` 和 `startup.milestone.home.content_ready`；
- Crash、ANR、白屏和首页成功率；
- Tab 首次进入、频繁切换、“我的”页状态和 WebView 入口。

放量过程中重点确认两件事：一是本地缩短的 `startup.stage.home_build` 在线上也下降；二是懒加载与按需创建没有引入新的功能失败。

最终大盘结果为：

| 指标 | 优化前 | 优化后 | 降幅 | 目标完成情况 |
| --- | ---: | ---: | ---: | --- |
| P50 | 1.8s | 1.5s | 约 16.7% | 达到降低 10% 的目标 |
| P90 | 4.6s | 3.1s | 约 32.6% | 达到降低 30% 的目标 |

线上 P90 与个人手机 Benchmark 的降幅不同是正常现象。线上尾部混合了设备、存储、CPU 调度、账号数据量和不同启动状态；个人手机实验只证明本轮修改对选定关键路径有效。

存量治理完成后，将优化后的稳定 Release 包作为新的 CI/Benchmark 对照基线，并根据新数据收紧总耗时和各阶段预算。

```text

→ 新 Benchmark 基线：个人手机约 1.74s
→ 新线上参考：P50 约 1.5s、P90 约 3.1s
→ 更新 startup.stage.home_build 和关键 Task 预算

```

## 7. 面试表达

### 7.0 高价值埋点

#### 1. 启动口径

> 这次启动优化的第一步不是直接改代码，而是先定义业务 TTFD，明确从哪里开始、到首页什么状态才算真正可见。

#### 2. 页面频繁切换白屏

> 恢复 ViewPager2 懒加载后，启动速度提升了，但重页面频繁切换时出现白屏，我们通过分阶段缓存，在保留启动收益的同时解决了页面稳定性问题。

#### 3. 问题定位

> 通过线下 Perfetto 分析后，我们发现主要问题是：首页提前加载了过多非首屏页面，同时静态 WebView 也进入了启动关键路径。

### 7.0 总结
总结来看，这次启动优化不是几个零散优化点的堆叠，而是一套完整的工程闭环：从线上监控预定位问题，到线下稳定复现、定义启动口径、选择分析工具，再通过 Perfetto 进行结构化分析和源码归因，之后完成方案分级、同口径验证、回归问题修复，最终将优化结果回填为新的基线和性能预算。

整个过程中，我们以 Android 系统启动链路为主线，分析不同阶段的治理手段，包括 Baseline Profile、ContentProvider 初始化治理、DAG 任务编排、XML 加载优化以及首屏渲染链路裁剪。最终沉淀的不只是一次启动耗时优化，而是一套可定位、可验证、可回归、可持续守护的启动性能治理方法。

### 7.1 2 分钟主线

可以按这条链路讲：

```text
产品目标 -> 线上 Stage -> 低端机复现 -> 口径 -> Perfetto 归因
-> 方案取舍 -> 性能复测 -> 功能回归 -> 灰度 -> 新基线
```

面试表达模板：

> 这个项目属于冷启动存量治理。产品提出大盘 P50 降低 10%、P90 降低 30%的目标，当时线上 P50 约 1.8s、P90 约 4.6s。沿线上埋点下钻后，发现 `startup.stage.home_build` 贡献尤其高，Task TopN 指向 `startup.task.home.viewpager.preload` 和 `startup.task.home.webview.init`。
>
> 为了放大问题并稳定复现，我们选择代表性低端机，固定 Release 包、账号、数据和启动场景，多轮跑 Benchmark。进入本地实验后第一步不是改代码，而是定义 TTFD：从 Perfetto 的 `bindApplication` 到首页工作台 View 添加并经历下一次 draw 后的 `TTFD_HomeWorkDesk`。
>
> 工具上用 Benchmark 证明同环境下前后是否变快，选择中位数轮次用 Perfetto 解释哪里慢。代表 Trace 的 TTFD 约 2790ms；按 Wall、Self 和 Count 下钻后，发现 `inflate` 106 次约 701ms、`RV OnLayout` 约 518ms、`traversal` 约 750ms，WebView 约 230ms。
>
> 回源码后定位到 ViewPager2 启动期预加载多个非首屏 Tab、首页模块一次性添加多个 View，以及 XML 静态 WebView。它们的共同问题是 TTFD 前执行了大量非首屏必要工作。
>
> 方案按收益和风险分级：P0 恢复 ViewPager2 懒加载，并把 WebView 改为按需创建；P1 做首页模块分批渲染和悬浮组件后置；P2 再处理 Application 初始化，因为本次 Trace 中它不是最大矛盾。
>
> 个人手机多轮 Benchmark 从约 2.98s 降到 1.74s，代表 Trace 从约 2790ms 降到 1774ms，目标 Slice 也同步下降。功能测试暴露了门店页重建白屏和“我的”页一次性事件丢失，我们分别用分阶段缓存和状态快照加 replay 修复，没有恢复启动期全量预加载。
>
> 逐步灰度后，线上 P50 从 1.8s 降到 1.5s，约下降 16.7%；P90 从 4.6s 降到 3.1s，约下降 32.6%，两项目标都达成。最后将优化包、阶段耗时和预算更新为新基线，交给 MR Benchmark、整包自动化和灰度继续守住。

### 7.2 高频追问与回答要点

| 面试官追问 | 回答要点 |
| --- | --- |
| 为什么不用 TTID？ | TTID 只代表首帧可见，可能只是 Splash 或壳子，不代表首页工作台模块可见 |
| 为什么起点是 `bindApplication`？ | 从这里开始进入业务相对可控的 Application、ContentProvider、Activity 创建链路 |
| 这个 TTFD 是不是没统计完整业务数据？ | 承认局限，但这是分层治理：先优化框架可见，再单独统计模块内部数据 |
| 为什么不用全链路打点？ | 打点能定义业务边界，但看不到系统 slice，且维护成本和噪声高 |
| 为什么 `doFrame` 高不是根因？ | `doFrame` 是外层帧调度入口，Self 很低，真正耗时在内部 traversal/layout/inflate/RV |
| 为什么 WebView `gone` 还会影响启动？ | `gone` 不代表不创建对象，WebView 创建可能触发 Chromium 初始化 |
| 为什么不恢复全量 `offscreenPageLimit`？ | 会回退 P0 懒加载收益，只是掩盖状态时序问题 |
| EventBus 丢事件怎么处理？ | 把 latest wins 的入口状态建模为状态快照，Fragment ready 后 replay |
