# 01｜季度目标来了，先查启动链路的哪一段？

## 本篇只解决一个问题

季度目标要求降低启动 P50 和 P90。接到任务后，应该立即在线下抓 Trace，还是先从线上数据缩小范围？

## 先看清要改善哪群用户

一季度目标是：

```text
P50：1.8s，降低 10%，目标 1.62s
P90：4.5s，降低 20%，目标 3.6s
```

P50 是中位数。它从 1.8s 降到 1.62s，需要让典型启动场景减少约 180ms。

P90 表示约 90% 的样本不超过该值。它从 4.5s 降到 3.6s，需要让长尾减少约 900ms，通常更容易暴露低端机、复杂首页、IO 和调度问题。

这是稳定版本上的存量治理，不是某次发版后的突然劣化。因此先分析线上长期分布，而不是先找最近一次代码变更。

## 为什么先看线上 Span？

线上启动链路已拆成多个 Stage。下钻后，`Stage_home_build` 在 P50 和 P90 中都占比较高，其中 P90 约 1.9s，是主要耗时阶段之一。

该阶段覆盖首页从 `onCreate` 开始，到页面首次渲染完成的构建过程。

这条数据只能得出：

> 首页构建和首屏渲染值得优先调查。

它不能直接证明 View 层级、RelativeLayout、ViewPager2 或 Application 初始化中的任何一项就是根因。

## 从 `Stage_home_build` 可以提出哪些猜想？

### 猜想一：一次创建了太多 View

如果首页 View 树过重，Trace 中应该出现较高的 inflate 次数，以及 measure、layout、draw 或 traversal 成本。

### 猜想二：布局约束成本过高

深层嵌套或复杂相对约束可能增加测量和布局成本。但不能因为 XML 中出现 RelativeLayout，就直接把它替换成 ConstraintLayout。

需要先证明目标布局位于启动关键路径，并且它的 measure/layout 确实是热点。

### 猜想三：非首屏页面提前创建

首页 ViewPager2 包含多个 Fragment。如果缓存数量设置过大，非首屏 Tab 也可能在冷启动阶段创建。

若猜想成立，Trace 中应同时出现多个 Fragment 初始化、inflate 次数增加和多个 RecyclerView 提前布局。

## 为什么不直接在个人手机上改代码？

个人设备上的一次启动，只能反映这个设备、这次调度和这份数据。它既不能代表线上 P50，也不能代表 P90。

线下设备的作用是稳定复现线上暴露的问题特征。为了放大首页构建、类加载和布局成本，本项目选择代表性低端机进行分析。

实验开始前需要固定：

- Release 或接近生产的非 debuggable 包；
- 设备与系统版本；
- 账号、权限和首页模块数据；
- 冷启动方式；
- 网络、缓存和登录状态；
- 编译模式与 Baseline Profile 状态。

## 三个典型判断

1. `Stage_home_build` 的 P90 是 1.9s：可以确定优先调查首页构建，不能直接确定某个 View 是根因。
2. 低端机上首页更慢：可以用来放大问题信号，不能把单机数据直接称为线上 P90。
3. P50 达标、P90 未达标：典型用户改善了，但长尾治理仍未完成。

## 常见误区

1. 接到目标后立即异步所有 SDK，不先确认主矛盾。
2. 只看平均值，不看 P50 和 P90。
3. `Stage_home_build` 高，就直接认定布局层级是根因。
4. 在个人高端机上跑一次，把结果当成线上分位数。
5. 不固定账号、首页数据和编译状态，导致结果不可复现。

## 本篇自测

1. P50 和 P90 分别代表什么治理问题？
2. `Stage_home_build` P90 约 1.9s 能证明什么？
3. 为什么三个初始方向都只能叫猜想？
4. 代表性低端机与线上 P90 有什么区别？
5. 进入线下分析前需要固定哪些条件？

## 一句话总结

线上分位数定义目标，Stage 收敛调查范围；具体根因必须留到受控实验和 Trace 中证明。
