# 04｜本地变快了，为什么还不能直接上线？

## 本篇只解决一个问题

ViewPager2 恢复懒加载、WebView 改为按需创建后，本地明显变快。怎样确认收益来自修改，并解决随之暴露的功能问题？

## 目标工作量真的下降了吗？

优化前后保持设备、Release 包、账号、首页数据、缓存、网络、`StartupMode`、`CompilationMode`、统计 SQL 和迭代次数一致。

总指标变化：

| 数据来源 | 优化前 | P0 后 |
|---|---:|---:|
| 个人设备 Benchmark | 约 2.98s | 约 1.74s |
| 代表 Trace 项目区间 | 约 2790ms | 约 1774ms |

两组数据来自不同测量方式，不能合并成同一个“最终优化率”。

目标 Slice 变化：

| Slice | 优化前 | P0 后 |
|---|---:|---:|
| inflate | 106 次 / 700.8ms | 62 次 / 294.3ms |
| `RV OnLayout` | 29 次 / 518.3ms | 18 次 / 178.4ms |
| traversal | 750.1ms | 327.2ms |
| layout | 516.1ms | 179.5ms |
| WebView | 2 次 / 229.9ms | 0 |
| binder transaction | 579 次 / 226.3ms | 382 次 / 183.5ms |

项目区间和目标 Slice 同时按预期下降，支持“非首屏工作被移出启动路径”这个解释。

Binder 没有清零是正常的。剩余调用可能来自生命周期、系统服务和窗口建立，不需要为了数字继续治理。

## 为什么门店页频繁切换后白屏？

恢复懒加载后，冷启动首次进入门店页正常；频繁切换 Tab 后出现白屏。生命周期日志显示 View 被重复创建和销毁，但接口与缓存数据正常。

临时提高目标页面缓存后，白屏消失。这项实验说明问题与 Fragment 重建有关，但不代表应该恢复启动期全量缓存。

最终采用分阶段缓存：

```text
冷启动：保持低缓存，只创建首页必要页面
→ 用户首次进入门店页
→ 运行期提高局部缓存
→ 减少后续频繁重建
```

启动性能和运行期稳定性发生在不同阶段，因此缓存策略也按阶段变化。

## 为什么“我的”页入口状态丢失？

入口显隐和红点原本通过一次性 EventBus 事件传递。

全量预加载时，目标 Fragment 很早就创建并注册；恢复懒加载后，事件可能先发出，Fragment 后创建，普通事件因此丢失。

```text
状态产生
→ EventBus 发出
→ Fragment 尚未 ready
→ 没有消费者
→ Fragment 后续创建
→ 页面缺少最新状态
```

旧缓存配置不仅缓存页面，还通过提前创建掩盖了状态时序问题。恢复全量缓存只是恢复这个隐式依赖。

最终改为最新状态快照加 replay：

```text
Activity 保存最新 MineEntryState
→ API 回调先更新快照
→ EventBus 继续发送实时通知
→ Fragment view ready 后主动读取最新状态
→ applyMineEntryState 统一更新显隐和红点
```

这是 latest-wins 状态：新消费者需要当前最新值，不需要重放历史上的每一次事件。

## 灰度时应该观察哪些结果？

实验组与对照组应尽量保持相似的设备档位、系统版本、账号结构、启动场景和发布时间窗口。

同时观察三类指标：

- 性能：P50、P90、`Stage_home_build`、关键 Task；
- 稳定性：Crash、ANR、白屏和冷启动成功率；
- 业务：Tab 首次进入、门店页恢复、“我的”页入口、WebView 功能。

线上结果：

| 指标 | 优化前 | 灰度后 | 结果 |
|---|---:|---:|---:|
| P50 | 1.8s | 1.5s | 下降约 16.7%，超过 10% 目标 |
| P90 | 4.5s | 3.1s | 下降约 31.1%，超过 20% 目标 |

本地 Benchmark、代表 Trace 和线上分位数口径不同，应该分别报告，不能选择最大降幅作为项目最终收益。

## 专项结束后留下什么？

优化后的稳定版本成为新基线，并回填：

- 启动 P50、P90；
- 首页框架可见区间；
- `Stage_home_build` 和关键 Task 预算；
- Macrobenchmark 基线；
- 灰度门禁和线上告警阈值。

后续改动超过预算时，应在合入、候选版本或灰度阶段被发现，避免性能一点点退回优化前水位。

## 三个典型判断

1. 项目区间下降，但 inflate 和 WebView 没变化：当前方案与收益之间仍缺少结构证据。
2. 恢复全量缓存能修复白屏：可以作为诊断实验，不应直接作为最终方案。
3. P50、P90 达标但白屏上涨：性能项目仍不能放量。

## 常见误区

1. 本地一次变快，就直接全量发布。
2. 只比较总耗时，不检查目标 Slice。
3. 功能回归后恢复全量缓存，吃掉启动收益。
4. 用一次性事件承载必须可恢复的最新状态。
5. 灰度只看启动数字，不看稳定性和业务成功率。
6. 混用 Benchmark、Trace 和线上分位数的降幅。
7. 专项结束后不更新基线和预算。

## 本篇自测

1. 为什么总耗时与目标 Slice 要同时下降？
2. 临时提高 Fragment 缓存为什么只是诊断实验？
3. “我的”页状态为什么适合快照加 replay？
4. P50 和 P90 是否达到原目标？
5. 新基线和预算怎样守住收益？

## 一句话总结

启动优化只有在目标工作量下降、功能回归被修复、线上分位数达标并形成新基线后，才算真正完成。
