> 难度：进阶
> 预计阅读时间：12 分钟

## 1. 项目骨架：启动优化第一步是定口径，不是改代码

启动优化最容易犯的错，是上来就改代码——异步初始化、删 SDK、懒加载一通操作，然后"感觉快了"。问题是：**没有口径，你无法证明优化真的改善了体感，也无法判断到底改对没改对。** 所以第一步是定义一个**可量化、可复现、边界清晰**的指标。

### 1.1 为什么选 TTFD 而不是 TTID

| 指标 | 含义 | 局限 |
|---|---|---|
| **TTID** | Time To Initial Display，首帧可见 | 可能只是 Splash 或首页壳子，**不代表核心业务可用** |
| **TTFD** | Time To Full Display，关键业务内容可见 | 终点需业务自己定义，口径要说清边界 |

> **面试一句话：** 我们没用 TTID，因为 TTID 只说明首帧出现，可能只是个壳子；用户真正"看到首页工作台模块框架"才是体感终点，所以选 TTFD。

### 1.2 本项目的 TTFD 定义

```text
TTFD = TTFD_HomeWorkDesk.ts − bindApplication.ts
```

- **起点**：Perfetto 系统 slice `bindApplication`
- **终点**：业务自埋 marker `TTFD_HomeWorkDesk`（`Trace.beginSection/endSection`）

终点的精确触发链：

```text
MainBodyFragment.initialize()
  → refreshDataByPrivilege() → presenter.getUserColumns()
  → onGetUserColumns()  // 拿到用户权限模块
  → 把首页权限模块 View 添加到 llColumns
  → 等下一次 onDraw()
  → StartupTraceTracker.finish() → Trace.beginSection("TTFD_HomeWorkDesk")
```

⚠️ 终点不能简单说成 `getUserColumns()`。准确表达：**`getUserColumns()` 返回权限模块后，View 被 add 到容器，并经历下一次 draw，才打 marker。** 统计的是"首页工作台框架首次可见"，不是接口返回或 addView 完成。

### 1.3 为什么要"等下一次 draw"

如果在接口返回 / `addView()` 后立即打点，统计到的只是**数据层 / 对象层完成**，用户其实还没看见。等一次 draw 意味着：View 已进树、至少经历一次绘制机会，才贴近"用户看见"。

> 🔧 **机制：为什么 addView 之后还要等一次 draw 才算"看见"？**
> `addView` 只是把 DecorView 交给 `WindowManager`，触发创建 **ViewRootImpl**（View 树与系统渲染的桥）。真正的像素要等：`ViewRootImpl.requestLayout()` 向 **Choreographer** 注册 vsync 回调 → 下一个 vsync 信号到来 → `performTraversals()` 跑完 measure/layout/draw → 提交给渲染线程。所以"add 完"和"画出来"之间**隔着一个 vsync 周期**，TTFD 必须等到那次 draw，量的才是体感。（这条链路的细节在模块三展开。）

### 1.4 口径的局限与分层治理

这个 TTFD 只代表"首页框架可见"，不代表模块内部网络数据加载完。但这是**有意分层**，不是为了数据好看：

| 层级 | 关注 | 优化方向 |
|---|---|---|
| 第一层（本次） | 首页框架何时可见 | View 创建、布局、WebView、路径裁剪 |
| 第二层（下一步） | 各模块数据何时可用 | 接口耗时、缓存、并发、局部渲染 |

> **为什么不把"所有数据加载完"当终点？** 首页进入时有三四十个接口，若以全部数据为终点，指标会强依赖网络 / 后端 / 并发 / 缓存命中，**波动巨大**，分不清是启动链路慢还是某个接口慢。

## 2. 🔧 机制注脚：为什么起点选 bindApplication

这是面试高频追问——"你起点为什么从 `bindApplication` 算，而不是从用户点击图标算？"答好这题需要懂**点击到 bindApplication 之间发生了什么、为什么那段不该算进你的优化账上**。

### 2.1 点击图标到 bindApplication，中间这条链

```text
Launcher.startActivity
  → Instrumentation.execStartActivity
  → ATMS（system_server）：查 ProcessRecord，发现无进程 → 冷启动
  → 回调 AMS.startProcessLocked → Process.start → socket 通知 Zygote
  → Zygote fork 出 App 进程
  → 子进程：关 socket fd → ActivityThread.main（prepareMainLooper / new ActivityThread / attach / loop）
  → attach 经 AMS.attachApplication 把 ApplicationThread 交给系统
  → AMS 反向调 bindApplication ←★ 你的起点在这
```

两个职责边界值得记牢（面试加分）：

- **ATMS**（Android 10 拆出）：管 Activity/Task 调度，**判断要不要新进程**。
- **AMS**：管进程创建与生命周期，**真正去拉进程**（`startProcessLocked` → Zygote）。

### 2.2 为什么 bindApplication 之前的不算你的优化账

> **面试表达：** 点击图标到 `ActivityThread.main` 之间，是 Launcher 发起、`system_server`（ATMS/AMS）调度、Zygote fork 进程——**这段受系统调度、进程创建开销、设备状态影响，不是业务代码能优化的可控区间**。从 `bindApplication` 开始才进入 Application → ContentProvider → Activity 创建这条**业务相对可控**的链路。所以起点选 `bindApplication`，量的是"我能改的那段"。

补一个常被追问的点——**为什么进程是 Zygote `fork` 而不是新建**：Android 进程依赖 ART + framework 大量库资源，Zygote 在开机时已预加载好，fork 直接继承，省去重做初始化。这也是为什么"冷启动"虽慢但还能接受。（fork 返回值、子进程精确顺序等细节收在附录篇。）
