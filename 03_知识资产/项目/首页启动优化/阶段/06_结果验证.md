# 阶段六 · 结果验证

> 回答：怎样证明收益来自修改，不是测量波动。
> 事实源：[[../启动优化笔记#6.1 二次性能验证]]

## 同口径要求

- 同设备档位、包、账号、数据、场景；
- 同样冷启动方式与采集配置；
- 同一条 TTFD SQL；
- 同样的 Slice 聚合口径；
- 多轮 Benchmark，而非单次结果。

## P0 前后证据

| 指标 | 优化前 | P0 后 |
|---|---:|---:|
| TTFD | 约 2790ms | 约 1774ms |
| `inflate` | 106次 / 700.8ms | 62次 / 294.3ms |
| `RV OnLayout` | 29次 / 518.3ms | 18次 / 178.4ms |
| `traversal` | 750.1ms | 327.2ms |
| WebView | 2次 / 229.9ms | 0 |

时间下降同时伴随目标 Slice 的 Count/Wall 下降，支持“关键路径工作量减少”的因果解释。

## 三层数据

- 个人手机 Benchmark：2.98s → 1.74s，约下降 41.6%。
- 代表 Perfetto TTFD：2790ms → 1774ms，约下降 36.4%。
- 线上数据：留给灰度阶段验证。

三组数据环境不同，不能混成一个优化率。
