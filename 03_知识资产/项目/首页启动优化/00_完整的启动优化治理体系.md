# 完整的启动优化治理体系

> 本文是启动优化的最高层知识框架。它内部包含增量劣化治理、存量优化、统一验证和基线回填，但整体只作为一个复习单元。

## 一句话定义

启动性能治理不是一次专项优化，而是一个持续降低启动水位、阻止新代码重新抬高水位的闭环。

```text
增量防线阻止变差
          ↓
存量优化主动降低水位
          ↓
性能、Trace、功能三重验证
          ↓
稳定基线与阶段预算回填
          ↓
下一轮增量防线守住新水位
```

## 增量劣化治理

增量侧按照问题发现时间建立多层防线：

| 时间点 | 防线 | 主要回答 |
|---|---|---|
| 编码期 | 静态 Lint | 是否引入主线程 IO、阻塞等待、过早初始化等高风险模式？ |
| 成员 MR | 固定设备构建 Release 包并运行 Macrobenchmark | 相对稳定基线是否发生可重复劣化？ |
| 候选版本 | 完整自动化性能测试 | 核心启动场景是否整体退化？ |
| 灰度期 | 同场景、同设备档位比较 P50、P90、Stage、Task | 真实流量中哪个分位数或阶段开始偏离？ |
| 全量期 | 线上性能监控 | 是否出现灰度样本无法覆盖的长尾问题？ |

这条线的目标不是主动寻找所有优化机会，而是尽量在更早阶段阻止新代码抬高稳定水位。

## 存量优化

存量侧处理稳定版本已经存在的启动成本：

```text
线上P50/P90或业务目标发现机会
→ 圈定启动场景与设备档位
→ 固定Release包、账号、数据和操作
→ 相同档位设备多轮Benchmark
→ 选择中位数轮次
→ 用Perfetto做全链路归因
→ 沿bindApplication、Application、Activity、首帧、TTFD分阶段治理
→ 继续下钻Stage与Task
```

Benchmark 负责证明相同环境下前后是否稳定变化；中位数轮次的 Perfetto 负责解释时间花在哪里。不能拿一次最快结果作为代表 Trace。

首页冷启动项目是存量治理案例：[[00_阅读导航|首页启动优化重写版]]。

## 统一验证

修改完成后必须同时通过三类验证：

1. **性能验证**：相同条件下多轮 Benchmark 是否稳定变快，灰度和线上分位数是否收敛；
2. **Trace 验证**：最初提出的目标 Slice、Stage、Task 是否按假设下降；
3. **功能安全**：删除、延迟、异步化或按需加载后，业务状态和用户路径是否仍然正确。

只有耗时下降不够：如果目标 Trace 没变化，可能只是实验噪声；如果功能出现白屏、事件丢失或状态错误，则是用功能风险换性能。

## 基线与预算回填

验证通过后，将优化后的稳定 Release 包作为新基线，并更新：

- 总启动耗时基线；
- `bindApplication/Application/Activity/首帧/TTFD` 阶段预算；
- Stage 与 Task 预算；
- MR Benchmark、候选版本自动化和灰度门禁阈值。

这样，存量优化得到的一次性收益会成为下一轮增量治理的检测标准。

## 面试表达

> 我把启动性能治理分成存量优化和增量劣化治理。增量侧按照问题发现时间建立多层防线：编码期用 Lint 识别主线程 IO、阻塞等待和过早初始化；成员 MR 在固定设备上构建 Release 包，通过 Macrobenchmark 和稳定基线比较；候选版本运行完整自动化性能测试；灰度阶段在相同场景和设备档位下比较 P50、P90、Stage 和 Task；全量发布后再由线上监控承接灰度覆盖不到的长尾。
>
> 存量侧从线上分位数或业务目标发现机会，在相同档位设备上多轮 Benchmark，选择中位数轮次用 Perfetto 做全链路归因，再沿 bindApplication、Application、Activity、首帧和 TTFD 分阶段治理。修改完成后同时验证性能、Trace 假设和功能安全，最后更新稳定基线和阶段预算，让存量收益进入下一轮增量治理。
