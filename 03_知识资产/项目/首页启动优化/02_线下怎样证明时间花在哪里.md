# 02｜线下怎样证明时间花在哪里？

## 本篇只解决一个问题

线上已经把方向收敛到首页构建。怎样稳定复现，并证明时间具体花在哪里？

## 为什么不能比较两次手动启动？

同一台手机连续冷启动，仍会受到温度、调度、缓存、编译状态和后台负载影响。

如果优化前取最慢一次、优化后取最快一次，几乎任何改动都可以“证明”有效。线下实验必须先控制变量，再比较多轮结果。

每轮保持：同一物理设备、系统、Release 包、账号、权限、首页数据、网络、缓存、登录状态、启动入口，以及相同编译和 Profile 状态。

本项目关注冷启动，可使用 `StartupMode.COLD`。Macrobenchmark 负责多轮测量；分析结构时，从中位数附近选取代表 Trace。

## TTID、TTFD 和项目区间有什么区别？

官方 TTID 是系统收到启动请求到首帧显示，回答用户何时第一次看到画面。

官方 TTFD 从系统收到启动 Intent 开始，到应用调用 `reportFullyDrawn()`，代表主要内容完成并达到应用定义的可用状态。

项目已有指标：

```text
TTFD_HomeWorkDesk.ts - bindApplication.ts
```

起点是目标进程的 `bindApplication`；终点是首页权限模块加入 View 树，并经历下一次 draw 后记录的 `TTFD_HomeWorkDesk` marker。

这段更准确地叫“首页框架可见区间”。它不是官方 TTFD，也不代表所有数据已经完成或页面完全可交互。

从 `bindApplication` 开始，是为了单独衡量业务相对可控的 Application、Activity 和首页构建路径。此前的进程创建仍属于用户启动体验，只是不在这个项目区间内。

等待下一次 draw，是因为数据返回或 `addView` 只表示对象已加入树；它还需要 measure、layout 和 draw。但 draw 完成也不严格等于 SurfaceFlinger 已经扫描显示。

## Macrobenchmark、marker 和 Perfetto 各自看什么？

| 工具 | 回答的问题 |
|---|---|
| Macrobenchmark | 相同条件下，多轮启动是否稳定变快 |
| 业务 marker | 项目想测量的起点和终点在哪里 |
| Perfetto | 区间内线程、渲染、Binder 和业务工作怎样分布 |
| 源码 | 哪段业务逻辑制造了 Trace 热点 |

ART 的解释执行、JIT、AOT 和 Profile 会影响启动耗时。Macrobenchmark 优化前后必须使用相同 `CompilationMode`，并记录 Baseline Profile 是否被安装。

## 怎样精确计算项目区间？

不要在 Perfetto 时间轴上肉眼估算。可以用 SQL 限定进程并计算两个 Slice 的时间差：

```sql
WITH app_slices AS (
  SELECT s.*
  FROM slice s
  JOIN thread_track tt ON s.track_id = tt.id
  JOIN thread t ON tt.utid = t.utid
  JOIN process p ON t.upid = p.upid
  WHERE p.name = 'com.kedacom.ovopark'
),
start AS (
  SELECT ts FROM app_slices
  WHERE name = 'bindApplication'
  ORDER BY ts LIMIT 1
),
finish AS (
  SELECT ts FROM app_slices
  WHERE name = 'TTFD_HomeWorkDesk'
  ORDER BY ts LIMIT 1
)
SELECT (finish.ts - start.ts) / 1000000.0 AS home_ready_ms
FROM start, finish;
```

必须限定目标进程，因为同一份 Trace 中可能出现其他进程或同名 Slice。优化前代表 Trace 的项目区间约为 2790ms。

## `Wall`、`Self` 和 `Count` 应该怎样看？

| 指标 | 含义 | 用途 |
|---|---|---|
| Wall | Slice 总时长，包含子 Slice | 找耗时区域 |
| Self | 扣除子 Slice后的自身耗时 | 区分容器与直接成本 |
| Count | 出现次数 | 区分单次重和高频累积 |

典型组合：

| 表现 | 判断 |
|---|---|
| Wall 高、Self 高、Count 少 | 单个重任务 |
| Wall 高、Self 高、Count 多 | 高频且单次不轻 |
| Wall 高、Self 低 | 外层容器，继续下钻 |
| Wall 接近 Self、Count 多 | 高频直接成本 |

父 Slice 的 Wall 已包含子 Slice。不能把 `traversal`、inflate 和 layout 的 Wall 直接相加，否则会重复计算。

## 这次 Trace 先暴露了什么？

| Slice | Wall | Self | Count |
|---|---:|---:|---:|
| `Choreographer#doFrame` | 753.7ms | 0.3ms | 10 |
| `traversal` | 750.1ms | 73.8ms | 10 |
| `inflate` | 700.8ms | 198.4ms | 106 |
| `RV OnLayout` | 518.3ms | 235.6ms | 29 |
| `WebView` | 229.9ms | 52.8ms | 2 |
| `binder transaction` | 226.3ms | 226.3ms | 579 |

`doFrame` 的 Wall 很高，但 Self 只有 0.3ms，说明它只是外层帧调度入口。真正成本位于内部 traversal、inflate、measure、layout、draw 或业务代码。

这些数据确定了需要回源码验证的热点，还没有确定技术根因。

## 三个典型判断

1. Benchmark 多轮变快，但目标 Slice 没变化：可能是环境噪声或其他路径变化，不能认定当前假设成立。
2. `doFrame` Wall 高、Self 很低：继续下钻子 Slice，不把 Choreographer 当根因。
3. inflate 和 traversal 都很高：二者存在父子重叠，不能直接相加后称为总收益空间。

## 常见误区

1. 把项目 marker 直接称为官方 TTFD。
2. 使用 debuggable 包给出生产性能结论。
3. 优化前后使用不同 CompilationMode。
4. 用单次最好结果证明收益。
5. 在 Perfetto UI 肉眼估算区间。
6. 把父子 Slice 的 Wall 直接相加。
7. `doFrame` Wall 高，就把 Choreographer 写成根因。

## 本篇自测

1. Benchmark、marker、Perfetto 和源码分别回答什么？
2. 官方 TTFD 与项目区间有什么区别？
3. 为什么必须固定 CompilationMode？
4. `doFrame` Wall 高、Self 低时应该怎样处理？
5. 为什么聚合 Wall 不能直接相加？

## 一句话总结

Benchmark 证明是否稳定变化，项目 marker 确定测量边界，Perfetto 再解释时间花在哪里。
