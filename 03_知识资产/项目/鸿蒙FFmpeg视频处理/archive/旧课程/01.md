# 01 · fftools 为什么会结束宿主 App

> 归档说明：这是分层重构前的课程原文；当前入口见 [[../../syllabus]]。

> 前置知识：知道 FFmpeg 命令、C 的 `exit()`、函数调用栈与线程局部变量。

## 问题来自运行模型变化

Mac 终端执行 `ffmpeg` 时，Shell 会启动独立进程。命令完成或发生错误后，fftools 调用 `exit(ret)`，结束自己的进程并把退出码交给操作系统。

```text
Shell
  -> ffmpeg 独立进程
  -> fftools
  -> exit(ret)
  -> 仅结束 ffmpeg 进程
```

项目把 fftools 编进 `.so` 后，它不再拥有独立进程，而是运行在鸿蒙 App 进程内。此时调用 `exit()`，被结束的是整个宿主 App。

```text
ArkTS
  -> Native .so
  -> fftools
  -> exit(ret)
  -> 整个 App 进程结束
```

根因不是普通崩溃，而是 fftools 的命令行程序假设与嵌入式运行环境冲突：它认为自己可以结束进程，App 却只希望结束一条命令。

## 为什么不能逐处改成 `return`

fftools 在参数解析、输入打开、滤镜初始化和编码等深层调用中都可能执行 `exit_program()`。这些位置通常跨越多层函数，无法通过一个普通 `return` 回到统一入口。

逐处改动还会侵入大量上游代码，遗漏风险高，后续升级 FFmpeg 时也难以维护。更合理的边界是统一拦截 `exit_program()`。

## 用 `setjmp / longjmp` 改造退出边界

目标是让 fftools 想“退出”时，不结束进程，而是跳回项目定义的命令入口，把返回码交给调用方。

`setjmp` 记录可返回的位置，`longjmp` 从深层调用栈跳回该位置。可把它理解为 C 语言中的受控异常边界。

| 机制 | 作用 | 类比 |
| --- | --- | --- |
| `setjmp(buf)` | 记录返回点 | `try` |
| `longjmp(buf, value)` | 从深层跳回 | `throw` |
| 非零返回分支 | 接收跳转结果 | `catch` |

### 1. 在命令入口记录返回点

项目将桌面程序的 `main(argc, argv)` 改造成可调用的 `exe_ffmpeg_cmd`，并在入口设置跳转点：

```c
int exe_ffmpeg_cmd(int argc, char **argv, Callbacks *callbacks)
{
    int saved_code = setjmp(ex_buf__);

    if (saved_code == 0) {
        g_callbacks = callbacks;
        // 解析参数并执行 fftools
    } else {
        main_return_code = received_nb_signals ? 255 : longjmp_value;
        int saved_error = main_return_code;
        reset_ffmpeg_state();
        return saved_error;
    }

    return main_return_code;
}
```

第一次进入时，`setjmp` 返回 `0`，执行正常流程。被 `longjmp` 跳回后，它进入非零分支，保存错误码、清理状态并返回调用方。

### 2. 把进程退出改成非局部跳转

```c
extern __thread jmp_buf ex_buf__;
extern __thread volatile int longjmp_value;

void exit_program(int ret)
{
    if (program_exit)
        program_exit(ret);

    longjmp_value = ret;
    longjmp(ex_buf__, ret);
}
```

所有深层 `exit_program(ret)` 最终都经过这一处。改动统一出口后，正常结束和异常结束都会回到 `exe_ffmpeg_cmd`。

```text
fftools 完成或出错
  -> exit_program(ret)
  -> longjmp
  -> exe_ffmpeg_cmd 的 setjmp 返回点
  -> return ret
  -> App 继续运行
```

## 为什么必须清理全局状态

独立命令行进程执行完就被销毁，全局变量会随进程释放。嵌入 App 后，同一进程会连续执行多条命令，旧任务状态不会自动消失。

若不清理，输入输出表、编码上下文、计数器和回调指针等状态可能污染下一条命令，导致第二次或后续执行异常。

因此跳回后必须执行：

```c
int saved_error = main_return_code;
reset_ffmpeg_state();
return saved_error;
```

顺序不能颠倒。`reset_ffmpeg_state()` 也会重置返回码；若先清理再保存，上层可能永远收到 `0`，把失败误判成成功。

## 为什么跳转状态必须线程局部

```c
__thread jmp_buf ex_buf__;
__thread volatile int longjmp_value;
```

FFmpeg 命令不在 ArkTS JS 线程执行。若多个线程共用同一个跳转点，线程 A 可能跳到线程 B 的栈帧，产生未定义行为。

`__thread` 让每个执行线程拥有独立跳转缓冲区和返回码，避免跳错执行现场。

线程局部只解决跳转状态隔离，不代表 fftools 可以并行执行。FFmpeg 工具层仍大量使用全局共享状态，任务调度层必须限制工作线程数量为 `1`，串行执行命令。

## 返回码如何进入上层

`exe_ffmpeg_cmd` 返回后，C++ 桥接层根据返回码触发结果回调：

```cpp
int ret = exe_ffmpeg_cmd(argc, argv, &callbacks);

if (ret == 0) {
    on_success();
} else {
    on_failed(ret);
}
```

“优雅退出”不是没有退出，而是把“结束宿主进程”转换成“结束本次命令并返回结果码”。

## 小结

1. fftools 原本是独立程序，调用 `exit()` 符合命令行运行模型。
2. 嵌入 `.so` 后，`exit()` 会结束宿主 App。
3. 项目用 `setjmp / longjmp` 在统一出口拦截进程退出。
4. 命令结束后先保存返回码，再清理全局状态。
5. 跳转状态按线程隔离，但 fftools 命令仍由上层串行调度。
