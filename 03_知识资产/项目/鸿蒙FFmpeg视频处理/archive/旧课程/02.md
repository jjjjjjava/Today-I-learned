# 02 · ArkTS 如何调用 fftools，fftools 又如何回调 ArkTS

> 归档说明：这是分层重构前的课程原文；当前入口见 [[../../syllabus]]。

> 前置知识：理解 [01.md](./01.md) 中的 `exe_ffmpeg_cmd` 与返回码；知道 ArkTS 和 C/C++ 属于不同运行时。

## 问题全景

Mac Shell 会把 FFmpeg 命令拆成 `argc / argv`，再启动 `ffmpeg` 进程。鸿蒙应用需要在不启动独立命令行进程的情况下，复用相同的 fftools 参数模型。

完整通信包含去程和回程：

```text
去程：ArkTS 命令数组
  -> AKI/NAPI
  -> C++ Native 函数
  -> argc / argv
  -> fftools

回程：fftools
  -> C 函数指针
  -> C++ 桥接函数
  -> AKI/NAPI
  -> ArkTS 回调
```

## 一、ArkTS 如何调用 Native fftools

### 1. 为什么普通 `.so` 不能直接调用

普通 `.so` 里即使存在 C++ 函数，ArkTS 模块系统也不知道如何初始化它、导出哪些符号，以及怎样转换两端参数。

项目使用 OpenHarmony NAPI 建立 ArkTS 与 C/C++ 的桥，并用 AKI 的宏和模板减少手写 NAPI 代码。

### 2. `JSBIND_ADDON` 注册什么

```cpp
JSBIND_ADDON(ffmpegutils)
```

这条宏把当前动态库声明为名为 `ffmpegutils` 的 Native Addon。Addon 名与动态库名对应：

```text
JSBIND_ADDON(ffmpegutils)
             |
             +-- libffmpegutils.so
```

它的意义不是执行 FFmpeg，而是为模块加载建立入口：ArkTS 导入 `libffmpegutils.so` 时，运行时知道需要调用 AKI 生成的模块初始化逻辑。

### 3. `JSBIND_PFUNCTION` 导出什么

```cpp
JSBIND_GLOBAL() {
    JSBIND_PFUNCTION(executeFFmpegCommandAPP);
}
```

`JSBIND_PFUNCTION` 绑定 C++ 函数指针，并生成 ArkTS 与 C++ 之间的适配信息：导出名称、参数转换、返回值转换、Promise 创建及异步执行策略。

概念上，它替代了这些手写 NAPI 工作：

```text
创建 ArkTS 函数对象
  -> 挂到模块 exports
  -> 读取 ArkTS 参数
  -> 转换为 C++ 参数
  -> 异步执行 C++ 函数
  -> 把结果转换回 ArkTS
  -> 完成 Promise
```

参考：[AKI JSBind 与 Promise 异步函数说明](https://gitee.com/openharmony-sig/aki/blob/master/README.md)。

### 4. `import` 后为什么函数可见

ArkTS 执行：

```typescript
import libAddon from 'libffmpegutils.so'
```

运行时发生的过程是：

```text
ArkTS 模块加载器定位 .so
  -> 加载动态库及其依赖
  -> 执行 Native Addon 初始化入口
  -> AKI 读取绑定信息
  -> 创建 ArkTS 函数包装对象
  -> 挂到模块 exports
  -> exports 返回给 libAddon
```

因此 `libAddon.executeFFmpegCommandAPP` 看起来像 ArkTS 函数，实际是 AKI 创建的包装函数，内部保存着真正 C++ 函数的绑定关系。

`.d.ts` 与运行时导出作用不同。`.d.ts` 只告诉 ArkTS 编译器函数名、参数和返回类型；Addon 初始化和 `exports` 才让函数在运行时真正存在。

参考：[OpenHarmony Native 模块导入说明](https://gitee.com/openharmony/docs/blob/master/zh-cn/application-dev/arkts-utils/arkts-import-native-module.md)。

### 5. ArkTS 参数如何变成 C++ 参数

ArkTS 发起调用：

```typescript
libAddon.executeFFmpegCommandAPP(uuid, cmds.length, cmds)
```

调用先进入 AKI 包装函数。AKI 根据被绑定函数的 C++ 签名执行类型转换：

```text
ArkTS string    -> std::string uuid
ArkTS number    -> int cmdLen
ArkTS string[]  -> std::vector<std::string> argv
```

C++ 目标函数形态如下：

```cpp
int executeFFmpegCommandAPP(
    std::string uuid,
    int cmdLen,
    std::vector<std::string> argv
);
```

项目代码再执行第二次适配，把 C++ 容器转换成 fftools 熟悉的命令行参数：

```text
std::vector<std::string>
  -> char **argv
  -> exe_ffmpeg_cmd(argc, argv)
```

第一层转换跨越 ArkTS 与 C++；第二层转换跨越 C++ 友好接口与 fftools 命令入口。

### 6. FFmpeg 为什么不阻塞 JS 线程

关键在 `JSBIND_PFUNCTION` 的 `P`。它把 C++ 函数映射成 Promise 异步函数，官方保证被绑定的 C++ 函数不在 JS 线程执行。

```text
JS 线程
  -> 创建 Promise
  -> 转换并保存 Native 参数
  -> 提交异步 Native 任务
  -> 立即返回 Promise

Native 非 JS 线程
  -> executeFFmpegCommandAPP
  -> exe_ffmpeg_cmd
  -> fftools 长时间执行

JS 线程
  -> 接收完成通知
  -> 转换返回值
  -> resolve / reject Promise
```

项目没有为每次调用手写 `std::thread`。线程切换由 AKI 的异步执行机制完成，底层可以复用执行器或线程池，不等于每次创建一条全新线程。

若改成同步的 `JSBIND_FUNCTION`，FFmpeg 会占用 JS 线程几十秒，导致页面无响应。

### 7. 去程全链路

```text
ArkTS import libffmpegutils.so
  -> OpenHarmony 加载 Native Addon
  -> AKI 初始化 exports
  -> ArkTS 调用 executeFFmpegCommandAPP
  -> AKI 将 napi_value 转成 C++ 参数
  -> JSBIND_PFUNCTION 提交异步任务
  -> vector<string> 转成 argc / argv
  -> exe_ffmpeg_cmd
  -> fftools
  -> libav*
```

## 二、fftools 如何回调 ArkTS

### 1. 为什么不能保存 ArkTS 函数地址

ArkTS 回调是 JS 虚拟机管理的对象，不是稳定的 C 函数地址。Native 不能直接保存其裸地址，也不能假设函数对象不会被垃圾回收。

执行任务前，ArkTS 先把回调注册到 AKI：

```typescript
libAddon.JSBind.bindFunction(
  uuid + '_onFFmpegProgress',
  options.onFFmpegProgress
)

libAddon.JSBind.bindFunction(
  uuid + '_onFFmpegFail',
  options.onFFmpegFail
)

libAddon.JSBind.bindFunction(
  uuid + '_onFFmpegSuccess',
  options.onFFmpegSuccess
)
```

`bindFunction` 在 AKI 的 JS 函数表中保存引用，并用字符串名称建立索引。UUID 区分不同任务，避免新任务覆盖旧任务的回调。

### 2. C++ 如何取回本次任务的 JS 函数

Native 方法根据相同 UUID 查询函数句柄：

```cpp
CallBackInfo callback_info;

callback_info.onFFmpegProgress =
    aki::JSBind::GetJSFunction(uuid + "_onFFmpegProgress");

callback_info.onFFmpegFail =
    aki::JSBind::GetJSFunction(uuid + "_onFFmpegFail");

callback_info.onFFmpegSuccess =
    aki::JSBind::GetJSFunction(uuid + "_onFFmpegSuccess");
```

C++ 此时拿到可调用的 JS 函数句柄，但 fftools 是 C 代码，不认识 `aki::JSFunction`。

### 3. 用 C 函数指针连接 fftools 与 C++

项目定义纯 C 回调协议：

```c
typedef struct Callbacks {
    void (*onFFmpegProgress)(int progress);
    void (*onFFmpegFail)(int code, const char *message);
    void (*onFFmpegSuccess)(void);
} Callbacks;
```

C++ 提供签名兼容的普通桥接函数，再把函数地址交给 fftools：

```cpp
Callbacks callbacks = {
    .onFFmpegProgress = onFFmpegProgress,
    .onFFmpegFail = onFFmpegFail,
    .onFFmpegSuccess = onFFmpegSuccess
};

exe_ffmpeg_cmd(argc, argv, &callbacks);
```

fftools 只依赖 `void (*)(int)` 等 C 函数指针，不需要依赖 AKI，也不需要理解 ArkTS。

### 4. fftools 如何触发进度

`exe_ffmpeg_cmd` 保存回调表：

```c
static Callbacks *g_callbacks = NULL;

int exe_ffmpeg_cmd(int argc, char **argv, Callbacks *callbacks)
{
    g_callbacks = callbacks;
    // 执行命令
}
```

fftools 根据已处理时间戳与总时长计算进度，再调用函数指针：

```c
int progress = pts * 100 / total_duration;

if (g_callbacks && g_callbacks->onFFmpegProgress) {
    g_callbacks->onFFmpegProgress(progress);
}
```

站在 fftools 视角，它只执行了普通 C 函数调用，并不知道后面还会进入 C++ 与 ArkTS。

### 5. `g_currentCallback` 补充任务上下文

C 回调 `void onFFmpegProgress(int progress)` 只有进度值，没有 UUID 或 `void *userData`，桥接函数无法从参数判断应该调用哪个 JS 函数。

因此 C++ 在执行命令前保存当前任务上下文：

```cpp
thread_local CallBackInfo *g_currentCallback;
g_currentCallback = &callback_info;
```

桥接函数再从当前线程取回 JS 函数：

```cpp
void onFFmpegProgress(int progress)
{
    if (g_currentCallback &&
        g_currentCallback->onFFmpegProgress) {
        g_currentCallback->onFFmpegProgress->Invoke<void>(progress);
    }
}
```

两个全局量不可混淆：

| 变量 | 所在层 | 保存内容 |
| --- | --- | --- |
| `g_callbacks` | C / fftools | C++ 桥接函数地址 |
| `g_currentCallback` | C++ | 本任务的 JS 函数句柄 |

UUID 解决回调注册表中的任务区分；`thread_local` 解决执行线程上的当前任务上下文。

### 6. `Invoke` 如何回到 JS 线程

FFmpeg 在非 JS 线程执行，不能直接操作 JS 虚拟机。桥接函数调用：

```cpp
js_function->Invoke<void>(progress);
```

AKI 会把 JS 函数执行调度到 JS 线程：

```text
FFmpeg Native 线程
  -> Invoke<void>(60)
  -> AKI 跨线程调度
  -> JS 线程执行 onFFmpegProgress(60)
```

AKI 文档说明：从非 JS 线程调用已绑定 JS 函数时，框架会调度 JS 线程，并阻塞 Native 调用线程，直到 JS 函数执行完成。

因此进度回调必须轻量。若回调执行重计算或同步 I/O，FFmpeg 工作线程也会被拖慢。

### 7. 成功和失败走另一条路径

进度在命令执行期间由 fftools 主动上报。成功和失败则由 [01.md](./01.md) 中的返回码决定：

```cpp
int ret = exe_ffmpeg_cmd(argc, argv, &callbacks);

if (ret == 0) {
    callback_info.onFFmpegSuccess->Invoke<void>();
} else {
    char message[1024] = {0};
    av_strerror(ret, message, sizeof(message));
    callback_info.onFFmpegFail->Invoke<void>(ret, message);
}
```

```text
执行期间：fftools -> C 函数指针 -> C++ -> ArkTS onProgress

执行结束：exe_ffmpeg_cmd 返回 ret -> C++ -> ArkTS onSuccess/onFailed
```

## 三、并发边界

UUID、`thread_local g_currentCallback` 和 `__thread ex_buf__` 能隔离任务身份、回调与跳转点，但 fftools 内部仍有大量全局共享状态。

因此项目在任务调度层限制工作线程数量为 `1`，让多条命令排队串行执行。通信隔离不等于底层具备真正并发能力。

## 完整双向链路

```text
ArkTS 构造命令并注册 UUID 回调
  -> Native Addon 导出函数
  -> AKI 转换参数并提交异步任务
  -> C++ 转 argc / argv
  -> exe_ffmpeg_cmd
  -> fftools 驱动 libav*
  -> C 函数指针上报进度
  -> C++ 从 thread_local 找回 JS 函数
  -> AKI 调度 JS 线程执行回调
  -> 命令结束后按返回码回调成功或失败
```

## 小结

1. `JSBIND_ADDON` 解决 `.so` 如何成为 ArkTS 可导入的 Native 模块。
2. `JSBIND_PFUNCTION` 解决函数导出、类型转换、非 JS 线程执行与 Promise 返回。
3. 项目把 ArkTS 命令数组还原为 fftools 使用的 `argc / argv`。
4. ArkTS 回调先按 UUID 注册，再由 C 函数指针、C++ 桥和 AKI 两跳回传。
5. AKI 在 JS 线程执行回调；Native 调用线程会等待回调完成。
6. 多条 fftools 命令仍由上层串行调度。
