# 鸿蒙录像下载与视频加水印：从下架整改到 FFmpeg 基础能力

> 归档说明：这是分层重构前的项目全景原文；当前入口见 [[../../syllabus]]。

> 技术栈：HarmonyOS / OpenHarmony、ArkTS、C/C++、AKI/NAPI、FFmpeg、fftools、Lycium、OH_AVCodec

## 项目全景

鸿蒙版本上线时，巡店模块沿用 H5 方案。受 Web 能力边界限制，语音对讲、录像下载、视频加水印等核心功能未能实现。华为在联合沟通群中多次发出整改警告，团队未在要求期限内完成补齐，最终版本被下架。下架事件使功能补齐从普通迭代升级为影响版本上架的紧急任务。

本项目聚焦录像下载与视频加水印。目标不只是补两个页面功能，而是在鸿蒙端建设统一媒体处理底座，让业务层通过 ArkTS API 调用录像下载、水印、转码等能力。

我独立负责技术调研、方案设计、功能开发、FFmpeg 源码修改、性能优化、测试验证及插件发布。平台沟通不由我负责；语音对讲虽由我参与，但不纳入本项目说明。

## 为什么选择 FFmpeg

录像下载不是普通 HTTP 文件下载。应用先通过取流接口获取设备 RTSP 地址，按业务策略使用主码流、不使用辅码流，再把 RTSP 媒体流保存为本地 MP4。

视频加水印需要把图片叠加到视频画面。画面像素发生变化，处理链路必须包含视频解码、图片合成、重新编码和文件封装。

团队调研过“网络模块拉流 + OpenGL 图像处理 + 系统编解码与封装”的组合方案。OpenGL 是图形渲染 API，不负责 RTSP 协议、媒体解复用、编解码和 MP4 封装。

组合方案理论可行，但需要拼接多套组件，自行维护时间戳、数据流、状态和异常。面对紧急整改周期，这条路线开发及维护成本过高。

FFmpeg 统一覆盖网络协议、解复用、编解码、滤镜和文件封装。录像下载与图片水印都能通过 fftools 命令完成，还能承载后续媒体处理需求，因此被选为鸿蒙端统一基础能力。

## FFmpeg 的核心能力

FFmpeg 不是单个“视频处理内核”，而是一组媒体库：

| 模块 | 核心职责 | 本项目用途 |
| --- | --- | --- |
| `libavformat` | 协议、I/O、解复用、封装 | 读取 RTSP，输出 MP4 |
| `libavcodec` | 音视频编解码 | 解码输入视频，编码水印结果 |
| `libavfilter` | 音视频滤镜 | 使用 `overlay` 合成图片水印 |
| `libavutil` | 时间戳、日志、内存与公共结构 | 支撑各模块运行 |
| `libswscale` | 缩放与像素格式转换 | 适配滤镜和编码输入 |
| `libswresample` | 音频重采样 | 仅在音频转换场景使用 |

直接调用 `libav*` 需要自行管理输入输出、编解码器、数据帧和错误状态。FFmpeg 源码中的 `fftools` 已把这些能力封装成命令行工具，负责解析参数并编排完整处理流程。

## 从 Mac 命令到鸿蒙 Native 调用

Mac 终端执行命令时，Shell 把命令拆成 `argc / argv`，启动独立 `ffmpeg` 进程。fftools 接收参数、驱动 `libav*`，完成后通过退出码结束进程。

```text
Mac Shell
  -> ffmpeg main(argc, argv)
  -> fftools
  -> libav*
  -> exit(ret)
```

鸿蒙应用不能直接复用桌面进程模型。项目把 fftools 编入 Native 动态库，将 `main(argc, argv)` 改造成可调用的 `exe_ffmpeg_cmd(argc, argv)`，再通过 AKI/NAPI 暴露给 ArkTS。

```text
ArkTS 命令数组
  -> AKI/NAPI
  -> exe_ffmpeg_cmd(argc, argv)
  -> fftools
  -> libav*
  -> 返回码与回调
```

这次搬运包含三类改造：交叉编译 FFmpeg；把进程入口改为函数入口；把终端退出、日志和退出码改成适合 App 的返回值、进度与结果回调。

## 编译搬运

OpenHarmony SDK/NDK 中的 LLVM、Clang 和链接器是真正执行交叉编译的工具链。Lycium 是 OpenHarmony C/C++ 三方库适配与构建框架，负责组织源码、配置、交叉编译和产物管理，本身不是编译器。

项目通过华为工单获取 OpenHarmony 适配版 FFmpeg 源码，基于 Lycium 修改 `HPKBUILD`，开启 RTSP、封装、滤镜及编解码等所需配置，最终把 FFmpeg 核心能力与 fftools 聚合为单一 `.so`。

参考：[OpenHarmony-SIG Lycium 构建说明](https://gitee.com/openharmony-sig/tpc_c_cplusplus/blob/master/lycium/Buildtools/README.md)。

## 四个核心工程问题

### 1. fftools 会结束宿主进程

fftools 原本属于独立命令行程序，内部调用 `exit()` 很正常。嵌入 `.so` 后，它与 App 共用进程，`exit()` 会直接结束整个宿主。

项目用 `setjmp / longjmp` 把“退出进程”改成“退出本次命令”，并在返回后清理 fftools 全局状态。详见 [01.md](./01.md)。

### 2. ArkTS 如何调用 Native fftools

`JSBIND_ADDON` 把 `.so` 注册为 Native Addon；`JSBIND_PFUNCTION` 导出异步 C++ 函数。ArkTS 导入模块后，AKI 负责参数转换、非 JS 线程执行和 Promise 完成。

项目再把 `std::vector<std::string>` 转换为 fftools 熟悉的 `argc / argv`。详见 [02.md](./02.md)。

### 3. fftools 如何回调 ArkTS

ArkTS 先按 UUID 注册进度、成功和失败函数。C++ 取回 JS 函数句柄，再通过纯 C 函数指针把回调交给 fftools。

fftools 调用 C 函数指针，C++ 桥接函数通过 AKI 调度 JS 线程执行回调。详见 [02.md](./02.md)。

### 4. 硬件编码与码率失效

初版 2 分钟视频加水印约需 150 秒，说明链路大概率仍在使用软件编码。向华为确认 `h264_ohosavcodec` 后，Native 日志又提示当前 FFmpeg 不包含该 codec。

项目获取包含 OpenHarmony 硬件编解码适配的源码版本，重新编译 `.so`，把耗时降至约 27 秒。随后又解决硬件编码器封装漏传码率的问题。详见 [03.md](./03.md)。

## 两条业务处理链

录像下载在编码与 MP4 兼容时尽量不改动画面，只读取 RTSP 媒体包并重新封装：

```text
RTSP
  -> 协议读取与解复用
  -> stream copy
  -> MP4 封装
```

图片水印必须改动画面：

```text
输入视频
  -> 解码
  -> overlay 合成水印
  -> h264_ohosavcodec 硬件编码
  -> MP4 封装
```

## 业务集成与异常处理

基础能力完成后，业务页面只需响应点击事件、获取接口数据、执行前置校验并调用 `ffmpeg_tools`。进度、成功和失败回调更新页面状态，响应式 UI 根据状态自动刷新。

明显无效的输入和运行条件在执行前拦截；RTSP、编解码、文件写入等运行时错误由 FFmpeg 返回码和失败回调处理。

## 最终成果

- 支撑鸿蒙录像下载与视频加水印上线，应用完成整改并重新上架。
- 2 分钟视频加水印由约 150 秒降至 27 秒，耗时降低约 82%，速度提升约 5.6 倍。
- 将能力发布至 [GitHub](https://github.com/jjjjjjava/ffmpeg_tools) 与 [OHPM `@prq/ffmpeg-tools`](https://ohpm.openharmony.cn/#/cn/detail/@prq%2Fffmpeg-tools)。
- 根据社区 [Issue #3](https://github.com/jjjjjjava/ffmpeg_tools/issues/3) 拆分并跟踪 [码率 Issue #5](https://github.com/jjjjjjava/ffmpeg_tools/issues/5)。
- 定位 OpenHarmony 硬件编码器封装漏传码率参数，并向上游提交 [Issue #IDMF3P](https://gitee.com/openharmony-tpc-incubate/FFmpeg/issues/IDMF3P)。

> 口径说明：`150s -> 27s` 是公司项目落地阶段数据。后续开源版本 README 记录了约 `15.68s` 的测试结果，版本和环境不同，不混作同一次对比。
