# 06｜修复完成后，怎样证明能力可以上线？

## 本篇只解决一个问题

Native 命令可以运行，不等于业务能力已经完成。怎样把录像下载、视频水印、性能和发布结果连成可复查的上线闭环？

## 先验证两条业务链

录像下载验证的不是“本地出现了文件”，而是 RTSP 输入能够稳定转成可播放 MP4：

```text
获取设备 RTSP 地址
→ 拉取主码流
→ stream copy
→ 生成本地 MP4
→ 校验时长、音视频与播放
```

视频水印需要验证完整重编码链：

```text
输入视频与水印图
→ 解码和 overlay
→ h264_ohosavcodec 编码
→ MP4 封装
→ 校验位置、画面、音频和播放
```

两者不能共用一个模糊的“导出成功”结论。下载关注取流和封装，水印还要覆盖像素合成与重新编码。

## 再验证 App 集成

页面调用需要覆盖一次完整状态变化：

```text
ArkTS 提交任务
→ Native 开始执行
→ 页面收到连续进度
→ 返回 success 或 failed
→ 页面恢复可操作状态
```

还要连续提交多次任务，确认单任务队列会等待上一条返回，再开始下一条；任一命令完成或失败后，App 进程都继续存活。

失败场景至少覆盖无效输入、RTSP 无法连接、输出路径不可写、编码器不可用和处理过程中断。业务层应收到明确失败结果，而不是卡在处理中。

## 性能验证看什么？

硬件编码回归保持输入视频、命令、设备和计时边界一致。公司项目阶段的结果是：2 分钟视频从约 150 秒降到约 27 秒，耗时下降约 82%。

除总耗时外，还要确认实际使用 `h264_ohosavcodec`、输出文件可播放、水印正确、音频正常。否则速度变化可能来自命令或输出能力被意外裁剪。

开源 README 中约 `15.68s` 的数据属于后续环境，单独保留，不替代公司阶段的验证结果。

## 码率验证看什么？

至少选择两个目标值，例如 `500k` 和 `300k`，验证目标越低时视频轨码率和文件大小会相应下降。

检查时同时保留三类数据：

1. 命令中的目标视频码率；
2. `ffprobe` 读取的视频轨码率；
3. 文件总码率和文件大小。

这样既能证明参数已经进入编码器，也不会把音频与封装开销误判成视频码率失效。

## 业务整改怎样闭环？

项目最终补齐鸿蒙端录像下载和视频加水印能力，完成测试与版本发布，应用重新上架。

个人工作范围包括技术调研、方案设计、功能开发、FFmpeg 源码修改、性能优化、测试验证和插件发布。平台沟通不是个人职责，语音对讲也不纳入本项目成果。

这条边界让项目叙述聚焦于实际完成的两项能力，避免把团队协作或其他功能写成个人产出。

## 为什么还要开源和反馈上游？

基础能力发布到 [GitHub](https://github.com/jjjjjjava/ffmpeg_tools) 和 [OHPM `@prq/ffmpeg-tools`](https://ohpm.openharmony.cn/#/cn/detail/@prq%2Fffmpeg-tools)。

其他鸿蒙项目可以复用 ArkTS 调用、fftools 改造和平台编解码能力。

社区 Issue #3 又暴露出硬件编码问题，其中码率问题拆为 Issue #5。修复 `OH_MD_KEY_BITRATE` 后更新插件。

由于根因位于底层适配，又向 OpenHarmony FFmpeg 提交 [Issue #IDMF3P](https://gitee.com/openharmony-tpc-incubate/FFmpeg/issues/IDMF3P)。

于是闭环从一次业务整改延伸到可复用组件：

```text
版本下架整改
→ 两项媒体能力上线
→ 性能达到可用水平
→ 应用重新上架
→ 能力发布到 GitHub / OHPM
→ 社区反馈触发底层修复
→ 修复回到插件与上游
```

## 三个典型判断

1. Native 返回 0：只能证明命令正常结束，还要验证输出内容和页面状态。
2. 性能明显提升：还要确认编码器、输入和计时口径一致。
3. 业务版本已上架：项目交付完成，但开源组件仍需响应真实使用反馈。

## 常见误区

1. 只验证成功路径，不验证错误回调和页面恢复。
2. 只检查文件存在，不检查时长、画面、音频和可播放性。
3. 用不同环境的性能数字组成一条优化曲线。
4. 用容器总码率替代视频轨码率。
5. 把平台沟通或语音对讲写入个人项目成果。

## 一句话总结

真正的交付不是“命令能跑”，而是两条业务链、App 回调、串行执行、性能、码率和发布结果都能被同一组事实复查。
## 小结

> 业务重新上架 → `ffmpeg_tools` 发布 GitHub 和 OHPM → 性能优化 → 社区问题反哺上游

这个项目形成了从业务落地、基础能力开源，到社区反馈、底层定位和上游回馈的完整闭环。

性能优化展示的是“从现象推断执行路径，再补齐构建能力”：发现 150 秒耗时，确认硬件 codec，依据 Native 日志定位产物缺失，获取适配源码并重新编译。

码率修复展示的是“沿参数链下钻”：从 GitHub 用户反馈出发，依次排除 ArkTS、fftools 和参数位置，最终定位到 Native 硬件编码器封装漏传字段。

最终形成完整闭环：

```text
业务落地
  -> 基础能力开源
  -> 社区 Issue
  -> 复现与底层定位
  -> 修改源码并重新发布
  -> 回馈 OpenHarmony 上游
```
