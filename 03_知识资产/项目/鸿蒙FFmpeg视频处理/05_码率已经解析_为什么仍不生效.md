# 05｜码率已经解析，为什么仍不生效？

## 本篇只解决一个问题

使用 `h264_ohosavcodec` 时，命令已经设置 `-b:v`，输出码率却没有按预期下降。参数究竟丢在哪一层？

## 问题从哪里进入？

`ffmpeg_tools` 开源后，GitHub 用户在 Issue #3 反馈硬件编码相关问题。排查发现，视频裁剪与码率、分辨率失效不是同一个根因，因此将码率问题拆为 Issue #5。

复现命令类似：

```text
ffmpeg -i input.mp4 \
  -c:v h264_ohosavcodec \
  -b:v 300k \
  -c:a aac \
  -y output.mp4
```

现象是命令执行成功，但输出仍保持较高码率。

## 先检查命令位置

FFmpeg 选项有输入和输出作用域。`-b:v 300k` 位于输出文件之前，因此它是输出视频流的目标码率，位置正确。

如果位置本身错误，参数可能作用于错误的文件或流。这里已经排除了这类命令构造问题。

## 怎样证明 fftools 已经收到参数？

继续跟踪参数解析，确认目标值已经进入 Native 编码参数：

```text
-b:v 300k
→ fftools 参数解析
→ format_->bit_rate = 300000
```

这条证据说明 ArkTS 参数构造和 fftools 解析没有丢值。接下来应检查平台编码器适配如何把 `format_` 写入系统配置。

## 参数在哪一层断了？

`h264_ohosavcodec` 的编码适配位于：

```text
libavcodec/ohosvideoencoder.cpp
```

`VideoEncoder::SetCodecFormat()` 会创建 `OH_AVFormat`，写入宽度、高度、像素格式和帧率，再调用 `OH_VideoEncoder_Configure()`。

源码已经得到 `format_->bit_rate`，却没有把它写入 `OH_AVFormat`：

```text
-b:v 300k
→ format_->bit_rate = 300000
→ SetCodecFormat 漏写 bitrate
→ OH_VideoEncoder_Configure 未收到目标码率
→ 编码器使用默认配置
```

根因不是“硬件编码天然不支持 `-b:v`”，而是 FFmpeg 与 OpenHarmony 编码器之间的适配层漏传字段。

## 源码怎样修复？

在调用 `OH_VideoEncoder_Configure()` 前，把码率写入平台格式对象：

```cpp
if (format_->bit_rate > 0) {
    OH_AVFormat_SetLongValue(
        avformat,
        OH_MD_KEY_BITRATE,
        format_->bit_rate
    );
}
```

修改后重新交叉编译 `.so`，替换 Native 产物，再用多组目标码率验证输出。

## 为什么设置 300k，看到的却约为 440 kbps？

`-b:v` 控制视频轨码率；播放器或文件信息页常展示容器总码率，其中还包含音频轨和 MP4 封装开销。

现有测试记录：

| 样本 | 显示码率 | 文件大小 |
|---|---:|---:|
| 原视频，6 分 48 秒 | 约 1012 kbps | 49.2 MB |
| 设置 `-b:v 500k` | 约 648 kbps | 31.5 MB |
| 设置 `-b:v 300k` | 约 440 kbps | 21.4 MB |

若音频约为 128 kbps，视频 300 kbps 加音频和封装开销后，总码率接近 440 kbps 是合理结果。不能只用总码率判断视频轨参数是否精确。

应单独读取视频轨：

```text
ffprobe -select_streams v:0 \
  -show_entries stream=bit_rate \
  -of default=noprint_wrappers=1 \
  output.mp4
```

## 修复怎样回到项目与社区？

项目重编并验证后，更新 GitHub 与 OHPM 版本。由于缺陷位于 OpenHarmony FFmpeg 的硬件编码适配层，又向上游提交 Issue #IDMF3P。

```text
社区反馈
→ 复现问题
→ 证明 fftools 已解析
→ 定位适配层漏传字段
→ 修改源码并重编
→ 更新插件
→ 回馈上游
```

## 三个典型判断

1. `-b:v` 位置正确：只排除了命令作用域问题，还不能证明底层收到配置。
2. `format_->bit_rate` 为目标值：问题已越过 fftools 解析层，应继续向平台配置追踪。
3. 总码率高于 `-b:v`：先区分视频轨、音频轨与容器总码率。

## 常见误区

1. 参数没生效就反复调整 ArkTS 字符串。
2. 看到 fftools 已解析参数，就认为平台编码器必然收到它。
3. 把总码率直接当成视频轨码率。
4. 用“VBR 有波动”解释所有偏差，却不检查参数传递链。
5. 只修改源码，不重新编译和替换 App 中的 `.so`。

## 本篇自测

1. 怎样排除 `-b:v` 的命令位置问题？
2. `format_->bit_rate = 300000` 能证明什么，不能证明什么？
3. 码率参数具体断在哪个函数、哪个平台对象之前？
4. 为什么设置 300k 后，文件总码率可能接近 440 kbps？
5. 修复底层源码后，为什么还要更新插件并反馈上游？

## 一句话总结

码率问题沿参数链从 ArkTS 追到 fftools，再落到 `SetCodecFormat()`，最终确认硬件编码适配漏写 `OH_MD_KEY_BITRATE`。
