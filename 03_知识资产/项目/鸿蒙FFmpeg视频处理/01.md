# 01 · 致命问题：命令跑完，整个 App 进程被关掉了

> 前置知识：知道 ffmpeg 是个命令行程序、了解 C 的 `exit()` 会结束进程、对 `main()` 返回有概念
> 难度：核心
> 预计阅读时间：10 分钟

## 先讲全局原理（贯穿三篇）

整套 `ffmpeg_tools` 的本质一句话：**借助 fftools（FFmpeg 的命令行工具层）连接底层的 libav* 库**。我们不直接写 libav* 的 C 函数，而是像「在 Windows 用 cmd 敲 `ffmpeg -i ... out.mp4`」那样，拼一条命令交给 fftools，由它去解析参数、驱动 libav* 完成编解码。

整门课就回答三个问题，对应三篇：

| 篇 | 问题 |
| --- | --- |
| 01（本篇） | fftools 作为命令行程序会 `exit` 杀进程，嵌进 App 怎么办？ |
| 02 | ①我们如何调用到 native 层的 fftools？②fftools 如何回调我们（进度/成功/失败）？ |
| 03 | 后续优化：硬件加速、码率为何失效 |

## 正文内容

这是 `ffmpeg_tools` 作为「库」必须先迈过去的第一道坎——正因为我们把 fftools 这个**命令行程序**嵌进了 App 进程，它的 `exit` 才会出事。先把现象说清楚，再讲为什么，最后讲怎么修。

### 一、现象：跑一次命令，App 直接没了

把 FFmpeg 当库嵌进鸿蒙 App，调用一条命令去转码/下载，**命令本身能跑完，但跑完那一刻整个 App 进程就被关闭了**——不是崩溃弹框，是「干净地退出」。换个命令、甚至命令参数写错时，App 也照样退出。

对一个工具库来说这是不可接受的：用户在你 App 里转了个视频，结果 App 自己关了。

### 二、根因：ffmpeg 是「程序」，它本来就打算结束进程

关键认知——**`ffmpeg` 原本是一个独立的命令行程序，不是一个库**。一个命令行程序跑完任务后做什么？当然是结束自己、把退出码还给操作系统。所以 fftools 的源码里，到处都是这种写法：

```c
// fftools 内部，遇到任何错误就调用它
exit_program(1);
```

而 `exit_program` 最终会调用 C 标准库的 `exit()`：

```c
void exit_program(int ret)
{
    if (program_exit)
        program_exit(ret);
    exit(ret);   // ❌ 关键：直接结束"当前进程"
}
```

`exit()` 的语义是**结束当前进程**。当 ffmpeg 是个独立程序时，「当前进程」就是 ffmpeg 自己，结束它天经地义。

但我们现在把 fftools 编进了 `.so`，跑在**宿主 App 的进程里**。此时「当前进程」=「整个 App 进程」。于是：

```text
独立程序时代：  exit() → 结束 ffmpeg 进程   → 没问题
嵌入库之后：    exit() → 结束宿主 App 进程  → App 被关掉
```

**一句话根因：fftools 假设自己独占进程、可以随意 exit；但作为库嵌入时，它的 exit 会把宿主一起带走。** 而且 ffmpeg 代码里这种 `exit_program(1)` 有几十处（参数错误、打不开文件、编码失败……任何一处出错都会触发），不可能逐个去改逻辑。

### 三、解法：用 setjmp / longjmp 把「退出进程」改成「退出本次命令」

我们要的效果是：ffmpeg 想「退出」时，**不要真的结束进程，而是回到我们调用它的地方**，把控制权和错误码还给我们。C 语言里实现「从很深的调用栈里一跳跳回某个预设点」的工具，正是 `setjmp` / `longjmp`。

可以把它类比成 C 版的「`throw` 异常 / `catch` 捕获」：

| 角色         | C 机制                | 类比              |
| ---------- | ------------------- | --------------- |
| 预先埋一个「落点」  | `setjmp(buf)`       | `try {`         |
| 从任意深处跳回落点  | `longjmp(buf, val)` | `throw val`     |
| 跳回后继续执行的代码 | `setjmp` 返回非 0 的分支  | `catch (val) {` |

#### 改法 1：把 exit 换成 longjmp（一处改动，覆盖几十处 exit_program）

```c
// 线程局部的跳转缓冲区
extern __thread jmp_buf ex_buf__;
extern __thread volatile int longjmp_value;

void exit_program(int ret)
{
    if (program_exit)
        program_exit(ret);

    // ❌ 原：exit(ret);
    // ✅ 现：保存返回码，跳回 setjmp 落点，而不是结束进程
    longjmp_value = ret;
    longjmp(ex_buf__, ret);
}
```

妙在：**所有 `exit_program(1)` 都走这一个函数**。只改这一处，几十处「退出」就全部从「杀进程」变成「跳回落点」，不用动 ffmpeg 的任何业务逻辑。

#### 改法 2：在命令入口埋好落点

在我们自己的执行入口 `exe_ffmpeg_cmd` 里用 `setjmp` 埋落点：

```c
int exe_ffmpeg_cmd(int argc, char **argv, Callbacks *callbacks)
{
    // 埋落点：第一次进来 setjmp 返回 0，走正常执行；
    // 被 longjmp 跳回来时返回非 0，走 else（相当于 catch）
    int savedCode = setjmp(ex_buf__);
    if (savedCode == 0) {
        // ===== 正常路径：真正去跑 ffmpeg =====
        ...
        // 正常跑完，ffmpeg 内部也会调 exit_program(0)，同样跳回这里
    } else {
        // ===== 被 longjmp 跳回来（出错或正常退出都会到这）=====
        main_return_code = received_nb_signals ? 255 : longjmp_value;
        int saved_error = main_return_code;   // 先把错误码存下来
        reset_ffmpeg_state();                 // 再清理全局状态
        return saved_error;                   // 把错误码交还给调用方
    }
    return main_return_code;
}
```

这样链路就变成：

```text
ffmpeg 内部出错/结束 → exit_program(ret) → longjmp 跳回 exe_ffmpeg_cmd 的 setjmp
   → 进程没死，函数正常 return ret → 控制权回到我们手里 → App 继续活着
```

**「优雅退出」到底优雅在哪**：不是真的退出进程，而是把一个**返回码 return 给调用者**；调用者（上层 C++）拿到这个码后，`ret==0` 就回调 `onSuccess`、非 0 就把它翻成消息回调 `onFailed`。也就是把「ffmpeg 想结束进程」翻译成「一次普通函数返回 + 一个结果码」，进程毫发无伤——这枚返回码怎么变成 `onSuccess/onFailed`，正是第二篇「fftools 如何回调我们」要接着讲的。

### 四、两个不能漏的细节

#### 细节 1：跳回来后必须 reset_ffmpeg_state

ffmpeg 是个老式命令行程序，内部用了**大量全局变量**（输入输出流表、编码器上下文、计数器……）。独立程序时代它跑完就 exit，进程销毁，全局变量自然清零，从不复用。

但现在我们让它「跳回来、不结束进程」，意味着**同一个进程里会反复执行多次命令**。上一条命令留下的全局状态如果不清，下一条就会读到脏数据 → 行为诡异甚至崩溃。所以跳回落点后要 `reset_ffmpeg_state()` 把这些全局量手动归零，保证「下一次执行时状态是干净的」。

> 注意顺序：**先 `saved_error = main_return_code` 存错误码，再 `reset` 清状态**。因为 reset 会把 `main_return_code`、`longjmp_value` 也清零，顺序反了错误码就被自己擦掉了，上层永远拿到 0（看起来成功，实则失败）。这个错误码后面「双向通信」一篇会接着用。

#### 细节 2：ex_buf__ 必须是线程局部（__thread）

```c
__thread jmp_buf ex_buf__;          // 每个线程一份跳转缓冲区
__thread volatile int longjmp_value;
```

FFmpeg 任务通常放在**子线程**执行（不能卡 UI），而且可能有多个任务并发。如果 `ex_buf__` 是全局共享的一份，A 线程的 `longjmp` 就可能跳到 B 线程的落点上 → 跳到一个已经返回、栈帧失效的地方 → 未定义行为。

加 `__thread` 让每个线程各持一份 `setjmp` 落点和错误码，互不干扰。这也是后面双向通信里「多个并发任务各自回调隔离」的基础。

### 小结

1. 现象：命令跑完 App 进程被关。
2. 根因：ffmpeg 本是独立程序，内部用 `exit()` 结束；嵌入库后 `exit()` 杀的是宿主进程。
3. 解法：`exit_program` 里把 `exit()` 换成 `longjmp`，在 `exe_ffmpeg_cmd` 入口 `setjmp` 埋落点 —— 一处改动覆盖几十处退出，把「结束进程」变成「返回调用方」。
4. 两个细节：跳回后 `reset_ffmpeg_state`（且先存错误码再清状态）、`ex_buf__` 用 `__thread` 保证多线程/并发安全。
