# 鸿蒙 FFmpeg 视频处理｜修改诊断

## 原笔记的问题

原笔记的技术材料比较完整，但项目背景、基础知识、Native 改造、性能问题和社区问题交叉出现。

读者能理解单个知识点，却不容易复述“版本为什么下架、两项能力怎样落地、问题如何逐层收敛”。

硬件编码接入与码率失效原本放在同一篇。前者是构建产物缺少 codec，后者是适配层漏传参数；两者现象相近，但证据链和根因不同。

Android MediaCodec、OpenGL、SurfaceTexture、OES 与 FBO 是理解逐帧处理的基础，但如果不标明边界，容易被误读为本项目实际实现。

原稿还包含一些与本次实际方案无关的底层扩展讨论，冲淡了单任务队列下真正需要掌握的调用链。

## 本次怎样重写

重写版以一次线上整改为主线：

```text
版本下架
→ 分析录像下载与视频水印
→ 选择并移植 FFmpeg
→ 改造 fftools 退出边界
→ 打通 ArkTS / Native 双向调用
→ 接入硬件编码
→ 修复码率参数链
→ 验证、重新上架并开源
```

01 先拆开两项业务：录像下载主要是 RTSP 解复用与重新封装，视频水印必须解码、合成、编码和封装。

再用容器、压缩码流、原始帧解释为什么处理成本不同，最后说明 FFmpeg 的方案优势。

Android 的 Surface/OpenGL 链只作为通用原理参照，并明确项目实际使用 FFmpeg `overlay` 与 OpenHarmony 硬件编码适配。

02 只解释 fftools 的进程退出语义怎样改成命令返回，并保留项目真实的单任务队列约束。

03 只保留一次 ArkTS 到 Native 的去程，以及进度、成功和失败的回程；任务回调直接对应当前队列任务。

04 与 05 分开两次问题分析：

```text
150 秒性能问题
→ codec 不存在
→ 构建产物缺少平台适配

码率失效问题
→ fftools 已解析
→ SetCodecFormat 漏写 bitrate
```

06 将功能、回调、串行任务、性能、码率、重新上架、GitHub/OHPM 发布和上游 Issue 收到一个结果闭环中。

## 删除或降级了什么

- 删除与单任务队列无关的扩展设计；
- 删除与实际问题无关的泛化工程风险；
- 不再把不同版本和环境下的 `27s`、`15.68s` 混为同一组结果；
- 不把 Android OpenGL 参考链路写成鸿蒙项目实现；
- 不把平台沟通和语音对讲写成个人项目成果。

## 新版阅读结果

六篇分别回答六个实际问题。读者可以按事件顺序理解项目，也可以在遇到相同现象时直接进入对应篇章。

每篇都保留具体场景、证据链、典型判断、常见误区和自测，不再额外堆叠抽象模板。
