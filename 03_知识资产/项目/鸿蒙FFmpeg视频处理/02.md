# 02 · 我们如何调用到 native 的 fftools，fftools 又如何回调我们

> 前置知识：01 篇的 `exe_ffmpeg_cmd` / 返回码；知道 ArkTS 运行在方舟 JS 虚拟机、类似 JNI 要跨语言边界
> 难度：核心
> 预计阅读时间：16 分钟

## 开篇

01 篇把进程保住了——`exe_ffmpeg_cmd` 现在能正常 return 一个返回码。这一篇把「通信」彻底打通，回答两个问题：

1. **去程**：我们（ArkTS）如何调用到 native 层的 fftools，让它执行命令？
2. **回程**：fftools 如何回调我们，把进度、成功、失败实时报上来？

整件事横跨三层，记住这张图，后面反复用：

```text
ArkTS 层    —— 你写 onProgress/onSuccess/onFailed 和发起调用的地方（JS 虚拟机，单线程）
  ↕  方舟编译器的 NAPI（类似 JNI 的跨语言桥）/ AKI（NAPI 的 C++ 语法糖）
C++ 层      —— napi_ffmpeg.cpp，桥接函数所在
  ↕  C 函数指针（C/C++ 通用 ABI）
C 层        —— fftools（ffmpeg.c），真正干活的地方
```

---

## 问题一 · 我们如何调用到 native 的 fftools（去程）

类比 JNI：ArkTS 代码不能直接 call 一个 C 函数，必须通过一座官方的桥。鸿蒙这座桥是 **NAPI**（方舟编译器提供的稳定 ABI），**AKI（`@ohos/aki`）是它的 C++ 语法糖**。调用分两步落地。

### 第 1 步：C++ 侧用 AKI 宏把函数「注册」出去

```cpp
JSBIND_ADDON(ffmpegutils)            // 声明这是个 addon 模块（对应 .so 名）
JSBIND_GLOBAL() {
    JSBIND_PFUNCTION(executeFFmpegCommandAPP);  // P = Promise，异步函数
    JSBIND_FUNCTION(showLog);                   // 普通同步函数
}
```

注册之后，`executeFFmpegCommandAPP` 这个 C++ 函数就对 ArkTS「可见」了。

### 第 2 步：ArkTS 侧按 .so 名 import，直接调用

```typescript
import libAddon from 'libffmpegutils.so'

libAddon.executeFFmpegCommandAPP(uuid, cmds.length, cmds)
  .then((code) => { /* 命令执行完，拿到返回码 */ })
```

### 关键：`JSBIND_PFUNCTION` 的 P = Promise，意味着开 worker 线程

这是去程最该讲清的点。`PFUNCTION` 不是普通同步函数，它让 AKI：

1. **另开一个 worker 线程**去执行这个 C++ 函数（方法和参数都在 worker 线程跑）；
2. 参数（`uuid`、`cmds` 等）由**方舟编译器框架从 JS 值转换成 native 层的 C++ 值**再递进去；
3. **立刻给主线程返回一个 Promise**，不等命令跑完——所以主线程不被阻塞，UI 不卡。

意义很大：`exe_ffmpeg_cmd` 可能跑几十秒，如果在 JS 主线程同步执行，整个 App 会卡死。放 worker 线程后，ArkTS 侧用 `.then()` 等结果，UI 照常流畅。**代价是后面回调要面对「子线程」这个事实**（问题二会处理）。

### worker 线程里发生了什么

`executeFFmpegCommandAPP` 在 worker 线程里做三件事：

```cpp
int executeFFmpegCommandAPP(std::string uuid, int cmdLen, std::vector<std::string> argv) {
    char** argv1 = vector_to_argv(argv);   // ① string[] → char** argv（注意补 NULL 终止符，见 01 篇约定）
    ...                                     // ② 取回本次任务的回调（问题二讲）
    int ret = exe_ffmpeg_cmd(cmdLen, argv1, &callbacks);  // ③ 真正执行命令
    ...
}
```

到这里「去程」就通了：**ArkTS `executeFFmpegCommandAPP` → AKI 派到 worker 线程 → 转 argv → `exe_ffmpeg_cmd` 跑命令**。

## 问题二 · fftools 如何回调我们（回程）

回程比去程难得多。难点是：`exe_ffmpeg_cmd` 跑在 **worker 线程的 C 代码**深处，它怎么反过来调到一个 **ArkTS 里的 JS 函数**（`onProgress`）？这要跨两道边界：语言边界（C↔JS）和线程边界（worker↔主线程）。

### 第 1 步：ArkTS 把回调按名字「寄存」，并强引用防 GC

JS 函数是虚拟机里的托管对象，C++ 不能直接拿它地址。所以先寄存：

```typescript
let uuid = generateUUID32();   // 每个任务一个唯一 id
libAddon.JSBind.bindFunction(uuid + "_onFFmpegProgress", options.onFFmpegProgress);
libAddon.JSBind.bindFunction(uuid + "_onFFmpegFail",     options.onFFmpegFail);
libAddon.JSBind.bindFunction(uuid + "_onFFmpegSuccess",  options.onFFmpegSuccess);
```

`bindFunction` 做的事：为这个 JS 函数建一个**持久引用（`napi_ref`）**、以「uuid+后缀」为名字存进 `.so` 的全局表。持久引用的意义是**强引用住它、不让 GC 回收**（否则函数一出栈就没了）。名字带 `uuid` 是为了区分不同任务（后面讲隔离）。

C++ 侧按同名取回，放进本次任务的回调结构、并记到一个**线程局部**指针：

```cpp
CallBackInfo cb;
cb.onFFmpegProgress = aki::JSBind::GetJSFunction(uuid + "_onFFmpegProgress");
// ...Fail / Success 同理
g_currentCallback = &cb;   // thread_local：记下"当前任务的 JS 回调们"
```

### 第 2 步（最关键）：把 C++ 桥接函数「伪装」成 C 函数指针塞给 fftools

`g_currentCallback` 里是 `aki::JSFunction*`——但 fftools 是**纯 C**，连这个 C++ 类型都不认识。fftools 只接受 C 函数指针。所以库定义了一组 C 回调类型：

```c
typedef struct Callbacks {
    void (*onFFmpegProgress)(int progress);     // 就是个 C 函数指针
    void (*onFFmpegFail)(int code, const char* msg);
    void (*onFFmpegSuccess)(void);
} Callbacks;
```

C++ 侧填进去的，是**我们自己写的 C++ 桥接函数的地址**：

```cpp
Callbacks callbacks = {
    .onFFmpegProgress = onFFmpegProgress,   // C++ 函数，但签名 void(int) 符合 C 函数指针
    .onFFmpegFail     = onFFmpegFail,
    .onFFmpegSuccess  = onFFmpegSuccess
};
exe_ffmpeg_cmd(cmdLen, argv1, &callbacks);
```

**为什么 C++ 函数能塞进 C 的函数指针？** 因为只要是「非成员的普通函数、签名匹配」，**函数指针就是 C 和 C++ 通用的 ABI**。桥接函数表面是个 `void(int)` 的 C 回调，内部却能写 C++、调 AKI。fftools 拿到后存进自己的全局变量：

```c
static Callbacks *g_callbacks = NULL;
int exe_ffmpeg_cmd(int argc, char **argv, Callbacks *callbacks) {
    g_callbacks = callbacks;   // ffmpeg 记下这组 C 函数指针
    ...
}
```

> ⚠️ 这里有**两个不同的全局变量，别混**：
> - `g_callbacks`（C 层 / ffmpeg.c）：存的是**C 函数指针**（指向桥接函数）。
> - `g_currentCallback`（C++ 层 / `thread_local`）：存的是本次任务真正的 **JS 函数引用**。

### 第 3 步：fftools 用 pts 算出进度，发起一次纯 C 调用

fftools 在转码主循环的进度上报处，用「已处理时间戳 pts / 总时长 duration」算百分比，然后调回调：

```c
// ffmpeg.c（真实代码，已简化）
if (g_callbacks && g_callbacks->onFFmpegProgress) {
    int progress = (int)((pts * 100) / total_duration);
    if (is_last_report) progress = 100;
    g_callbacks->onFFmpegProgress(progress);   // ★ 一次纯 C 函数指针调用
}
```

站在 fftools 的视角，这就是**一次再普通不过的 C 函数调用**——它不知道、也不关心这个指针后面是 C++、是 AKI、是 JS。它边转码边上报，这就是「实时」的来源。

### 第 4 步：C 带不了上下文 → 桥接函数靠 g_currentCallback 找回 JS 函数

这是你抓得最准、也最难的一点。看桥接函数签名：

```cpp
void onFFmpegProgress(int progress) {   // 只有一个 int，没有"这是哪个任务"的信息
    if (g_currentCallback && g_currentCallback->onFFmpegProgress) {
        g_currentCallback->onFFmpegProgress->Invoke<void>(progress);  // 调到 JS
    }
}
```

fftools 调它时只塞了 `progress`，**没塞「该调哪个任务的哪个 JS 函数」**——因为 C 函数指针签名 `void(int)` 里**没有 `void* userdata` 这种上下文槽位**，纯 C 指针不像 C++ lambda 能「捕获」上下文。

所以桥接函数自己去 `g_currentCallback`（thread_local，第 1 步设好的）里**捞回本任务的 JS 函数**。这就是 `g_currentCallback` 这个「暗接头」存在的根本原因：补上 C 函数指针带不了的那段上下文。

### 第 5 步：Invoke 跨线程投递回主线程消息循环

最后 `Invoke<void>(progress)` 发生在 **worker 线程**，但 JS 虚拟机是**单线程**的，worker 线程不能直接执行 JS。NAPI 的标准机制是：worker 线程不「执行」JS，只把「调用 onProgress(60)」**打包成消息、投递到主线程的事件循环**，由主线程在合适时机执行：

```text
[worker 线程] Invoke<void>(60) → AKI/NAPI 打包、投递
———— 线程边界 ————
[主线程] 消息循环取出 → 执行你写的 onProgress(60) → 更新 UI（安全）
```

**所以回调里更新 UI 是安全的**——真正碰 UI 那一下已被切回主线程，框架替你做掉了，不用自己切线程。

### 成功与失败：承接 01 篇那枚返回码

进度走 `onFFmpegProgress`；命令结束时，回到 01 篇 `exe_ffmpeg_cmd` 那枚**返回码**：

```cpp
int ret = exe_ffmpeg_cmd(cmdLen, argv1, &callbacks);
if (ret != 0) {
    char err[1024] = {0};
    av_strerror(ret, err, sizeof(err));   // 错误码 → 人能看懂的消息
    cb.onFFmpegFail->Invoke<void>(ret, err);   // 回调 onFailed
} else {
    cb.onFFmpegSuccess->Invoke<void>();        // 回调 onSuccess
}
```

这正是 01 篇「优雅退出」的下半场：**ffmpeg 的「退出」被翻成一枚返回码，调用者据此回调 `onSuccess` / `onFailed`**。能拿到正确错误码的前提，是 01 篇「先存错误码再 reset」那个顺序没搞反。

### uuid 为什么不可省，以及一个诚实纠偏

如果不用 uuid、只有一个全局回调名，同时跑任务 A、B 时 B 的回调会覆盖 A，进度就串台。加 uuid 后每个任务回调名天然不同，再配合 `g_currentCallback` 是 `thread_local`——每个任务在自己线程取到的永远是自己那份回调。

| 机制 | 作用 |
| --- | --- |
| `uuid` + 命名约定 | 区分不同任务的回调登记，防串台 |
| `g_currentCallback` 是 `thread_local` | 每线程取到自己的回调 |
| `ex_buf__` / `longjmp_value` 是 `__thread`（01 篇） | 每线程自己的跳转落点和错误码 |

⚠️**诚实纠偏**：回调能隔离，**不代表 fftools 能真并发**。源码注释明写「FFmpeg 内部大量全局变量，不支持多线程并发执行，调度层应确保串行」。`g_callbacks`、解复用表等都是全局的，两条命令同进程并行会互踩。所以正确姿势是：**通信层做到「谁的回调回给谁」，执行层由上层调度器（`FFmpegManager`）排队、一条跑完 `reset`（01 篇）再跑下一条**。

## 小结

**去程（如何调用到 fftools）**：
1. C++ 用 AKI 宏 `JSBIND_PFUNCTION` 注册函数；ArkTS import .so 直接调。
2. P=Promise → AKI 开 worker 线程执行、参数经方舟编译器转 native、立即返回 Promise 给主线程，不卡 UI。
3. worker 线程里转 argv → `exe_ffmpeg_cmd`。

**回程（fftools 如何回调我们）**：
4. ArkTS `bindFunction` 把 JS 函数以 `napi_ref` 强引用按名字寄存；C++ 取回存 `g_currentCallback`。
5. 把 C++ 桥接函数当 C 函数指针装进 `Callbacks` 交给 fftools，存于 `g_callbacks`（两个全局别混）。
6. fftools 用 `pts/duration` 算进度，发起**纯 C 调用** `g_callbacks->onFFmpegProgress`。
7. C 带不了上下文，桥接函数靠 `thread_local g_currentCallback` 捞回 JS 函数。
8. `Invoke` 经 NAPI 跨线程投递回主线程消息循环执行 → UI 安全。
9. 结束时按返回码回调 `onSuccess`/`onFailed`（承接 01 篇返回码）。
10. uuid + 线程局部做回调隔离；但 fftools 因全局变量须上层串行调度。
