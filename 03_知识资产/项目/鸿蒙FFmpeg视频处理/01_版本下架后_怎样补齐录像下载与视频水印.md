# 01｜版本下架后，怎样补齐录像下载与视频水印？

## 本篇只解决一个问题

鸿蒙版本因为媒体能力缺失被下架。录像下载与视频水印分别需要怎样的音视频处理链，最终为什么选择 FFmpeg？

## 版本下架，需要补齐什么能力？

鸿蒙巡店模块最初沿用 H5。受 Web 能力边界限制，录像下载、视频加水印等功能没有按期补齐，版本最终被下架。

任务由普通迭代升级为恢复上架的紧急整改。本项目范围明确为：

- 从设备 RTSP 主码流生成本地 MP4；
- 给已有视频叠加图片水印并导出；
- 建立可由 ArkTS 调用的 Native 媒体能力；
- 不把语音对讲纳入本项目。

个人负责技术调研、方案设计、功能开发、FFmpeg 源码修改、性能优化、测试验证和插件发布；平台沟通不写成个人职责。

## 录像下载为什么不是普通文件下载？

普通 HTTP 下载通常对应服务端已经存在的完整文件，客户端只需按字节保存。设备提供的 RTSP 地址则代表一个持续产生音视频数据的媒体会话。

项目需要从 RTSP 流中取得 H264 视频和 AAC 音频压缩数据，再按照 MP4 的轨道、时间戳和索引规则写成本地文件。

```text
RTSP
→ 读取媒体流
→ 取得 H264 / AAC 压缩数据
→ 整理轨道与时间戳
→ stream copy
→ MP4 重新封装
```

录像下载没有改变画面和声音。输入编码与 MP4 兼容时，可以直接搬运压缩 sample，不需要把 H264 解码为原始画面，也不需要再次编码。

## MP4、H264、YUV 和 RGB 是什么关系？

这四个概念不在同一层。

### MP4 是容器

MP4 负责把视频轨、音频轨、编码信息、时间戳、索引和实际媒体数据组织成一个文件。它不是编码格式，也不是一张可以直接绘制的画面。

最小结构可以理解为：

```text
MP4
├── ftyp：文件类型与兼容信息
├── moov：轨道、编码格式、时间戳和 sample 索引（stbl）
└── mdat：H264、AAC 等压缩数据
```

`moov` 像目录，告诉播放器有哪些轨道、使用什么编码，以及某个 sample 在 `mdat` 的什么位置、应该在什么时间播放。

`mdat` 保存真正的压缩数据。它不是一组 RGB 图片，也不是已经解码的 YUV 帧。

### H264 是压缩视频码流

原始视频由连续画面组成，数据量很大。H264 会利用单帧内部的相似区域，以及连续画面之间的大量重复信息进行压缩。

- I 帧能够独立恢复画面，适合作为解码起点；
- P 帧主要参考之前的画面；
- B 帧可以参考其他画面，进一步减少重复数据；
- GOP 是一组连续编码画面，通常围绕关键 I 帧组织。

因此 H264 sample 中保存的是压缩语法、参考关系和画面差异，不是可以直接修改的像素矩阵。给视频加水印前，必须先解码。

### 解码后为什么常见 YUV420？

YUV 将画面拆成亮度和色度：

```text
Y：亮度信息
U / V：颜色信息
```

人眼对亮度细节更敏感，对颜色细节相对不敏感。YUV420 让四个亮度采样共享一组色度信息，可以在视觉变化较小的情况下减少原始画面数据量，因此被视频编码链路广泛使用。

屏幕最终通过红、绿、蓝三种分量显示颜色。GPU 采样视频帧时，可以把 YUV 或平台图形缓冲转换成 shader 可计算的 RGB 颜色，再进行水印和滤镜处理。

完整层级是：

```text
MP4 容器
→ 解封装
→ H264 压缩 sample
→ 解码
→ YUV420 原始画面或平台图形缓冲
→ GPU 采样为可计算的 RGB 颜色
→ 显示或继续处理
```

## 视频加水印为什么必须重新编码？

水印需要处理视频中的每一帧，所以必须把 H264 解码，还原出原始画面。GPU 采样画面并得到可计算的 RGB 颜色，再通过混合绘制出带水印的新画面。

新画面的像素已经与原视频不同，旧 H264 sample 不能继续复用，只能重新编码并写入新容器。

```text
MP4 / RTSP
→ 解封装
→ H264 压缩 sample
→ 解码为 YUV 原始画面
→ GPU 采样并混合水印
→ 带水印的新画面
→ 重新编码为 H264
→ 封装为新 MP4
```

Muxer 只负责组织已经编码好的 H264、AAC sample。它不能直接接收 YUV、RGB 或 GPU 中尚未编码的图像。

这也是录像下载与视频水印的根本差异：

```text
录像下载：像素不变，压缩 sample 可以复用
视频水印：像素改变，必须解码、处理和重新编码
```

## MediaCodec 与 OpenGL 怎样完成这条链路？

以 Android API 作为通用原理参照，一条完整的视频水印导出链路可以拆成：

```text
MediaExtractor
→ 从 MP4 读取 H264 / AAC sample

MediaCodec Decoder
→ 将 H264 解码为原始画面

OpenGL
→ 采样视频与水印，生成新画面

MediaCodec Encoder
→ 将新画面编码为 H264

MediaMuxer
→ 将新 H264 与 AAC 封装为 MP4
```

视频处理链里有两个方向相反的 Surface：

```text
Decoder output Surface
→ 解码器向 Surface 写画面
→ SurfaceTexture / OpenGL 消费画面

Encoder input Surface
→ OpenGL 向 Surface 写新画面
→ 编码器消费并编码画面
```

连起来就是：

```text
MediaCodec Decoder
→ Decoder output Surface
→ SurfaceTexture / OES 视频纹理
→ OpenGL 水印合成
→ Encoder input Surface
→ MediaCodec Encoder
```

这个模型解释了为什么解码器不能直接连接 Muxer：中间的 OpenGL 已经改变画面，必须由编码器生成新的压缩 sample。

## GPU 怎样绘制水印？

OpenGL 把视频画面作为纹理，通常用两个三角形组成一个矩形，再让 GPU 执行渲染管线：

```text
顶点数据
→ 顶点处理
→ 图元装配
→ 光栅化
→ 片元处理
→ 测试 / Alpha 混合
→ 写入 framebuffer
```

- 顶点处理决定矩形的位置、大小、旋转和纹理坐标；
- 图元装配把顶点组成两个三角形；
- 光栅化生成三角形覆盖区域内的片元；
- 片元处理分别采样视频纹理和水印纹理；
- Alpha 混合按照透明度组合两种颜色；
- 最终颜色写入编码器输入 Surface 对应的 framebuffer。

Alpha 混合的最小模型是：

```text
输出颜色
= 水印颜色 × 水印透明度
+ 视频颜色 × (1 - 水印透明度)
```

这段 Android MediaCodec/OpenGL 链路用于解释通用音视频原理，不是本项目的实际实现代码。

## 为什么最终选择 FFmpeg？

团队调研过 RTSP、OpenGL、系统编解码和封装组件的组合方案。它在技术上可行，但需要自行维护取流、解复用、时间戳、解码、渲染、编码、封装和错误状态。

面对恢复上架的周期，项目选择 FFmpeg 统一承载这些能力：

| 模块 | 项目中的职责 |
|---|---|
| `libavformat` | RTSP、解复用、时间戳和 MP4 封装 |
| `libavcodec` | 视频解码与编码 |
| `libavfilter` | 使用 `overlay` 合成图片水印 |
| fftools | 解析命令并编排完整处理流程 |

两条实际业务链最终落为：

```text
录像下载：
RTSP
→ libavformat 读取和解复用
→ H264 / AAC stream copy
→ MP4 封装

视频水印：
输入视频
→ 解封装
→ 解码
→ libavfilter overlay
→ h264_ohosavcodec 硬件编码
→ MP4 封装
```

方案移植到鸿蒙 Native 的过程是：

```text
OpenHarmony 适配源码
→ HPKBUILD 声明所需协议、滤镜和 codec
→ Lycium 组织配置与构建
→ OpenHarmony SDK/NDK 工具链执行交叉编译
→ 聚合 libav*、fftools 与平台适配
→ 生成单一 .so
```

Lycium 是三方库适配与构建框架，不是编译器。真正执行编译和链接的是 OpenHarmony SDK/NDK 中的 Clang、LLVM 与链接器。

桌面命令入口也需要改造成 App 可调用的函数入口：

```text
桌面：ffmpeg main(argc, argv)
鸿蒙：exe_ffmpeg_cmd(argc, argv)
```

## 三个典型判断

1. RTSP 录像保存：画面不变且编码兼容时，使用 stream copy 重新封装。
2. 视频加水印：画面像素改变，必须解码、合成、重新编码。
3. Android OpenGL 链路：用于说明通用原理；项目实际使用 FFmpeg `overlay` 和 OpenHarmony 硬件编码。

## 常见误区

1. 把 MP4、H264、YUV 和 RGB 当成同一层数据。
2. 把 RTSP 地址理解为一个可以直接复制的 MP4 文件。
3. 认为 stream copy 什么都不处理，不需要整理时间戳和封装格式。
4. 认为可以直接在 H264 字节上绘制图片。
5. 认为 Muxer 可以接收 GPU 图像并自动完成编码。
6. 把 MediaCodec/OpenGL 原理链写成项目实际实现。

## 一句话总结

录像下载是在不改变像素的前提下取出 H264/AAC 并重新封装；视频水印则必须还原画面、完成 GPU 合成并重新编码，FFmpeg 用一套 Native 能力覆盖了两条处理链。
