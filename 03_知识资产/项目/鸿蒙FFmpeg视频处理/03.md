# 03 · 后续优化：鸿蒙下启用硬件加速，与「码率设置为何失效」

> 前置知识：01 篇返回码、ffmpeg 命令分「输入选项/输出选项」的位置概念；知道软编码（libx264）很吃 CPU
> 难度：进阶
> 预计阅读时间：12 分钟

## 正文内容

前两篇解决的是「能不能稳定跑起来」（01 进程不退、02 双向通信）。这一篇是「跑得好不好」：先让处理变快（硬件加速），再让输出可控（码率）。这两件事在鸿蒙上其实拴在同一根绳上——下面会看到，正是「换了硬件编码器」才暴露出「码率设置失效」。

### 一、为什么需要硬件加速

以「2 分钟视频加水印」为例。加水印这件事天生**没法零拷贝**：水印要叠在画面像素上，必须把视频**解码**成原始 YUV 帧、叠完再**重新编码**。瓶颈就在解码 + 编码这两头，尤其纯软件编码（`libx264`）极吃 CPU，在手机上又慢又烫又费电。

硬件加速的思路：把解码/编码交给**芯片里专门的编解码单元（GPU/NPU 硬件 codec）**，而不是 CPU 软算。本库实测：2 分钟视频硬件加水印约 **15.68s**。

### 二、鸿蒙下怎么启用：一个 codec 名 `h264_ohosavcodec`

鸿蒙系统提供的硬件 H.264 编解码器，在 FFmpeg 里以一个 codec 名字暴露：

```text
h264_ohosavcodec
```

它**既能当硬件解码器、又能当硬件编码器**。在命令里怎么用，取决于 ffmpeg 命令的「位置语义」（选项作用于它后面紧跟的对象：输入选项在 `-i` 前、输出选项在输出文件前）——放在输入侧还是输出侧：

```text
ffmpeg -c:v h264_ohosavcodec -i in.mp4   ...   -c:v h264_ohosavcodec   -y out.mp4
       └──── 在 -i 之前：硬件解码器 ────┘        └─ 在输出前：硬件编码器 ─┘
```

这正是库里 `FFmpegCommandBuilder` 的实现（`build()`）：

```typescript
// 硬解码：codec 放在 -i 之前（输入选项）
if (this.useHwDecode) cmd.push('-c:v', 'h264_ohosavcodec');
...
for (const f of inputFiles) cmd.push('-i', f);
...
// 硬编码：codec 放在滤镜之后、输出之前（输出选项）
if (this.useHwEncode) cmd.push('-c:v', 'h264_ohosavcodec');
```

所以 `hwaccel()` = 解码端 + 编码端都用它；`hwDecode()` / `hwEncode()` 可单独开。**同一个 codec 名，靠位置区分解码还是编码**——这是鸿蒙这套硬件能力在 fftools 里的用法关键。

### 三、容易忽略的两个前提

光在命令里写 `h264_ohosavcodec` 还不够，能跑起来有两个隐形前提：

#### 前提 1：`.so` 本身要支持这个硬件 codec

社区通用的 FFmpeg `.so` 默认**不带** `h264_ohosavcodec`（它是鸿蒙平台特有的）。本库专门**更换过 FFmpeg.so**，用的是华为工单提供的、编进了鸿蒙硬件编解码支持的版本。换句话说：硬件加速的能力一半在命令、一半在底层 `.so`——`.so` 里没编进这个 codec，命令写了也会报「找不到编码器」。

#### 前提 2：硬件解码并非任何场景都需要

要分清三类操作，别滥用硬件：

| 操作 | 要不要解码/编码 | 该不该上硬件 |
| --- | --- | --- |
| 转封装 / 下载 / 裁剪（零拷贝） | `-c:v copy`，**根本不解码** | 不需要硬件，最快最省电 |
| 加水印 / 缩放 / 转码 | 必须解码 + 重编码 | 上硬件，收益最大 |

**零拷贝场景上硬件反而是负优化**——明明不用动像素，却去走解码+编码，白白慢且耗电。这呼应了整套库「按要不要重编码分层」的设计。

> 顺带说清水印那条命令的真相：库里 `watermark` 只在**编码端**用了 `h264_ohosavcodec`（`-c:v` 放在 overlay 之后），解码端走常规路径。因为 overlay 滤镜要在 CPU 可访问的内存里改像素，硬件解码出来的帧不一定直接能喂给滤镜。**硬件加速不是全有或全无——解码、编码可以各自独立选硬件或软件**，加水印拿到的主要收益来自「硬件编码」这一头（编码通常是更重的那头）。

### 四、码率设置为何失效（真实根因在 native 源码）

这是你最早就关心的问题，也是本课题里最值得讲的一个排查。

#### 4.1 现象

用 `h264_ohosavcodec` 硬件转码时，**即使命令里显式写了 `-b:v 300k` / `-b:v 500k`，输出视频始终是较高码率**，码率参数完全没生效。

#### 4.2 关键排查结论：不是命令写错了

很自然会先怀疑命令层——是不是没拼 `-b:v`？是不是位置放错了（`-b:v` 是输出选项，得在输出文件前）？这些都要排除，但排查后确认：**命令是对的，`-b:v 300k` 位置也对，ffmpeg 也确实把它解析进了 `format_->bit_rate`**。问题不在调用方式。

真正的根因在更深一层——**OHOS 版 FFmpeg 的硬件编码器封装源码漏写了码率**。

#### 4.3 根因：`ohosvideoencoder.cpp` 没把 bit_rate 写进硬件编码器配置

`h264_ohosavcodec` 这个硬件编码器，在 FFmpeg 源码里由 `libavcodec/ohosvideoencoder.cpp` 实现，它要把编码参数装进鸿蒙的 `OH_AVFormat`、再交给 `OH_VideoEncoder_Configure` 去配置硬件编码器。看它的 `VideoEncoder::SetCodecFormat()`：

```cpp
int VideoEncoder::SetCodecFormat() {
    ...
    OH_AVFormat *avformat = OH_AVFormat_Create();
    OH_AVFormat_SetIntValue(avformat, OH_MD_KEY_WIDTH,        format_->width);
    OH_AVFormat_SetIntValue(avformat, OH_MD_KEY_HEIGHT,       format_->height);
    OH_AVFormat_SetIntValue(avformat, OH_MD_KEY_PIXEL_FORMAT, format_->pixelFormat);
    OH_AVFormat_SetStringValue(avformat, OH_MD_KEY_CODEC_MIME, format_->codecMime.c_str());
    OH_AVFormat_SetDoubleValue(avformat, OH_MD_KEY_FRAME_RATE, format_->frameRate);
    // ❌ 宽、高、像素格式、MIME、帧率都写了，唯独 bit_rate 没写进去！
    int32_t ret = OH_VideoEncoder_Configure(encoder_, avformat);
    ...
}
```

宽、高、像素格式、MIME、帧率都老老实实写进了 `avformat`，**唯独 `format_->bit_rate` 没有被写入**。于是链路断在了最后一米：

```text
-b:v 300k → ffmpeg 解析 → format_->bit_rate = 300000 ✅
          → SetCodecFormat() 构造 OH_AVFormat 时，根本没把 bit_rate 放进去 ❌
          → OH_VideoEncoder_Configure 配置硬件编码器：没收到目标码率
          → 硬件编码器用自己的默认（高）码率 → "设置不生效"
```

**你设的码率不是被忽略，而是在 OHOS 封装层被「漏传」了——它压根没走到硬件编码器面前。**

#### 4.4 解法：补上这行，重编 `.so`，替换产物

在 `SetCodecFormat()` 里、`OH_VideoEncoder_Configure` 之前补上码率写入：

```cpp
// 添加码率设置
if (format_->bit_rate > 0) {
    OH_AVFormat_SetLongValue(avformat, OH_MD_KEY_BITRATE, format_->bit_rate);
}
```

然后三步落地：

1. **改源码**：上面这段补进 `libavcodec/ohosvideoencoder.cpp`。
2. **重编 FFmpeg**：基于改后的源码，重新交叉编译 OHOS 平台的 FFmpeg。
3. **替换产物**：把新编出来的 `.so` 替换进运行环境。

> 这正好印证了本篇前半段那句「硬件加速一半在命令、一半在 `.so`」——这次连「码率能不能生效」都取决于 `.so` 里封装层的实现，命令层无论怎么写都救不回来。

#### 4.5 修复后的效果（实测数据）

原始视频：6 分 48 秒，49.2 MB，约 **1012 kbps**。同一条命令分别设 300k / 500k：

| 目标码率 | 实际输出码率 | 文件大小 | 相比原视频 |
| --- | --- | --- | --- |
| 500k | 约 648 kbps | 31.5 MB | 体积 −36% |
| 300k | 约 440 kbps | 21.4 MB | 体积 −56% |

（6 分 48 秒视频单次转码约 67.77s。）

验证命令：

```text
ffmpeg -i input.mp4 -c:v h264_ohosavcodec -b:v 300k -c:a aac -y low_bitrate_300k.mp4
ffmpeg -i input.mp4 -c:v h264_ohosavcodec -b:v 500k -c:a aac -y low_bitrate_500k.mp4
```

注意：**实际码率（440k / 648k）略高于设定值（300k / 500k）是正常的**——这是「粗略码率控制（VBR）」而非「精确恒定码率」，编码器会在画质和码率间权衡。关键是趋势对了：1012k → 440k，码率确实被压下来了，目的达成。要更精确可再上 CBR/maxrate+bufsize 等约束，但那是另一个话题。

#### 4.6 回馈上游

这是 OHOS 版 FFmpeg 自身的实现缺失，所以修复也回馈给了上游：

- 已向 OpenHarmony 官方 FFmpeg 仓库提交 **Issue**（`gitee.com/openharmony-tpc-incubate/FFmpeg` · IDMF3P）。
- 计划整理并提交 **MR**，把这段码率写入合入官方源码。
- 同步更新 `ffmpeg_tools`，把修复后的 `.so` 推到仓库。

**面试表达：这个问题的价值在于「敢往下钻一层」——现象在 ArkTS（码率没效果），很多人停在命令层反复试参数；但真正的 bug 在 native 硬件编码器封装漏写 `bit_rate`，只有把 `-b:v` 一路跟到 `format_->bit_rate`、再跟进 `SetCodecFormat()` 才会发现它没被写进 `OH_AVFormat`。定位后补一行、重编 `.so`、并回馈上游。**

### 小结

1. 硬件加速解决「加水印/转码」这类必须重编码的慢操作，靠芯片硬件 codec，2 分钟水印约 15.68s。
2. 鸿蒙用 `h264_ohosavcodec` 一个名字，靠**位置**区分硬件解码（`-i` 前）/硬件编码（输出前）。
3. 两个前提：`.so` 必须编进该 codec（本库换了华为版 `.so`）；零拷贝场景别上硬件。
4. 码率失效的真实根因**不在命令层**，而在 OHOS 版 FFmpeg 的 `ohosvideoencoder.cpp::SetCodecFormat()`：它写了宽高/像素格式/帧率，唯独漏写 `bit_rate`，导致 `-b:v` 被硬件编码器配置丢弃。
5. 解法：补 `OH_AVFormat_SetLongValue(avformat, OH_MD_KEY_BITRATE, format_->bit_rate)`，重编 `.so` 替换；并向 OpenHarmony 上游提 Issue/MR。
6. 实测 300k→440k、500k→648k，体积降 36%~56%；略高于设定值属 VBR 正常行为。
