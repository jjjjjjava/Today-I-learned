# 03 · 硬件编码接入与线上码率问题

> 前置知识：理解 [01.md](./01.md) 的命令返回机制和 [02.md](./02.md) 的双向通信；知道 FFmpeg 输入选项与输出选项的位置语义。

## 一、为什么图片水印很慢

录像下载在编码格式与 MP4 兼容时，可以直接复制压缩后的媒体包并重新封装，无需修改视频像素。

```text
RTSP
  -> 协议读取与解复用
  -> stream copy
  -> MP4 封装
```

图片水印会改变每一帧画面，无法只做封装转换。完整链路必须解码、合成、重新编码：

```text
输入视频
  -> 视频解码
  -> overlay 合成图片水印
  -> H.264 重新编码
  -> MP4 封装
```

初版功能可以运行，但 2 分钟视频加水印约需 150 秒，处理时间超过视频本身时长。根据耗时表现，判断当前链路大概率仍在使用 CPU 软件编码，没有进入平台硬件编码通道。

## 二、硬件 codec 不是写一条命令就能启用

项目向华为确认 FFmpeg 调用 OpenHarmony 硬件编解码能力的方式，获得平台 codec 名称：

```text
h264_ohosavcodec
```

水印命令将输出编码器改为：

```text
ffmpeg -i input.mp4 \
  -i watermark.png \
  -filter_complex "overlay=main_w-overlay_w-10:main_h-overlay_h-10" \
  -c:v h264_ohosavcodec \
  -c:a copy \
  -y output.mp4
```

`-c:v h264_ohosavcodec` 位于输入和滤镜之后、输出文件之前，因此作用于输出视频流，表示使用 OpenHarmony H.264 硬件编码器。

第一次加入该参数后，Native 日志提示当前 FFmpeg 不存在对应 codec。命令写法正确，但已编译 `.so` 没有包含 OpenHarmony 的 `ohosavcodec` 适配。

```text
指定 h264_ohosavcodec
  -> Native 报告 codec 不存在
  -> 排除 ArkTS 命令问题
  -> 定位当前 FFmpeg 构建缺少平台 codec
```

项目再次与华为沟通，获取包含 OpenHarmony 硬件编解码适配的 FFmpeg 源码版本。随后修改 `HPKBUILD` 与相关配置，重新交叉编译单一 `.so`，替换 Native 产物并回归验证。

完整优化路径不是“把编码器名称换掉”，而是：

```text
150 秒性能现象
  -> 判断软件编码
  -> 向华为确认平台 codec
  -> 命令指定 h264_ohosavcodec
  -> 日志发现构建产物缺少 codec
  -> 获取带 ohosavcodec 的源码
  -> 修改构建配置并重新编译
  -> 替换 .so
  -> 回归性能与输出文件
```

## 三、性能结果

公司项目落地阶段的统一口径：

| 指标 | 优化前 | 优化后 |
| --- | ---: | ---: |
| 视频时长 | 2 分钟 | 2 分钟 |
| 加水印耗时 | 约 150 秒 | 约 27 秒 |
| 耗时降幅 | - | 约 82% |
| 速度提升 | - | 约 5.6 倍 |

更准确的表述是“接入 OpenHarmony 系统硬件编解码能力”，不要笼统写成“使用 GPU/NPU 编码”。芯片实现可能使用专用媒体编解码单元。

当前开源仓库 README 还记录了 2 分钟视频约 `15.68s` 的后续测试结果。该数据来自后续版本或不同环境，不能与公司阶段的 `150s -> 27s` 混作同一次对比。

## 四、开源后收到码率问题反馈

`ffmpeg_tools` 发布后，GitHub 用户在 [Issue #3](https://github.com/jjjjjjava/ffmpeg_tools/issues/3) 反馈硬件编码相关能力问题。

排查发现，视频裁剪与码率/分辨率参数失效属于不同根因，因此将码率问题拆分为独立的 [Issue #5](https://github.com/jjjjjjava/ffmpeg_tools/issues/5) 跟踪。

问题现象是：使用 `h264_ohosavcodec` 时，即使命令指定 `-b:v`，输出仍保持较高码率。

```text
ffmpeg -i input.mp4 \
  -c:v h264_ohosavcodec \
  -b:v 300k \
  -c:a aac \
  -y output.mp4
```

## 五、先排除 ArkTS 与 fftools 命令层

`-b:v` 是输出视频流选项，位置需要在输出文件之前。检查用户命令后，确认参数位置正确。

继续跟踪参数传递，确认 fftools 已把目标码率解析进 Native 编码参数：

```text
-b:v 300k
  -> fftools 参数解析
  -> format_->bit_rate = 300000
```

这一步把怀疑范围从 ArkTS 命令构造和 fftools 参数解析，缩小到 OpenHarmony 硬件编码器封装。

## 六、根因在 `ohosvideoencoder.cpp`

`h264_ohosavcodec` 的 Native 编码适配位于：

```text
libavcodec/ohosvideoencoder.cpp
```

`VideoEncoder::SetCodecFormat()` 创建 `OH_AVFormat`，写入宽度、高度、像素格式、编码类型和帧率，再调用 `OH_VideoEncoder_Configure`。

```cpp
OH_AVFormat *avformat = OH_AVFormat_Create();

OH_AVFormat_SetIntValue(
    avformat,
    OH_MD_KEY_WIDTH,
    format_->width
);

OH_AVFormat_SetIntValue(
    avformat,
    OH_MD_KEY_HEIGHT,
    format_->height
);

OH_AVFormat_SetDoubleValue(
    avformat,
    OH_MD_KEY_FRAME_RATE,
    format_->frameRate
);
```

代码已经收到 `format_->bit_rate`，却没有把它写入 `OH_AVFormat`。参数链断在调用系统硬件编码器之前的最后一层。

```text
-b:v 300k
  -> fftools 正确解析
  -> format_->bit_rate = 300000
  -> SetCodecFormat 漏写 bitrate
  -> OH_VideoEncoder_Configure 未收到目标码率
  -> 硬件编码器使用默认码率
```

## 七、修改源码并重新发布

在 `OH_VideoEncoder_Configure` 前补充码率配置：

```cpp
if (format_->bit_rate > 0) {
    OH_AVFormat_SetLongValue(
        avformat,
        OH_MD_KEY_BITRATE,
        format_->bit_rate
    );
}
```

随后重新执行发布链路：

```text
修改 ohosvideoencoder.cpp
  -> Lycium 重新交叉编译
  -> 生成新的单一 .so
  -> 替换 ffmpeg_tools Native 产物
  -> 使用多组目标码率回归
  -> 更新 GitHub 与 OHPM 版本
```

该缺陷来自 OpenHarmony FFmpeg 的硬件编码适配，项目又向上游提交 [Issue #IDMF3P](https://gitee.com/openharmony-tpc-incubate/FFmpeg/issues/IDMF3P)。

## 八、验证数据与码率口径

现有测试记录：

| 样本 | 码率 | 文件大小 |
| --- | ---: | ---: |
| 原视频，6 分 48 秒 | 约 1012 kbps | 49.2 MB |
| 设置 `-b:v 500k` | 约 648 kbps | 31.5 MB |
| 设置 `-b:v 300k` | 约 440 kbps | 21.4 MB |

目标 `500k` 和 `300k` 控制的是视频轨码率。播放器或文件信息页显示的总码率，还包含音频轨码率与 MP4 封装开销。

因此不能仅用文件总码率判断 `-b:v` 是否精确。应分别检查视频轨与容器总码率：

```text
ffprobe -select_streams v:0 \
  -show_entries stream=bit_rate \
  -of default=noprint_wrappers=1 \
  output.mp4
```

若音频约为 `128k`，视频 `300k` 加音频与封装开销后，总码率接近 `440k` 是合理现象。这比简单归因于 VBR 更完整。

## 九、项目价值

性能优化展示的是“从现象推断执行路径，再补齐构建能力”：发现 150 秒耗时，确认硬件 codec，依据 Native 日志定位产物缺失，获取适配源码并重新编译。

码率修复展示的是“沿参数链下钻”：从 GitHub 用户反馈出发，依次排除 ArkTS、fftools 和参数位置，最终定位到 Native 硬件编码器封装漏传字段。

最终形成完整闭环：

```text
业务落地
  -> 基础能力开源
  -> 社区 Issue
  -> 复现与底层定位
  -> 修改源码并重新发布
  -> 回馈 OpenHarmony 上游
```

## 小结

1. 图片水印必须重新编码，初版 150 秒耗时暴露出软件编码瓶颈。
2. 命令指定 `h264_ohosavcodec` 后报错，根因是当前 `.so` 未编入平台 codec。
3. 获取带 OpenHarmony 硬件适配的源码并重编后，公司阶段耗时降至约 27 秒。
4. GitHub 社区随后反馈 `-b:v` 不生效，根因是 `SetCodecFormat()` 漏写 `OH_MD_KEY_BITRATE`。
5. 修改 Native 源码、重编并发布后，又向 OpenHarmony FFmpeg 上游提交 Issue。
6. 判断码率效果时，需要区分视频轨码率和文件总码率。

## 思考题

1. 命令指定 `h264_ohosavcodec` 后提示 codec 不存在，为什么继续修改命令参数没有意义？
2. 如何证明 `-b:v` 已经通过 fftools 解析，从而把怀疑点移到硬件编码封装？
3. 为什么设置视频码率 `300k` 后，文件总码率可能接近 `440k`？
4. 公司阶段的 `27s` 与开源版本的 `15.68s` 为什么不能直接放进同一组性能对比？
