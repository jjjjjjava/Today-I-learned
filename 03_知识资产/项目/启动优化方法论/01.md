# 启动优化方法论：增量治理与存量优化

> 前置知识：Android Application/Activity 基本启动过程，Macrobenchmark 与 Perfetto 的基本用途
> 难度：进阶
> 预计阅读时间：18 分钟

## 一、总论：启动优化解决两类问题

启动优化不是异步、延迟加载、Baseline Profile 等技巧的集合，而是一套持续治理启动耗时的方法。它解决两类不同的问题：

```text
启动性能治理
├── 增量劣化治理：防止新代码、新 SDK 和新版本继续抬高启动水位
└── 存量启动优化：降低稳定版本中已经存在的启动耗时
```

两条治理线的职责不同：

- **存量优化负责把水位降下来**，产出一个更健康的新基线；
- **增量治理负责守住新基线**，防止业务迭代重新吃掉优化收益。

无论问题从哪条线进入，处理时都复用同一个闭环：

```text
发现 → 归因 → 治理 → 验证
 ↑                    │
 └── 新基线、预算和防线回填 ─┘
```

## 二、增量劣化治理：把问题尽可能拦在用户之前

增量治理关注的是“新改动相对稳定基线是否变慢”。完整防线按照问题被发现的时间从早到晚排列：

```text
静态代码检测
    ↓
成员 MR 的 CI Benchmark
    ↓
候选版本的自动化性能测试
    ↓
灰度版本对比
    ↓
线上长尾监控
```

越靠前，发现成本越低但覆盖有限；越靠后，数据越接近真实用户，但漏网代价越高。

### 第一层：静态代码 Lint 检测

Lint 的价值是发现**不运行应用也能判断的高风险代码模式**，例如：

- 在 `Application.onCreate()` 或启动 Task 中直接执行文件、数据库或网络 IO；
- 在启动主线程调用已知的阻塞 API；
- 新增 `CountDownLatch.await()`、`Future.get()`、同步锁等待等启动阻塞；
- 新增自动初始化的 `ContentProvider`；
- 在启动阶段直接调用已知重型 SDK 初始化 API；
- 新增启动任务却没有声明所属 Stage、线程、依赖关系和预算；
- 在首屏前创建 WebView、全量 Fragment 或不可见页面。

但必须明确它的能力边界：

> **Lint 能识别危险写法，不能证明代码实际增加了多少毫秒。**

一段看起来普通的代码可能因为数据量、设备或 SDK 内部实现变得很慢；一段命中规则的代码也可能不在真实关键路径。因此，Lint 是第一层低成本筛查，不能替代 Benchmark。

### 第二层：成员 MR 的 CI Benchmark

当成员提交涉及启动路径的 MR 时，CI 构建候选 Release 包，在固定设备、账号、数据、网络和启动场景下运行 Macrobenchmark。

对比对象应当是：

> **同一套测试环境下构建和测量的稳定基线 Release 包。**

线上 P50/P90 可以帮助制定目标和预算，但不能直接与 CI 单机数据混为一组进行比较，因为两者的设备分布、样本量和环境不同。

CI 门禁同时检查两类限制：

```text
相对稳定基线是否明显劣化
            ＋
总耗时或某个 Stage 是否超过绝对预算
```

例如：

- TTFD 相对基线增加超过允许阈值；
- `app_init` 虽然没有让总时间大幅增长，但自身超过阶段预算；
- LOW 档位设备的 P90 或多轮尾部结果明显恶化；
- 新增 SDK 初始化 Task 超出其申报预算。

CI Benchmark 具有噪声，不能简单因为一次运行慢了就阻塞 MR。需要固定环境、多轮测量，并基于历史波动确定合理阈值。

### 第三层：候选版本自动化性能测试

MR 阶段偏向快速反馈，候选版本自动化测试偏向完整覆盖。它可以在夜间、提测或发版前执行：

- 完整冷启动、温启动和关键启动入口；
- LOW/MID/HIGH 代表机型；
- 自动登录、首次安装、升级安装等重点场景；
- 总耗时和各 Stage/Task 预算；
- 启动后的首页功能、路由和 SDK readiness。

这层回答的是：

> 多个改动集成到同一个候选版本后，整体启动性能是否仍然满足发布标准？

它能发现单个 MR 测试未覆盖、多个改动叠加或者构建产物变化造成的问题。

### 第四层：灰度版本对比

灰度阶段已经进入真实设备和真实用户路径，是增量问题最重要的线上防线之一。

比较时必须尽量保证同群：

```text
候选版本 vs 上一个稳定版本
+ 相同启动类型和入口
+ 相同设备档位
+ 相同系统区间
+ 足够样本量
```

观察指标包括：

- 总启动耗时 P50、P90 和超时率；
- LOW/MID/HIGH 各档位的分位数；
- 各 Stage 的增量贡献；
- Stage 下各 Task 的增量贡献；
- Crash、ANR 和关键业务成功率。

ARouter 劣化案例体现的就是这条下钻链：

```text
候选版本 P50/P90 明显劣化
        ↓
Stage 对比定位到 Application/onCreate 阶段
        ↓
Task 对比定位到 arouter.init
        ↓
同版本、同档位设备本地复现
        ↓
Perfetto 发现主线程 Dex/class scan
        ↓
定位编译期注册 wiring 失效、运行时扫描兜底
```

这里需要保持证据边界：P50/P90、Stage 和 Task 只能说明“问题集中在哪里”，最终根因仍要由本地复现、Trace 和代码变化共同证明。

### 第五层：线上长尾监控

全量发布后仍可能出现灰度没有覆盖的问题，例如：

- 极少数设备型号或 ROM；
- 特殊账号、Push 或 DeepLink 路径；
- 长期使用后的数据库、缓存和磁盘状态；
- 极端 CPU、IO、内存或温度环境；
- 灰度样本不足以暴露的 P95/P99 长尾。

线上监控负责发现这些漏网问题。发现后仍然回到同一条处理链：

```text
版本 → 场景 → 设备档位 → Stage → Task → 本地复现 → Perfetto
```

## 三、存量启动优化：主动降低稳定版本的启动水位

存量治理不是某个候选版本突然劣化，而是稳定版本本身距离性能目标仍有差距。

例如产品提出本期目标：

- P50 整体启动耗时降低 10%；
- P90 降低 30%，重点改善低端机和长尾用户。

P90 的目标可以比 P50 更激进，因为 CPU、IO、类加载和复杂 UI 等问题通常会在低端设备上被明显放大。

### 存量治理的完整流程

```text
线上 P50/P90 或业务目标发现机会
        ↓
确定主要场景和设备档位
        ↓
同档位设备多轮 Macrobenchmark
        ↓
按 TTFD 排序，选择中位数代表轮次
        ↓
使用 Perfetto 做启动全链路分析
        ↓
提出可证伪的单一优化假设
        ↓
修改后重新 Benchmark 与 Trace
        ↓
灰度验证并建立新基线
```

这里要区分三种证据的职责：

| 证据 | 回答的问题 |
|---|---|
| 线上 P50/P90 | 哪类用户慢、值不值得投入、优化后大盘是否成立 |
| Macrobenchmark | 相同条件下修改前后是否稳定地变快 |
| 中位数轮次 Perfetto | 具体慢在哪、为什么慢、优化假设是否成立 |

因此不能简单说“存量优化就是跑 Benchmark”。更准确的说法是：

> 线上数据或业务目标负责发现机会，Benchmark 负责稳定复现和前后比较，Perfetto 负责根因解释。

## 四、按照启动全链路分析存量问题

启动优化不能只盯着 `Application.onCreate()`，而要沿用户启动关键路径逐阶段分析。

```text
进程创建 / bindApplication
        ↓
Application.onCreate
        ↓
Activity.onCreate / 首页构建
        ↓
首帧 measure-layout-draw
        ↓
首屏数据完成 / TTFD
```

### 阶段一：进程创建与 `bindApplication`

这一阶段常见成本包括：

- APK、Dex 和类加载；
- `installProvider` 及三方库自动初始化；
- ART 解释执行、JIT/AOT 编译状态；
- 资源读取和缺页；
- 启动关键代码在 Dex 中的布局。

对应优化手段包括：

#### Baseline Profile

为关键用户路径提供 Profile，引导 ART 对关键类和方法进行 AOT 编译，减少首次启动时的解释执行和 JIT 成本。

#### Startup Profile

向构建工具描述启动关键代码，指导启动相关类的 DEX 布局，使启动路径代码更集中。

需要纠正一个容易被追问的说法：

> **D8 是把 Java/Kotlin 字节码转换成 DEX 的编译器，不应表述为“通过 D8 压缩 `loadDexFile`”。**

更准确的表达是：Baseline Profile 优化运行时编译状态；Startup Profile 影响 DEX 布局。它们可能改善 `bindApplication` 附近的类加载和代码执行，但不能把整个阶段简单等同为 `loadDexFile`。

此外还可以检查：

- 是否存在不必要的 ContentProvider；
- 是否加载了首屏不需要的类和库；
- 是否存在过多 Dex、资源 IO 或动态扫描；
- 构建插件是否退回运行时扫描兜底。

### 阶段二：`Application.onCreate`

这里通常聚集大量 SDK 和应用基础设施初始化。治理重点不是“全部并发”，而是缩短启动关键路径。

第一步先分类：

| 初始化任务 | 治理方式 |
|---|---|
| 已经无业务使用 | 删除僵尸 SDK 或无效初始化 |
| 业务入口前必须就绪 | 保留在关键路径并正面优化 |
| 某功能首次使用前才需要 | 按需初始化或入口等待 |
| 首屏完全不需要 | 延迟到 TTFD 后 |

第二步再处理依赖关系。有些 SDK 存在真实顺序约束，例如 Token Header 依赖网络基础配置，业务入口又依赖 Token Header 已就绪。

这时可以用 DAG 建模：

- 每个任务声明稳定名称、依赖、线程和等待点；
- 使用拓扑排序验证依赖合法且无环；
- 无依赖任务可以并发；
- 有依赖任务在前置完成后释放；
- `BUSINESS_ENTRY` 只等待必要任务的依赖闭包；
- 其余任务移动到 TTFD 后或具体功能入口。

DAG 的真正价值不是炫耀调度算法，而是：

> **显式暴露真实依赖，删除虚假等待，只让业务入口等待最小必要集合。**

### 阶段三：`Activity.onCreate` 与首页构建

这个阶段不只有 XML inflate，还可能包括：

- Window、Theme 和 DecorView 构建；
- XML 解析和 View 反射创建；
- Fragment 和 ViewPager 页面实例化；
- RecyclerView、Adapter 和数据绑定；
- WebView/Chromium 初始化；
- 首屏不显示的控件被提前创建。

分析时可以在 Perfetto 中观察：

- `LayoutInflater.inflate`；
- Fragment View 创建；
- RecyclerView 首次布局；
- WebView/Chromium 初始化；
- 大量重复的资源加载或对象创建。

常见治理原则是：首屏需要的立即构建，非首屏内容按需构建，可选预热放到 TTFD 后。

### 阶段四：首帧 UI 渲染与 `performTraversals`

`ViewRootImpl.performTraversals()` 会驱动 View 树的 measure、layout 和 draw。这里需要关注的不只是“XML 重不重”，而是：

- View 层级和节点总量；
- 是否反复触发 measure/layout；
- RecyclerView 首次布局工作是否过多；
- 不可见页面是否参与首帧构建；
- 图片、资源或数据绑定是否阻塞主线程；
- 后台 SDK 任务是否争抢 CPU，导致主线程或 RenderThread 调度不足。

治理目标是减少首帧前需要创建、测量、布局和绘制的总工作量。

### 阶段五：首屏数据完成与 TTFD

首帧出现不代表页面已经可用。TTFD 可能还依赖：

- 用户和权限状态；
- 工作台或首页接口；
- 数据解析和适配；
- 首屏列表构建；
- 下一帧真正绘制完成。

因此优化目标应同时关注：

- TTID：用户何时看到第一帧；
- TTFD：用户何时看到主要内容并可以正常使用。

如果只优化第一帧，却把大量工作推到第一帧之后、TTFD 之前，可能只是让启动看起来更快，并没有缩短用户等待时间。

## 五、验证：证明性能有效、归因成立、功能安全

一次优化至少需要四层验证。

### 第一层：性能有效

- 相同设备和条件重新运行多轮 Macrobenchmark；
- 比较修改前后的中位数和尾部结果；
- 检查 P50 目标和 P90 目标是否分别达成。

### 第二层：归因成立

- 代表轮次 Perfetto 中目标 Stage/Task 是否按假设缩短或移到 TTFD 后；
- 相关系统信号是否同步变化；
- 是否只是把耗时转移到了另一段关键路径。

### 第三层：功能安全

- 首页内容、Tab、状态恢复正常；
- WebView 首次入口和登录态正常；
- SDK readiness 与依赖关系正常；
- Crash、ANR、内存和卡顿没有恶化。

### 第四层：线上成立

- 小流量灰度观察 P50/P90、Stage/Task 和样本量；
- 按设备档位检查收益是否符合预期；
- 同时观察功能成功率与稳定性指标；
- 逐步放量，避免一次性扩大风险。

自测负责基本正确性，但不能替代 Benchmark；Benchmark 负责本地性能证据，但不能替代真实用户灰度。

## 六、优化完成后的回填

存量治理完成后，至少要沉淀：

- 优化后的稳定基线 Release 包或基线数据；
- 总启动耗时和各 Stage 的新预算；
- 关键 Task 的耗时与线程约束；
- 新增 SDK 和启动任务的 MR 评审规则；
- CI Benchmark 或 Release 产物校验；
- 自动化测试、灰度和线上告警规则；
- 对应功能的回归用例和回滚方案。

最终形成完整轮转：

```text
存量治理降低启动水位
        ↓
建立新的稳定基线和阶段预算
        ↓
增量治理通过 Lint、CI、自动化、灰度和线上守住基线
        ↓
发现漏网劣化
        ↓
重新进入归因、治理和验证
```

## 七、面试表达版本

> 我把启动性能治理分成存量优化和增量劣化治理。增量侧按照问题发现时间建立多层防线：静态 Lint 识别主线程 IO、阻塞等待和过早初始化等高风险模式；成员 MR 在固定设备上构建 Release 包，通过 Macrobenchmark 与稳定基线比较；候选版本再跑完整自动化性能测试；进入灰度后按相同场景和设备档位比较 P50、P90、Stage 和 Task；全量发布后用线上监控补充灰度无法覆盖的长尾问题。存量侧则从线上分位数或业务目标发现机会，在相同档位设备上多轮 Benchmark，选择中位数轮次用 Perfetto 做全链路归因，再沿 bindApplication、Application、Activity、首帧和 TTFD 分阶段治理。优化后同时验证性能、Trace 假设和功能安全，最后更新稳定基线与阶段预算，让存量收益进入下一轮增量治理。

## 思考题

1. 为什么 MR Benchmark 必须和相同环境下的稳定基线包比较，而不能直接拿 CI 单机结果与线上 P50/P90 比较？
2. 如果灰度版 P90 明显上升、P50 基本不变，你会如何判断这是低端机真实劣化，还是候选版样本结构发生了变化？
3. 一个 SDK 可以放到后台线程执行，但它仍然位于 TTFD 前。你会从哪些证据判断它应该被删除、延后、保留还是纳入 DAG？
