## 承接 01：静态一帧 → 动态视频

01 篇把「给一帧 YUV 加水印」整条管线走通了——这「一帧」的能力其实已经能干活：**抽视频首帧、加个水印，就是一张封面图**。

但视频不止一帧。1080p 60fps 是源源不断的帧流。最直觉的想法：每来一帧，就像贴静态图那样 `texImage2D` 上传一次。**行不行？先算笔账。**

## 1. 图片能每帧上传，视频为什么不能

静态图片进 GPU 的老路：

```
Bitmap（Java 堆）
  → glBindTexture 绑定纹理
  → GLUtils.texImage2D(...)   ← 这一步发生 CPU → GPU 内存拷贝
  → bitmap.recycle()
```

图片只上传**一次**，拷贝成本忽略不计。视频不行——算一笔账：

| 项 | 数值 |
|---|---|
| 1080p 一帧 | 1920×1080×**4** ≈ **8 MB** |
| 60fps 每秒 | ≈ **480 MB** 走 CPU→GPU 总线 |
| 单帧拷贝耗时 | ~8–16 ms |
| 一帧预算（60fps） | **16.67 ms** |

> **结论：光是拷贝就快把一帧的预算吃光。** 视频帧绝不能走「每帧把像素从 CPU 搬到 GPU」这条老路。

⚠️ **看清贵在哪条轴**：贵的是 **CPU 内存 → GPU 显存**那一次拷贝（`texImage2D` 干的事），不是「Java → Native」。零拷贝的解法恰恰**靠 Native 共享内存**——让解码结果直接落在 GPU 够得着的那块 Native 内存里，CPU 完全不插手搬运。**Native 共享内存是解药，不是问题。**

## 2. 零拷贝管线（输入侧）

核心一句话：**别上传数据，让纹理直接指向 MediaCodec 解码好的那块内存。**

### 搭建：消费者 / 生产者两端，封装同一个 BufferQueue

| 步骤 | 做什么 | 本质 |
|---|---|---|
| ① | `glGenTextures` 拿一个 **OES 纹理 ID** | GPU 侧的句柄 |
| ② | `SurfaceTexture(textureId)` | BufferQueue 的**消费者**端封装，把新帧挂到这个纹理 ID |
| ③ | `Surface(surfaceTexture)` 透传给 MediaCodec | BufferQueue 的**生产者**端封装 |

> BufferQueue 底层通常持有约 **3 个 GraphicBuffer**（每个能存一帧；数量其实由生产者/消费者**协商**，不硬绑三缓冲），生产者写、消费者读，循环复用。

### 运行：每帧的流转

```
MediaCodec 生产：dequeueBuffer 拿一块空闲 GraphicBuffer → 写入解码帧 → queueBuffer 交还
        ↓ onFrameAvailable（只通知「有新帧」，不自动更新纹理）
GL 线程主动调 surfaceTexture.updateTexImage()
        → 把 OES 纹理对象内那根「数据指针」换指向最新这帧的 GraphicBuffer（换指针，非拷贝）
        ↓
片元着色器用 samplerExternalOES 采样这帧 → 走第①篇那条管线
        ↓
渲染结果 → 上屏（见「视频上屏与中间层处理」笔记）
```

### 三个易错钉子

| 钉子 | 说清 |
|---|---|
| `updateTexImage()` ≠ `texImage2D()` | 前者**换指向**——id、纹理对象都不变，只改对象内那根指针指向最新 GraphicBuffer；后者**搬数据**。前者全程**零像素拷贝**。⚠️ 名字是 `updateTexImage`，是 **SurfaceTexture 的 Java 方法，不是 `gl*` 调用**——别写成 `glUpdateTexture` |
| `onFrameAvailable` **只通知** | 它不更新纹理；是你在 **GL 线程**主动调 `updateTexImage()` 才真正消费。通知和消费是**两步、两个线程** |
| 为什么 GPU 能 direct 读 | BufferQueue 是**系统分配的 Native 层共享内存（GraphicBuffer）**，不是 MediaCodec 的 Java 层缓冲区 → GPU 可直接访问，无需 CPU 中转 |

### 为什么必须用 OES 外部纹理

| | `GL_TEXTURE_2D` | `GL_TEXTURE_EXTERNAL_OES` |
|---|---|---|
| 图像来源 | 自己 `texImage2D` 上传 | Camera / MediaCodec 等外部源 |
| 底层格式 | RGBA | YUV / 厂商私有 |
| 片元采样器 | `sampler2D` | `samplerExternalOES`（需 `#extension GL_OES_EGL_image_external : require`） |

> OES 采样时**隐式做 YUV→RGB**，所以只认 RGBA 的 `sampler2D` 接不住解码帧。相比第①篇，**着色器只改这一处采样器**，管线骨架完全没变——只是给芯换了纹理来源。

## 3. 回到水印：原理 + 渲染结果往哪送

解码帧现在成了一张可采样的 OES 纹理，回到加水印。

### 水印原理

手里两张纹理——视频帧是 **OES**（`samplerExternalOES`，采样顺带 YUV→RGB），水印是普通 **2D**（`sampler2D`，本就 RGBA）。在**片元着色器**里判断当前片元是否落在水印区域：

- **在** → 按水印该像素的 α 混合：`结果 = 画面色 ×(1−α) + 水印色 × α`；
- **不在** → 直接输出画面色。

**位置**由水印的顶点/纹理坐标画定，**混不混**由 α 决定（α=0 全画面，α=1 全水印，中间半透明）。

### 渲染出的这帧「带水印 RGB」往哪送？

如果要编码存成视频文件，得把这帧交给 MediaCodec 编码器。链路是：

```
encoder.createInputSurface()        ← 编码器吐出一个输入 Surface，提供给 OpenGL 用
  → eglCreateWindowSurface(它)       ← 封装成 EGLSurface
  → eglMakeCurrent(它)               ← 选定它（渲染就落到它的默认 FBO0）
  → 画出带水印的帧
  → eglSwapBuffers(它)               ← 把这帧交给编码器 → 编码器输出 H264 → MediaMuxer 写进容器
```

> ❓ **留一个问题（待第④篇 EGL 解决）**：这里的 **EGL / FBO 到底是什么**？`eglMakeCurrent` 绑的 EGLSurface 和那个「默认 FBO0」是什么关系、谁带谁？为什么换一个 EGLSurface 就换了渲染去向（屏幕 ↔ 编码器），而 GL 这段画水印的代码却一字不改？——见 **06_EGL**。
>
> （另：`createInputSurface` 的编码端细节属采集/编码模块，本课范围外，这里只把「渲染结果怎么交出去」的口子留着。）

### 收束

零拷贝整条因果链（输入侧）：**双端封装同一 BufferQueue（共享内存）→ SurfaceTexture 把帧挂上纹理 ID → `updateTexImage` 换指针（非拷贝）→ OES 接住非 RGBA 的外部帧。** 一次像素拷贝都没有。

> 渲染结果如何上屏（窗口 Surface → `eglSwapBuffers` → SurfaceFlinger）、以及多级滤镜的 FBO 中间层处理，见 → **「视频上屏与中间层处理」笔记**。

## 思考题

1. 用一句话说清 `updateTexImage()` 和 `texImage2D()` 的本质区别。如果有人说「视频每帧也是上传到 GPU 显存」，错在哪？
	1. 对于 1080p、60fps 视频，每秒数据量近 GB 级，简单拷贝管线扛不住，更别说每 16ms 渲染一次。需要零拷贝管线：BufferQueue 是 Native 共享内存，`updateTexImage` 只是把 OES 纹理指针指向最新解码帧，**换指向而非搬数据**。说「上传到显存」就错在它根本没发生 CPU→GPU 拷贝。
2. 为什么视频帧必须用 `samplerExternalOES` 而不能用普通的 `sampler2D`？这和解码帧的「底层格式」有什么关系？
	1. `sampler2D` 只能处理 RGBA；OES 能接 YUV / 厂商私有格式，且采样时**隐式做 YUV→RGB**。解码帧底层就是 YUV，所以必须 OES。

> 「双 Surface 谁是谁的输出」「单层滤镜要不要 FBO」两题，随上屏 / FBO 内容移到「视频上屏与中间层处理」笔记。
