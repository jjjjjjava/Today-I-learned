# 渲染异常排查：两个真实踩坑 + 定位手法

> 前置知识：02（零拷贝/OES/updateTexImage）、03/04（FBO、纹理单元工位）、05（混合）、06（EGL/TLS）
> 难度：实战（踩坑复盘）
> 本篇不讲新机制，只记两个**真实遇到的渲染异常**，重点是「**怎么定位**」——GPU 没断点没 printf，定位靠两板斧：
> **① 把着色器里的中间变量当颜色输出（shader 版 printf）；② 用显眼的 clear 色 / 固定常数做二分对照。**
> 时序类问题再加三事件日志，确凿证据上 AGI / RenderDoc 抓帧。

## 问题一：处理 JPG 水印素材导致画面**全黑**

### 现象
给视频帧叠 JPG 水印后，**整张画面全黑**——不是"水印没显示"，而是连视频主画面也没了。这说明污染发生在视频主纹理的采样或混合环节，不只是水印那一层。

### 根因（JPG 专属）：JPG 没有 alpha 通道
水印混合一般是按水印 alpha 叠：

```glsl
finalColor = mix(videoColor, wmColor, wmColor.a);   // alpha 当插值因子
```

JPG **天生没有 alpha 通道**，解码后 `wmColor.a` 处处是 `1.0` → `mix` 等于**用水印整张图盖满全屏**。若水印图是深色/黑底（或用的是 `videoColor * wmColor` 正片叠底，黑=0），结果就是**全屏黑**。

> 守追问：即使把 JPG 解码进 `ARGB_8888` 的 Bitmap，alpha 也会被解码器**补成 255**（这条通道 JPG 本就没有）。所以 "`hasAlpha=false`" 和 "alpha 恒 255" 是同一件事的两个证据。

### 怎么定位

**第 0 步 · 进 GPU 前在 CPU 拦一刀（最便宜）**

```kotlin
val bmp = BitmapFactory.decodeFile(jpgPath)
Log.d("WM", "hasAlpha=${bmp.hasAlpha()} config=${bmp.config} " +
            "a@center=${Color.alpha(bmp.getPixel(bmp.width/2, bmp.height/2))}")
```

JPG 解出来 `hasAlpha=false`、抽样 alpha 恒 `255` → 一行日志就锁定怀疑，根本不用进着色器。

**第 1 步 · shader 可视化把 `wm.a` 画成灰度（实锤）**

```glsl
// gl_FragColor = mix(videoColor, wmColor, wmColor.a);     // 原逻辑先注掉
gl_FragColor = vec4(wmColor.a, wmColor.a, wmColor.a, 1.0); // 把 alpha 当颜色看
```

- 屏幕**全白** → alpha 处处 1.0 → 实锤 JPG 无 alpha。
- 再换 `gl_FragColor = videoColor;`，黑屏消失 → 隔离出"视频纹理本身没问题，污染在混合"。

**第 2 步 · 二分混合因子 / 换素材对照**
- `mix(video, wm, wm.a)` → `mix(video, wm, 0.5)` 固定系数：画面恢复半透明叠加 → 证明问题就在 `wm.a` 这个因子。
- 换一张**带 alpha 的 PNG**（局部透明）其它不动：正常了 → 控制变量法坐实是素材 alpha。

**第 3 步（可选）· `glReadPixels` 抽样**：渲染到 FBO 后读几个像素 RGBA，确认数值，可写进自动化自测。

### 修复
1. 换 **PNG**（带 alpha）；
2. 或在 shader 里用**亮度/colorkey 自造 alpha**（如 `float a = step(0.1, dot(wmColor.rgb, vec3(0.299,0.587,0.114)))`）；
3. 或只在**水印矩形区域**采样混合，区域外直接走 `videoColor`（限定纹理坐标范围）。
4. 顺手把通用坑一起堵：视频 OES 与水印 2D 严格分到**两个纹理单元工位**（`glActiveTexture` + `glUniform1i` 各指各的工位号），并打 `glGetShaderInfoLog` / `glGetProgramInfoLog` 排除双 sampler 合并后链接失败。

### 面试一句话
> "加 JPG 水印导致全黑，我先在 CPU 侧 `hasAlpha()` 一眼怀疑素材没 alpha；进 shader 把 `wm.a` 画成灰度，全白坐实 alpha 恒 1——根因是 JPG 无 alpha 通道，`mix` 的插值因子恒为 1，水印整张盖满屏幕。修复是换带 alpha 的 PNG 或在 shader 里用亮度阈值自造 alpha，并把视频 OES 与水印 2D 分到两个工位。"

## 问题二：首帧黑屏（OES 纹理还没内容就 draw）

### 现象
**首帧黑、后续正常**。这个"首帧"特征基本锁定一类问题：**时序——渲染发生在"数据/目标 ready 之前"**。（和首页启动里"门店页/我的页"那个回归取舍同源：**状态生产早于 UI 消费 ready**。）

### 根因
零拷贝链路里，`SurfaceTexture` 要等解码器塞进第一帧、回调 `onFrameAvailable` 后，`updateTexImage()` 才把那帧 latch 到 OES 纹理。**渲染抢在第一帧到达前**，OES 纹理是空的，采样输出黑 → 首帧黑。

### 怎么定位

**第 0 步 · 红 clear 分大方向（注意读法，别下错结论）**

```kotlin
glClearColor(1f, 0f, 0f, 1f); glClear(GL_COLOR_BUFFER_BIT)
```

红 clear 区分的是「**有没有画上去**」：
- **看到红** = 全屏四边形**根本没画 / 没覆盖屏幕**（draw 没执行、Surface 目标没 ready、`glViewport` 还是 0、program 失效）。
- **看到黑** = 四边形**画了，但输出是黑**（OES 空 / 采样错 / 混合错）。

⚠️ 本问题（OES 空但 draw 了）属于后者：四边形是画了的，采样空 OES → 黑 → **多数情况看到黑，不是红**。
⚠️ driver 相关坑：若开了 `GL_BLEND` 且空 OES 采样返回透明 `(0,0,0,0)`，红底会透出来 → 又可能看到红。**所以颜色只用来分大方向，不能单独定论。**

**第 1 步 · 三事件时间戳，看 draw 是否早于首帧（决定性铁证）**

```kotlin
setOnFrameAvailableListener { Log.d("RZ", "onFrameAvailable t=${now()} thread=${tname()}") }
val ok = surfaceTexture.updateTexImage(); Log.d("RZ", "updateTexImage ts=${surfaceTexture.timestamp}")
Log.d("RZ", "draw #$frameIndex t=${now()}")
```

判据：**`draw #0` 时间戳早于第一次 `onFrameAvailable`** → 实锤渲染抢跑。这条才是定罪证据，红/黑只负责分流。

**第 2 步 · 坐实**
- `SurfaceTexture.getTimestamp()`：首帧若没真正 latch，它是 `0`；逐帧打，第一个非黑帧之前一直 0。
- 或 `AtomicInteger availableFrames`：`onFrameAvailable` +1，渲染只在 `>0` 时 `updateTexImage` 并 -1；记录"在 count==0 时发生的 draw"，与黑帧对齐即确认。

**第 3 步 · 对照实验（gating）最终确认**

```kotlin
if (!firstFrameLatched) { glClearColor(0f,1f,0f,1f); glClear(GL_COLOR_BUFFER_BIT); return }
```

首帧变绿（被闸拦下）→ 证明确有一次 draw 发生在任何帧 latch 之前；加闸后黑屏消失 → 同时验证修复有效。

**第 4 步（确凿/重武器）· 抓帧**：AGI / RenderDoc / Mali Graphics Debugger 抓第一帧，看 draw call 当时绑定的 OES 纹理是不是空的。OES 外部纹理在抓帧工具里有时不好看，日常先用 0–3 步，抓帧留作压舱。

### 修复
- 渲染由 `setOnFrameAvailableListener` 驱动，**收到回调才 `updateTexImage` + draw**；
- `updateTexImage` 必须在 GL 线程、`eglMakeCurrent` 之后调（TLS 那套）；
- 每帧开头 `glClear` 兜底首帧脏缓冲；渲染目标等 `surfaceChanged` 拿到尺寸再 `glViewport`；
- 每帧应用 `getTransformMatrix` 防方向/裁切异常。

### 面试一句话
> "首帧黑屏我归到一类——渲染早于数据 ready 的时序问题。我先用红 clear 分流：看到的是黑，说明四边形画了但输出黑，排除了'目标没 ready/没 draw'那一类；再打 `onFrameAvailable` 和 `draw` 的时间戳，发现首帧 draw 早于第一帧到达 → 坐实渲染没等 OES latch 就抢跑。修复是把渲染交给 `onFrameAvailable` 驱动，`updateTexImage` 后才 draw。这跟启动优化里'状态生产早于 UI 消费 ready'是同一类问题。"

## 收口：渲染问题定位方法论

> GPU 没断点没 printf，定位渲染问题两招：
> **① 把着色器里的中间变量（alpha、纹理坐标、采样结果）直接当颜色输出来"看见"它；**
> **② 用显眼的 clear 色或固定常数做二分对照，把范围劈半。**
> 时序类加三事件时间戳日志，**颜色负责分流、时间戳负责定罪**；确凿证据上 AGI / RenderDoc 抓帧。
