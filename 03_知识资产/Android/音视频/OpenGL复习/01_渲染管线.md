# OpenGL 渲染基础：从「给一帧视频加水印」倒推整条渲染管线

> 前置知识：音视频主链路（解码 → YUV → 渲染）、Android 基础
> 难度：进阶（复习）
> 预计阅读时间：12 分钟

## 用一个问题驱动全文

先解封装、解码——这两步交给系统 API（`MediaExtractor` / `MediaCodec`）就行，我们只管调用。真正要我们亲自指挥 GPU 的，是**渲染**。拿最具体的一个需求当线索：

> **给一帧视频画面打上水印。**

手里有两样东西：一帧解码出来的 **YUV**，和一张 **RGB 水印图**。问题立刻来了——水印是 RGB，画面是 YUV，**两种色彩空间没法直接叠加**。所以这件事天然分两步：

1. 先把 YUV **渲染成 RGB**；
2. 再把水印和画面**混合**到一起。

这恰好把本篇要回答的三件事钉死了：**① 什么是渲染、为什么非 GPU 不可；② CPU 怎么隔层指挥 GPU；③ GPU 内部怎么一步步把一帧 YUV 变成屏幕上的 RGB。** 答完，再回头解决「加水印」。

---

### 1. 什么是渲染，为什么非得交给 GPU

**色彩空间**：屏幕底层硬件就是一排排 RGB 三个小色点，每个分量 8bit = 1 字节，所以「显示」最终一定要落到 RGB。而 YUV 是另一种表示——**Y 是亮度，U/V 是色度（色差，承载「该是什么颜色」的信息）。⚠️ 注意 U/V 是色度，不是对比度。**

为什么传输/存储爱用 YUV？因为人眼对亮度敏感、对色度迟钝，于是 YUV420 敢对色度抽样：每 4 个像素存 4 个 Y、只存 1 个 U、1 个 V = 6 字节；同样 4 像素 RGB 要 4×3 = 12 字节，省一半。但省的是色度精度，**真要上屏还得转回 RGB**。

> **渲染的本质 = 算出每个像素最终该显示什么 RGB。** YUV→RGB 只是其中一种活（还有变换、采样、混合）。单看一个像素，YUV→RGB 就是几句加权加法：`R = a·Y + b·U + c·V`，简单到不能再简单。

难的不是公式，是**数量**：1080p 一帧 1920×1080 ≈ **207 万**像素，60fps 就是**每秒上亿次**同一个公式。CPU 几十个核、还要兼顾系统逻辑，扛不住这种「同一套简单运算重复百万次」的活。GPU 数千核各管一小片像素 + 超高显存带宽，正是为这个场景生的。

| | 并行度 | 内存带宽 | 适合 |
|---|---|---|---|
| CPU | 几十核，逐块推进 | 50~100 GB/s，还要兼顾系统 | 复杂分支、串行逻辑 |
| GPU | 数千核，各管一小片像素 | 高带宽显存 1TB/s+ | 同一套简单运算，重复百万次 |

> **核心直觉：渲染是「同一个公式，对几百万像素各算一遍」——这正是 GPU 的主场。**

### 2. CPU 怎么隔层指挥 GPU

CPU 指挥自己很容易——机器指令、寄存器，直接跑。GPU 有自己的专用指令集，CPU 够不着，中间隔三层：

1. **OpenGL ES**：一组让 CPU「下命令给 GPU」的 API（ES = for Embedded Systems，OpenGL 的移动精简版）。它是**主机端下命令**的接口——设状态、传数据、发起绘制。
2. **着色器（Shader）**：真正**跑在 GPU 上**的小程序，就像一个编译好的可执行程序，只不过它在 GPU 上执行。⚠️ OpenGL 与着色器不是「粗略 vs 精细」，而是分工：OpenGL 在 **host 端发号施令**，着色器是 **device 端干活的程序**。
3. **GLSL**：写着色器用的语言，类 C。

> **思路：我们用一串字符串写好 GLSL 着色器 → 运行时调 OpenGL API 把它编译、链接成 GPU 程序 → 把数据（顶点坐标、纹理等）喂进去 → 驱动 GPU 执行，按我们要的方式算出每个像素的颜色。**

着色器分两个，各管一段：

- **顶点着色器**：决定**顶点位置**——平移/旋转/缩放/投影（输出写内建 `gl_Position`）。每个顶点跑一次（矩形 4 个顶点跑 4 次）。
- **片元着色器**：决定**每个像素的颜色**——纹理采样、YUV→RGB、混合、滤镜（输出写 `gl_FragColor`）。每个片元跑一次（百万像素跑百万次）。

> ⚠️ 全文统一叫法：决定颜色的是**片元着色器**，没有「纹理着色器」这种东西，采样只是它的一项工作。

### 3. 渲染管线：一帧 YUV 怎么走成一帧 RGB

GPU 把一帧画出来走一条固定流水线，**六步**：

```
顶点数据 → 顶点处理 → 图元装配 → 光栅化 → 片元处理 → 测试/混合 → 写入帧缓冲
```

| 阶段 | 干了什么 |
|---|---|
| **顶点处理**（顶点着色器） | 经空间变换确定每个顶点位置（视频通常就一个矩形 4 个顶点） |
| **图元装配** | 把离散顶点**组装/连成**图元（三角形）。⚠️ 是「攒起来」不是「切开」：你从没给过 GPU 一个矩形，给的是 4 个点，装配把它们连成 2 个三角形 |
| **光栅化** | 把三角形覆盖区切成成千上万个**片元**（未来的像素），并为每个片元**插值**算出它的纹理坐标——⚠️ 算出的是**坐标（地址）**，不是颜色 |
| **片元处理**（片元着色器） | 拿插值来的纹理坐标去纹理**采样取色**（YUV→RGB 的公式就写在这里），算出该片元最终颜色 |
| **测试/混合** | 丢弃不该显示的片元，**或把新颜色与帧缓冲里已有颜色混合**——水印的 alpha 混合就发生在这一步 |
| **写入帧缓冲** | 最终颜色写入帧缓冲——**可能是屏幕 Surface，也可能是离屏 FBO**（做多级处理时写 FBO） |

⚠️ **两个最易记串的点（专门焊死）**：

- **图元装配是「组装」不是「拆分」**：你给的是离散顶点，装配把它们连成三角形。
- **光栅化插值出的是「纹理坐标 = 去纹理哪取色的地址」，不是颜色本身**。坐标 → 颜色是**两步**：光栅化给地址，片元着色器才拿地址采样出颜色。

**为什么少量顶点 + 一张纹理能填满百万像素**？就靠光栅化插值：你只给了 4 个角的坐标 + 4 个角的纹理坐标，GPU 按每个片元在三角形里的相对位置，自动插值算出它自己的纹理坐标。

```
屏幕中心像素 → 插值得纹理坐标 (0.5, 0.5) → 取图正中间的颜色
屏幕左侧像素 → 插值得纹理坐标 (0.1, 0.5) → 取图左边对应颜色
```

#### 这条链的主角：三类变量

「顶点上的 4 个纹理坐标」怎么变成「每个片元各自的纹理坐标」？答案藏在 GLSL 三类变量里，用「数据从哪来、到哪去」记：

| 变量类型 | 含义 | 典型例子 | 数据流向 |
|---|---|---|---|
| **attribute** | 逐顶点输入，每个顶点不同 | 顶点坐标 `aPosition`、纹理坐标 `aCoordinate` | CPU → 顶点着色器 |
| **uniform** | 全局常量，所有顶点/片元共享、只读 | 变换矩阵 `uMatrix`、纹理采样器 `uTexture` | CPU → 着色器（一次设好） |
| **varying** | 顶点着色器 → 片元着色器，**自动插值** | 传给片元的纹理坐标 `vCoordinate` | 顶点 → 光栅化插值 → 片元 |

> **灵魂链**：**attribute**（CPU 给 4 个角的纹理坐标）→ **顶点着色器把它写入 varying** → **光栅化对 varying 插值**，每个片元一份 → 片元着色器读这份 varying 当**地址**去采样。
>
> 顶点着色器是**传递者**：varying 由它声明并输出，光栅化只负责插值。少了顶点着色器这一棒，链就断了。

### 4.回到水印：双纹理 + 在「测试/混合」阶段按 alpha 混

三件事齐了，回到「给一帧加水印」。手里两张纹理，类型还不一样：

- **画面**：解码帧是一张 **OES 外部纹理**（`samplerExternalOES`），片元着色器对它采样时顺带 YUV→RGB；
- **水印**：是一张普通 **2D 纹理**（`sampler2D`），本来就是 RGBA。

「哪些位置该混、怎么混」由**两件事**共同决定，GPU 不会自己猜：

1. **位置由几何/坐标决定**：水印只占画面一小块——这块在哪，是你给水印的**顶点坐标/纹理坐标**画定的。出了这块，要么根本不生成水印片元，要么采到水印图的透明边（α=0）。
2. **混不混由 alpha 决定**：在水印区域内，按水印每像素的 α 做混合——
   `结果 = 画面色 ×(1−α) + 水印色 × α`。α=0 处退化成纯画面，α=1 处全是水印，中间是半透明。

> **混合这个动作发生在片元着色器算出颜色之后。** 落地有两种架构：**单 pass**——一个片元着色器里挂两个采样器（OES + 2D），都采完在 shader 里 `mix`；**多 pass**——先用 FBO 把 OES 视频渲成一张普通 RGB 纹理，再开 `GL_BLEND` 把水印 quad 画上去。
>
> 至于 **OES 纹理怎么免拷贝吃到解码帧、FBO 怎么串多级处理、混合公式细节**——是后面 ②③④ 篇的正题。本篇只把主干钉住：**加水印 = 两张纹理 + 在「测试/混合」阶段按 α 混。**

### pivot：但这只是「静态一帧」

上面整条管线，处理的是**手里这一帧**。可视频是**动态的**——帧多、过渡快、源源不断。如果每帧都像贴静态图那样把数据重新上传一遍，扛得住吗？这正是第 ② 篇的入口问题：**静态图片能每帧 `texImage2D` 上传，视频帧为什么不行、零拷贝怎么做。**


### 收束：一句话串起来 + 回到主链路地图

> CPU 把顶点/纹理数据放进**直接内存(DirectBuffer)**让 GPU 能直接读 → 编译链接出着色器**程序** → **顶点着色器**给每个顶点定位、写 varying → **光栅化插值**切片元、算每片元纹理坐标(地址) → **片元着色器**按地址采样取色(含 YUV→RGB) → **测试/混合**按 α 叠水印 → 写入**帧缓冲** → 上屏。

放回四篇的大地图，本篇是第一块「芯」：

```
解码出 YUV / 解码帧
   ↓
【OpenGL：把帧当纹理 → GPU 处理 → 转 RGB / 滤镜 / 变换 / 显示】   ← 本篇讲这条管线
   ↓
EGL 把结果交给窗口系统 → SurfaceFlinger 合成 → 上屏
```

| 复习篇 | 加的是什么 |
|---|---|
| **① 渲染基础与管线（本篇）** | GPU 怎么把一帧变成屏幕像素 |
| ② 渲染视频画面 | 让 GPU 零拷贝吃到「动起来的帧」（OES 纹理登场） |
| ③ 矩阵变换与画中画 | 坐标系、纠正比例、平移缩放、半透明混合公式 |
| ④ EGL 与上屏 | 渲染结果交给谁、怎么不撕裂 |

你笔记里的 `GLSurfaceView` / `Renderer` / `IDrawer` 那套，本质只是把这条流水线的**生命周期**包好：`onSurfaceCreated`（一次性建纹理）、`onSurfaceChanged`（设视口）、`onDrawFrame`（每帧驱动绘制）。框架是壳，**这条管线才是芯**。
