# Android 音视频 OpenGL：从解码输出到 GPU 处理

> 前置知识：MediaExtractor / MediaCodec / Surface / MediaMuxer 的主链路
> 难度：进阶
> 预计阅读时间：15 分钟

## 正文内容

这一篇从音视频主链路进入 OpenGL。这里不把 OpenGL 当成独立图形学课程来学，而是只抓 Android 音视频里最关键的一段：

```text
MediaCodec 解码
  -> Surface / BufferQueue / GraphicBuffer
  -> SurfaceTexture
  -> OES 外部纹理
  -> OpenGL shader 处理
  -> Encoder input Surface
  -> MediaCodec 编码
  -> MediaMuxer 封装
```

OpenGL 在这里的定位是：

> 视频帧进入 GPU 后的处理层，负责预览、旋转、裁剪、缩放、滤镜、水印，以及把处理后的画面送入编码器。

### 1. 视频处理走 CPU 的问题及解决方案

如果不用 Surface / OpenGL 的零拷贝路线，视频帧从 `MediaCodec` 解码出来后，通常会走 CPU 可访问的输出缓冲：

```text
MediaCodec
  -> dequeueOutputBuffer()
  -> getOutputBuffer()
  -> YUV ByteBuffer
  -> CPU 处理
  -> glTexImage2D / glTexSubImage2D 上传 GPU
  -> 渲染
```

这条 CPU 路线可以做，但问题很明显：

- 每帧都要让像素数据经过 CPU。
- 如果 CPU 做 YUV 到 RGB 转换，会有额外计算成本。
- 即使把 YUV 平面上传给 GPU 再由 shader 转换，仍然绕不开 CPU 内存到 GPU 纹理的上传。
- 视频是高频大数据流，1080p / 30fps 这类场景很容易被拷贝、内存带宽和格式转换拖慢。

所以 CPU 路线的问题不是“不能做”，而是：

> 每帧都要让图像数据从解码器到 CPU，再从 CPU 上传到 GPU；视频帧数据量大、频率高，这个成本很快会成为瓶颈。

解决方案是走 Surface 零拷贝路线。

更常见的视频播放或视频处理路线，是把 `Surface` 配给解码器：

```kotlin
decoder.configure(format, surface, null, 0)
```

这里的核心变化是：

> `MediaCodec` 不再把解码后的 YUV 输出到应用层 `ByteBuffer`，而是通过 `Surface` 输出到底层图形缓冲。

这条链路可以这样理解：

```text
Surface
  -> BufferQueue producer 端的封装

SurfaceTexture
  -> 持有 BufferQueue consumer 端

GraphicBuffer
  -> BufferQueue 中真正承载图像数据的底层图形缓冲
```

完整流程：

```text
SurfaceTexture 持有 consumer 端
        ↓
Surface 包装 producer 端
        ↓
Surface 传给 MediaCodec.configure()
        ↓
MediaCodec 作为 producer dequeueBuffer()
        ↓
拿到一个 GraphicBuffer
        ↓
硬解码器把 YUV 图像写进 GraphicBuffer
        ↓
MediaCodec queueBuffer()
        ↓
SurfaceTexture 收到新帧通知
        ↓
应用调用 updateTexImage()
        ↓
SurfaceTexture 把最新帧关联到 OES 外部纹理
        ↓
OpenGL 在 shader 中采样这帧
```

这里的“零拷贝”要准确理解：

> 零拷贝不是没有 buffer，也不是没有队列，而是应用层 CPU 不再读出 YUV，也不再通过 `glTexImage2D` 把每帧上传到 GPU。

底层图像数据不在 Java heap 里的 `byte[]` 中，而是在图形系统分配的 native graphic buffer 中，可以被硬解码器、GPU、显示系统通过句柄共享访问。

这里会遇到一个概念：`GL_TEXTURE_EXTERNAL_OES`。它不需要单独深挖，只要和普通纹理做一个最小区分：

```text
GL_TEXTURE_2D
  -> 普通纹理
  -> 通常由应用通过 glTexImage2D 上传 RGBA 等像素数据
  -> shader 中使用 sampler2D

GL_TEXTURE_EXTERNAL_OES
  -> 外部纹理
  -> 通常接收相机、MediaCodec、SurfaceTexture 这类外部图像源
  -> 底层可能是 YUV 或厂商私有格式
  -> shader 中使用 samplerExternalOES
```

一句话：

> `GL_TEXTURE_2D` 是“应用上传给 OpenGL 的普通纹理”；`GL_TEXTURE_EXTERNAL_OES` 是“外部系统组件交给 OpenGL 采样的图像”。

OES 这一块现在不需要深挖。等真正进入多级滤镜、FBO、离屏渲染、编码输出时，再补它的限制和转换方式。

### 2. OpenGL 基础知识：OpenGL、GLSL 和 Shader

三者关系：

```text
OpenGL ES
  -> CPU 侧控制 GPU 渲染管线的 API

GLSL
  -> 编写 shader 的语言

Shader
  -> 运行在 GPU 上的小程序
```

应用通过 OpenGL ES 编译、链接、绑定 shader program，并发起 draw call。真正对每个顶点、每个片元执行逻辑的是 GPU 上的 shader。

视频处理里，通常是把解码帧当作纹理输入，然后画一个矩形：

```text
视频纹理
  -> 两个三角形组成的矩形
  -> shader 采样并处理
  -> 写入 framebuffer
```

### 3. GPU 处理视频画面的基本流程

#### 3.1 GPU 处理视频画面的流程与每一步作用

简化后的 GPU 渲染管线可以这样看：

```text
顶点数据
  -> 顶点 shader
  -> 图元装配
  -> 光栅化
  -> 片元 shader
  -> 测试 / 混合
  -> 写入 framebuffer
```

每一步的作用：

| 阶段 | 作用 |
|---|---|
| 顶点数据 | 提供矩形的顶点坐标和纹理坐标。视频画面通常画在一个由两个三角形组成的矩形上。 |
| 顶点 shader | 处理顶点坐标和纹理坐标，决定画面的位置、大小、旋转、缩放、裁剪关系。 |
| 图元装配 | 把顶点组织成图元，视频画面常见的是两个三角形拼成一个矩形。 |
| 光栅化 | 把三角形覆盖的区域转换成一批片元，并为每个片元插值得到纹理坐标。 |
| 片元 shader | 根据纹理坐标去视频纹理采样，计算当前片元的颜色，可做滤镜、水印、颜色处理。 |
| 测试 / 混合 | 丢弃不该显示的片元，或把当前颜色和目标缓冲中已有颜色混合。 |
| 写入 framebuffer | 把最终颜色写入当前绑定的 framebuffer；如果目标是 Surface，底层可能写入 Surface 背后的 GraphicBuffer。 |

#### 3.2 顶点 shader 管什么

顶点 shader 主要处理：

```text
顶点坐标
  -> 决定这个矩形画到哪里、画多大、怎么旋转、怎么缩放

纹理坐标
  -> 决定从视频纹理的哪一块取图像
```

所以，几何类操作通常优先想到顶点坐标或纹理坐标：

```text
旋转
缩放
镜像
裁剪
改变显示区域
```

顶点 shader 会输出 `gl_Position`，并把纹理坐标传给片元 shader。光栅化阶段会自动插值，使每个片元都拿到自己的纹理坐标。

#### 3.3 片元 shader 管什么

片元可以近似理解为“候选像素”，但不完全等于最终像素。因为片元后面还可能经过裁剪、深度测试、模板测试、混合等阶段，最后才写成 framebuffer 里的像素。

片元 shader 主要做：

```text
拿到插值后的纹理坐标
  -> 去 OES / 2D 纹理采样
  -> 计算当前片元的颜色
  -> 输出颜色值
```

颜色类操作通常发生在片元 shader：

```text
灰度
反色
亮度
对比度
滤镜
水印混合
颜色矩阵
```

注意，如果输入是 OES 外部纹理，底层图像不一定是标准 RGBA；但 shader 采样后拿到的是可用于颜色计算的结果，可以在当前理解层面近似看成颜色值。

### 4. OpenGL 的输出：EGL 把原生 Surface 接给 OpenGL

前面解决的是 OpenGL 从哪里读：

```text
SurfaceTexture + OES texture
  -> 让 OpenGL 采样解码出来的视频帧
```

但 OpenGL ES 本身是跨平台图形 API，它不直接绑定 Android 的窗口系统。Windows、Linux、Android 都可以有 OpenGL / OpenGL ES，但它们底层的窗口、buffer 和显示系统都不同。

所以中间需要一层适配：

```text
OpenGL
  -> 跨平台图形 API，负责怎么画

EGL
  -> OpenGL ES 和原生窗口系统之间的适配层

Android Surface
  -> Android 原生窗口 / BufferQueue 入口
```

在 Android 视频链路里，EGL 的关键作用是：

> 把 Android 的 `Surface` 包装成 OpenGL ES 可以渲染的 `EGLSurface`，并把它和当前 `EGLContext` 绑定起来。

所以这句话要说准确：

> `SurfaceTexture / OES texture` 解决“OpenGL 从哪里采样视频帧”；`EGLSurface` 是 EGL 基于 Android `Surface` 创建出来的渲染目标，让 OpenGL 的绘制结果能进入这个 `Surface` 背后的 BufferQueue。

如果要把 OpenGL 处理后的画面送给编码器，就需要先从编码器创建一个 input Surface：

```kotlin
val encoder = MediaCodec.createEncoderByType("video/avc")

val encodeFormat = MediaFormat.createVideoFormat("video/avc", width, height)
encodeFormat.setInteger(MediaFormat.KEY_BIT_RATE, bitRate)
encodeFormat.setInteger(MediaFormat.KEY_FRAME_RATE, frameRate)
encodeFormat.setInteger(MediaFormat.KEY_I_FRAME_INTERVAL, 1)
encodeFormat.setInteger(
    MediaFormat.KEY_COLOR_FORMAT,
    MediaCodecInfo.CodecCapabilities.COLOR_FormatSurface
)

encoder.configure(
    encodeFormat,
    null,
    null,
    MediaCodec.CONFIGURE_FLAG_ENCODE
)

val encoderInputSurface = encoder.createInputSurface()
encoder.start()
```

这个 `encoderInputSurface` 可以理解为：

> 编码器暴露出来的输入端原生 `Surface`。OpenGL 不能直接画到 Android `Surface`，需要先由 EGL 基于它创建 `EGLSurface`。

然后 EGL 把这个 `Surface` 包装成 `EGLSurface`：

```text
eglCreateWindowSurface(display, config, encoderInputSurface, attrs)
```

再把它设为当前绘制目标：

```text
eglMakeCurrent(display, eglSurface, eglSurface, eglContext)
```

从这一刻开始，OpenGL 的 draw call 会写入这个 `encoderInputSurface` 背后的 buffer。

当一帧画完后：

```text
eglSwapBuffers(display, eglSurface)
```

可以理解为：

> 当前这一帧画完了，把 buffer 提交给 Surface 背后的消费者。

这里的消费者就是：

```text
MediaCodec Encoder
```

所以，OpenGL 的输出没有一个“默认进入编码器”的位置。它写到哪里，取决于当前绑定的 framebuffer：

```text
eglMakeCurrent() 绑定的是屏幕相关 EGLSurface
  -> glDrawArrays() 的结果写到屏幕 Surface 背后的 buffer
  -> 最终用于显示

eglMakeCurrent() 绑定的是 encoder input Surface 创建的 EGLSurface
  -> glDrawArrays() 的结果写到编码器 input Surface 背后的 buffer
  -> eglSwapBuffers() 后交给 MediaCodec Encoder

当前绑定的是 FBO
  -> 绘制结果写到 FBO 绑定的纹理或 renderbuffer
  -> 不会直接显示，也不会直接编码
```

如果没有把 EGL 的 draw surface 切到编码器创建的 input Surface，GPU 处理结果就不会进入编码器。它可能只是画到了屏幕 Surface，也可能画到了某个离屏 FBO，取决于当前 OpenGL 绑定的目标。如果当前没有有效的 `EGLSurface` 或 framebuffer，绘制调用就没有有效输出，甚至可能产生 OpenGL 错误。

一句话记：

> OpenGL 永远写入当前绑定的 framebuffer；如果要让编码器拿到画面，就必须用 encoder input Surface 创建 `EGLSurface`，绘制时 `eglMakeCurrent()` 到它，并通过 `eglSwapBuffers()` 提交这一帧。

### 5. 加水印保存成 MP4 的完整链路

`MediaMuxer` 只能写入已经编码好的 sample，例如 H264 / AAC。它不能直接写 OpenGL 处理后的原始图像。

如果只是把旧 MP4 里的压缩帧搬到新 MP4：

```text
MediaExtractor
  -> MediaMuxer
```

画面内容不会发生变化。

但加水印、滤镜、裁剪、缩放这些操作改变的是解码后的图像内容，所以保存成新 MP4 时必须重新编码：

```text
H264 压缩帧
  -> 解码
  -> 原始图像
  -> OpenGL 修改像素结果
  -> 重新编码成 H264
  -> Muxer 封装
```

如果只是播放预览：

```text
MediaCodec Decoder
  -> SurfaceTexture
  -> OES texture
  -> OpenGL
  -> 屏幕 Surface
```

如果要加水印并保存成新 MP4：

```text
MediaExtractor
  -> 读取 H264/AAC 压缩帧

MediaCodec Decoder
  -> 解码 H264
  -> 输出到 decoder output Surface

SurfaceTexture / OpenGL
  -> 接收解码帧作为 OES texture
  -> shader 做水印、滤镜、裁剪、缩放
  -> 绘制到 encoder input Surface

MediaCodec Encoder
  -> 从 input Surface 接收 OpenGL 画好的图像
  -> 编码成 H264/H265 压缩帧

MediaMuxer
  -> addTrack(encoderOutputFormat)
  -> writeSampleData(encodedBuffer, bufferInfo)
  -> 生成新 MP4
```

这里要分清两个 Surface：

```text
Decoder output Surface
  -> 解码器的输出口
  -> 解码器生产图像，SurfaceTexture / OpenGL 消费图像

Encoder input Surface
  -> 编码器的输入口
  -> OpenGL 生产图像，编码器消费图像
```

所以，解码和编码是两条方向相反的 Surface 链路：

```text
解码：
MediaCodec Decoder
  -> Surface
  -> SurfaceTexture / OpenGL

编码：
OpenGL
  -> Surface
  -> MediaCodec Encoder
```

因此，凡是改变画面像素内容，并且要保存成新视频文件，通常都必须走：

```text
解码 -> OpenGL 处理 -> 编码 -> 重封装
```

面试口径：

> `MediaMuxer` 只能封装已经编码好的压缩帧，不能直接封装 OpenGL 处理后的图像。加水印或滤镜发生在解码后的图像层，会改变每一帧的像素内容，所以不能直接搬运旧 H264 sample。正确链路是用 `MediaCodec Decoder` 解码，把帧通过 `SurfaceTexture` 交给 OpenGL 处理，再把 OpenGL 的渲染结果画到 `MediaCodec Encoder` 的 input Surface，由编码器重新编码成 H264，最后通过 `MediaMuxer` 写入新 MP4。

## 当前模块面试复述

可以这样完整复述：

> Android 视频处理里，OpenGL 主要负责解码后图像帧的 GPU 处理。相比 `getOutputBuffer()` 拿 YUV 再上传 GPU，Surface 路线会让 `MediaCodec` 把解码结果写入底层 `GraphicBuffer`，通过 `BufferQueue` 交给 `SurfaceTexture`，再由 `SurfaceTexture` 绑定到 `GL_TEXTURE_EXTERNAL_OES` 外部纹理，OpenGL 可以直接采样这帧，避免 CPU 读 YUV 和每帧 `glTexImage2D` 上传。OpenGL 侧通过顶点 shader 控制画面位置、大小、旋转、裁剪，通过片元 shader 对纹理采样并计算颜色，从而实现滤镜、水印等处理。如果只是预览，EGL 可以基于屏幕相关的 `Surface` 创建 `EGLSurface`；如果要保存成新 MP4，EGL 可以基于编码器的 input Surface 创建 `EGLSurface`，OpenGL 的绘制结果提交给编码器，再由 `MediaCodec Encoder` 编码成 H264，最后交给 `MediaMuxer` 封装。
