# 音视频基础：从“原始数据”到“可播放文件”

> 前置知识：Android 基础、二进制数据、文件与流的基本概念 难度：入门 预计阅读时间：12 分钟

## 正文内容

这篇只解决一个核心问题：

> 什么是音频，什么是视频，他们的底层是什么？又是如何被压缩以便于传输的？

先把整条链路压成一行：

MP4 容器  
  -> 解封装  
  -> H264/H265 视频码流 + AAC 音频码流  
  -> 解码  
  -> YUV 视频帧 + PCM 音频帧  
  -> YUV 转 RGB 渲染到屏幕 + PCM 送 AudioTrack/音频栈播放

这行就是本课题的骨架。后面的概念都要挂回这条链路上。

### 1. 视频的本质：时间轴上的图像序列

视频不是一个神秘格式，本质是很多张图像按时间连续播放。每一张图像叫一帧。

帧 = 某一时刻的一张画面  
视频 = 帧 + 时间顺序

**帧率**回答“每秒播放多少张图”，单位是 fps。它主要影响运动是否流畅。 **码率**回答“每秒消耗多少 bit”，单位是 bps。它主要影响体积、带宽占用和压缩后保留的信息量。

常见误解是把帧率和码率混成一个东西。它们相关，但不等价：

|参数|回答的问题|主要影响|
|---|---|---|
|帧率 fps|每秒多少帧|流畅度、运动细腻程度|
|码率 bps|每秒多少数据|文件体积、带宽、压缩质量|

帧率高但码率低，画面可能流畅但糊。码率高但帧率低，单帧可能清楚但运动不顺。

### 2. 图像为什么常用 YUV，而不是只用 RGB

RGB 是显示设备最直观的颜色表达：红、绿、蓝三通道组合出颜色。屏幕最终也是按 RGB 发光。

但视频编码链路更喜欢 **YUV**：

Y = 亮度  
U/V = 色度

原因来自人眼特性：人对亮度变化更敏感，对色度细节没那么敏感。所以视频可以尽量保留 Y，压缩 U/V 的分辨率，在视觉损失不明显的前提下降低数据量。

这就是 **YUV420** 常见的原因：

YUV444：每个 Y 都有自己的 U/V  
YUV422：每两个 Y 共用一组 U/V  
YUV420：每四个 Y 共用一组 U/V

你可以把它理解成：画面轮廓和明暗尽量保留，颜色细节适当“合租”。

Android 与工程里还会遇到不同内存排布：

|格式|大致排布|常见场景|
|---|---|---|
|I420 / YUV420P|Y... U... V...|FFmpeg 解码输出常见|
|NV12|Y... UVUV...|硬件、平台链路常见|
|NV21|Y... VUVU...|Android 摄像头采集常见|

这里要抓住本质：**它们主要差在内存排布，不是画面内容的物理意义变了。**

### 3. 音频的本质：把连续声波离散化

声音在物理上是连续声波，计算机只能处理离散数字。

PCM 做的事情就是：

连续声波 -> 采样 -> 量化 -> 二进制编码 -> PCM

三步分别对应：

|步骤|做什么|关键参数|
|---|---|---|
|采样|按固定时间间隔记录振幅|采样率，如 44.1kHz/48kHz|
|量化|把连续振幅映射到有限整数级别|位深，如 16bit|
|编码|把整数值组织成二进制数据|PCM 数据流|

采样率解决“时间上取多密”，位深解决“振幅上分多细”。 声道数解决“有几路独立声音”，例如单声道、双声道。

这里要区分两个“编码”：

PCM 的编码：把量化后的采样值写成二进制  
AAC/H264 的编码：压缩音视频数据，减少体积

同一个中文词，处在不同层级。

### 4. 为什么还需要 H264 和 AAC

YUV 和 PCM 都是解码后的原始数据，体积很大。 所以存储和传输时一般要压缩：

视频：YUV -> H264/H265  
音频：PCM -> AAC/MP3

视频压缩能成立，是因为画面里有大量冗余：

空间冗余：同一帧里，大面积区域相似  
时间冗余：连续帧之间，大部分画面没变

H264 中的 I/P/B 帧就是围绕时间冗余组织的：

|帧类型|是否能独立解码|依赖关系|压缩特点|
|---|---|---|---|
|I 帧|能|不依赖其他帧|体积大，适合作为锚点|
|P 帧|不能|依赖前面的 I/P 帧|存变化，体积较小|
|B 帧|不能|依赖前后参考帧|压缩率高，但调度复杂|

**GOP** 是一组连续图像，通常从 I 帧开始。播放器 seek 时常先跳到 GOP 起点，因为那里有可独立或更稳定恢复的解码锚点。

**IDR** 是特殊 I 帧。遇到 IDR 后，解码器会丢弃旧参考链，重新开始，避免旧错误继续污染后面的帧。

### 5. AAC 的 ADIF 和 ADTS

AAC 是常见音频压缩格式。它有两类常见封装方式：

|格式|结构|更适合|
|---|---|---|
|ADIF|一个统一头部 + 连续音频数据|文件存储，从头解码|
|ADTS|每帧都有头部|流式传输、丢包恢复、seek|

判断原则很简单： 如果数据要在中间位置恢复、网络中断后继续同步，每帧带头的 ADTS 更有优势。
### 6. 软解、硬解、GPU 的职责边界

Android 里常见三个角色：

软解：CPU 跑解码算法，例如 FFmpeg 软件解码器  
硬解：专用硬件解码单元工作，Android 常通过 MediaCodec 访问  
GPU：负责渲染、YUV 转 RGB、缩放、特效等

常见误解是“GPU 解码就是硬解”。更准确地说，硬解通常指专用编解码硬件；GPU 更常出现在渲染环节。

工程判断上：

|方案|优点|风险|
|---|---|---|
|硬解 MediaCodec|省电、性能好、适合移动端|厂商差异、兼容性问题|
|软解 FFmpeg|行为更可控、格式支持广|CPU 压力大、耗电|

移动端播放器通常要有软硬解切换策略，而不是只押一个路径。

## 用五个学习视角压实这一篇

### Crossover：它本质像什么

在不假设你额外背景的前提下，只用这篇笔记内部已有类比：

|音视频概念|可迁移结构|
|---|---|
|视频帧|翻页动画书的一页|
|帧率|翻页速度|
|码率|每秒愿意花多少纸张/墨水细节|
|PCM 采样|每隔一小段时间记录一次声波高度|
|YUV420|亮度细节保留，颜色细节多人共用|
|GOP/IDR|一段视频里的重新开始点|

元模式是：**连续世界离散化 + 冗余压缩 + 按时间调度**。

### Occam：这一篇学到哪算够

本篇的目标不是写播放器，而是建立分类能力。够用标准是：

看到一个名词，能判断它是：  
容器 / 压缩编码 / 原始数据 / 时间戳 / Android 实现入口

如果暂时只复习基础，不需要深入 H264 熵编码、运动估计、OpenGL shader 或 MediaCodec 状态机。

### Prototype：最小可验证练习

先不要写完整播放器。最小原型只验证“我分得清层级”：

给一个 MP4 文件：  
1. 能说出它是容器  
2. 能说出里面可能有 H264 视频流和 AAC 音频流  
3. 能说出解码后视频是 YUV，音频是 PCM  
4. 能说出 YUV 最终要转 RGB 显示，PCM 最终进音频播放链路

如果要动手，最小 API 路径是：

MediaExtractor 拆流  
MediaCodec 解码视频到 Surface 或 ByteBuffer  
MediaCodec 解码音频到 PCM  
AudioTrack 播放 PCM
