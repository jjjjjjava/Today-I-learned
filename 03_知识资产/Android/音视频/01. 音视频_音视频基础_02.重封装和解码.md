# 重封装和解码：从「给视频加水印」倒推整条链路

> 前置知识：MP4 / H264 / AAC / YUV / PCM 的基本分层
> 难度：进阶
> 预计阅读时间：15 分钟

## 这篇要回答的那个问题

不背链路，先抛一个真问题，让链路被它一节一节逼出来：

> **给定一个 MP4，如果让我们给视频画面加一个水印，再导出成新的 MP4，该怎么处理？**

把它拆成四问，整篇就是顺着这四问往下推：

1. **MP4 是什么？里面的音视频流怎么拽出来？** —— 逼出**解封装**
2. **拽出来的流能直接加水印吗？** —— 逼出**解码**
3. **加完水印的画面能直接塞回容器吗？** —— 逼出**编码 + 重封装**
4. **如果不是导出，而是边播边看呢？** —— 逼出**同步**

整条链路先压成一行，后面每一问都在往这条线上挂节点：

```text
MP4 ─解封装→ H264/AAC 压缩帧 ─解码→ YUV/PCM ─处理(水印)→ ─编码→ H264 ─重封装→ 新 MP4
                                                  └ 若是「边播边看」，这里换成 ─同步→ 渲染/播放
```

一个核心判断先记住：**只要不改画面内容，重封装根本不用解码**（H264 还是 H264，AAC 还是 AAC，只是从旧容器搬到新容器）。只有要改画面——加水印、滤镜、转码、改分辨率、精确裁到非关键帧——才被迫走「解码 → 处理 → 重编码 → 封装」这条重路。

## 问题一：MP4 是什么，怎么把流拽出来（解封装）

### 1.1 MP4 容器的最小模型

MP4 是树状结构，主要由两类信息组成：**元数据**（编码格式、索引）和**实际媒体数据**。

```text
MP4
├── moov：元数据，描述轨道、编码格式、解码配置、每帧位置和时间
│   ├── trak：视频轨道
│   │   └── stbl：sample table
│   │       ├── stsd：sample description，记录编码格式和解码配置，如 avc1/avcC
│   │       └── 其他表：记录 sample 大小、时间戳、关键帧、数据偏移等索引
│   └── trak：音频轨道
│       └── stbl：sample table
│           ├── stsd：sample description，记录编码格式和解码配置，如 mp4a/esds
│           └── 其他表：记录 sample 大小、时间戳、数据偏移等索引
└── mdat：媒体数据，真正存放 H264/AAC 等压缩数据
```

`stsd` 里记录的编码格式和解码配置，会被 `MediaExtractor.getTrackFormat()` 解析成 `MediaFormat`，给到我们：

```text
MediaFormat.KEY_MIME = video/avc
MediaFormat.KEY_WIDTH / KEY_HEIGHT
csd-0 / csd-1   // SPS / PPS，解码器靠它知道「怎么解」
```

对应关系：

| 结构 | 作用 | Android API 对应 |
|---|---|---|
| `moov` | 文件目录和索引 | `setDataSource()` 后被解析 |
| `trak` | 一条音频/视频/字幕轨道 | `trackCount` / `getTrackFormat()` |
| `stbl` | sample 的时间、大小、位置、关键帧信息 | `sampleTime` / `sampleFlags` / 内部读取索引 |
| `mdat` | 真正的压缩数据 | `readSampleData()` 的读取来源 |

所以：`getTrackFormat()` 能拿到 `mime`，是因为它读的是 `moov` 里的轨道描述；`readSampleData()` 读到 H264/AAC，是因为它按 sample table 到 `mdat` 里取真正的压缩帧。

### 1.2 解封装：MediaExtractor 怎么做

> 解封装本质：`MediaExtractor` 从容器里取出压缩帧和轨道信息。

第一步，创建并设置数据源（它会自动解析容器）：

```text
MediaExtractor()
setDataSource(path)
```

第二步，遍历并选择轨道。**判断轨道类型看 mime 的前缀**——`video/` 开头是视频轨，`audio/` 开头是音频轨（不是 `/video`）：

```text
for i in 0 until trackCount:
    format = getTrackFormat(i)
    mime = format.getString(KEY_MIME)
    // video/avc        -> H264 视频轨
    // audio/mp4a-latm  -> AAC 音频轨
selectTrack(videoTrackIndex)
```

第三步，读取压缩帧。**这里要钉死一个 API 细节**：

```text
size = readSampleData(byteBuffer, 0)   // 返回值是 size(int)，把压缩帧读进 byteBuffer
pts  = sampleTime                       // PTS 走单独的属性 getSampleTime()
flag = sampleFlags                      // 关键帧等标志走 getSampleFlags()
advance()                               // 移到下一帧
```

> ⚠️ **Extractor 这边没有 BufferInfo**。`readSampleData` 只吃 `(buffer, offset)`、只返回 size；时间戳和 flags 是另外两个属性拿的。`BufferInfo` 是 MediaCodec / MediaMuxer 那边才有的东西，别在这里就把它请出来。

读出来的是 **H264 压缩帧**，不是 YUV、更不是 RGB。

## 问题二：拽出来的能直接加水印吗（解码）

**不能。** 拽出来的是 H264 压缩帧（熵编码后的数据），画面信息被压没了，必须先解码还原成 YUV 像素，才能在上面画水印。

> 解码本质：`MediaCodec` 把 H264/AAC 压缩帧，还原成可渲染/播放的原始数据（YUV / PCM）。

### 2.1 MediaCodec 是生产者-消费者模型

它有输入、输出两个缓冲区队列：我们把压缩帧送进**输入缓冲区**，MediaCodec 解码后把 YUV/PCM 放进**输出缓冲区**，我们再取走。

**先分清两个东西，这是最容易混的地方：**

| | 谁给的 | 给几次 | 内容 |
|---|---|---|---|
| `MediaFormat` | `getTrackFormat()` → `configure()` 时传 | **整条轨道一次** | 「怎么解」：分辨率、`csd-0/csd-1`(SPS/PPS) |
| `BufferInfo` | 每帧解码输出时 | **每帧一份** | 「这一帧的标签」：size / presentationTimeUs / flags |

> ⚠️ 解码器靠 **MediaFormat 里的 SPS/PPS** 才知道码流该怎么解，这个在 `configure(format, surface, null, 0)` 时一次性给。**不是从 BufferInfo 里拿**——BufferInfo 只带单帧的时空标签。

### 2.2 输入端：填进去还要「交回去」

```text
inIndex = dequeueInputBuffer()           // 拿到一个空输入 buffer 的 index
inBuf   = getInputBuffer(inIndex)         // 拿到实际 buffer
size    = extractor.readSampleData(inBuf, 0)
queueInputBuffer(inIndex, 0, size, sampleTime, flags)   // ★ 必须这一步！
extractor.advance()
```

> ⚠️ 填完 input buffer **不会自动解码**。必须 `queueInputBuffer(...)` 把它交回给解码器，解码才会发生；而且 **PTS 就是在这一步随帧送进去的**（`sampleTime` → 这一帧的 presentationTimeUs）。

### 2.3 输出端：配不配 Surface 两条路

```text
outIndex = dequeueOutputBuffer(bufferInfo)
```

- **不配 Surface**：`getOutputBuffer(outIndex)` 取出 YUV，自己在 CPU 侧处理，再 `releaseOutputBuffer(outIndex, false)`。
- **配了 Surface**：不取 YUV，直接 `releaseOutputBuffer(outIndex, true)`，把这一帧推给 Surface 去渲染/被消费。

加水印走的就是配 Surface 的零拷贝路线。

### 2.4 加水印：GPU 零拷贝（这段是 OpenGL 复习已掌握的）

把解码器的输出 Surface 接到 GPU 上：

```text
1. 生成一个 OES 纹理 id → 用它创建 SurfaceTexture → 包成 Surface
2. decoder.configure(format, surface, null, 0)   // 解码结果直接进这个 Surface
3. 每帧 releaseOutputBuffer(index, true)
     → 触发 onFrameAvailable
     → surfaceTexture.updateTexImage()  // 更新 OES 纹理的内容，指向这一帧
4. shader 采样 OES 纹理（采样时隐式完成 YUV → RGB）
     → 视频帧作底图，另一张 2D 纹理（「万店掌」水印）以半透明混合模式叠在上面
```

> 解码端的方向是：**「我给解码器一个 Surface，让它往里写」**。记住这个方向，下一问的编码端正好相反。
>
> 术语精度：更新纹理内容的方法是 `SurfaceTexture.updateTexImage()`。

至此画面上有水印了，但它现在是 GPU 里的像素，还在内存/显存里，不是文件。

## 问题三：加完水印能直接塞回容器吗（编码 + 重封装）

**不能。** 容器（mdat）只收压缩帧，不收裸像素。加完水印的画面要先**重新编码**成 H264，再**重封装**进新容器。

### 3.1 编码：方向和解码相反

> 解码是「我给解码器 Surface」；编码是「**编码器给我 Surface**」。

```text
1. encoder = MediaCodec(编码器)，configure(编码 format)
2. inputSurface = encoder.createInputSurface()   // ★ 编码器吐出一个输入 Surface
3. 用 EGL 把 inputSurface 设成渲染目标，把带水印的画面渲染到它上面
4. 编码器自己取走画面、编码成 H264
5. dequeueOutputBuffer(bufferInfo) → 拿到编码后的 H264 压缩帧
```

> ⚠️ 离线导出**不走 GLSurfaceView**（那是给屏幕预览用的）。导出场景要 `encoder.createInputSurface()` 拿到编码器的输入 Surface，往它上面画。
>
> 备注：`createInputSurface()` 的完整闭环（EGL 怎么把这个 Surface 接进渲染管线）属于「编码端」专题，本篇先记住方向和定位。

### 3.2 重封装：MediaMuxer 怎么做

> 重封装本质：`MediaMuxer` 把已经编码好的 H264/AAC 压缩帧，按正确的轨道格式、时间戳、标志写进新容器。

```text
1. muxer = MediaMuxer(outputPath, MUXER_OUTPUT_MPEG_4)
2. videoTrack = muxer.addTrack(videoFormat)   // 声明轨道元数据，不是写数据
   audioTrack = muxer.addTrack(audioFormat)
3. muxer.start()
4. muxer.writeSampleData(trackIndex, byteBuffer, bufferInfo)
```

`addTrack(format)` 不写媒体数据，它是在**声明新 MP4 的轨道元数据**（有哪些轨、各自什么编码、宽高、采样率……）。但这里的 `format` 来源**要分两种轨道**：

| 轨道 | 改没改画面 | addTrack 的 format 从哪来 |
|---|---|---|
| 音频轨 | 没动，直接搬运 | 复用 `extractor.getTrackFormat()` 的旧 format |
| 视频轨 | **重编码过** | 用**编码器**抛出 `INFO_OUTPUT_FORMAT_CHANGED` 后 `encoder.getOutputFormat()` 的**新 format** |

> ⚠️ 视频重编码后分辨率、`csd` 都可能变了，**不能拿解封装时的旧 format 去 addTrack**，否则元数据和实际码流对不上。只有没动的音频轨才能直接复用旧 format。

`writeSampleData` 的 `byteBuffer` 来自编码器的 `dequeueOutputBuffer`，`bufferInfo` 告诉新容器这帧的 size / PTS / 关键帧标志。

### 3.3 对照：不改画面就别解码

如果需求只是「换个容器」而不改画面，整条重路全省掉：

```text
extractor.readSampleData → byteBuffer(H264，原样)
muxer.writeSampleData(byteBuffer, bufferInfo)
// H264 还是 H264，AAC 还是 AAC，无解码、无编码
```

## 问题四：如果不是导出，而是边播边看（同步）

导出是离线处理，不涉及现实时间。但**播放必须按播放时间轴发生**——解码可以提前跑，渲染不能乱跑。这就是同步要解决的。

### 4.1 两个时间，别搞反

| | 是什么 | 一句话 |
|---|---|---|
| 帧的 **PTS** / presentationTimeUs | **应然**：这一帧「应该在第几 ms 被显示」 | **不是**解码时间、不是处理时间、不是「读到就立刻渲染」 |
| **播放时钟** (master clock) | **现实**：现在真实播到了第几 ms | 由音频实际进度或系统时间推出来 |

> 这篇最核心的一句：**PTS 是目标呈现时刻（应然），不是它被解码/处理的时刻。** 视频解码速度可能远快于正常播放速度，所以不能按解码速度直接显示。

### 4.2 选哪个当主时钟

**首选音频主时钟**——音频是连续流，`AudioTrack` 和音频硬件稳定消费 PCM，进度基本贴合现实；视频是离散帧，更适合去等/追/丢。

```text
audioClockUs = firstAudioPtsUs + playedFrames * 1_000_000 / sampleRate
```

`playedFrames` 是**实际播放出去**的 PCM 帧数（优先 `AudioTrack.getTimestamp()`，简化用 `playbackHeadPosition`）——注意是「播放到的」，不是 `write()` 写进去的（写进去 ≠ 已播放）。

**没有音频轨**时才退回系统时钟：

```text
baseSystemTimeUs = System.nanoTime() / 1000   // 播放起点记一次
currentClockUs   = firstVideoPtsUs + (System.nanoTime()/1000 - baseSystemTimeUs)
```

### 4.3 渲染决策：早了等，到了渲，晚了丢

```text
diffUs = videoPtsUs - clockUs
diffUs > 0          -> 视频早了：等 diffUs
diffUs ≈ 0          -> releaseOutputBuffer(index, true)   渲染
diffUs < -阈值      -> releaseOutputBuffer(index, false)  丢帧追赶
```

```kotlin
val videoPtsUs = bufferInfo.presentationTimeUs
val clockUs = firstAudioPtsUs + playedFrames * 1_000_000L / sampleRate
val diffUs = videoPtsUs - clockUs
when {
    diffUs > 0       -> { Thread.sleep(diffUs / 1000); codec.releaseOutputBuffer(outputIndex, true) }
    diffUs < -50_000 -> { codec.releaseOutputBuffer(outputIndex, false) }   // 晚太多，丢帧
    else             -> { codec.releaseOutputBuffer(outputIndex, true) }
}
```

**为什么让视频追音频，而不是反过来**：音频一旦等待/跳变会爆音、很刺耳；视频丢一两帧人眼基本无感。所以拿音频当基准、让视频去对齐它。

### 4.4 边界：离线处理不是同步问题

回到我们的主问题——加水印导出时，**不是在真实播放**，不需要 `AudioTrack`、不需要主时钟。音频不变就直接搬：

```text
读：sampleData + sampleTime
写：bufferInfo.set(0, size, sampleTime, flags) → writeSampleData
```

如果做裁剪，再统一对时间戳重基准：

```text
outPtsUs = inSampleTimeUs - startPtsUs
```

## 当前模块面试口径

> **解封装 / 重封装**：MP4 里 `moov` 存轨道和 sample 索引，`mdat` 存真正的 H264/AAC。`MediaExtractor` 用 `getTrackFormat()` 读轨道格式、按 `mime` 前缀（`video/`、`audio/`）判断轨道类型，`selectTrack()` 选中后按 sample table 从 `mdat` 里 `readSampleData()` 读出压缩帧——PTS、flags 走 `sampleTime` / `sampleFlags`，Extractor 这边没有 BufferInfo。重封装时 `MediaMuxer.addTrack(format)` 声明新轨道元数据，`writeSampleData()` 写压缩帧。不改画面就不用解码。

> **解码**：解码器输入端吃 `readSampleData()` 读出的 H264/AAC，`dequeueInputBuffer` → `getInputBuffer` 填充后必须 `queueInputBuffer()`（PTS 随这步送进去）才会解码。「怎么解」靠 `configure()` 时传的 MediaFormat（含 SPS/PPS = csd-0/csd-1），不是 BufferInfo。输出端不配 Surface 就 `getOutputBuffer` 拿 YUV/PCM；视频播放/处理常配 Surface，`dequeueOutputBuffer` 后 `releaseOutputBuffer(index, true)` 把帧推给 Surface，少一次 CPU 拷贝。

> **编码 + 重封装**：加水印要改画面，必须解码成 YUV → GPU 叠水印 → 重编码。编码端方向和解码相反：`encoder.createInputSurface()` 吐出输入 Surface，用 EGL 渲染到它上面，编码器产出 H264。重封装时**重编码过的视频轨**要用编码器输出的新 format（`INFO_OUTPUT_FORMAT_CHANGED` 后 `getOutputFormat()`）去 `addTrack`，没动的音频轨才能复用旧 format。

> **同步**：`presentationTimeUs` 是这一帧应当展示的媒体时间（应然），不是解码/处理时间。播放时维护一个播放时钟（首选音频主时钟，`audioClockUs = firstAudioPtsUs + playedFrames * 1e6 / sampleRate`，`playedFrames` 取实际播放进度），用 `diff = videoPtsUs - clockUs` 决策：早了等、到了渲、晚太多丢帧。让视频追音频，因为音频等待/跳变会爆音。无音频轨时用 `System.nanoTime()` 建系统时钟。

1. `getTrackFormat()` 能拿到 `mime`，`readSampleData()` 读到的却是 H264/AAC 压缩帧——分别因为它们读的是 MP4 的哪一部分？
2. 解码器靠什么知道「这条码流该怎么解」？这个信息放在 MediaFormat 还是 BufferInfo 里？为什么？
3. 填完 input buffer 后如果忘了 `queueInputBuffer()`，会发生什么？PTS 是在哪一步交给解码器的？
4. 加水印导出时，给编码器的 Surface 从哪来？和给解码器的 Surface 在「谁创建、谁往里写」上有什么相反之处？
5. 重封装时，视频轨的 `addTrack(format)` 能不能直接复用解封装拿到的旧 format？音频轨呢？为什么不一样？
6. 为什么说 PTS 是「展示时间」而不是「解码/处理时间」？
7. 视频帧 PTS = 1000ms，但音频时钟才走到 800ms，这帧应该等、渲、还是丢？换成音频时钟已到 1100ms 呢？
8. 为什么同步通常让视频追音频，而不是音频追视频？

10. 没有音频轨道时，用什么当播放时钟？
11. 离线加水印时为什么不需要音频主时钟？音频不变时 `sampleTime` 怎么写进新文件？做裁剪又要怎么重基准？
