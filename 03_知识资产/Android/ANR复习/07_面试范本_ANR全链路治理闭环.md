## 一、主答范本（约 2.5 分钟，口语）

**开场定位：**

> 我们的 ANR 治理不是单点救火，是一套「四层防线 + 救火闭环」的飞轮：防线从代码合入前一直排到线上，越早的防线越便宜；漏网的进救火闭环，救火的教训再回填成更靠前的防线。我按一个问题的生命周期从左到右讲。

**第①层 · 合入前静态检测：**

> 最便宜的一层。自定义 lint 扫主线程风险模式——主线程 `runBlocking`、同步 IO、`Application.onCreate` 里直接同步 `SDK.init()`；debug 包和自动化环境全程开 StrictMode。再加制度卡口：CODEOWNERS 把 Application、主进程四大组件的代码划给稳定性 owner 强制 review；新 SDK 接入要过 checklist——是否主线程同步初始化、init 耗时有没有实测数据。

**第②层 · 线下自动化测试：**

> CI 上跑 UI 自动化 + monkey 扫核心路径。关键认知：ANR 是低概率尾部事件，CI 很难直接复现它，所以 CI 拦的是它的**先导指标——主线程占用**：Looper 慢消息超阈值、StrictMode 抓到主线程 IO，直接 fail。把「ANR」翻译成「主线程长消息」，它就变成可自动化判定的东西了。

**第③层 · 灰度：**

> 新版本灰度期看 ANR 率，但不看绝对值，看**灰度组 vs 对照组横向对比**——纵向比上线前后会被版本、节假日这些混杂变量污染。判收敛三条件缺一不可：**最小样本量**防小数定律的偶然波动；**最短观察窗口**要覆盖完整使用周期（工作日+周末），防止把自然低谷当成生效；**比率下降阈值**——两组比率差过预设降幅（如相对降 ≥50%）才算数，防止把统计噪声当疗效。超标就暂停扩量。我们是 toB 场景、没有完整灰度平台，落地是服务端维护企业 ID 白名单、客户端登录时带企业 ID 取开关状态，不发版就能调放量；全量 = 白名单改「全部」。

**第④层 · 线上常态化监控：**

> 全量后靠常态化监控接长尾。我们用 Bugly，它本质是个**进程内旁观者**，能力和局限都从「进程边界」一句话推出来：watchdog 往主线程 post 探活消息发现疑似卡死；轮询 `getProcessesInErrorState()` 定性真 ANR——系统对第三方 App 没有 ANR 广播；抓 `Thread.getAllStackTraces()` 的 Java 栈。局限同样推出来：漏报 Input ANR（超时判在系统侧 InputDispatcher 的 waitQueue，不经过 MessageQueue，探活消息照常被处理）；拿不到系统级 CPU（8.0 起 /proc 受限）；5s 固定采样和 ANR 时刻不对齐，常抓到主线程 Native 态趴 `nativePollOnce` 的干净帧。要时机精确就走主动介入：Matrix 拦 SIGQUIT，handler 只往 pipe 写一字节，dump、注销 handler、`kill` 补发都在 catcher 普通线程里顺序执行、时序可控——补发那一刻 handler 必已卸载，SignalCatcher 稳定收到，系统流程不被破坏。

**救火闭环（发现 → 归因 → 治理）：**

> 告警触发——ANR 率突增或单 issue 爆量——分发到我。归因按 SOP：**单帧不定案，聚合才定案**。
> 第一步聚合分诊：沿**设备轴**（分布均匀→怀疑代码；集中某机型→怀疑 ROM 兼容；集中低端机→资源紧张放大临界代码）和**入口轴**（集中某页面→那条业务链路）读分布——这是**共性归因**；爆量时间点和版本/补丁上线对齐——**爆发归因**；高影响面单 issue 深挖 trace——**单点归因**。
> 然后：**定性**（类型与阈值语境从 shortMsg 拿：Service 前台 20s/后台 200s、Broadcast 5s/60s、Provider 10s、Input 5s）→ **验伪**（`nativePollOnce` 干净帧作废换样本）→ **判态归因**三条路：RUNNABLE + 耗时栈 = 自己太忙（我们修过的多在这：主线程同步 release 播放器、runBlocking、存相册 IO）；BLOCKED + waiting to lock = 锁链追踪，拿锁地址全局搜持锁线程，追到环即 AB-BA 死锁；环境类用代理证据（线程数暴多 = 进程内卷；多样本落点随机 + 低端机集中 = 进程外挤压）。
> **治理：动态止损优先于修代码。** 预埋降级开关的，远程一键关问题功能，秒级止血零发版；没开关的走热修复，patch 按条件灰度下发，同样走对照组 + 收敛三条件验证——**二次爆炸就灰度置零停止放量，更严重就打新 patch 回滚旧的**；最后才是线下修复合入下个版本。

**回填收尾：**

> 闭环最后一步不是「修完了」，是**回填**：这次靠线上监控才发现的，下次能不能 lint 阶段就拦住？比如主线程存相册 IO 的 issue，修完后 lint 规则和 SDK checklist 都加了对应条目。防线越转越密——这就是飞轮。字节公开数据：抖音/头条崩溃率两年降 30%+，靠飞轮转很多圈，不是单次治理。

## 二、toB 收敛判据（灰度段被追问「试点企业才一两家怎么判收敛」时用）

样本量撑不起统计对比时换三层判据，不单靠客户沉默：

1. **确定性复现**：用归因结论写复现用例，测试环境验证 fix 后不再触发——不依赖线上样本量；
2. **自有监控过滤归零**：Bugly 后台按该 issue 指纹（stack 签名）+ 企业 ID 过滤，看观察窗口内命中是否真归零——客观数据；
3. **企业沉默仅作补充**，且先确认对方窗口期内确实用过触发场景——沉默是主观且滞后的信号。

## 四、讲述策略

1. **时间紧的裁剪顺序**：开场定位 + 救火闭环 + 回填（约 80 秒）→ 防线待追问展开。差异化竞争力在归因 SOP 和闭环，防线是抬高度的框架。
2. **诚实口径**（06 篇验证过的策略）：Bugly 机制带「闭源、行为观察还原」前提；灰度主动亮 toB 落地。暴露真实数据边界 = 证明真干过。
3. **和启动优化项目的互文**：被问「除了 ANR 还治理过什么」，同一套四层防线换掉具体工具就是启动防劣化版本（lint/CODEOWNERS → Macrobenchmark CI 卡口 → 灰度对比 15% 停扩量 → 阶段埋点+慢消息两级定位），体系复用本身就是加分点。
