> 前置知识：第 4、5 篇（Bugly 三组件、SIGQUIT 机制、三步分析法）
> 难度：实战（面试口语版）
> 预计阅读时间：10 分钟
> 缘起：2026-07-02 二复。主链路已顺畅，但复述暴露 8 处勘误（最大的三处：①系统无 ANR 广播 ②进程内拿不到系统 CPU ③空闲主线程是 Native 态非 Sleeping），且原 SOP 第一步「看系统 CPU」是你实际从未执行过的步骤。本篇按真实数据边界重构成可直接开口的版本。

## 重构原则（为什么这版更受面试官青睐）

你原版的问题不在知识量，在**口径与事实不符**：说「收 ANR 广播」「第一步看系统 CPU」，追问一句就塌。重构版的核心是一根主线——

> **Bugly 是一个「进程内的旁观者」，它的全部能力和全部局限，都从「进程边界」这一句话推出来。**

面试官听到你用一个原理推出一串结论，比听你背一串组件名的评价高一档。

## 一、主答范本（约 90 秒，口语）

> 我们线上用 Bugly 做 ANR 监控，按影响用户数排序治理。先说它大致怎么工作——**Bugly 闭源，下面是根据行为观察 + 公开资料还原的机制，不是读过源码的确定结论**，这个前提我会带着说，避免被当成"我知道内部实现"。
>
> 这类 ANR 监控 SDK **通常会组合几类手段**，Bugly 大致也是这个组合：
>
> 一是**主线程 watchdog/Handler 探测**：往主线程 post 一条消息、定时检查是否被处理，用来发现"疑似长时间无响应"——这是最通用、最容易自己实现的一招，是核心。
>
> 二是**在合适时机 dump 线程栈、线程状态、设备信息**：疑似卡死时用 `Thread.getAllStackTraces()` 这类 API 抓自身进程的全线程 Java 栈暂存——这一步天然只能拿到 **Java 栈**，拿不到 native。
>
> 三是**通过 `ActivityManager.getProcessesInErrorState()` 做定性确认**：轮询查自己进程是否真的被 AMS 标成 `NOT_RESPONDING`，确认是真 ANR 才上报，同时能拿到 `shortMsg`/`longMsg`——平台 issue 标题里的 reason 就是这么来的。系统对第三方 App 没有 ANR 广播，这一步只能靠轮询，不是收广播。
>
> 有些 SDK 还会用 **FileObserver 监听 `/data/anr/`**，或用 **SIGQUIT hook** 辅助捕获系统的 ANR trace——但这条路受系统版本和权限限制很大（高版本 SELinux 收紧后基本读不到），不能说所有版本都可靠，**更像历史方案或兜底手段，不是核心机制**，不该放在第一位讲。
>
> 不管具体实现细节如何，这类"进程内旁观者"方案有个**共同的能力边界**：拿不到系统级 CPU（8.0 起 `/proc` 挂了 hidepid、SELinux 挡了 `/proc/stat`，只能读自己进程的）；容易漏报 Input ANR（Input 超时判在系统侧 waitQueue，不经过 MessageQueue，探活消息照常被处理）；固定周期探活和 ANR 真实发生时刻天然不对齐——所以经常抓到「干净帧」：主线程 **Native 态趴在 `nativePollOnce`**，其实是卡顿已经过去、消息队列空闲的现场。要时机精确，就得像 xCrash / Matrix 那样拦截 SIGQUIT，在系统判定那一刻 dump。
>
> 所以我的分析 SOP，是按这套数据的能力边界设计的。

## 二、SOP 范本（约 60 秒，接上段）

> **第一原则：单帧不定案，聚合才定案。**
>
> **Step 1 · 聚合分诊**：单帧不定案，在打开任何一份 trace 之前，先在 issue 聚合层面回答三个问题——这三问用的是同一份聚合数据，只是沿两条不同的轴（**设备轴 / 入口轴**）去读，外加一道严重度门槛：
>
> 1. **值不值得关注**——看影响用户数。数量少，通常先不追；但要结合机型集中度看，即使总数不高，如果几乎全集中在某一款机型、其他机型几乎为零，也值得提前介入——这往往是设备专属 bug 的早期信号，越晚查成本越高。
> 2. **代码问题还是环境/兼容问题**（读设备轴，方向都是"优先怀疑"、不是"就是"，仍要回 Step4 验证）——
>    - 分布均匀 → 优先怀疑业务代码、公共组件、通用链路本身有问题（不挑环境，走到哪台机器都复现，比如 `runBlocking` 同步等待、`release` 同步调用）；
>    - 集中在某一款机型/系统版本 → 优先怀疑 ROM 差异、厂商兼容问题、系统 API 行为差异，或该机型本身硬件性能短板；
>    - 集中在低端机型 → 可能是 CPU/IO/内存资源紧张，把原本"勉强能接受"的代码放大成了 ANR（不是单纯"环境导致"，而是环境把本就临界的代码戳破了）。
>    以上都只是**先验假设**，要回到 Step4 用代理证据（trace 里线程数是否暴多、多份样本主线程落点是否随机且都是正常代码）去验证或推翻。
> 3. **公共组件问题还是特定业务链路问题**（读入口轴）——分布集中在某个特定页面/入口，更像是那条业务链路自己的问题。比如 `CameraClickActivity` 里 `saveToAlbum` 把存相册 IO 放主线程（`ID: 2848AFD7`），issue 只在打开这个页面时出现，其他页面不受影响，方向直接锁定这条链路内部。
>
> 带着这三问给出的先验假设进 Step2~4，比空手打开 trace 瞎猜省一大截功夫。我处理过单 issue 影响 45000+ 用户、占比 12% 的 ANR，都是从这三问入手的。
>
> **Step 2 · 定性**：ANR 类型和 reason 从 issue 标题（shortMsg）拿，不从线程栈猜。类型定了，阈值语境才定——Service 前台 20s/后台 200s、Broadcast 5s/60s、Provider 10s、Input 5s。
>
> **Step 3 · 验伪**：主线程 Native 态趴 `nativePollOnce` 的干净帧直接作废，换同 issue 其他样本。
>
> **Step 4 · 判态归因**，三条路：
> - **RUNNABLE + 耗时栈 → 自己太忙**。我们修过的大多在这：主线程同步 release ijkPlayer、DataStore 在主线程 `runBlocking`、存相册 IO 放主线程；
> - **BLOCKED + waiting to lock → 被锁困住**，做锁链追踪：拿锁地址全局搜持锁线程，看它在干嘛。最典型一例是极验一键登录：它把联通 SDK 的带锁任务 post 到主线程，主线程等锁 A，追下去两个联通线程 A→B、B→A 反向加锁，AB-BA 死锁，主线程被拖死——闭源库定位得到改不了，只能反馈或换方案；
> - **环境类（CPU 饥饿）**：Bugly 没有系统 CPU 段——那段在系统 trace 里是 system_server 的 `ProcessCpuTracker` 写的，我们拿不到——所以我用**代理证据**：trace 里自己进程线程数暴多、大量 RUNNABLE 子线程，是「进程内卷」，trace 直接可见；同 issue 多份样本栈落点随机又都是正常代码、且低端机集中，才推断进程外挤压。
>
> **Step 5 · 治理回归**：理想流程是修复 → 灰度 → 对比该 issue 影响用户数收敛，收敛了才算闭环，再全量发布。我们实际是 toB 场景，没有完整灰度平台，一般靠**测试环境验证、试点客户先上、低峰期发布、准备快速回滚包**来替代灰度闭环。
>
> 灰度维度可以按**企业 ID 开关**——toB 本来就是按企业客户切分用户群，先在合作企业上放，比按设备/系统版本分更贴合业务。落地上有个关键点：**开关不能硬编码在客户端**，那样每次调整灰度范围都要重新发版，失去了灰度"不发版也能实时控制放量"的意义。正确做法是**服务端维护一份灰度企业白名单，客户端登录时带企业 ID 去要开关状态**——没有专门配置中心的话，用现有登录接口顺带多返回一个字段就够，成本很低；客户端本地只 if-else 决定走新逻辑还是旧逻辑。全量的动作，就是服务端把白名单从"部分企业"改成"全部"，不用重新发版。
>
> SDK 上报侧配套：登录拿到企业 ID 后调用监控 SDK 的自定义用户属性接口（如 `CrashReport.putUserData(context, "enterprise_id", id)`），这台设备之后所有 ANR 上报都会自动带上这个字段，后台就能按"issue + 企业 ID"过滤。
>
> 但试点企业量往往很小（1、2 家），没法靠"数字降没降"做统计对比，闭环判据要换一套，不能单靠"企业没反馈就当修好了"——沉默是主观且滞后的信号，企业可能只是没碰到触发场景，不代表真的修好。换成三层判据：① **确定性复现**——用 Step4 定位到的根因写复现用例，测试环境验证 fix 后不再触发，不依赖线上样本量；② **自有监控按 issue ID + 企业 ID 过滤**——主动去 Bugly 后台用这个 issue 的指纹（stack 签名）+ 企业 ID 过滤，看观察窗口内命中次数是否真归零，这是客观数据；③ 企业沉默只作补充信号，且要先确认该企业窗口期内确实用过触发场景。
>
> 一句话方法论：**先定性、再验伪、后归因；单帧不定案、聚合才定案；修复必回归。**

## 三、追问弹药库（每条一口气答完）

| 追问 | 一句话答案 |
|---|---|
| 为什么常抓到干净帧？ | Watchdog 5s 定时采样，采样时刻 ≠ ANR 时刻，抓到时卡顿已过去，主线程回到 `nativePollOnce` 空闲等待 |
| 系统 ANR 日志里的 CPU 段哪来的？ | system_server 的 `ProcessCpuTracker` 在 `appNotResponding` 时采写的；App 进程 8.0 后读不到 `/proc/stat` 和他进程 `/proc/[pid]` |
| 为什么漏报 Input ANR？ | Input 超时判定在系统侧 InputDispatcher 的 waitQueue（从 eventTime 起算），不经过 App 的 MessageQueue，探活消息照常被处理 |
| 为什么没有 ANR 回调？ | 系统就没提供（不同于 crash 的 UncaughtExceptionHandler），只能轮询 `getProcessesInErrorState()` 查 `NOT_RESPONDING` |
| xCrash 和 Matrix 谁更稳、为什么？ | 都拦 SIGQUIT；xCrash 在信号上下文直接 dump（async-signal-safe 约束 + 补发竞态），Matrix handler 只 write pipe，dump/卸载/补发在普通线程**顺序执行、时序可控**，补发时 handler 必已卸载 |
| 爆雷时找哪个 Service 比对超时？ | 遍历 `mExecutingServices` 找 `executingStart` **最早**的（趴得最久的），用 now − executingStart 和阈值比 |
| 死锁在 trace 里怎么确认？ | main `waiting to lock <地址>` → 全局搜地址找持锁线程 → 它又在等另一把锁 → 追到成环即 AB-BA；修复方向是统一全局加锁顺序 |
| 聚合分诊具体在看什么？ | 同一份聚合数据沿两条轴读：设备轴判断代码 vs 环境问题，入口轴判断公共 vs 特定组件问题；外加严重度门槛（总数少但机型高度集中也要看） |
| 你们 ANR 修复怎么做灰度验证？ | 如实说：toB 场景没有完整灰度平台，按企业 ID 开关先在试点企业上放，用测试环境验证、低峰发布、回滚包兜底 |
| 试点企业样本量太小，怎么判断收敛？ | 换判据，不单靠客户沉默：①根因复现用例过测试环境 ②按 issue ID + 企业 ID 过滤自有监控，看命中次数是否归零 ③企业沉默只作补充，且要先确认对方窗口期内真用过触发场景 |
| 企业 ID 开关怎么推给用户、怎么全量？ | 不硬编码在客户端，服务端维护灰度白名单，客户端登录带企业 ID 去要开关状态（没配置中心就用登录接口顺带传字段）；全量就是服务端把白名单改成"全部"，不用重新发版 |

## 四、避坑口径对照（原版 → 重构版）

| 你原来说的 | 改成 | 为什么 |
|---|---|---|
| 「Bugly 收 ANR 广播确认」 | 轮询 `getProcessesInErrorState()` | 系统无 ANR 广播，懂行的当场按住 |
| 「第一步看系统 CPU 排除环境」 | 「系统 CPU 段我们拿不到，环境类用线程数/聚合分布做代理」 | 说没执行过的步骤=追问即塌；暴露数据边界=证明真干过 |
| 「主线程状态是睡眠，在 MessageQueue.next」 | 「Native 态趴在 nativePollOnce」 | Sleeping 专指 Thread.sleep，一眼分深浅 |
| 「IMS 的 inputReceiver 接收事件」 | 系统侧是 **InputReader**（EventHub→InboundQueue）；`InputEventReceiver` 是应用侧收 socket 的那半 | 两个名字撞脸但分属两个进程 |
| 「精确判断靠 xCrash/Matrix 对 handler 的处理」 | 靠**拦截 SIGQUIT**，在系统判定那一刻 dump | Matrix 的 Looper 监控是另一条产品线（卡顿），别揉在一起 |
| 「遍历找最近的 Service」 | 找 `executingStart` **最早**的 | 超时消息只是触发器，判据是趴得最久的那个 |
