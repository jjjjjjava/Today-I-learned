# 第 6 篇 · ANR 线上治理方法论：防线、归因与止损

> 前置知识：01～05 篇。前五篇解决“ANR 是什么、系统如何判定、trace 怎么分析、线上如何拿到现场”；本篇解决“团队如何减少 ANR、线上突然增加时如何归因、不同发布阶段如何决策”。
>
> 本篇定位：面试方法论。重点是形成一条能讲清楚、也经得起追问的治理主线，不展开完整 Lint 插件、监控平台或热修复框架的建设细节。

---

## 一、先建立完整坐标系

ANR 治理不是“线上拿到一条 trace，然后修一段代码”，而是两个部分组成的闭环：

```text
前置防线：Lint 静态检测 → 自动化/压力测试 → 灰度监控 → 全量常态化监控
                                                         │
                                                         │ 漏网问题
                                                         ↓
线上治理：发现异常 → 聚合分诊 → 单点/聚合/爆发归因 → 分阶段止损与修复
                                                         │
                                                         ↓
                                           定向灰度验证 → 扩量 → 经验回填
```

这里要先承认一个现实：

> Lint、自动化测试和灰度能够提前拦截常见、稳定复现和影响面较大的问题，但无法穷举真实用户的机型、系统负载、数据量和线程时序。进入全量后，仍然会剩下一批线上长尾 ANR。

因此，我们的责任不是承诺“线上零 ANR”，而是：

1. 尽量把问题发现时间前移；
2. 漏到线上后能够快速判断影响面和原因；
3. 根据问题所处的发布阶段选择代价最小的止损方式；
4. 验证修复确实有效，而且没有产生新的稳定性问题。

## 二、第一部分：四层前置防线

### 2.1 Lint：拦截静态可识别的危险调用

Lint 适合检查“不运行程序，只看代码结构就能识别”的风险，例如：

- 明确的主线程入口调用 `Thread.sleep()`；
- 生命周期或主线程任务直接调用已知的同步阻塞 API；
- `BroadcastReceiver.onReceive()` 中出现团队禁止的耗时调用；
- 项目已经明确禁止在主线程使用的同步 I/O、等待或 SDK 初始化方法。

面试时只需要把实现原理说到下面这层：

> 自定义 Android Lint 可以让 Detector 实现 `SourceCodeScanner`，通过 `getApplicableMethodNames()` 声明关注的方法名，再覆写 `visitMethodCall()` 接收对应的方法调用。回调中继续校验方法所属类、签名和调用上下文，确认是目标危险调用后，通过 `context.report()` 报告问题，并在 MR/CI 的 lint 任务中拦截。

简化示意：

```kotlin
class BlockingCallDetector : Detector(), SourceCodeScanner {

    override fun getApplicableMethodNames() =
        listOf("sleep", "await", "get")

    override fun visitMethodCall(
        context: JavaContext,
        node: UCallExpression,
        method: PsiMethod
    ) {
        if (!isTargetBlockingMethod(context, method)) return
        if (!isKnownMainThreadContext(node)) return

        context.report(
            ISSUE,
            node,
            context.getLocation(node),
            "禁止在主线程入口执行阻塞等待"
        )
    }
}
```

不能只匹配 `get()`、`await()` 这些方法名，因为业务代码中可能存在大量同名方法。必须继续确认接收者类型和方法签名，否则误报会非常严重。

Lint 的边界也要说清楚：它擅长发现明确的代码模式，不擅长判断运行时数据量、CPU 抢占、Binder 对端卡顿和偶发锁竞争。因此它只是第一道低成本防线，不等于 ANR 检测平台，也不要求每个线上 ANR 最后都转化成一条 Lint。

### 2.2 自动化与压力测试：发现可复现问题，拦截先导指标

自动化测试可以由两类用例组成：

#### 第一类：确定性核心链路

使用 UI Automator 等工具反复执行启动、登录、首页、拍照、同步、切换账号等核心路径，尽量使用固定版本、固定数据和固定操作，使问题可以比较和复现。

#### 第二类：随机与压力场景

使用 Monkey 等工具持续生成触摸、按键和系统事件，配合低端机、长时间运行、前后台切换、大数据量等条件放大并发和资源问题。Monkey 在应用真正产生 ANR 时可以直接停止并报告，也可以通过固定 seed 重放同一组随机事件。

但是，ANR 是一个低概率、强环境相关的尾部事件，只把“有没有直接跑出 ANR”作为门禁，容易漏掉临界问题。因此自动化还应观察先导指标：

- 主线程是否出现超过团队阈值的长消息；
- StrictMode 是否发现主线程磁盘或网络访问；
- 核心组件回调是否出现明显超时；
- 是否出现异常的线程膨胀、连续同步 Binder 调用或长时间锁等待；
- 同一测试环境下，候选版本相对基准版本是否明显劣化。

这里的正确口径是：

> 自动化测试既能直接抓住稳定复现的 ANR，也能通过主线程长消息、同步 I/O 等先导指标提前发现风险；但它不能证明线上不会再发生长尾 ANR。

### 2.3 灰度监控：用真实流量判断候选版本

灰度阶段的核心不是简单地“看新版本 ANR 数量”，而是：

```text
同一时间窗口
候选版本/灰度人群
            vs
稳定版本/对照人群
```

重点观察：

- ANR 率是否高于稳定版本，而不是只看绝对数量；
- 是否出现稳定版本没有的新聚类；
- 旧聚类在候选版本中是否明显放大；
- 问题是否集中在特定机型、系统、地区、页面或实验组；
- 随着灰度比例扩大，问题是否持续增长。

候选版本和稳定版本应尽量处于相同时间窗口。只做“上线前 vs 上线后”的纵向比较，容易受到节假日、流量变化、后端状态和系统更新等外部因素干扰。

### 2.4 全量常态化监控：承接灰度覆盖不到的长尾

全量后持续观察：

- 整体 ANR 率及其趋势；
- 用户可感知 ANR 率；
- 新增和高影响聚类；
- 按版本、设备、Android 系统、地区、Activity 和 ANR 类型切片后的异常；
- 某个旧聚类是否突然爆发。

灰度样本有限，而且用户行为、数据量和设备状态不可能完全覆盖，所以全量监控不是灰度失败后的补救，而是长期存在的最后一道防线。

## 三、第二部分：线上问题的三层归因

三种归因不是三套互斥流程，而是在回答三个不同的问题：

| 归因层次 | 回答的问题 | 主要证据 |
|---|---|---|
| 单点归因 | 这一条 ANR 为什么发生？ | ANR 类型、主线程状态、完整线程栈、锁链、Binder/系统现场 |
| 聚合归因 | 这一批 ANR 有什么共同边界？ | 版本、机型、系统、地区、入口、公共栈、聚类分布 |
| 爆发归因 | 为什么从这个时间点开始突然增加？ | 指标拐点、增量聚类、受影响人群、变更时间线、反向验证 |

实际处理通常是：

```text
先聚合分诊确定影响面和优先级
        ↓
再挑有代表性的单点 trace 证明技术机制
        ↓
如果指标是突然上涨，再补做爆发归因解释“为什么是现在”
```

### 3.1 单点归因：证明这一条为什么卡住

单点归因就是前几篇的 trace 分析：

1. 先确认 ANR 类型和超时语境；
2. 判断抓栈是否有效，排除抓取过晚的 `nativePollOnce` 干净帧；
3. 看主线程是在运行耗时任务、等待锁、等待 Binder，还是没有得到调度；
4. 如果主线程等锁，沿锁地址找到持锁线程并继续追踪；
5. 如果怀疑系统负载、Binder 对端或 CPU 饥饿，结合 Perfetto、系统线程和多样本证据验证。

单点归因解决“技术上怎么卡住”，但一条样本不能代表整批问题，也不能单独证明某个版本变更导致了爆发。

### 3.2 聚合归因：寻找一批问题的共同边界

聚合归因不是简单地把堆栈放在一起看，而是沿多个维度切分：

- **机型/性能档位**：集中单一机型，优先调查 ROM、系统 API 或硬件差异；集中低端机，说明资源紧张可能放大了临界代码；
- **Android 版本**：集中某个系统版本，调查系统行为变化和兼容分支；
- **业务入口**：集中固定 Activity、Service 或功能入口，优先调查对应业务链路；
- **公共调用栈**：主线程最终位置不同，但都经过同一个 SDK 或基础组件，优先调查公共组件；
- **地区/渠道/企业**：调查地区配置、服务端路由、数据差异和定制代码分支；
- **App 版本**：只在某个版本出现，说明它可能与该版本或该版本承载的配置变化有关。

注意这些结论只是缩小调查范围。例如“集中低端机”不能直接归因成设备差，而应继续判断：

- 是低端机专属代码分支有问题？
- 是计算任务太多，导致主线程或关键线程拿不到足够 CPU？
- 是线程数量过多造成进程内竞争？
- 还是原本勉强运行的同步 I/O、锁等待被低端机放大？

### 3.3 爆发归因：解释为什么突然增加

爆发归因不能只说：

> 新版本发布后 ANR 上升，所以一定是新版本代码导致的。

版本发布、远程开关、服务端变化、SDK 配置、用户流量和系统环境可能在相近时间发生变化。合理的爆发归因要完成下面六步。

#### 第一步：确认是真爆发，而不是数量幻觉

优先看 ANR 率，而不是 ANR 数量：

```text
ANR 率 = 发生 ANR 的用户数 / 活跃用户数
```

同时检查统计口径、上报延迟、活跃用户变化和样本量。用户量翻倍导致 ANR 数量翻倍，并不等于质量劣化。

#### 第二步：找到指标开始异常的拐点

尽量定位到具体版本、灰度批次和时间窗口：

```text
14:00  候选版本从 5% 扩到 20%
14:10  ANR 率开始偏离稳定版本
14:30  新聚类快速增长
```

拐点越精确，需要排查的变更范围越小。

#### 第三步：拆解是谁贡献了增量

假设稳定版本 ANR 率为 `0.10%`，候选版本为 `0.80%`，总增量是 `0.70` 个百分点；其中某个新锁等待聚类增加了 `0.60` 个百分点，那么它解释了约 86% 的增量：

```text
聚类增量贡献度
= 该聚类增加的 ANR 率 / 整体增加的 ANR 率
= 0.60 / 0.70
≈ 86%
```

爆发归因应优先调查贡献增量最大的聚类，而不是只调查堆栈最显眼或最新出现的问题。

#### 第四步：圈定受影响人群

继续切片确认边界：

```text
是否只发生在候选版本？
是否只集中低端机或某款设备？
是否只发生在特定 Android 版本？
是否只发生在升级后首次启动？
是否只发生在某地区、企业或实验组？
```

人群边界会帮助我们把“全版本有问题”缩小成更具体的假设，例如“新版本中，Android 12 低端机在升级后首次进入首页时发生”。

#### 第五步：对齐变更时间线并用单点证据证明机制

需要检查的不只是 Git 提交，还包括：

- App 版本和依赖升级；
- SDK、构建工具和插件变化；
- 远程配置、功能开关和 AB 实验；
- 服务端接口、数据量和超时策略；
- 地区或企业定制配置；
- Android 系统升级和设备结构变化。

找到相关变化后，再回到代表性 trace 或 Perfetto，证明主线程为什么被该变化卡住。至此得到的是一个有证据的因果假设，而不只是时间相关性。

#### 第六步：通过反向变化验证因果

最有力的闭环证据是：

```text
关闭问题开关 / 暂停问题路径 / 发布修复
                  ↓
目标聚类下降
                  ↓
整体 ANR 率同步回落，且没有转移成新的聚类
```

所以爆发归因可以压缩成一句话：

> 找准拐点，拆出贡献增量最大的聚类，圈定受影响人群，对齐变化事件，用单点 trace 证明卡顿机制，最后通过关闭或修复后的指标回落验证因果。

## 四、第三部分：按照发包阶段选择治理策略

修复方式不能脱离问题所处阶段。相同 ANR，在灰度期和已经全量后的最优决策不同。

### 4.1 灰度期发现问题

优先顺序是：

```text
暂停继续扩量
    ↓
有开关：关闭问题功能或切回旧路径
    ↓
修复并生成新的候选包
    ↓
针对受影响人群重新灰度
```

暂停灰度只能阻止更多用户升级，已经安装候选版本的用户不会自动回到旧版本。因此：

- 已安装用户能够通过远程开关切回旧路径时，优先使用开关止损；
- 没有开关时，需要发布修复版本；
- 如果影响严重、已安装用户很多，而且公司存在合规的热修复能力，才考虑热修复已安装版本。

### 4.2 已经全量后发现长尾或爆发问题

先根据影响面、增长速度、核心链路和修复风险判断紧急程度：

| 情况 | 处理策略 |
|---|---|
| 有可靠降级开关 | 先关闭问题路径，快速止损，再准备永久修复 |
| 问题紧急且热修复渠道合规 | 下发补丁并由开关控制范围，逐步验证 |
| 问题紧急但不能热修复 | 发布紧急修复版本，推动用户升级 |
| 问题影响较低且趋势稳定 | 合入下一个正常版本，按常规灰度验证 |
| 根因尚未确认或修复风险过高 | 优先降级功能或缩小影响面，不仓促替换未知风险代码 |

### 4.3 正确理解开关、热修复和新包

三者解决的问题不同：

- **开关**：改变用户走哪条代码路径，通常是最快的止损手段；
- **热修复**：修改已安装版本的代码实现。以 classloader 型 `patch.dex` 方案为例，调用方仍然调用同一个类和方法签名，但运行时类加载机制优先使用补丁中的修复实现；不同热修复框架也可能采用方法替换等机制；
- **新版本**：通过正式发布渠道交付完整修复，但只有用户安装更新后才生效。

`patch.dex` 不是所有 Android App 都能通用采用的发布方式。Google Play 分发的应用不能从 Play 以外下载 dex、JAR、`.so` 等可执行代码来自我更新。因此面试时应说明：

> 热修复只适用于公司已有、经过安全验证并符合实际分发渠道政策的补丁体系；Google Play 场景优先使用功能开关和正式修复版本。

## 五、第四部分：修复验证与经验回填

### 5.1 修复不是“代码改完了”，而是两个维度都通过

#### 性能与稳定性有效

- 线下复现用例不再触发；
- 目标 ANR 聚类的发生率明显下降；
- 整体 ANR 率没有被其他新聚类抵消；
- 低端机、目标系统和高风险数据场景下仍然成立。

#### 功能安全

- 新旧路径的核心功能正确；
- 异常、超时和降级流程可用；
- 没有引入新的 Crash、ANR 或数据一致性问题；
- 热修复或开关关闭后能够安全恢复。

### 5.2 根据聚合结论做定向灰度

聚合归因不仅用于定位，也决定修复先灰度给谁：

```text
问题集中某机型       → 该机型优先验证
问题集中 Android 12  → Android 12 优先验证
问题集中某地区       → 该地区优先验证
问题集中某企业       → 企业白名单试点
问题集中升级首启     → 构造升级链路重点验证
```

定向人群验证通过后，再逐步扩大。每个阶段都同时观察：目标聚类、整体 ANR 率、Crash 率和核心业务指标。

### 5.3 经验回填，但不追求把所有问题都做成 Lint

一次问题处理结束后，选择最合适的防线回填：

- 稳定可复现的场景，补进自动化或压力测试；
- 某类主线程风险，补进开发 checklist 或已有静态检查；
- 某个高风险机型/系统，补进测试矩阵；
- 某种爆发模式，补充聚类、版本和人群维度的告警；
- 某类紧急问题，补充开关、回滚和灰度停止条件。

回填的目标不是机制越多越好，而是让同类问题下一次更早暴露、处置成本更低。

## 六、面试主答范本

> 我们的 ANR 治理分为前置防线和线上治理两部分。
>
> 前置防线首先是静态检查。自定义 Lint 可以通过 `SourceCodeScanner` 关注目标方法名，再覆写 `visitMethodCall()` 检查方法所属类型和调用上下文，拦截主线程明确的阻塞调用。然后在线下用固定核心链路和 Monkey 压力测试，一方面直接发现可复现 ANR，另一方面观察主线程长消息、StrictMode 同步 I/O 等先导指标。接着进入灰度，对比同一时间窗口内候选版本和稳定版本的 ANR 率、聚类及设备分布。全量后则通过常态化监控承接灰度覆盖不到的长尾问题。
>
> 线上发现问题后，我会从三个层面归因。单点归因回答这一条为什么卡住，主要分析 ANR 类型、主线程栈和锁链；聚合归因回答这一批有什么共性，按版本、机型、系统、地区、业务入口和公共调用栈切分；爆发归因回答为什么这个时间点突然上涨，要先确认是发生率真实增加，找到指标拐点和贡献增量最大的聚类，再圈定受影响人群，对齐版本、开关、SDK 或服务端变化，最后通过关闭问题路径或修复后的指标回落验证因果。
>
> 治理策略取决于发布阶段。灰度期优先暂停扩量，有开关就切回旧路径，然后发修复候选包重新定向灰度；全量后则根据紧急程度选择降级开关、合规热修复、紧急新包或下个版本修复。暂停灰度不会让已安装用户自动回滚，所以必须考虑已安装用户的止损。修复后既要验证目标聚类和整体 ANR 率下降，也要验证功能安全，再根据聚合结论从目标机型、系统或企业开始逐步放量。最后把复现用例、测试矩阵、监控维度或发布停止条件回填到前置防线。

## 七、追问速答

### 1. 自动化测试为什么不能保证没有 ANR？

因为 ANR 经常依赖真实设备负载、数据量、Binder 对端和线程时序。自动化能抓稳定复现问题并观察先导指标，但无法穷举线上环境。

### 2. 聚合归因和爆发归因有什么区别？

聚合归因找“一批问题共同发生在哪里”；爆发归因找“为什么从这个时间点开始增长”，后者必须加入时间线、增量贡献和反向验证。

### 3. 为什么不能只看新版本发布前后？

因为时间本身带来流量、节假日、后端和系统环境变化。同一窗口的候选版本与稳定版本对比，更容易把变化归因到候选版本。

### 4. 为什么暂停灰度后还要止损？

暂停灰度只是不再增加新用户，已经安装候选版本的用户不会自动回退，仍然需要开关、补丁或修复版本。

### 5. 如何证明爆发原因找对了？

目标聚类解释了主要增量，受影响人群和变更范围吻合，单点 trace 能证明技术机制，并且关闭或修复该变化后，目标聚类及整体 ANR 率同步回落。
