# 第 1 篇 · ANR 是什么，以及它凭什么判你「无响应」

> 前置知识：知道 Android 有主线程（UI 线程）、有 Looper/MessageQueue、进程间通过 Binder 通信
> 难度：入门
> 预计阅读时间：10 分钟
> 本篇按「为什么需要 → 如何设计 → 关键设计点 → 不止一种」四段组织，是你亲手重构的核心笔记。

---

## 正文内容

### 1. 为什么需要 ANR

设想一个场景：没有 ANR 机制，你点击一个按钮，App 卡住不动了。

- **用户视角**：他只知道应用动不了了，但分不清是**暂时的短暂卡顿**，还是**已经彻底死锁、再也回不来**。用户只能疯狂点击，或者长按关机来强杀进程，体验极差。
- **系统视角**：系统没有一个**统一的客观标准**去判断这个 App 是「慢了一点」还是「废了」，也因此没法替用户做决定——要不要弹个框，让用户选择把它关掉。
- **开发者视角**：事后啥也拿不到，不知道当时卡在哪个线程、哪行代码、哪个方法。

正因为这三方都有痛点，我们需要一套机制来解决它们。这就是 ANR，它要同时解决三个问题：

```text
1. 给系统一个「无响应」的客观判定标准      → 超时阈值
2. 给用户一个出口                       → 弹框：继续等待 / 关闭应用
3. 给开发者留下现场                     → dump 各线程堆栈到 traces
```

> 一句话：**ANR 就是系统识别「App 关键任务超时无响应」，然后提示用户、并记录现场的一套约定机制。**

这里要把定义校准准：ANR 判的不是"主线程卡没卡"这种 App 内部状态，而是**系统视角下"我交代的有时限任务，你到点完成没有"**。判官是系统，不是 App 自己。

### 2. 如何设计一个 ANR

如果让你来设计这套检测机制，最自然的参照物是**看门狗（Watchdog）**：

> A 给 B 派发一个任务，同时 A 开启一个定时器。B 在给定时间内处理完任务，会回来找 A 关闭定时器。如果 A 的定时器先被触发，说明 B 没按时完成——看门狗触发。

把它落到 ANR，就是「**埋雷 → 拆雷 → 爆雷**」三步：

```text
埋雷：系统向 App 派发任务的同时，向自己（system_server）的消息队列里埋入一颗"炸弹"（超时延时消息）。
拆雷：App 在给定时间内处理完任务后，通过 Binder 回调系统方法，把这颗炸弹从消息队列里取出并销毁。
爆雷：App 没来得及拆雷，系统消息队列处理到这颗炸弹消息，触发爆雷流程：
      → 判定 ANR
      → 收集现场（向应用进程、以及 system_server 等相关进程发送 SIGQUIT 信号，dump 各进程线程堆栈到 traces）
      → 前台进程弹出系统 ANR 弹窗，后台进程可能直接被杀
```

注意一个细节：**炸弹埋在系统进程自己的消息队列里**，不是埋在 App 里。这正好引出第 3 点。

（这是「组件类 ANR」——Service / Broadcast / Provider 的通用模型。Input ANR 不发定时炸弹，而是在事件分发循环里**持续主动检查**，后面模块单独讲。）

### 3. 最关键的设计点：计时和判定为什么放在系统进程？

因为 **App 进程一旦卡死，它无法执行任何操作**——你不能指望一个已经死锁的进程，还能稳定地给自己计时和判定。

> 就像你不能指望一个晕倒的人，自己举手报告「我晕倒了」。裁判不能是选手本人。

所以必须由一个**独立的、不会被 App 主线程拖垮的进程**来当裁判，持续观测和判定 App——这个进程就是 `system_server`（AMS 所在的系统进程）。它在 App 外部冷眼旁观，App 死没死、卡没卡，都不影响它到点检查那颗雷还在不在。

### 4. ANR 不止一种

既然 ANR 的本质是「系统为重要的用户任务提供超时检测标准」，那这个"任务"就不止用户的 input 点击事件。常见有四类（先混个脸熟，差异下一模块细讲）：

```text
Input ANR           ── 用户点击/滑动后，事件没被及时消费
Service ANR         ── Service 生命周期回调没及时执行完
Broadcast ANR       ── BroadcastReceiver.onReceive 没及时返回
ContentProvider ANR ── Provider 初始化/发布没及时完成
```

> 核心认知：**ANR 不是单纯在等"主线程卡不卡"，而是系统在等 App 完成某个有时限的关键任务；不同任务 → 不同类型的 ANR。**

## 思考题

> 这几个问题直接对应大纲里的可验证能力，能说清逻辑即可。

1. 面试场景：「主线程明明在跑合法长任务（比如解析大 JSON），CPU 占用很高，按理没『卡死』，为什么系统还是判它 ANR？」用本篇定义回答——系统判的到底是什么？
2. 「埋雷-拆雷-爆雷」里，拆雷动作由谁发起、通过什么通道、告诉谁？如果这个 Binder 回调通道被堵住，会发生什么？
3. 为什么不能让 App 自己起一个子线程当看门狗来检测主线程、然后自己上报 ANR？这种做法和系统级检测相比差在哪？（提示：除了"子线程也可能受影响"，再想想哪种 ANR 它根本探测不到。）
