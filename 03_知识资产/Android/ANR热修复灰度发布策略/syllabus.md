# ANR热修复灰度发布与收敛验证策略 · 课程大纲

> 这份大纲定义了完成本课题后你将掌握的所有能力。
> 学习深度：标准
> 文档数量因人而异，但掌握内容不打折扣。

## 背景与衔接

这门课的内容是你在 grill 阶段已经和我逐条敲定的一条完整链路——"修复 → 推送 → 灰度圈选 → 收敛判断 → 止血 → 全量收口"。grill 帮你**做出了每一步的决策**；这门课要做的是把每一步**背后的原理讲透、串成体系**，让你不仅能复述结论，还能在面试官追问"为什么"的时候接得住、能推导、能应对变种问题。

Tinker框架本身的dex/so/资源加载机制是**另一门课**（`../tinker热修复原理/`），这里不涉及。

## 核心掌握项

完成本课题后，你将能够：

### 模块一：分发架构与职责边界（对应Q1）
- [x] 能说明为什么"灰度决策"必须放在服务端而不是客户端，并区分Tinker客户端`patchCheck()`熔断和服务端灰度决策各自解决的是什么问题
- [x] 能说出一次完整的客户端"签到检查更新"过程中，客户端上报什么信息、服务端凭什么做判断、返回什么结果
- [x] 能说明Bugly热更新控制台开箱即用覆盖了分发链路的哪些环节，如果自建需要补齐哪些组件

### 模块二：灰度圈选策略设计（对应Q2上半）
- [x] 能根据issue的机型/系统/地域分布特征，判断该用定向灰度还是随机比例灰度，并说出背后的统计学原因
- [x] 能解释为什么需要设置同期不下发补丁的对照组，而不能仅做补丁前后的纵向时间对比
- [x] 能说明灰度比例为什么要分阶段放量（如5%→20%→50%→100%），每个阶段的放量条件本质在控制什么风险

### 模块三：收敛判断的度量方法论（对应Q2下半）
- [x] 能解释为什么"影响用户数"必须换算成比率、不能直接比较绝对值，尤其是灰度组样本量随阶段变化的场景
- [x] 能说出"收敛"判定需要同时满足的三个条件（最小样本量、最短观察窗口、比率下降阈值），并分别说出每个条件在防止哪一类误判
- [x] 能用实验设计的视角，解释"横向对比灰度组vs对照组"相比"纵向对比补丁前后"本质上排除了什么干扰因素

### 模块四：止血回滚与全量收口
- [x] 能区分"停止扩量"和"主动回滚"两级止血手段各自的适用场景、代价与不可逆性
- [x] 能解释为什么Tinker客户端自带的崩溃熔断覆盖不了ANR类问题，止血动作必须由服务端灰度监控主动触发
- [x] 能说明为什么"补丁灰度到100%"不等于问题闭环，必须让代码改动回归主干、进入下一次全量发布

## 不在本课题范围内

- Tinker本身dex/so/资源在运行时如何被加载合并（见另一门课`tinker热修复原理`）
- Bugly SDK的具体接入代码、上报字段的API细节
- 分桶算法的数学/代码级实现（如一致性哈希的具体实现）
- ANR之外其他问题类型（内存泄漏、纯崩溃）治理流程的差异点
