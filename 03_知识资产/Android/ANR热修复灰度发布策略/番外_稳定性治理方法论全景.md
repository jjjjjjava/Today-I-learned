# 番外：稳定性治理方法论全景——灰度在大厂坐标系里的位置

> 来源：`03.md`复习时由"节假日观察窗口"问题延伸而来，素材为字节跳动ArchSummit公开分享
> 作用：把本课题（ANR热修复灰度）挂进完整的稳定性治理方法论坐标系，面试时用于抬升回答高度
> 难度：入门（框架记忆型）

## 完整框架：防线 + 救火 = 一个飞轮

整个方法论由两部分咬合而成，**先设防线拦截，漏网的走救火闭环，救火的教训回填防线**：

```
        ┌──────────────────────────────────────┐
        ↓（回填：教训变成更靠前的防线）           │
静态检测 → 线下自动化测试 → 灰度 → 线上常态化监控  │
                              │（漏网爆发）      │
                              ↓                 │
                    发现 → 归因 → 治理 → 防劣化 ──┘
```

### 第一部分：四层防线（防劣化体系，按问题被发现的时间从早到晚）

核心逻辑：**越早的防线越便宜但覆盖有限，越晚的防线越逼近真实但代价越大**。目标是让绝大多数问题被最便宜的早期防线拦住。

| 防线 | 时机 | 拦什么 | 漏网代价 |
|---|---|---|---|
| ① 代码提交时静态检测 | 代码未运行 | 扫代码即可发现的模式问题 | ≈0 |
| ② 线下自动化劣化测试 | 合入后发布前 | 跑起来才暴露的劣化（启动/内存/帧率） | 未达用户，回炉 |
| ③ 灰度劣化发现和归因 | 部分真实用户 | 只有真实机型/网络/使用路径才触发的问题 | 波及一小撮用户 |
| ④ 线上常态化劣化监控 | 全量发布后 | 灰度都没暴露的长尾问题 | 100%用户，最贵 |

### 第二部分：救火闭环（单个线上问题的生命周期）

| 阶段  | 回答的问题          | 子项                               |
| --- | -------------- | -------------------------------- |
| 发现  | 出事了吗？怎么第一时间知道？ | 线上监控 → 报警 → 问题分发                 |
| 归因  | 为什么出事？         | 单点归因 / 共性归因 / 爆发归因               |
| 治理  | 怎么摁下去？         | 问题防护 / **动态止损（热修复、降级开关）** / 线下修复 |
| 防劣化 | 以后怎么不再犯？       | 把教训固化成机制，**回填到四层防线**             |

### 飞轮转动

防线拦住大部分 → 漏网的救火 → 救火教训变成新防线（"这次靠线上监控才发现，下次能不能静态检测就拦住？"）→ 防线越来越密。字节公开数据：抖音/头条等崩溃率两年优化30%+，靠的是飞轮转很多圈，不是单次治理。

## 本课题在坐标系里的位置

ANR热修复灰度横跨**归因→治理**两环，卡在最关键接缝上：

- 聚合分诊（机型/系统/地域分布特征）＝ **共性归因**，同时是灰度圈选策略的输入
- 热修复补丁本身 ＝ 治理里的**动态止损**（不发版止血）
- 灰度圈选 + 对照组 + 收敛三条件 ＝ 让动态止损**能被安全执行**的保障——没有灰度，热修复就是对100%用户的豪赌
- 整个灰度环节 ＝ 四层防线里的**第③层**

**面试一句话定位**："我负责的是稳定性闭环里'归因→动态止损'这一段，用灰度把热修复这个止损手段的风险敞口控制住。"

## 可引用的真实数字（面试弹药）

- 抖音性能AB实验标准：**对照组与实验组进组用户各达100万、保持至少5天**才产出结论——印证收敛判断的"最小样本量 + 最短观察窗口"两条件（`03.md`）
- 字节防劣化体系四层：静态检测 / 线下自动化 / 灰度劣化发现归因 / 线上常态化监控
- TinkerPatch平台：条件下发（＝灰度圈选）+ 异常自动回退与快速回滚（＝止血两级）
