## 正文内容

### 一、把"插数组"这件事落地，会冒出三个问题

01结尾说：Tinker的本质就是把`patch.dex`合法地插到`dexElements`最前面。听起来就一段反射代码的事。但真要落地，立刻冒出三个问题：

1. **谁来插、什么时候插？** 插入动作本身也是代码，也要在你的App进程里跑。跑早了没进程，跑晚了（规则三）业务类已经登记、插了白插。
2. **插的`patch.dex`从哪来？** 服务器为了省流量，下发的是**差分包**（只含"改动部分"，几十KB到几MB），不是一个能直接塞进数组的完整dex。
3. **插失败了怎么办？** 这个留到模块四，本篇先把前两问讲透。

模块一的全部内容，就是回答问题1和问题2。

### 二、问题1：插入必须抢在所有业务类"登记"之前

把你熟悉的启动流程和插入动作画在一条时间线上：

```
t0  bindApplication：系统建好PathClassLoader（书库清单=APK里的dex）
t1  系统用这个管理员加载 MyApplication 类，并new出实例      ← 注意这一步！
t2  attachBaseContext()被调用 ← Tinker在这里执行插入（tryLoad()）
t3  之后任何类的首次加载 → patch.dex排最前，修复版优先命中
```

先套用**规则三**得到一条推论：

> **凡是在插入动作（t2）完成之前就被登记的类，这个进程里永远是老版本，补丁对它无效。**

所以插入必须越早越好。App开发者能拿到的最早执行钩子，就是`Application.attachBaseContext()`——这就是"什么时候插"的答案，没有更早的选择了。

但是盯住t1：**`MyApplication`这个类本身，是在t2之前就被系统加载登记的**——必须如此，不然实例都new不出来。再套规则三：

> **Application这个类，是全场唯一"注定永远无法被热修复"的业务类。**

顺带你也知道了"谁来插"的答案的前半段：插入代码只能写在Application的`attachBaseContext()`里，由Application自己触发。

### 三、推论：业务逻辑一行都不能写在Application里

假设你像普通项目一样，把业务逻辑直接写进Application：

```java
public class MyApplication extends Application {
    private UserManager userManager;              // 直接引用业务类

    @Override
    protected void attachBaseContext(Context base) {
        super.attachBaseContext(base);
        tryLoadPatch();                           // 插入补丁
        userManager = new UserManager();          // 业务初始化
    }
}
```

两个致命问题：

1. **`MyApplication`自己修不了**（上一节刚推导过）。你写在里面的初始化逻辑有bug？热修复救不了，只能发版。
2. **污染会扩散**。在`tryLoadPatch()`执行完之前跑到的任何代码，碰到的类都会被提前加载登记（规则三），全部落进"永远修不了"的名单。业务写得越多、引用得越多，死名单越长，而且你根本控制不住哪些类被提前碰到了。

所以问题变成：**怎么让"t2之前被登记的类"数量最小、且完全可控？**

Tinker的答案是把Application做成一个"**无菌壳**"——`TinkerApplication`：

- 壳里**一行业务逻辑都没有、一个业务类都不引用**。指向业务的唯一线索是一个**字符串**：

```java
public class SampleApplication extends TinkerApplication {
    public SampleApplication() {
        super(ShareConstants.TINKER_ENABLE_ALL,
              "tinker.sample.android.app.SampleApplicationLike");   // 字符串！
    }
}
```

- **为什么必须是字符串而不是类引用？** 因为字符串不会触发类加载。如果壳里写了`new SampleApplicationLike()`或者哪怕一个字段类型引用，这个类连同它牵连的类就会在t2之前被登记，全部报废。传字符串是**物理上**阻止业务类被提前加载——这才是这个设计的根本原因，"编译期解耦"只是它的表层说法。
- 壳在`attachBaseContext()`里的动作顺序严格固定：**先**反射调用`TinkerLoader.tryLoad()`完成插入（t2），**然后才**用`Class.forName(那个字符串)`反射实例化`ApplicationLike`，并把`onCreate()`等生命周期逐个转发给它。

品一下最后一步的含金量：`ApplicationLike`是**插入完成之后第一个被加载的业务类**——它的首次查找发生在t3，走的已经是"补丁优先"的路径。也就是说：

> **连"Application初始化逻辑"本身都是可热修复的**——只要它写在`ApplicationLike`里。第三节反例里修不了的300行初始化，搬进`ApplicationLike`就全都修得了。

而t2之前被登记的"死名单"，收敛为：壳 + `tinker-android-loader`模块的十几个类。这份名单是Tinker自己的、固定的、永不需要热修的类。这就是模块一第一条掌握项的完整答案。

### 四、问题2：差分包变成patch.dex——"合并"与"加载"是两个时刻、两个进程

服务器下发的差分包不能直接插，必须先和手机上已安装APK里的老dex**合并**，还原出一份完整的新dex（就是我们说的`patch.dex`）。这个合并涉及dex格式解析和重组，计算量不小，还要做dexopt预编译——放在冷启动的关键路径上，用户每次启动都得卡几秒，不可接受。

Tinker把这件事拆成**两个阶段、两个进程**：

1. **合并阶段（慢，做一次，后台）**：补丁下载完成后，业务代码调`TinkerInstaller.onReceiveUpgradePatch(context, 补丁路径)`，拉起一个**独立的`:patch`子进程**（`TinkerPatchService`）在后台执行：老dex + 差分包 → 合并成完整`patch.dex` → dexopt预编译 → 产物落盘到`/data/data/<包名>/tinker/`。**全部成功后，写一个patch info记录文件**（记录当前可用补丁的版本和校验值）。整个过程不打扰用户正在用的前台App。
2. **加载阶段（快，每次冷启动，主进程）**：**下一次冷启动**的`attachBaseContext()`里，`tryLoad()`只做轻量的事：读patch info → 校验产物完整性（MD5）→ 把现成的`patch.dex`插入查找链最前。读文件+反射插入，毫秒级，不拖累启动。

三个"为什么"现在都有了着落：

- **为什么必须等下次冷启动？** 规则三。本进程里出bug的类早已登记，缓存不可逆，当场插了也白插。只有杀进程重来、登记簿清空，"补丁排最前"的布局才有意义。
- **为什么Tinker不自己重启App？** 强杀进程是极差的用户体验，框架不越这个权。合并完就静静等用户下一次自然冷启动。（业务方可以选择在合适时机——比如App退到后台时——主动杀进程催生效，但那是业务策略，不是框架行为。）
- **为什么不每次启动实时合并、省掉后台那步？** 合并是一次性、计算密集的工作，产物稳定不变；冷启动加载是高频、要求低延迟的操作。把慢的挪到后台只做一次，把快的留在关键路径——典型的"预计算换运行时性能"，和你做接口设计时"写时计算 vs 读时计算"是同一个权衡。

### 五、完整链路串讲（模块一收口）

现在把一次补丁从生成到生效的所有关键节点串起来——这就是第二条掌握项要求你能口述的内容：

```
[构建机] 用基准包+修复后代码，生成差分补丁包
    ↓ 上传分发服务，灰度下发（课程1的内容）
[用户设备·主进程] App运行中下载补丁包 → 调用onReceiveUpgradePatch()
    ↓
[用户设备·:patch子进程] 后台合并：老dex+差分包 → 完整patch.dex
                        → dexopt → 落盘 → 写patch info    ←【合并时刻】
    ↓ （等待……用户该干嘛干嘛）
[下次冷启动·主进程] TinkerApplication.attachBaseContext()
    → tryLoad()：读patch info → MD5校验 → patch.dex插入查找链最前  ←【生效时刻】
    → 反射实例化ApplicationLike，转发生命周期
    → 业务代码开始跑，所有类首次查找都是补丁优先 → 修复版生效
```

记住"合并"和"生效"是**两个不同时刻**：合并发生在下载后的后台，生效发生在下次冷启动。中间可以隔几分钟，也可以隔三天——patch info文件就是横跨这两个时刻的"交接凭证"。

下一篇进模块二：`tryLoad()`里"插入查找链最前"这半句话，在不同Android版本上做法完全不同——Android 7.0以下是真的反射改`dexElements`数组，7.0及以上换成了整个new一个新ClassLoader。为什么会分家？这就要讲到Dalvik和ART的差异了。
