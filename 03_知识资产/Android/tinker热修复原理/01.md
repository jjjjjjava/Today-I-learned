# 类加载器基础：APK里的代码是怎么跑起来的

> 前置知识：Android App进程启动流程（Zygote fork → bindApplication → 创建Application）；**不需要**事先了解ClassLoader、dex、双亲委派中的任何一个词
> 难度：入门
> 预计阅读时间：15分钟

## 正文内容

### 一、从你已经懂的流程里，挖出一个你没注意过的问题

你熟悉这条链路：

```
Zygote fork进程 → bindApplication → 系统反射创建你的Application实例 → attachBaseContext → onCreate
```

现在盯住"**反射创建你的Application实例**"这一步，问一个从没问过的问题：

> 系统要`new`一个`MyApplication`对象——可是此刻进程刚fork出来，内存里根本还没有`MyApplication`这个类。**类的代码躺在磁盘上的APK文件里，它是怎么进到内存、变成一个能用的类的？**

干这件事的角色，就叫**类加载器（ClassLoader）**。你在启动流程里见过的`loadApkDex`、`LoadedApk.getClassLoader()`，就是系统在准备这个角色。整篇文章就讲清楚它的三条工作规则——就三条。这三条规则是整门课的地基，Tinker的所有设计都是从它们推出来的。

### 二、类在磁盘上长什么样：dex是装类的集装箱

先看货物本身。你写的`MyApplication.java`，经过编译后变成字节码，打包APK时和成百上千个其他类一起，被装进一个叫 **`classes.dex`** 的文件里（类太多装不下就再来一个`classes2.dex`、`classes3.dex`……）。你把任何一个APK当zip解压，都能看到这几个dex文件。

所以记住第一个对应关系：

> **dex文件 = 装了一大批类的集装箱**。你的APK里有几个dex，进程启动时这些dex就是"货源"。

而"**加载一个类**"这个动作的准确含义是：去dex里找到这个类的字节码记录，读进内存，构建出一个`Class`对象（可以理解为这个类的"说明书"：有哪些字段、哪些方法、方法代码在哪）。之后`new`实例、调方法，全靠这份说明书。

还有一个重要事实：类**不是**启动时一口气全加载的，而是**第一次被用到时才加载**（懒加载）。你的App有一万个类，启动只碰到三百个，就只加载三百个。

### 三、类加载器：一个"图书管理员"

现在给这套东西一个好记的模型：

| 模型 | 真实身份 |
|---|---|
| 书库 | dex文件（一批类的集装箱） |
| 书 | 一个类的字节码 |
| 书名 | 全类名，如`tinker.sample.android.app.MainActivity` |
| **图书管理员** | **ClassLoader** |
| 借书登记簿 | 已加载类的缓存 |

你（虚拟机）报一个书名，管理员去他管的书库里翻，翻到了就把书取出来登记、交给你。

你的App进程里，主要有两位管理员：

1. **BootClassLoader**——管**系统书库**：`Activity`、`String`、`Context`这些Android framework和Java核心类。
2. **PathClassLoader**——管**你的APK书库**：你自己写的所有类、你引入的三方库。它手里的书库列表，就是你APK里那几个dex。

这第二位就是主角。**bindApplication阶段`LoadedApk.getClassLoader()`创建的，就是这个PathClassLoader**——你之前说的"loadApkDex加载类加载器"，干的就是"雇好这位管理员、把APK的dex书库清单交到他手上"这件事。此后进程里所有你自己的类，都由他负责取。

两位管理员之间有上下级关系：PathClassLoader的上级（parent）是BootClassLoader。这个上下级关系引出第一条规则。

### 四、规则一：双亲委派——先问上级，上级没有才自己找

管理员收到一个书名后，标准工作流程是固定的三步（这就是`loadClass()`方法的逻辑，伪代码）：

```java
Class loadClass(String 书名) {
    // 第1步：查自己的借书登记簿——这本书之前借出过吗？
    Class c = 查缓存(书名);
    if (c != null) return c;          // 借出过，直接给缓存里那本

    // 第2步：先问上级（parent）有没有这本书
    c = parent.loadClass(书名);
    if (c != null) return c;          // 上级有，用上级的

    // 第3步：上级没有，才自己翻书库（这一步叫 findClass）
    return findClass(书名);
}
```

第2步就是**双亲委派**：任何类先交给上级找，上级找不到才轮到自己。所以：

- 你要`String`：PathClassLoader问上级BootClassLoader → 系统书库里有 → 用系统的。
- 你要`MainActivity`：问上级 → 系统书库里没有 → PathClassLoader自己翻APK的dex → 找到。

**为什么要这么设计？** 防伪。假如没有这条规则，谁往你的书库里塞一本假的`java.lang.String`，你的进程就会用上被篡改的核心类——安全体系全崩。有了"先问上级"，`String`永远从系统书库取，你书库里的同名假书永远轮不到被翻开。（顺带的好处：同一个类全进程只有一份，不会两个管理员各造一份说明书打架。）

### 五、规则二：dexElements数组——按顺序翻书库，先找到先赢

第3步"自己翻书库"，PathClassLoader内部具体怎么翻？

他管的书库不止一个（`classes.dex`、`classes2.dex`……），这些书库在他内部排成一个**有序数组**，字段名叫 **`pathList.dexElements`**。翻的方式朴素到让人意外——**for循环按顺序一个一个翻**：

```java
Class findClass(String 书名) {
    for (Element dex : dexElements) {     // 按数组顺序逐个书库找
        Class c = dex.findClass(书名);
        if (c != null) return c;          // 找到了？立刻返回，后面的书库不看了
    }
    throw new ClassNotFoundException();
}
```

关键就一句：**找到即返回，排在后面的dex永远没机会被翻到**。

现在做个思想实验。假设有人在这个数组的**最前面**插了一个新书库`patch.dex`，里面只装了一本书：修复过bug的`MainActivity`。数组变成：

```
[ patch.dex , classes.dex , classes2.dex ]
     ↑              ↑
 修复版MainActivity   老的buggy版MainActivity（还在，但永远轮不到）
```

之后第一次有人要`MainActivity`：for循环先翻`patch.dex`→找到修复版→返回。**老的类一个字节都没被删改，只是被"挡"在了后面。**

到这里你其实已经自己推导出Tinker dex补丁的核心机制了。是的，就这么简单：**Tinker干的事，本质就是想办法把补丁dex合法地插到这个数组的最前面**（高版本Android的做法略有变化，后面的模块会讲，但"补丁优先于原始dex被查找"这个本质不变）。

### 六、规则三：登记簿不可逆——加载过的类，这个进程里永远换不掉

回看`loadClass()`的**第1步**：先查登记簿，借出过就直接给缓存的那本。

这条规则的狠处在于：**登记簿只进不出**。一个类一旦被加载，它的`Class`对象就被缓存，进程活着的整个期间，之后对这个类的所有请求都直接命中缓存——**第2步、第3步再也不会执行**。虚拟机没有提供任何"把这个类注销掉、重新加载一遍"的机制。

再做个思想实验：进程已经跑了一阵，老版`MainActivity`早就被加载过、登记在册了。这时你才把`patch.dex`插到数组最前面——有用吗？

> 没用。下次要`MainActivity`，第1步查登记簿直接命中老版返回，你插在最前面的补丁dex根本没机会被翻。

这条规则决定了Tinker的两个关键行为，下一篇会正式展开：**补丁为什么必须等下次冷启动才生效**，以及**插入动作为什么必须抢在启动的最早时刻做**。

### 七、三条规则收拢

| 规则 | 一句话 | 决定了Tinker的什么 |
|---|---|---|
| 双亲委派 | 先问上级，上级没有才自己找 | 补丁只能修你自己的类，动不了系统类 |
| dexElements顺序查找 | 按数组顺序翻dex，先找到先赢 | 补丁dex插到最前 = 修复类"遮蔽"原类 |
| 已加载缓存不可逆 | 登记过的类永远用缓存，无法重载 | 必须冷启动才生效；插入必须抢最早时机 |
