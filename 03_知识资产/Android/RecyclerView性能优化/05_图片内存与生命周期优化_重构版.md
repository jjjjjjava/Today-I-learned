# 05｜Item 离屏后，资源为什么还在消耗？

> 本篇只解决一个问题：**一个 Item 已经看不见，甚至已经被复用，为什么图片、任务、播放器和内存仍可能继续消耗资源？**

---

## 5.0｜先把本篇放回整体性能模型

前四篇已经处理了 RecyclerView 的四类主要成本：

```text
创建 Holder → 绑定数据 → 布局与绘制 → 数据更新
```

但列表还有一类容易被忽略的成本：

```text
Item 展示期间启动资源
→ Item 离屏或被复用
→ 旧资源没有及时停止
→ CPU、内存、网络和主线程继续承压
```

因此，本篇关注三件事：

1. **单个资源是否过大**：例如缩略图却解码了原图；
2. **资源是否活得过久**：例如 Item 离屏后视频仍在播放；
3. **临时对象是否产生得过快**：例如每次绑定都创建大量对象。

可以先记住一个模型：

```text
资源压力 ≈ 单次资源体积 × 同时存活数量 × 创建频率 × 存活时间
```

优化不等于“什么都不创建”，而是控制这四个变量。

---

## 5.1｜场景一：缩略图为什么会吃掉几十 MiB？

### 5.1.1 文件大小不等于 Bitmap 内存

JPEG、WebP 的文件大小是**压缩后的存储或传输体积**；图片显示前通常要解码成像素数据。

以 `ARGB_8888` 为例：

```text
Bitmap 内存 ≈ 解码宽度 × 解码高度 × 4 Byte
```

一张 `4000 × 3000` 的 JPEG，即使文件只有 `2 MB`，完整解码后仍约占：

```text
4000 × 3000 × 4 Byte ≈ 45.8 MiB
```

如果 Item 最终只显示 `400 × 300`，接近目标尺寸的 Bitmap 只需：

```text
400 × 300 × 4 Byte ≈ 0.46 MiB
```

两者相差约 100 倍。

### 5.1.2 真正该优化的是“解码尺寸”

低效路径：

```text
下载或读取原图
→ 完整解码 4000 × 3000
→ 占用约 45.8 MiB
→ ImageView 再缩小显示
```

更合理的路径：

```text
确定 ImageView 的显示尺寸
→ 按目标尺寸请求或采样
→ 解码出接近显示尺寸的 Bitmap
→ 显示
```

`ImageView.scaleType = centerCrop` 只决定图片在 View 中**如何显示**，不保证上游已经按目标尺寸解码。

### 5.1.3 使用图片库时怎么做？

Glide：

```kotlin
Glide.with(imageView)
    .load(item.imageUrl)
    .override(targetWidth, targetHeight)
    .centerCrop()
    .into(imageView)
```

Coil：

```kotlin
imageView.load(item.imageUrl) {
    size(targetWidth, targetHeight)
    crossfade(false)
}
```

先检查以下问题：

- `ImageView` 尺寸是否明确；
- 请求尺寸是否接近实际显示尺寸；
- 是否为了缩略图统一请求原图；
- 圆角、模糊、裁剪等变换是否确有必要；
- 快速滑动时是否同时启动了过多解码任务。

> 核心结论：**缩略图优化的关键不是“文件压得更小”，而是“不要解码出用不到的像素”。**

## 5.2｜场景二：Holder 已复用，旧结果为什么还会回来？

### 5.2.1 复用改变了 Holder 的身份

```text
Holder 绑定 A
→ 启动 A 的异步任务
→ Holder 被复用给 B
→ A 的任务完成
→ 旧结果写进正在展示 B 的 Holder
```

这里有两个问题：

- **正确性问题**：B 显示了 A 的结果；
- **性能问题**：A 已无展示价值，任务却仍消耗 CPU、I/O 或网络。

更推荐的职责分工是：

```text
Repository / ViewModel
→ 完成网络、数据库和复杂计算
→ 生成 UI Model
→ Adapter / Holder 只负责展示
```

### 5.2.2 确实需要在 Holder 中启动任务时

要同时守住两道门：

```text
重新绑定时取消旧任务
＋
回收时取消与旧 Item 强关联的任务
```

```kotlin
class ItemHolder(
    itemView: View,
    private val scope: CoroutineScope
) : RecyclerView.ViewHolder(itemView) {

    private var bindJob: Job? = null

    fun bind(item: Item) {
        bindJob?.cancel()

        bindJob = scope.launch {
            val result = loadSomething(item)
            ensureActive()
            title.text = result
        }
    }

    fun recycle() {
        bindJob?.cancel()
        bindJob = null
    }
}

override fun onViewRecycled(holder: ItemHolder) {
    holder.recycle()
    super.onViewRecycled(holder)
}
```

注意：`cancel()` 只是发出取消信号。阻塞 I/O 或不检查取消状态的计算，不一定会立即停止。

## 5.3｜Attached、Detached、Recycled 到底怎么选？

不要把三个回调理解成同一个“离开页面”事件。

| 状态 | 绑定关系 | 适合做什么 |
|---|---|---|
| `onViewAttachedToWindow()` | 通常仍绑定当前 Item | 开始仅对可见 Item 有意义的工作 |
| `onViewDetachedFromWindow()` | 可能仍保留 | 暂停视频、动画、高频 UI 更新 |
| `onViewRecycled()` | 原绑定关系即将失效 | 取消旧任务、移除观察者、释放强关联资源 |

关键区别：

```text
Detached = 暂时看不见，但可能还记得自己是谁
Recycled = 原身份即将失效，可能马上变成另一个 Item
```

### 一个视频 Item 的典型策略

```text
Attached  → 恢复播放
Detached  → 暂停播放
Recycled  → 解绑数据并释放旧 Item 强关联资源
页面销毁   → 由页面或更高层统一彻底清理
```

资源释放也要考虑重建成本。频繁 Detached 时就彻底销毁播放器，可能从“占用过久”变成“反复创建”。应结合资源重量、复用概率和业务体验决定释放层级。

## 5.4｜每次绑定都必须覆盖当前 Item 的完整状态

RecyclerView 会复用 View，因此绑定不是“补充变化”，而是把 View 恢复成当前 Item 应有的状态。

错误示例：

```kotlin
if (item.coverUrl != null) {
    Glide.with(holder.cover)
        .load(item.coverUrl)
        .into(holder.cover)
}
```

当新 Item 没有图片时，代码什么都不做，旧图片可能残留。

更完整的写法：

```kotlin
Glide.with(holder.cover)
    .load(item.coverUrl)
    .placeholder(R.drawable.cover_placeholder)
    .error(R.drawable.cover_error)
    .fallback(R.drawable.cover_placeholder)
    .into(holder.cover)
```

这类处理首先保证**复用正确性**，其次才是避免旧请求和无效工作。它与“按目标尺寸解码”不是同一种收益：

```text
完整覆盖状态 → 首先解决显示错误
控制解码尺寸 → 直接降低解码与内存成本
```

### 点击监听器也不能记住旧位置

推荐在 Holder 初始化时注册一次，并使用当前 Item：

```kotlin
class ItemHolder(
    itemView: View,
    private val onClick: (Item) -> Unit
) : RecyclerView.ViewHolder(itemView) {

    private var currentItem: Item? = null

    init {
        itemView.setOnClickListener {
            currentItem?.let(onClick)
        }
    }

    fun bind(item: Item) {
        currentItem = item
    }

    fun recycle() {
        currentItem = null
    }
}
```

如果点击时读取 `bindingAdapterPosition`，必须先排除 `RecyclerView.NO_POSITION`。不要永久捕获绑定时的旧 `position`。

## 5.5｜场景三：没有泄漏，为什么仍频繁 GC？

### 5.5.1 内存抖动不是内存泄漏

```text
内存抖动：对象能被回收，但创建和回收过于频繁
内存泄漏：对象本应被回收，却仍被错误引用
```

滚动时，主线程本来就要处理获取 Holder、绑定、布局和绘制。如果绑定或绘制又持续分配临时对象，就可能形成：

```text
高频分配 → 堆增长 → GC → CPU 波动 → 慢帧风险
```

但“发生 GC”不等于“GC 导致卡顿”。必须验证 GC 的频率、耗时，以及它是否与慢帧重合。

### 5.5.2 优先检查“高频 × 大量 × 昂贵”

建议排查顺序：

```text
大 Bitmap 与错误解码尺寸
→ 动态 inflate / 动态子 View
→ 富文本、复杂格式化与集合转换
→ LayoutParams 和 Item 尺寸变化
→ 绘制回调中的临时对象
→ 普通小对象
```

#### 把重复计算前移

不推荐：

```kotlin
holder.price.text = DecimalFormat("0.00").format(item.price)
holder.time.text = expensiveDateFormat(item.timestamp)
holder.title.text = buildComplexSpannable(item.title)
```

可以在后台或 ViewModel 中生成 UI Model：

```kotlin
data class ProductUiModel(
    val id: Long,
    val displayPrice: String,
    val displayTime: String,
    val styledTitle: CharSequence
)
```

但预计算不是免费午餐：如果大量 Item 长期保存很重的富文本对象，可能用长期内存换取绑定时间。应根据列表规模和复用频率权衡。

#### 避免反复重建子 View

```kotlin
holder.tagContainer.removeAllViews()
item.tags.forEach { tag ->
    val view = inflater.inflate(R.layout.item_tag, holder.tagContainer, false)
    holder.tagContainer.addView(view)
}
```

它同时产生：

```text
对象分配 + View 树变化 + requestLayout + measure/layout
```

可考虑复用已有标签 View、固定槽位显示/隐藏，或在标签未变化时通过 Payload 跳过重建。

#### 绘制对象应尽量复用

```kotlin
class DividerDecoration : RecyclerView.ItemDecoration() {
    private val paint = Paint(Paint.ANTI_ALIAS_FLAG)
    private val bounds = Rect()
}
```

`onDraw()`、`onDrawOver()` 可能比绑定调用得更频繁，不应每帧重复创建 `Paint`、`Rect` 等对象。

> 优化目标不是机械追求“零分配”，而是先消除真正进入关键路径的高频、大量、昂贵分配。

## 5.6｜一条可执行的排查路径

### 图片内存过高

```text
原图分辨率是多少？
→ ImageView 实际显示多大？
→ 请求与解码尺寸是否接近目标？
→ 是否同时持有过多大 Bitmap？
→ Profiler 中 Bitmap 占用是否下降？
```

### Item 离屏后仍消耗资源

```text
这项工作是否只对可见 Item 有意义？
→ 是：Detached 时暂停
→ 是否与旧 Item 身份强关联？
→ 是：重新绑定或 Recycled 时取消/解绑
→ 页面销毁时由更高层统一清理
```

### Holder 出现旧状态

```text
绑定是否覆盖全部可变状态？
→ 空值分支是否也明确提交或清空？
→ 旧任务是否取消或校验身份？
→ 点击是否捕获了旧 position？
```

### 滚动时频繁 GC

```text
先找到慢帧附近的 GC
→ 查看高频分配类型和调用点
→ 优先修改一个高频、大量、昂贵来源
→ 用相同场景复测分配率、GC 和慢帧
```

## 5.7｜常见误区

1. **图片文件只有 2 MB，解码后也只占 2 MB。**  文件体积不等于像素内存。
2. **设置 `centerCrop` 就已经按目标尺寸解码。**  它主要控制显示方式。
3. **用了 Glide，就不用处理空 URL。**  如果空分支没有提交新请求或清空 View，旧图仍可能残留。
4. **Detached 后一定马上 Recycled。**  Detached 后仍可能保留原绑定关系并进入缓存。
5. **所有异步任务都适合放进 Holder。**  网络、数据库和复杂计算通常应放在更高层。
6. **看到 GC 就必须优化。**  先确认频率、耗时及其与慢帧的关系。
7. **`onBindViewHolder()` 必须零分配。**  应优先处理高频、大量、昂贵的分配。
8. **清理 ImageView 请求等于清空图片库缓存。**  前者主要解除目标与请求的关系，后者是全局缓存策略。

## 5.8｜本篇速记

```text
图片过大      → 按显示尺寸请求和解码
旧结果回写    → 新绑定取消旧任务，并校验当前身份
离屏仍在工作  → Detached 暂停可见性工作
Holder 将复用 → Recycled 清理旧 Item 强关联资源
频繁 GC       → 找到高频 × 大量 × 昂贵的分配
```

> 最终原则：**控制资源体积，缩短无效存活时间，降低高频创建，并让资源生命周期与 Holder 状态对齐。**
