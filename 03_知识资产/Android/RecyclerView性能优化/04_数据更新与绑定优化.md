# 04｜数据更新与绑定：只做真正变化的工作

## 1. 本篇只解决一个问题

> **数据变化后，怎样把更新范围缩到最小，并让每次绑定足够轻？**

整个优化模型只有三层：

```text
DiffUtil
→ 缩小“哪些 Item 需要更新”

Payload
→ 缩小“一个 Item 内哪些 View 需要更新”

轻量绑定
→ 降低“每次必要更新”的成本
```

高频数据还需要限频或合并，防止 Diff 和 UI 更新本身变成负担。

---

## 2. 先区分：修改数据与通知变化

正确顺序是：

```text
先产生新数据
    ↓
再告诉 RecyclerView 哪些位置发生变化
```

`notifyDataSetChanged()` 不负责修改数据，它只是声明“整个数据集都可能变了”。

| 通知方式 | 声明范围 | 绑定范围 |
|---|---|---|
| `notifyDataSetChanged()` | 整个数据集 | 失效范围最大 |
| `notifyItemChanged(position)` | 一个 Item | 默认完整绑定该 Item |
| `notifyItemChanged(position, payload)` | 一个 Item 的局部内容 | 可只更新对应子 View |

---

## 3. DiffUtil：找出哪些 Item 变了

假设新闻模型为：

```kotlin
data class News(
    val id: Long,
    val title: String,
    val likeCount: Int
)
```

DiffUtil 需要回答两个不同问题：

```kotlin
val NEWS_DIFF = object : DiffUtil.ItemCallback<News>() {
    override fun areItemsTheSame(old: News, new: News): Boolean =
        old.id == new.id

    override fun areContentsTheSame(old: News, new: News): Boolean =
        old == new
}
```

| 回调 | 判断的问题 | 常用依据 |
|---|---|---|
| `areItemsTheSame()` | 是否是同一个业务实体？ | 稳定、唯一的业务 ID |
| `areContentsTheSame()` | 这个实体的展示内容是否改变？ | UI 数据内容比较 |

同一新闻点赞数从 20 变为 21：

```text
areItemsTheSame()    = true
areContentsTheSame() = false
```

含义是“同一个 Item 内容更新”，而不是“删除旧 Item，再插入新 Item”。

---

## 4. ListAdapter 与 AsyncListDiffer 怎么选

### 普通列表：优先 ListAdapter

```kotlin
class NewsAdapter : ListAdapter<News, NewsHolder>(NEWS_DIFF) {
    override fun onBindViewHolder(holder: NewsHolder, position: Int) {
        holder.bind(getItem(position))
    }
}
```

```kotlin
adapter.submitList(newList)
```

内部大致完成：

```text
旧列表 + 新列表
→ 后台计算差异
→ 主线程应用结果
→ 派发局部更新
```

Diff 比较可以在后台进行，但真正的 View 绑定、布局和绘制仍在主线程。

### 已有自定义 Adapter 体系：使用 AsyncListDiffer

它通过组合方式管理列表，更灵活；`ListAdapter` 本质上是对这套常用流程的封装。

---

## 5. 为什么必须提交不可变快照

错误写法：

```kotlin
val list = mutableListOf(A, B, C)
adapter.submitList(list)

list.add(D)
adapter.submitList(list)
```

旧列表和新列表是同一个对象，Diff 可能无法观察到可靠的前后差异。

推荐写法：

```kotlin
val newList = oldList + D
adapter.submitList(newList)
```

更新 Item 也创建新对象：

```kotlin
val updated = oldNews.copy(
    likeCount = oldNews.likeCount + 1
)
```

原则是：

> **DiffUtil 比较的是两个时刻的快照；如果旧快照也被原地改掉，就失去了比较基准。**

## 6. Payload：只更新 Item 内真正变化的部分

假设只有点赞数变化。完整绑定可能重复设置标题、图片和布局；Payload 可以只更新点赞数。

```kotlin
data class NewsPayload(
    val titleChanged: Boolean = false,
    val likeCountChanged: Boolean = false
)
```

```kotlin
override fun getChangePayload(old: News, new: News): Any =
    NewsPayload(
        titleChanged = old.title != new.title,
        likeCountChanged = old.likeCount != new.likeCount
    )
```

```kotlin
override fun onBindViewHolder(
    holder: NewsHolder,
    position: Int,
    payloads: MutableList<Any>
) {
    if (payloads.isEmpty()) {
        holder.bindFull(getItem(position))
        return
    }

    val item = getItem(position)
    payloads.filterIsInstance<NewsPayload>().forEach { payload ->
        if (payload.titleChanged) holder.title.text = item.title
        if (payload.likeCountChanged) {
            holder.likeCount.text = item.likeCount.toString()
        }
    }
}
```

完整链路：

```text
submitList(newList)
→ 找到同一个业务 Item
→ 确认内容发生变化
→ getChangePayload()
→ 局部绑定
```

### Payload 不是强保证

Holder 不可见、状态失效或其他条件变化时，之后仍可能执行完整绑定。因此：

- `payloads` 为空时必须完整绑定；
- 完整绑定必须恢复所有 View 状态；
- Payload 只能作为减少工作量的优化路径。

### 什么时候值得使用

```text
低频更新 + 完整绑定只是少量属性赋值
→ 收益可能很小

高频更新，或完整绑定包含图片、富文本、动态 View、布局变化
→ 通常更有价值
```

---

## 7. 让完整绑定保持轻量

`onBindViewHolder()` 在主线程运行，快速滚动时一帧可能连续绑定多个 Item。

### 把昂贵且与 View 无关的加工提前完成

不推荐反复格式化：

```kotlin
holder.time.text = formatTimestamp(item.timestamp)
```

可在 ViewModel 或后台生成 UI Model：

```kotlin
data class NewsUiModel(
    val id: Long,
    val title: String,
    val displayTime: String
)
```

适合提前处理：

- 日期、价格、文件大小格式化；
- 排序、过滤和复杂映射；
- Markdown、HTML、富文本解析；
- 复杂状态组合和字符串拼接。

简单减法和轻量分支不必为了“零计算”而过度设计。

### 不在绑定中阻塞主线程

不要在绑定阶段执行：

```text
文件读取 / 数据库查询 / 同步网络请求 / 大图解码
```

更合理的链路：

```text
后台获取与加工
→ UI Model
→ submitList()
→ 主线程只负责呈现
```

### 谨慎动态创建子 View

每次绑定都 `removeAllViews()`、inflate、addView，会产生分配和重新布局。可根据场景：

- 复用已有子 View；
- 结构固定时预创建并切换内容或可见性；
- 数据未变时通过 Payload 避免重建；
- 数量很多时再评估专用布局或嵌套列表。

---

## 8. 高频更新：先限频，再 Diff，再 Payload

以下载进度为例，如果每收到一个字节就提交列表，Diff 和 UI 派发本身也会过载。

推荐流程：

```text
下载层产生大量进度事件
        ↓
限频或合并，例如每 100～500 ms 更新一次 UI
        ↓
创建新 Item 与新列表快照
        ↓
submitList()
        ↓
Diff 找出变化 Item
        ↓
Payload 只更新进度条和百分比
```

DiffUtil 不负责计算进度，它只比较新旧 UI 数据。

动态时间文案也类似：“几分钟前”会随时间变化，不能只在首次进入页面时计算一次。可通过定时信号产生新 UI 快照，再用 Diff + Payload 更新对应 TextView。

---

## 9. 用 Trace 验证收益

不要假设 Payload 一定提升多少。应同时测量耗时和调用次数：

```kotlin
Trace.beginSection("NewsAdapter#fullBind")
try {
    bindFull(holder, item)
} finally {
    Trace.endSection()
}
```

```kotlin
Trace.beginSection("NewsAdapter#payloadBind")
try {
    bindLikeCount(holder, item)
} finally {
    Trace.endSection()
}
```

在 Perfetto 或 System Trace 中比较：

- 完整绑定与局部绑定各调用多少次；
- 单次耗时和总耗时；
- 慢帧期间是否出现连续绑定；
- 优化后是否把峰值降到帧预算以内。

---

## 10. 推荐决策链

```text
数据发生变化
├── 整个列表真的都不确定？
│   └── 是：才考虑全量刷新
└── 能得到旧、新列表？
    └── 用 DiffUtil 找变化 Item
        ↓
某个 Item 只有部分字段变化？
├── 否：完整绑定
└── 是：评估 Payload
        ↓
更新频率很高？
└── 先限频或合并事件
```

## 11. 本篇自测

1. `areItemsTheSame()` 与 `areContentsTheSame()` 分别回答什么？
2. 为什么原地修改同一个可变列表会破坏 Diff 的比较基础？
3. Payload 为什么不能替代完整绑定？
4. 为什么后台计算 Diff 不代表列表更新完全离开主线程？
5. 下载进度为什么应先限频，再使用 Diff 和 Payload？

### 本篇一句话总结

> **DiffUtil 缩小 Item 范围，Payload 缩小 View 范围，轻量绑定降低单次成本，而高频事件必须先限频。**
