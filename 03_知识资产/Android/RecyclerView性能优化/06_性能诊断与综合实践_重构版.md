# 06｜列表已经卡了，第一步到底查什么？

> 本篇只解决一个问题：**当用户说“这个列表很卡”时，如何从模糊感受走到可验证的根因，而不是凭经验乱改代码？**

---

## 6.0｜先建立唯一主线

前五篇分别讨论了创建、复用、绑定、布局绘制、数据更新，以及图片与资源生命周期。但真实项目不会主动告诉你“这是绑定问题”。你看到的通常只有：

> 首次进入商品列表，快速滑动时偶尔卡一下。

诊断的任务，是把这句话逐步收敛为证据链：

```text
线上发现异常
→ 固定场景并稳定复现
→ 找到真正的慢帧
→ 判断线程为什么没按时完成
→ 定位关键阶段
→ 提出可证伪假设
→ 单变量实验
→ 相同条件复测
→ 灰度并观察线上回归
```

先记住三条纪律：

1. **先找慢帧，不先猜方法。**
2. **相关性不是因果，必须做实验。**
3. **优化前后条件必须一致。**

---

## 6.1｜第一步：把“很卡”改写成可复现问题

### 6.1.1 慢帧不等于平均 FPS 低

60 Hz 屏幕单个刷新周期约为：

```text
1000 ms ÷ 60 ≈ 16.67 ms
```

但不能把所有超过 `16.67 ms` 的帧简单归为同一种问题，因为还要考虑：

- 90 Hz、120 Hz 等不同刷新率；
- VSync、线程调度和渲染管线；
- 不同工具和平台的卡顿口径。

工程上应优先使用工具给出的实际帧指标，并关注**帧时间分布和尾部体验**，而不只看平均值。

### 6.1.2 分位数在回答什么？

如果某平台按 FPS 从高到低统计，通常有：

```text
P50 ≥ P90 ≥ P99
```

例如：

```text
P50 = 56，P90 = 43，P99 = 18
```

它表达的是：多数访问接近流畅，但尾部少量访问非常卡。具体定义要以监控平台口径为准。

### 6.1.3 一条合格的问题描述

不要写：

> 商品列表线上很卡。

应写成：

> 应用 8.2.0 中，Android 12 某档低端机在冷启动、清空图片缓存后首次进入商品列表，并立即快速滑动时，尾部帧体验明显下降；第二次进入相对正常。

至少固定：

```text
应用版本 + 设备/系统 + 冷热启动 + 缓存状态
+ 测试数据 + 网络条件 + 操作脚本 + 采集方式
```

只有条件固定，优化前后的数据才可比较。

---

## 6.2｜第二步：找到慢帧后，先看主线程状态

不要一上来就展开 `onBindViewHolder()`。先问：**主线程为什么没有按时完成？**

| 状态 | 主线程发生了什么 | 首要方向 |
|---|---|---|
| `Running` | 正在 CPU 上执行 | 主线程自身做了重任务 |
| `Runnable` | 已准备执行，但没拿到 CPU | CPU 竞争或调度延迟 |
| `Blocked / Sleeping` | 正在等待结果 | 锁、I/O、Binder 或同步等待 |

### 三个具体画面

#### Running 很长

```text
主线程拿到了 CPU
→ 自己执行 inflate、bind、layout 或计算
→ 工作本身太重
```

#### Runnable 很长

```text
主线程已经准备好
→ 但多个图片解码线程占用 CPU
→ 主线程迟迟拿不到运行机会
```

主线程实际只执行 5 ms，也可能因为此前等待 18 ms 而错过截止时间。

#### Blocked 很长

```text
主线程发起同步调用
→ 等待锁、磁盘、Binder 或后台结果
→ 自己没有执行，但帧仍然无法完成
```

> 先区分“执行慢、排队慢、等待慢”，因为三者的修复方式完全不同。

---

## 6.3｜第三步：如果主线程 Running 很长，再判断是哪一阶段

把前五篇的知识映射到 Perfetto 关键路径：

| 主要证据 | 初步分类 | 回到哪类优化 |
|---|---|---|
| `onCreateViewHolder → inflate` 较宽 | 创建瓶颈 | 简化 Item、减少集中创建、检查预热与 Pool |
| `onBindViewHolder` 较宽 | 绑定瓶颈 | Payload、预计算、移除同步 I/O、减少分配 |
| `onLayout / layoutChildren / measure` 较宽 | 布局瓶颈 | 稳定尺寸、减少 `requestLayout()`、检查嵌套 |
| `draw / dispatchDraw` 较宽 | 主线程绘制瓶颈 | 过度绘制、复杂 Path、透明叠层 |
| RenderThread / GPU 延迟 | 渲染瓶颈 | 阴影、模糊、裁剪、大图与 GPU 压力 |

### 6.3.1 创建慢

典型证据：

```text
onCreateViewHolder
└── inflate
```

如果首次进入或快速滑动集中发生，而第二次进入明显改善，优先检查：

- Item 层级和控件是否过重；
- 是否短时间创建了过多 Holder；
- 嵌套列表是否可共享 `RecycledViewPool`；
- 预取、缓存或预热策略是否与场景匹配。

验证实验：只用简化布局替换 Item，或只预热少量 Holder，然后观察 `inflate` 和慢帧是否同步下降。

### 6.3.2 绑定慢

典型证据：`onBindViewHolder` 在慢帧关键路径中反复出现且较宽。

优先检查：

- 是否每次完整绑定；
- 是否进行格式化、排序、富文本构建或集合转换；
- 是否执行同步文件、数据库或网络操作；
- 是否产生大量临时对象；
- 图片请求和转换参数是否过重。

系统 Trace 只能看到整个 bind 时，可加入业务 Trace：

```kotlin
trace("RV.bind.price") { bindPrice(item) }
trace("RV.bind.image") { bindImage(item) }
```

### 6.3.3 布局慢

典型证据：

```text
RecyclerView.onLayout
layoutChildren
measure / layout
```

优先检查：

- Item 尺寸是否反复变化；
- 绑定是否频繁触发 `requestLayout()`；
- 是否存在深层嵌套、权重或嵌套 RecyclerView；
- ItemAnimator 是否放大更新成本；
- 一次更新是否影响了过多 Item。

验证时一次只改一个变量，例如只关闭 ItemAnimator，或只固定 Item 尺寸。

### 6.3.4 绘制或渲染慢

不要只看主线程 `draw`。主线程提交较快，不代表 RenderThread 或 GPU 已及时完成。

优先检查：

- 过度绘制和大面积透明叠层；
- 阴影、模糊、圆角裁剪；
- 复杂 Path；
- 大图缩放；
- 频繁 `invalidate()`；
- RenderThread 与 GPU 完成时间。

## 6.4｜第四步：主线程不重时，检查三类隐藏瓶颈

### 6.4.1 图片线程造成 CPU 竞争

图片解码在后台，不代表它不会影响主线程。

可能链路：

```text
冷缓存下大量图片并发解码
→ CPU 核心被后台线程占用
→ 主线程长时间 Runnable
→ 错过帧截止时间
```

合格验证：

```text
固定设备、数据、缓存、网络和脚本
→ 只把图片替换为固定占位图
→ 重录 Perfetto
→ 比较 Runnable 时间与慢帧数量
```

两者同步改善，才支持“图片解码造成 CPU 竞争”的判断。

### 6.4.2 GC 与高频分配

锯齿形内存曲线本身不是结论。完整证据应是：

```text
滚动或绑定阶段高频分配某类对象
→ GC 频率或暂停时间上升
→ GC 与慢帧重合
→ 移除该分配后两者同步改善
```

工具组合：

- Perfetto：看 GC 是否进入慢帧关键时间段；
- Memory Profiler：看分配速率、对象类型和调用点。

### 6.4.3 主线程同步阻塞

常见来源：

- 同步磁盘 I/O；
- 锁竞争；
- Binder 调用；
- `Future.get()`、`Thread.join()`；
- 主线程数据库查询；
- 等待后台任务结果。

如果主线程主要是 `Blocked`，盲目简化 Item 布局通常不会解决问题。

## 6.5｜工具不是越多越好：每个工具只回答一个问题

| 工具 | 最适合回答的问题 |
|---|---|
| Bugly Pro | 哪些页面、版本、设备和用户场景异常？ |
| JankStats | 哪个业务状态更容易出现慢帧？ |
| Perfetto | 这一帧为何没有按时完成？ |
| CPU Profiler | 关键时间段里哪个方法消耗 CPU？ |
| Memory Profiler | 哪些对象在高频分配或占用内存？ |
| 自定义 Trace | `bind` 等业务区间内部哪一步慢？ |
| Macrobenchmark | 优化前后是否稳定、可重复地改善？ |

推荐顺序：

```text
线上分层
→ JankStats / 基准锁定场景
→ Perfetto 找关键帧和线程状态
→ Profiler 或自定义 Trace 下钻
→ Macrobenchmark 验证收益
→ 灰度观察线上回归
```

不要反过来从 CPU Profiler 的“总耗时最高方法”直接推断某一帧的根因。

---

## 6.6｜第五步：把线索写成可证伪假设

一个合格假设必须包含五部分：

```text
固定场景
＋ 疑似机制
＋ 可观测证据
＋ 单变量实验
＋ 预期变化
```

示例：

> 在指定低端机、冷图片缓存和固定商品数据下，首次快速滑动时，多个图片解码线程占用 CPU，使主线程长时间处于 Runnable。若只关闭图片加载，其他条件不变，则 Runnable 等待和慢帧数量应同步下降。

为什么强调“可证伪”？因为如果实验结果不符合预期，你就应放弃或修正假设，而不是继续为原判断找理由。

---

## 6.7｜第六步：只改一个变量，再用相同条件复测

错误实验：

```text
同时改布局、图片、线程池和缓存
→ 指标改善
→ 不知道哪个改动有效
```

正确实验可以是：

- 只关闭图片加载；
- 只关闭 ItemAnimator；
- 只替换简化版 Item；
- 只将完整绑定改为 Payload；
- 只移除一种高频对象分配；
- 只把一项同步工作移出主线程。

复测时保持：

```text
同设备 + 同数据 + 同缓存 + 同网络
+ 同操作脚本 + 同采集方式 + 多轮执行
```

不要只记录“体感更流畅”，至少比较：

- 慢帧数量与帧时间分布；
- 关键 Slice 宽度；
- `Runnable` / `Blocked` 时间；
- GC 次数和暂停；
- 分配速率；
- CPU 与内存变化。

## 6.8｜完整案例：首次滑动卡，第二次正常

### 现象

低端设备首次进入商品列表并快速滑动时卡顿，第二次进入相对正常。

### 线上线索

```text
问题集中在 Android 12 低端设备
＋ 新版本尾部指标变差
＋ 冷缓存场景更明显
＋ 图片方法在采样堆栈中高频出现
```

注意：图片堆栈只是线索，不是结论。

### 固定复现

```text
指定设备与系统
→ 固定应用版本和商品数据
→ 清空图片缓存
→ 固定网络或本地 Mock
→ 进入页面后立即快速滑动
→ 多轮采集 Perfetto
```

### 关键证据

```text
主线程 Running 不长
＋ 主线程 Runnable 较长
＋ 同期多个图片解码线程运行
＋ 这些区间与慢帧重合
```

### 假设

冷缓存集中解码造成 CPU 竞争，使主线程不能及时获得 CPU。

### 单变量实验

只将图片替换为固定占位图。

如果 `Runnable` 时间和慢帧数量同步下降，假设得到支持。

### 修复方向

- 按显示尺寸请求图片；
- 控制解码并发；
- 优化缓存策略；
- 快速滑动时避免无价值请求；
- 检查首屏与预取策略。

### 闭环

```text
相同脚本复测
→ 小比例灰度
→ 比较同机型、同系统、同场景的尾部指标
→ 同时确认图片正确性、内存和崩溃率无回归
```

## 6.9｜标准诊断记录模板

```text
问题场景：
在【设备/系统/版本】下，以【缓存与网络状态】进入【页面】，执行【固定动作】时出现慢帧。

线上线索：
【监控平台指标】异常，主要集中在【机型/系统/版本/场景】。

线下证据：
Perfetto 显示主线程主要处于【Running/Runnable/Blocked】；关键路径中的【Slice/线程】异常。

性能假设：
【某机制】导致【线程状态或关键路径异常】，进而错过帧截止时间。

验证实验：
只修改【单一变量】，其他条件保持一致。

验证结果：
修改后【关键 Slice/等待/GC/慢帧】是否同步变化。

修复与复测：
实施【具体修复】，使用相同基准多轮测量。

线上闭环：
灰度后【尾部帧指标/挂起率】改善，且功能、内存和崩溃指标无回归。
```

## 6.10｜常见误区

1. **看到采样堆栈就认定根因。**  堆栈只是定位线索。
2. **只看平均 FPS。**  平均值会掩盖尾部少量严重卡顿。
3. **主线程只运行 5 ms，所以帧不可能卡。**  它可能先 Runnable 或 Blocked 了很久。
4. **最宽 Slice 一定是根因。**  它是强线索，还要通过单变量实验验证。
5. **一次修改多个模块。**  这样无法建立因果关系。
6. **只在高端机测试。**  线上尾部问题常集中在低端机和特定系统。
7. **线下变快就结束。**  还要灰度并观察真实用户指标和副作用。
8. **工具越多，结论越可靠。**  关键不是工具数量，而是证据能否形成闭环。

## 6.11｜本篇速记

```text
用户说卡
→ 固定场景
→ 找到慢帧
→ 看 Running / Runnable / Blocked
→ 再分创建 / 绑定 / 布局 / 绘制 / 图片 / GC / 阻塞
→ 写成可证伪假设
→ 单变量实验
→ 相同条件多轮复测
→ 灰度与线上回归
```

工具速记：

```text
Bugly Pro       → 哪些线上场景异常
JankStats        → 哪种业务状态容易卡
Perfetto         → 这一帧为什么没完成
Profiler         → 哪个方法或对象有问题
自定义 Trace     → 业务步骤内部哪里慢
Macrobenchmark   → 优化收益是否稳定可重复
```

> 最终原则：**先确认哪一帧出了问题，再确认线程为什么没按时完成；任何根因判断，都要经得起单变量实验。**
