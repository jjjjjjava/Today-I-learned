# 01｜整体性能模型：先判断时间花在哪里

## 1. 本篇只解决一个问题

> **RecyclerView 的一条 Item，从数据变成屏幕画面，经过哪些阶段？**

只有先看清执行链路，才能判断卡顿属于创建、绑定、布局、绘制、更新，还是内存与 GC。

---

## 2. 先看一个滚动场景

用户向上滑动列表，位置 20 即将进入屏幕。RecyclerView 大致要完成：

```text
找到位置 20 需要的 Holder
        ↓
有可复用 Holder？
├── 有：必要时重新绑定
└── 无：创建 Holder，再绑定
        ↓
测量 Item 尺寸
        ↓
摆放 Item
        ↓
绘制并显示
```

即使数据一条都没变，滚动仍然需要获取 Holder、布局和绘制；有时还需要创建与绑定。

> **数据不变，只表示“不需要处理新数据”，不表示 RecyclerView 没有工作。**

---

## 3. 数据到画面的完整链路

```text
Repository / 数据源
        ↓
ViewModel 准备 UI 数据
        ↓
Adapter 接收列表
        ↓
Recycler 获取可用 ViewHolder
        ├── 近端缓存命中：可能直接使用
        ├── Pool 命中：通常重新绑定
        └── 未命中：创建后再绑定
        ↓
onBindViewHolder()
        ↓
LayoutManager 决定哪些 Item 可见，并测量、摆放
        ↓
Item View 执行 measure / layout / draw
        ↓
渲染与显示
```

这不是每次都从头到尾执行的固定流水线。缓存命中位置不同，成本也不同：

| Holder 来源 | 是否创建 | 是否绑定 | 是否布局、绘制 |
|---|---:|---:|---:|
| 有效近端缓存 | 否 | 可能不需要 | 需要 |
| RecycledViewPool | 否 | 通常需要 | 需要 |
| 无可复用 Holder | 是 | 是 | 需要 |

核心规律：

> **复用可以省创建，某些近端缓存还可以省绑定；但必要的布局和绘制不会因为复用而消失。**

---

## 4. 四个角色不要混淆

### Adapter：决定“显示什么、用哪种结构”

- `getItemCount()`：有多少条数据。
- `getItemViewType()`：当前位置使用哪种 Item 结构。
- `onCreateViewHolder()`：创建对应结构。
- `onBindViewHolder()`：把数据写入 View。

Adapter 不应负责网络、数据库等数据获取。

### ViewHolder：拿着 Item View

```kotlin
class NewsHolder(itemView: View) : RecyclerView.ViewHolder(itemView) {
    val title: TextView = itemView.findViewById(R.id.title)
}
```

ViewHolder 持有视图引用，但不管理缓存。

### Recycler：决定“Holder 从哪里来”

它负责查找、缓存、回收与复用 ViewHolder。

### LayoutManager：决定“Item 放在哪里”

它负责可见范围、测量、排列和滚动，不负责创建 Holder。

一句话记忆：

```text
Adapter：显示什么、用什么结构
ViewHolder：拿着 Item View
Recycler：Holder 从哪里来
LayoutManager：Item 放在哪里
```

## 5. 为什么 20 ms 会卡

屏幕按刷新率周期性显示新画面：

| 刷新率 | 理论单帧时间 |
|---:|---:|
| 60 Hz | 约 16.67 ms |
| 90 Hz | 约 11.11 ms |
| 120 Hz | 约 8.33 ms |

但这段预算不是 RecyclerView 独占的。一帧还可能包含输入、动画、其他 View、渲染和系统合成等工作。

例如在 60 Hz 设备上：

```text
创建 Holder       4 ms
绑定数据           8 ms
布局与绘制         7 ms
-----------------------
合计              19 ms
```

应用可能赶不上本帧截止时间，只能继续显示上一帧，于是用户看到停顿。

VSync 通常仍然按时到来；问题是应用没有及时准备好新帧。

> **性能分析不能只看平均值，更要看偶发或连续的慢帧峰值。**

## 6. 六类成本归因

看到卡顿时，先分类，不要先调缓存：

| 类别 | 常见迹象 | 可能原因 |
|---|---|---|
| 创建重 | 首次进入或快速滚动时明显 | inflate 慢、视图树复杂、viewType 过细 |
| 绑定重 | `onBindViewHolder()` 耗时高 | 图片、富文本、动态 View、对象分配、阻塞操作 |
| 布局重 | measure/layout 频繁或耗时 | 层级深、重复 `requestLayout()`、复杂尺寸依赖 |
| 绘制重 | draw 或 GPU 压力高 | 过度绘制、复杂装饰、透明叠层、动画 |
| 更新重 | 数据变化时卡顿 | 全量刷新、高频 Diff、完整绑定过多 |
| 内存/GC | 周期性尖峰 | 频繁分配、图片占用高、缓存过大 |

---

## 7. 推荐排查顺序

```text
第一步：卡顿发生在什么时候？
├── 首次展示
├── 快速滚动
├── 反向滚动
└── 数据更新

第二步：Trace 中哪一段变长？
├── create / inflate
├── bind
├── measure / layout
├── draw
└── GC

第三步：只优化证据指向的阶段
```

例如“快速滚动时 bind 很重”，优先检查绑定逻辑，而不是直接把缓存改成 100。

---

## 8. 常见误区

- **错：ViewHolder 负责缓存。** Recycler 才负责缓存与复用。
- **错：LayoutManager 创建 Item。** Holder 由 Adapter 创建。
- **错：数据没变，滚动就没有工作。** 布局和绘制仍会发生。
- **错：60 Hz 时 RecyclerView 可独占 16.67 ms。** 整帧所有任务共享预算。
- **错：卡顿说明 VSync 没来。** 通常是应用错过了帧截止时间。

### 本篇一句话总结

> **RecyclerView 优化的起点，是把慢帧归因到创建、绑定、布局、绘制、更新或 GC，而不是寻找万能开关。**
