# 02｜复用与缓存：滚动时 Holder 从哪里来

## 1. 本篇只解决一个问题

> **一个 Item 即将出现时，RecyclerView 如何找到可用的 ViewHolder？**

列表有 10,000 条数据，不等于创建 10,000 个 Holder。RecyclerView 只维护屏幕及附近需要的一小批视图，并在滚动中反复复用。

---

## 2. 用“位置 8 离屏又返回”理解三层区域

假设位置 8 刚滑出屏幕，随后用户立刻反向滑动。

### Scrap：本轮布局的临时工作区

布局过程中，原有 Holder 可能被暂时 detach：

```text
原来可见的 Holder
        ↓ 临时 detach
      Scrap
        ↓ 本轮布局重新判断
        ├── 仍需要：重新 attach
        └── 不需要：进入后续缓存或回收
```

Scrap 服务于“当前这一轮布局”，不是容量较小的长期缓存池。

### mCachedViews：刚离屏、可能很快返回

位置 8 的 Holder 仍保留位置与绑定状态。如果它很快返回且数据没有失效，就可能直接使用，无需重新绑定。

> mCachedViews 保存的不是业务数据，而是“Holder 仍与原位置有效关联”的状态。

### RecycledViewPool：只保留结构

Holder 进入 Pool 后，旧位置不再重要，只保留：

```text
这是 viewType = 1 的视图外壳
```

新位置如果也是 `viewType = 1`，可以复用这套 View 结构；由于数据通常不同，仍需重新绑定。

---

## 3. 成本阶梯

```text
Scrap / 有效 mCachedViews 命中
成本最低：可能直接使用
        ↓
RecycledViewPool 命中
省创建，但通常需要绑定
        ↓
全部未命中
创建 + 绑定，成本最高
```

| 来源 | 保留什么 | 主要匹配依据 | 通常重新绑定？ |
|---|---|---|---:|
| Scrap | 本轮布局状态 | position、状态等 | 通常不需要 |
| mCachedViews | 位置与有效绑定状态 | position 等 | 可能不需要 |
| RecycledViewPool | 指定类型的视图结构 | viewType | 通常需要 |

简化查找链：

```text
Scrap
  ↓
mCachedViews
  ↓
ViewCacheExtension（通常未配置）
  ↓
RecycledViewPool
  ↓
onCreateViewHolder()
  ↓
onBindViewHolder()
```

---

## 4. Pool 为什么按 viewType 分桶

Pool 要保证复用的视图结构兼容，因此按 `viewType` 保存 Holder。

### 应拆类型：结构确实不同

- 普通新闻和大图视频使用不同布局树。
- 广告卡片和内容卡片的子 View 不同。
- 两类 Holder 无法安全共用相同视图引用。

### 通常不拆：结构相同，只是数据或样式不同

例如标题颜色不同：

```kotlin
holder.title.setTextColor(
    if (item.isImportant) Color.RED else Color.BLUE
)
```

类型过细会把 Pool 切成许多小桶，降低命中率；类型过粗则会让绑定逻辑复杂，甚至造成结构不兼容。

判断标准不是“数据是否不同”，而是：

> **两条数据能否安全使用同一套 Item View 结构？**

---

## 5. 复用为什么容易产生错乱

同一个 Holder 会先后显示不同数据，因此完整绑定必须覆盖所有状态。

错误写法：

```kotlin
if (item.isImportant) {
    holder.title.setTextColor(Color.RED)
}
```

如果该 Holder 下一次显示普通新闻，颜色可能仍是红色。

正确写法：

```kotlin
holder.title.setTextColor(
    if (item.isImportant) Color.RED else Color.BLUE
)
```

每次完整绑定都要覆盖：

- 文本、颜色、背景；
- `visibility`、选中和激活状态；
- 图片占位、旧图片请求；
- 展开与折叠状态；
- 与当前数据对应的监听行为。

> **复用错乱通常不是“缓存拿错了”，而是绑定没有恢复完整状态。**

---

## 6. 缓存为什么不是越大越好

```kotlin
recyclerView.setItemViewCacheSize(10)
```

增大 mCachedViews 可能提高短距离反向滚动的命中率，但每个 Holder 都持有完整 Item View，可能还持有图片、子 View 和监听器。

收益与成本同时存在：

```text
可能收益：少创建、少绑定
可能成本：内存增加、资源持有更久、边际命中下降
```

Pool 可按类型设置容量：

```kotlin
pool.setMaxRecycledViews(VIEW_TYPE_NEWS, 10)
```

推荐原则：

1. 普通纵向列表先使用默认值。
2. 发现大量重复创建后，再判断是否为 Pool 容量或 viewType 问题。
3. 经常短距离往返时，才考虑适当增加近端缓存。
4. 用命中率、创建次数、内存和慢帧数据验证收益。

---

## 7. 缓存与预取不是一回事

```text
缓存：保留过去已经完成的工作
预取：提前完成未来可能需要的工作
```

它们会协作，但解决的问题不同。预取将在第 03 篇展开。

---

## 8. 三个典型判断题

### 情况 A：位置 20 在 mCachedViews 中有效命中

可能结果：免创建，也免绑定；之后仍需必要的布局与绘制。

### 情况 B：位置 20 未命中近端缓存，但 Pool 有相同 viewType

可能结果：免创建，重新绑定位置 20 的数据，再布局和绘制。

### 情况 C：Pool 里只有其他 viewType

可能结果：结构不兼容，需要创建对应类型 Holder，再绑定。

---

## 9. 常见误区

- **错：mCachedViews 缓存业务数据。** 它缓存仍保留位置和绑定状态的 Holder。
- **错：Scrap 是长期缓存。** 它是本轮布局的临时区域。
- **错：相同 viewType 表示数据相同。** 它只表示视图结构兼容。
- **错：Pool 命中就不绑定。** Pool 通常只省创建。
- **错：缓存越大一定越流畅。** 还要考虑命中收益、内存和 GC。
