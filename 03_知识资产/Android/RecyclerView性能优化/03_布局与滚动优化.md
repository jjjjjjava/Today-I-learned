# 03｜布局与滚动优化：Holder 有了，为什么仍会卡

## 1. 本篇只解决一个问题

> **即使 Holder 已经成功复用，为什么滚动仍可能出现慢帧？**

因为复用主要减少创建和部分绑定，Item 入屏仍需完成必要的测量、摆放与绘制。

```text
获取 Holder
    ↓
必要时绑定
    ↓
measure：算尺寸
    ↓
layout：定位置
    ↓
draw：画内容
```

---

## 2. 第一类成本：视图树本身太重

视图树越深、节点越多，每次 measure、layout 和 draw 分发通常要遍历更多对象。

```text
LinearLayout
└── FrameLayout
    └── LinearLayout
        └── TextView
```

优化重点不是机械替换某一种布局，而是删除没有布局作用、绘制作用或语义作用的节点。

不要形成错误规则：

- `ConstraintLayout` 不一定总比简单 `LinearLayout` 快。
- 看到 `RelativeLayout` 不代表必须重构。
- 层级数量只是线索，还要观察 `layout_weight`、`wrap_content` 和尺寸依赖。

> **目标是降低实际测量与遍历成本，不是追求某个布局名称。**

---

## 3. 第二类成本：同一布局被重复触发

### 为什么会重复测量

常见原因：

- `layout_weight` 需要统计并重新分配空间；
- 复杂 `wrap_content` 或父子尺寸相互依赖；
- 绑定时修改 `LayoutParams`；
- 无条件调用 `requestLayout()`；
- 父 View 给出的约束发生变化。

例如每次绑定都设置相同高度：

```kotlin
holder.itemView.layoutParams = params
holder.itemView.requestLayout()
```

即使高度没有变化，也可能触发额外布局工作。

更合适的写法：

```kotlin
val params = holder.itemView.layoutParams
if (params.height != targetHeight) {
    params.height = targetHeight
    holder.itemView.layoutParams = params
}
```

尺寸真正变化时重新布局是必要成本；优化的是“参数没变，却反复请求布局”。

### requestLayout 与 invalidate

| 调用 | 表达的含义 | 典型后续工作 |
|---|---|---|
| `requestLayout()` | 尺寸或位置可能失效 | measure / layout，通常随后绘制 |
| `invalidate()` | 外观需要重绘 | draw，通常不改变尺寸 |

例如颜色变化通常只影响绘制；高度变化则必须重新布局。文字内容是否影响尺寸，要看约束和实际布局。

## 4. `setHasFixedSize(true)` 到底固定什么

```kotlin
recyclerView.setHasFixedSize(true)
```

它表达的是：

> **Adapter 内容变化不会改变 RecyclerView 自身的宽高。**

典型场景：RecyclerView 高度为 `match_parent`。列表从 100 条变成 101 条，容器高度仍是屏幕高度。

它不表示：

- 所有 Item 等高；
- Item 不再 measure/layout；
- RecyclerView 永远不重新布局；
- 开启后一定有明显收益。

若 RecyclerView 为 `wrap_content`，自身尺寸依赖 Item 内容，就应谨慎使用。

## 5. 预取：把未来工作提前做

快速滚动时，Item 入屏后再集中执行：

```text
获取或创建 Holder
→ 绑定
→ measure / layout
→ draw
```

容易形成耗时峰值。预取会根据滚动方向和距离，尝试利用主线程可用时间提前准备即将出现的 Item，内部通常由 `GapWorker` 协调。

```text
当前帧有余量
    ↓
提前获取 Holder
    ↓
必要时创建和绑定
    ↓
暂存，等待入屏
```

关键认识：

- 预取通常不是减少总工作，而是分散工作峰值。
- 入屏时仍有必要的 measure、layout 和 draw。
- 当前帧预算不足时，预取可能无法完成。
- 预测错误或数量过多会制造无用工作和额外内存占用。

### 嵌套横向列表

外层纵向 RecyclerView 中包含横向 RecyclerView 时，可以参考内层首屏真实可见数量设置：

```kotlin
val layoutManager = LinearLayoutManager(
    context,
    RecyclerView.HORIZONTAL,
    false
)
layoutManager.initialPrefetchItemCount = 4
```

数值不是越大越好，应围绕“即将出现的首屏需要多少 Item”实测调整。

## 6. ItemDecoration：少一个 View，不等于没有绘制

统一分割线可用 ItemDecoration 绘制：

```text
getItemOffsets()：预留间距
onDraw()：在 Item 下方绘制
onDrawOver()：在 Item 上方绘制
```

与每个 Item XML 增加分割线 View 相比，它可以减少 View 创建和布局节点，但分割线的绘制工作仍然存在。

绘制回调会频繁执行，应避免：

- 每帧创建 `Paint`、`Rect` 等对象；
- 读取资源或分配 Bitmap；
- 复杂路径计算；
- 遍历大量无关 Item。

---

## 7. ItemAnimator：动画也在消耗帧预算

新增、删除、移动或内容变化时，ItemAnimator 可能持续计算属性、触发重绘，并暂时持有更多 Holder。

如果高频内容更新导致闪烁或卡顿，可以先只关闭 change animation：

```kotlin
(recyclerView.itemAnimator as? SimpleItemAnimator)
    ?.supportsChangeAnimations = false
```

如果业务完全不需要 Item 动画：

```kotlin
recyclerView.itemAnimator = null
```

前者仍保留新增、删除和移动动画；后者关闭全部动画。优先选择影响范围更小的方案。

---

## 8. 过度绘制与层级深是两种问题

过度绘制指同一像素在一帧内被多次覆盖：

```text
RecyclerView 白色背景
└── Item 白色背景
    └── 不透明卡片白色背景
```

如果最终只看到最上层，下面的背景绘制可能是浪费。

常见来源：

- Activity、RecyclerView、Item 设置相同不透明背景；
- 不透明图片下方仍绘制背景；
- 多层容器各自绘制背景；
- 大面积透明或半透明叠层。

但要区分：

| 问题 | 主要成本 |
|---|---|
| 层级深 | View 节点多，遍历和分发更多 |
| 过度绘制 | 同一像素被反复覆盖，像素填充更多 |

一个没有背景和内容的容器仍有遍历成本，但不一定增加一层背景过度绘制。

## 9. 推荐排查顺序

```text
滚动卡顿
├── create / bind 高？→ 回到第 02、04 篇
├── measure / layout 高？
│   ├── 检查层级与尺寸依赖
│   └── 检查重复 LayoutParams / requestLayout
├── draw 高？
│   ├── 检查背景与透明叠层
│   └── 检查 Decoration 与动画
└── 入屏瞬间峰值？
    └── 检查预取数量与嵌套列表
```
