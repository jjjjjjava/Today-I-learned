## 01. 项目背景

我这个项目是在万店掌主线项目里做的视频水印处理性能优化。万店掌里有很多视频加水印的场景，比如任务里的临时图库视频、视频下载后的水印留痕等。原有方案主要是通过 FFmpeg 命令做水印合成，整体是偏软解、软处理、软编的链路。

这个方案能用，但是性能比较差。我们当时测过，一个 1 分 30 秒左右的视频，处理耗时接近 2 分钟。用户拍完视频或者下载视频后，还要等水印处理完成，体验很差，也经常有用户反馈处理慢的问题。

这个需求找到我们的时候，原本 leader 在看这块，但他被临时抽去处理更紧急的老板需求，所以这块就交给我接手。他当时同步给我一个初步思路：继续走 FFmpeg，但是重新编译 FFmpeg so，加入硬解、硬编以及 H265 支持。

## 02. 我的职责

我接手后主要负责两件事：第一是重新评估技术方案，判断是沿用 leader 提到的自编译 FFmpeg so 方案，还是切换到 Android 原生的 MediaCodec + OpenGL ES 管线；第二是设计核心处理链路，包括硬解码、OpenGL 水印合成、硬编码输出，以及后续黑屏、音视频同步，兜底这些工程问题

## 03. 技术选型

当时我主要比较了两个方案。

第一个方案是继续使用 FFmpeg，重新编译 FFmpeg so，把硬件解码、硬件编码和 H265 支持加进去。这个方案的优点是上层调用改动小，仍然可以沿用原有 FFmpeg 命令模式。但我评估后觉得它有几个问题。

第一是包体积。我们项目历史上已经接入了多个播放器和视频相关 SDK，比如 ijk、萤石这类，它们本身就带 native so。我把类似 so 放到 Android Studio 里看过体积，基本都是二三十 MB 级别。即使 FFmpeg 可以裁剪能力，重新引入一套支持硬编硬解的 so，包体积增长仍然不可避免。

第二是可维护性。FFmpeg 对我们业务层来说还是偏黑盒，出了问题需要看 native 日志、编译参数、设备 codec 支持，甚至要排查 so 内部逻辑。对于线上机型兼容问题，定位成本会比较高。

第三是链路控制力。如果 FFmpeg 要走高性能路线，本质上也要调用 Android 的硬件编解码能力，或者接近 Surface、MediaCodec、OpenGL 这一套平台能力。那与其隔着 FFmpeg 间接控制，不如直接基于 Android 原生管线实现，数据路径和异常处理都更可控。

所以我最后主导选择了 MediaCodec + OpenGL ES 的方案。它的开发成本更高，但优势是包体积可控、链路透明、性能路径更直接，而且团队也能沉淀一套 Android 视频处理能力。

## 04.实现链路

实际实现上，他是分为了五个步骤：解封装，解码，渲染（混合），编码，重封装

第一阶段是拆轨和解码。我用 MediaExtractor 读取输入视频，找到视频轨和音频轨。视频轨交给 MediaCodec Decoder 处理。这里我没有让 Decoder 输出 ByteBuffer 给 CPU，而是给 Decoder 配置了一个 Surface，这个 Surface 来自 SurfaceTexture。SurfaceTexture 又绑定到 OpenGL 的 OES 外部纹理，所以解码后的画面可以直接作为 GPU 纹理被 OpenGL 采样。

第二阶段是 OpenGL 合成。我创建 EGL 环境，并为编码器的 inputSurface 创建 EGLSurface。每解出一帧后，调用 SurfaceTexture.updateTexImage 获取最新视频帧，同时拿到 transform matrix。然后 OpenGL shader 里采样两张纹理：一张是视频帧的 OES Texture，另一张是水印 Bitmap 上传后的 2D Texture。通过 alpha blend 把水印叠加到视频画面上。

第三阶段是编码。我没有把 OpenGL 渲染结果读回 CPU，而是直接把画面渲染到 MediaCodec Encoder 的 inputSurface。也就是说，GPU 合成后的结果直接进入硬编码器。每帧渲染完成后，设置这一帧的 presentationTime，再 swapBuffers，让编码器拿到这帧数据。

第四阶段是封装。编码器输出 H264 或 H265 视频数据后，通过 MediaMuxer 写入视频轨。音频轨因为不需要加水印，所以直接从原视频里按原始 sampleTime 写入 muxer，最后输出一个带水印的新 MP4。

## 05.难点

### 1.难点一：数据拷贝和格式转换

第一个难点是数据路径。最直观的做法是让 MediaCodec 解码输出 ByteBuffer，然后应用层拿到 YUV 数据，再把它转成 RGB 或上传成 OpenGL 2D 纹理去合成水印。但这个方案性能不理想，因为每一帧都要经过 CPU 内存读写、格式转换和纹理上传。

以 1080p 视频为例，YUV420 一帧大概是 1920 × 1080 × 1.5，也就是 3MB 左右。30fps 的情况下，光原始 YUV 数据搬运就接近 90MB/s。如果再转成 RGBA，一帧会到 8MB 左右，30fps 就是 240MB/s 级别，还不算 YUV 转 RGB、纹理上传和 GPU 同步的开销。

所以我最后没有走 ByteBuffer 路径，而是让 decoder 直接输出到 SurfaceTexture，再通过 OES 外部纹理让 OpenGL 采样。这样应用层不需要拿到每帧原始像素，也不需要每帧手动上传纹理，数据路径会短很多。

### 2.**难点二：JPG 水印全黑/透明度异常**

第二个难点是水印素材格式导致的渲染异常。我们一开始遇到过 JPG 水印素材合成后画面发黑、局部黑底甚至全黑的问题。这个问题本质上和水印纹理的像素格式、alpha 通道以及 OpenGL 混合方式有关。

JPG 本身没有 alpha 通道，而水印合成通常需要透明背景。如果直接把 JPG decode 出来的 Bitmap 上传成纹理，再按带 alpha 的方式去混合，就可能在不同机型或不同 Bitmap config 下出现黑底、透明度异常、颜色异常。

我的处理方式是把水印中间态统一成 ARGB_8888 的 Bitmap，必要时统一转成 PNG 作为水印纹理源。上传到 OpenGL 后开启 GL_BLEND，混合函数使用 SRC_ALPHA, ONE_MINUS_SRC_ALPHA。这样水印透明区域、文字颜色和视频底图之间的关系就稳定了。

### 3.难点三：首帧黑屏和时间戳

第三个难点是首帧黑屏和时间戳处理。首帧黑屏主要是 SurfaceTexture 和 encoder inputSurface 的时序问题。如果 encoder 已经收到一帧，但 SurfaceTexture 还没有真正 update 到解码后的画面，OpenGL 可能只是清了一次屏，结果第一帧就是黑的。

我的处理方式是严格控制每帧顺序：decoder releaseOutputBuffer 并 render 到 Surface 后，再调用 SurfaceTexture.updateTexImage，拿 transform matrix，然后执行 drawFrame，设置当前帧的 presentationTime，最后 swapBuffers 给 encoder。这样可以避免 encoder 先吃到 clearColor 或空纹理。

时间戳方面，因为视频重新编码了，所以不能按处理速度生成时间戳，而是要沿用原始帧的 presentationTimeUs。渲染完成后把这个时间戳设置到 EGLSurface，单位从微秒转成纳秒。音频轨直接 remux，保留原始 sampleTime。这样输出视频的音频和视频都沿用原始时间线。

## 06.最终结果

最终效果上，性能提升比较明显。我们用同一个 1 分 30 秒左右的视频做对比，原 FFmpeg 软处理链路耗时接近 2 分钟，新方案处理耗时大概 13.47 秒。按这个数据算，耗时从 120 秒左右降到 13.47 秒，整体降低约 88.8%。

对用户侧来说，原来拍完或下载完视频后还要等很久，现在基本十几秒就能完成水印处理，等待感明显降低。对业务链路来说，视频水印、压缩、上传或下载完成回调可以更快进入下一步，失败和超时概率也会降低

另外一个收益是没有额外引入一套新的 FFmpeg so。因为我们没有选择重新编译并打包 FFmpeg 硬编硬解版本，所以避免了二三十 MB 级别的包体积增长，也减少了 native 层维护成本

这次之后，我们沉淀了一套 Android 原生视频处理思路：MediaCodec 负责硬解硬编，OpenGL ES 负责纹理合成，MediaMuxer 负责封装。后面类似的视频加水印、视频压缩、视频下载后处理，都可以复用这套处理模型，而不是每次都堆 FFmpeg 命令

## 07.复盘

复盘的话，我觉得这类方案最大的风险在兼容性，所以工程化上要补三类兜底：第一是设备能力检测，判断 H264/H265、分辨率、encoder inputSurface 等支持情况；第二是失败回退，MediaCodec 或 GL 异常时回退到原 FFmpeg 方案；第三是质量校验，不只看文件是否生成，还要校验首帧、时长、音视频同步和输出文件大小。

## 08. 提问

### 1.**你怎么判断 FFmpeg 是软解软编？**

当时原链路是通过 FFmpeg 命令 overlay 水印，没有接平台硬编硬解相关能力，处理耗时也基本随视频时长线性增长，CPU 占用比较明显。所以我把它判断为偏软解、CPU filter 和软编的处理模式。严格来说，我没有逐函数 profile FFmpeg 内部，而是从命令链路和运行表现判断它不是 Surface-to-Surface 的硬件链路。

### 2.为什么不用 ByteBuffer

如果用 ByteBuffer，解码后的 YUV 数据会回到 CPU。后面要么 CPU 做水印合成，要么再把 YUV/RGB 上传到 GPU。这个路径每帧都有内存拷贝和格式转换。SurfaceTexture/OES Texture 可以避免这部分开销。

### 3.**OpenGL 怎么叠水印**

视频帧是一张 OES 外部纹理，水印是一张普通 2D 纹理。片元着色器里根据当前纹理坐标判断是否落在水印区域，如果在水印区域就采样水印纹理，并按 alpha 做混合；如果不在水印区域就直接输出视频颜色。

### 4.**音频怎么处理**

水印只影响视频轨，所以音频不重新编码。直接用 MediaExtractor 读取音频 sample，保留原始 sampleTime 和 flags，写入 MediaMuxer。这样速度快，也能减少音质损失和音画同步问题

### 5.为什么JPG会变黑

JPG 没有透明通道，所以如果业务上把它当成透明水印来用，透明区域其实并不存在。很多时候所谓的透明背景会变成黑色或其他底色。OpenGL 混合时如果 alpha 数据不正确，就会把黑色底也混进去。统一 ARGB_8888 和 PNG 中间态，本质是把 alpha 语义补齐

### 6.**你为什么不用 glReadPixels？**

glReadPixels 会把 GPU 渲染结果读回 CPU，这会造成 GPU pipeline stall，而且又产生一次大数据拷贝。我的目标是让结果直接进 encoder inputSurface，所以不需要 glReadPixels

### 7.**为什么不用普通 GL_TEXTURE_2D 存视频帧？**

如果普通 2D 纹理，就需要应用层拿到解码帧再上传纹理。SurfaceTexture 对应的是 GL_TEXTURE_EXTERNAL_OES，decoder 可以直接输出到 Surface，OpenGL 通过 OES 外部纹理采样，这更适合视频帧。

### 8.**音频不重新编码会不会有问题**

一般不会，因为水印只改视频轨。只要输出容器支持原音频格式，比如 AAC，就可以直接 remux。需要注意的是写入 muxer 时保留原 sampleTime 和 flags。

### 9.**首帧黑屏怎么验证解决了？**

我会取输出视频首帧做截图，和原视频首帧对比，同时在处理日志里看第一帧是否经过 updateTexImage 和 drawFrame，再确认 encoder 第一帧的 PTS 是否是原视频第一帧时间戳，而不是默认 0 的空帧

### 10.结果怎么测的？

我用同一段视频、同一台测试设备、同一套水印素材分别跑原 FFmpeg 链路和新 MediaCodec/OpenGL 链路，记录从开始处理到输出文件生成完成的耗时。原方案接近 2 分钟，新方案是 13.47 秒。为了避免偶然值，实际应该跑多轮取平均，并覆盖不同分辨率、H264/H265、横竖屏视频。

### 11.**还有哪些不足**

不足主要是兼容性和验证成本。MediaCodec/OpenGL 性能更好，但不同厂商 codec 实现、H265 支持、分辨率限制、Surface 生命周期都有差异。所以这个方案必须配合设备能力检测、fallback 和质量校验，不能只靠主流程跑通
